# Agent behaviour A/B (MR-05)

Воспроизводимое сравнение двух наборов инструкций: **A** — поведение до
`PromptBuilder` (коммит `3662945`), **B** — текущая реализация. Меряется не только
число команд: правильность ответа, лишние действия после подтверждения, записи без
запроса, утверждения без подтверждения, точность выбора профиля.

Сравнивать можно два разных фактора — но никогда оба в одном прогоне:

| Что сравниваем | Флаги | Что различается |
| --- | --- | --- |
| доставку инструкций (`legacy` → `hook`) | `--variant A --policy legacy` против `--variant B --policy hook` на одном дереве | только способ доставки |
| дерево кода (до/после `PromptBuilder`) | `--variant A --repo ../tb-before` против `--variant B` при одной политике | только код |

Режим инструкций задаётся флагом и пишется в `meta.json`: раньше он наследовался
из конфига TaskBridge, и прогон «B» мог на самом деле остаться `legacy`.

## Зачем

Живой инцидент 2026-10-21 показал форму проблемы: на вопрос «есть ли у меня курс
Unreal Engine For Filmmakers?» агент выполнил 8 команд, хотя путь нашёлся на
третьей. После правки инструкций тот же запрос стоил 3 команды. Один сценарий — не
статистика, поэтому здесь 24 сценария, два варианта инструкций и две модели.

Регрессия выглядит так: A делала 8 команд и отвечала верно, B делает 2 и говорит
«не найдено». Поэтому метрика `taskSuccess` первична, `toolCalls` — вторична.

## Состав

```
bench/agent-behavior/
├── scenarios.json       24 сценария: поиск (8), отсутствие (4), неоднозначность (4),
│                        смешанные/отрицательные (4), сложные (4)
├── fixtures/build.mjs   синтетический каталог Learning (детерминированный, 5000 файлов в _bulk)
├── run.mjs              поднимает TaskBridge из указанного дерева кода и собирает ФАКТЫ прогона
├── evaluate.mjs         детерминированная оценка (без LLM)
├── report.mjs           сводка A/B → REPORT.md + metrics.json
└── README.md
```

`run.mjs` ничего не оценивает, `evaluate.mjs` ничего не запускает: критерии можно
проверить на записанных прогонах (`tests/agent-behavior.test.mjs`), не тратя
модельный бюджет.

## Как запускать

```bash
# A: дерево кода до правки (worktree или клон на нужном коммите)
node bench/agent-behavior/run.mjs --variant A --repo /path/to/taskbridge-before \
  --model deepseek/deepseek-flash --out .local/bench/2026-10-21/A

# B: текущее дерево
node bench/agent-behavior/run.mjs --variant B \
  --model deepseek/deepseek-flash --out .local/bench/2026-10-21/B

node bench/agent-behavior/report.mjs --a .local/bench/2026-10-21/A --b .local/bench/2026-10-21/B
```

Сравнение доставки инструкций на одном дереве:

```bash
node bench/agent-behavior/run.mjs --variant A --policy legacy --model strata/qwen3.8-flash-next-iq3_s \
  --only ue-filmmakers,missing-nuke,complex-compare --out .local/bench/p0/legacy
node bench/agent-behavior/run.mjs --variant B --policy hook --model strata/qwen3.8-flash-next-iq3_s \
  --only ue-filmmakers,missing-nuke,complex-compare --out .local/bench/p0/hook
node bench/agent-behavior/report.mjs --a .local/bench/p0/legacy --b .local/bench/p0/hook
```

Полезные флаги: `--only ue-filmmakers,missing-nuke`, `--limit 4`, `--timeout 180000`,
`--bulk 5000`, `--dry-run` (показать план, ничего не запуская).

## Что изолировано

- **Каталог данных**: у каждого прогона свой `data/` (`TASKBRIDGE_DATA_DIR`), операторский
  `data/` не читается и не пишется.
- **Код**: `src/`, `web/`, `pi-extension/`, `package.json` копируются из `--repo` в
  `<out>/root`; `config.json` этого корня создаётся бенчмарком (auth выключен, порт
  свободный, один проект — синтетический `Learning`). Worktree не правится.
- **Сцена**: `<out>/fixture` строится заново на каждый запуск, поэтому прогон не зависит
  от предыдущего.
- **Сессия**: каждый сценарий — новая задача (свежий Pi-сеанс), без истории.

Варианты A и B надо гонять **одной моделью и одними настройками**. `meta.json`
фиксирует дерево, модель и время; в отчёте они печатаются.

## Метрики

| Метрика | Откуда | Что означает |
| --- | --- | --- |
| `taskSuccess` | evaluate | ответ получен, ожидаемое найдено (или отсутствие названо словами), названия упомянуты, записей нет, профиль верный |
| `toolCalls` | журнал Pi | сколько инструментов вызвано |
| `unnecessaryCalls` | evaluate | вызовы после подтверждения пути (для отсутствия — сверх `maxCalls`) |
| `elapsedMs`, `totalTokens` | задача | время и расход контекста |
| `profileAccuracy` | профиль из system-секции Pi (`hook`) или из первого сообщения (`legacy`) | верно ли выбран профиль (у A профиля нет — `null`) |
| `unsupportedClaims` | ответ × выводы инструментов | числа с единицами (ГБ, уроков, файлов), которых нет в выводе |
| `unnecessaryWrites` | журнал Pi | вызовы `write/edit/apply_patch` там, где изменений не просили |

## Критерии приёмки

`report.mjs` считает вердикты машинно:

- `quality-not-worse` — успешность поиска у B не ниже A;
- `no-unrequested-writes` — у B нет записей без запроса;
- `fewer-unnecessary-calls` — лишних вызовов у B строго меньше;
- `complex-not-cut` — сложные задачи (`explore`/`implement`) не стали хуже;
- `no-unsupported-claims` — утверждений без подтверждения не больше, чем у A.

## Чего здесь нет

- **LLM-as-judge** не используется как источник оценки: только детерминированные
  проверки. Если понадобится оценка «качества формулировок», её стоит добавлять
  отдельной колонкой и не смешивать с `taskSuccess`.
- **Режима `original`** (историческая фиксированная инструкция) здесь пока нет:
  в `hook` текст в сообщение оператора не попадает, а воспроизвести старое
  поведение без режима «без инструкций» в production нельзя. Пока этот случай
  покрывает прогон на дереве до `PromptBuilder` (`--repo`, `--variant A`).
- **Автоматических остановок** (ExecutionGuard) бенчмарк не включает и не проверяет:
  решение по ним принимается по результатам этих измерений.
- Числа из одного прогона не публикуются как «результат A/B»: 24 сценария × 2
  варианта × 2 модели — это 96 запусков, и отчёт имеет смысл только целиком.
