# TaskBridge KMP — план разработки (Desktop + Android)

Цель: KMP-клиент (Compose Multiplatform) для управления агентными сессиями через daemon TaskBridge. Клиент **не управляет Pi напрямую** — он работает только с API v1 daemon'а и является такой же поверхностью, как браузер и `taskbridge pi`.

Зависимость: `TASKBRIDGE_BACKEND_PLAN.md`, этапы **B3 (API v1)** и **B4 (мультиклиентность)**. До их завершения можно делать только K0–K1 на моках.

## 2. Модули

```
:shared:api        — DTO, envelope событий, REST/WS-клиент, коды ошибок
:shared:data       — репозитории, SessionStream, outbox промптов, локальный кэш
:shared:domain     — модели UI-уровня, редьюсер событий в состояние сессии
:shared:ui         — общие Compose-экраны и компоненты
:androidApp        — Activity, уведомления, фоновая работа, pairing по QR
:desktopApp        — окно, tray, системные уведомления, горячие клавиши
```

Правило: `:shared:api` — только транспорт и DTO, без бизнес-логики. Вся логика восстановления потока — в `:shared:data`.

## 3. Ключевые механизмы (главные источники багов)

### 3.1 SessionStream — поток событий без дыр и дублей

- Хранит `lastSeq` по каждой сессии (в памяти и в кэше).
- Подключение: `hello {clientId, clientKind, fromSeq = lastSeq}` → `snapshot` → история → live.
- Дедупликация: событие с `seq <= lastSeq` игнорируется.
- Обнаружение дыры: пришло `seq > lastSeq + 1` → дозапросить `GET /events?fromSeq=` и только потом применять.
- `live {delta}` (стриминг текста) не имеет `seq`, применяется только к текущему незавершённому сообщению; финальное `message.assistant` его заменяет.
- Переподключение: экспоненциальный backoff с jitter, сброс при успешном `snapshot`; мгновенная попытка при смене сети / возврате в foreground.

### 3.2 Outbox промптов

- Каждый prompt получает `idempotencyKey` (UUID) **до** отправки и сохраняется локально.
- Статусы: `pending → sent → queued → dispatched` (последние два — по событиям сервера).
- Повтор отправки после обрыва — с тем же ключом. Дубля на стороне агента быть не может.
- В UI сообщение видно сразу, со статусом.

### 3.3 Редьюсер состояния

- Чистая функция `(SessionState, Event) → SessionState` в `:shared:domain`.
- Покрывается тестами на фикстурах backend: прогон всей записанной сессии даёт ожидаемое итоговое состояние.
- UI подписан только на `StateFlow<SessionState>`, никакой логики в Composable.

### 3.4 UI-запросы расширений

- Показываются диалогом / карточкой в сессии и как уведомление.
- После ответа с другого устройства (`ui.resolved`) диалог закрывается сам с пометкой, кто ответил.
- Ответ на уже разрешённый запрос (`409`) — не ошибка для пользователя, просто закрыть диалог.

## 4. Этапы

### K0. Каркас проекта

- [ ] KMP-проект с `:androidApp`, `:desktopApp` и shared-модулями из раздела 2.
- [ ] detekt, форматтер, CI (сборка обеих платформ + тесты).
- [ ] Решение по кэшу: Room KMP или SQLDelight.
- [ ] Koin-граф, логирование с `sessionId`.

**Готово, когда:** пустые приложения собираются и запускаются на Android и Desktop в CI.

---

### K1. API-клиент и модели

- [ ] DTO по схеме API v1 (сгенерировать или сверять контрактным тестом со схемой backend).
- [ ] REST-клиент на все эндпоинты B3, обработка кодов `404/409/423/429` в типизированные ошибки.
- [ ] WS-клиент: `hello`, `ping/pong`, разбор кадров `snapshot / event / live / presence / error`.
- [ ] Авторизация токеном, хранение адреса daemon'а и токена.
- [ ] Тесты на Ktor MockEngine с фикстурами backend.

**Готово, когда:** все фикстуры backend разбираются без ошибок; неизвестный тип события не роняет клиент (логируется и пропускается).

---

### K2. Синхронизация (SessionStream + outbox)

- [ ] SessionStream из 3.1.
- [ ] Outbox из 3.2.
- [ ] Редьюсер из 3.3.
- [ ] Отдельный поток списка сессий (`/v1/stream`) для главного экрана.

**Готово, когда:** тесты проходят:
- обрыв соединения посреди turn и переподключение — ни одного пропуска и дубля;
- события пришли не по порядку / с дырой — дозапрос и корректное состояние;
- повтор отправки prompt после обрыва — один prompt на сервере;
- 100 прогонов подряд без флаки.

---

### K3. Локальный кэш

- [ ] Кэш списка сессий и последних N событий каждой сессии.
- [ ] Открытие приложения без сети показывает последнее известное состояние с пометкой «офлайн».
- [ ] `lastSeq` сохраняется, чтобы после перезапуска приложения догружать только новое.
- [ ] Очистка кэша по размеру/возрасту.

**Готово, когда:** холодный старт без сети показывает сессии; после появления сети догружается только разница.

---

### K4. Главный экран — список сессий

- [ ] Группировка по Workspace.
- [ ] Для каждой сессии: провайдер, заголовок, состояние (`WORKING / WAITING_USER / IDLE / HIBERNATED / RESTORABLE / EXTERNAL`), текущая активность (например, `pytest tests/world_model`), время работы / последней активности.
- [ ] Индикатор ожидания модели (`waiting_model`, позиция в очереди).
- [ ] Предупреждение о нескольких живых сессиях в одном cwd.
- [ ] Сортировка: `WAITING_USER` сверху, затем `WORKING`, затем остальные.
- [ ] Pull-to-refresh / ручное обновление.

**Готово, когда:** состояния на экране совпадают с браузером и CLI в реальном времени при трёх параллельных сессиях.

---

### K5. Экран сессии

- [ ] Лента: сообщения пользователя (с источником — Android / Desktop / CLI / Web), ответы ассистента со стримингом, карточки инструментов (свёрнутые, с раскрытием и загрузкой полного вывода).
- [ ] Поле ввода: отправка, выбор режима (follow-up / steer) при `WORKING`, статус сообщения из outbox.
- [ ] Кнопка interrupt, видимая только в `WORKING / WAITING_USER`.
- [ ] UI-запросы расширений (3.4).
- [ ] Presence: кто ещё подключён.
- [ ] Ленивая подгрузка старой истории при прокрутке вверх.

**Готово, когда:** длинная сессия (1000+ событий) прокручивается плавно; стриминг не вызывает рекомпозицию всей ленты.

---

### K6. Управление сессиями

- [ ] Создание сессии: выбор Workspace, провайдера, модели, заголовка.
- [ ] Resume для `HIBERNATED / RESTORABLE`, stop с подтверждением.
- [ ] Pin (держать живой), переименование.
- [ ] Команды: смена модели, compact.
- [ ] Для `EXTERNAL`: View / Clone (Take ownership — когда будет готов B9).

**Готово, когда:** все действия корректно обрабатывают `409` (например, stop уже остановленной сессии) без ошибок для пользователя.

---

### K7. Android-специфика

- [ ] Pairing по QR-коду (URL daemon'а + токен), ручной ввод как запасной вариант.
- [ ] Уведомления:
  - `WAITING_USER` — высокий приоритет, с действием «Открыть»;
  - завершение turn — обычный приоритет;
  - группировка по сессии, без спама при частых событиях.
- [ ] Фоновая работа (только LAN, без push-сервиса):
  - пока есть сессии в `WORKING` — foreground service с постоянным уведомлением и WS-подключением к `/v1/stream`;
  - проверить ограничения типов foreground service и лимиты времени на целевых API Android, выбрать допустимый тип;
  - fallback — периодическая проверка через WorkManager.
- [ ] Реакция на смену сети (Wi-Fi ↔ мобильная, потеря сети): мгновенная попытка переподключения, понятный статус «daemon недоступен».
- [ ] Разрешение на уведомления, поведение при отказе.

**Готово, когда:** телефон в кармане 30 минут с работающим агентом получает уведомление о `WAITING_USER`; после смены сети лента догружается без дыр.

---

### K8. Desktop-специфика

- [ ] Иконка в трее со сводкой (сколько `WORKING`, есть ли `WAITING_USER`).
- [ ] Системные уведомления.
- [ ] Горячие клавиши: отправка, interrupt, переключение между сессиями.
- [ ] Сохранение размера окна и последней открытой сессии.
- [ ] Автозапуск (опционально).

**Готово, когда:** Desktop-клиент можно держать свёрнутым весь день и не пропустить ни одного `WAITING_USER`.

---

### K9. Стабилизация

- [ ] Сквозной сценарий: CLI → detach → Android → Desktop → CLI на одной живой сессии, один PID Pi на всём пути.
- [ ] Chaos на стороне клиента: убить приложение посреди отправки, выключить Wi-Fi во время стриминга, перезапустить daemon при открытом экране сессии.
- [ ] Проверка утечек подписок/соединений (длительная работа Desktop, многократные входы/выходы из экрана на Android).
- [ ] Логи клиента с `sessionId` и `seq`, экспорт логов для отладки.

**Готово, когда:** сквозной сценарий и chaos-набор проходят стабильно; нет растущих соединений/памяти за ночь работы Desktop.
