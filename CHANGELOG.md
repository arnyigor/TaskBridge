# TaskBridge — что в какой версии

Версия видна в шапке интерфейса (`· v0.8.3 · 4bf6e18`) и в `GET /api/info`
(`build.version`, `build.commit`). Баг относится к той версии, которая была
запущена в момент наблюдения.

## 0.9.3-dev — CLI `taskbridge` (шаг 5a)

Административный/клиентский CLI поверх работающего сервера. Не владеет Pi и
не запускает собственного агента — только находит сервер, стартует его как
фоновый процесс, открывает последнюю сессию в браузере и пишет статус.

- `taskbridge open [path]` — последняя сессия по каталогу (или всё задание),
  открывает браузер; если сервер не запущен — поднимает его detached и ждёт
  готовности.
- `taskbridge status` — запущен ли, PID, URL, data-каталог.
- `taskbridge doctor` — конфиг, data-каталог, stale-лок.
- `taskbridge start` / `stop` — detached-запуск и остановка по instance-lock.

Поле `bin` в package.json. Отдельный процесс-владелец агента (5c) — следующий
крупный шаг; этот CLI к нему стабилен.

## 0.9.3-dev — graceful shutdown агента (шаг 5b, P-0)

Штатный рестарт (Ctrl+C, `taskbridge stop`) больше не оставляет осиротевших
Pi и висящего llama.cpp-роутера.

- `TaskManager.close()`: останавливает приём новой работы (очередь), затем по
  каждой живой сессии `closeStdin → (2500мс) killTree` (семантика как у
  `RuntimeControl.closePi`) и останавливает роутер.
- Вызывается из `SIGINT/SIGTERM` сервера с жёстким таймаутом 6с, чтобы
  Ctrl+C всегда завершался. Полный раздельный host (5c) — следующий этап;
  дизайн и альтернативы — в `docs/agent-host-separation.md` и README.
- Покрытие: 2 теста в `tests/manager.test.mjs` (graceful и принудительный kill).

## 0.9.3-dev — AgentHost через IPC (шаг 5c, P-2 фундамент)

Разделение host ⇄ gateway начинает жить двумя файлами поверх транспорта
`src/ipc.mjs`.

- `src/agent-host.mjs`: `AgentHost` собирает агентную сторону (lock, store,
  TaskManager, router) и отдаёт её через IPC-диспетчер команд (задачи, события,
  модель, approvals, mcp) плюс форвардит `task-event` в gateway.
- `src/host.mjs`: отдельный headless-процесс владельца агента (без HTTP),
  токен подписан в `data/host-ipc.json`. `server.mjs` не тронут — legacy-монолит
  остаётся рабочим дефолтом и откатом до полного переключения.
- Транспорт `src/ipc.mjs`: token-auth, newline-JSON поверх loopback TCP,
  REQ/RES + EVENT/SUBSCRIBE, клиент с реконнектом (нужно для переживания
  рестарта gateway). Отдельно проверено в `tests/ipc.test.mjs`.
- Фикс, найденный при этом: `TaskManager.close()` теперь дренит запущенный pump
  до закрытия store (`#drainPump`) и `#executeInitial`/`#setStatus` прерываются
  при `closing`, чтобы фоновая запись события не упала на закрытый store.
- Покрытие: `tests/ipc.test.mjs` (5), `tests/agent-host.test.mjs` (2).

## 0.9.3-dev — Gateway через IPC (шаг 5c, P-3 начало)

`src/gateway.mjs`: HTTP/SSE-фронтенд без владения агентом — каждый клиентский
вызов транслируется в IPC-команду host'у. Статика, маршруты задач (message,
cancel, compact, apply, model, thinking, pending, approvals, events, state),
SSE-канал с реплеем и фан-аутом `task-event` (тот же контракт, что в монолите).

- `src/gateway.mjs` — модуль (`createGateway`) + условный CLI: опт-ин, не
  задействован в `npm start`; монолит остаётся дефолтом и откатом.
- Диспетчер host пополнен (`setAutoCompaction`, `cleanupWorktree`).
- Фикс в gateway: `handleStream` деструктурировал `{events}` из ответа
  диспетчера, но тот возвращает массив — на этом SSE закрывался после
  реплея (catch → res.end). Теперь читает массив напрямую.
- Гейтвей при close гасит открытые сокеты, чтобы `server.close` не висел на
  SSE-подписке.
- Покрытие: `tests/gateway.test.mjs` — полный путь HTTP→IPC→host→событие→SSE.

## 0.9.3-dev — split: running and acceptance (шаг 5c, P-3 финал)

Разделение становится реально запускаемым процессом и доказано acceptance'ом.

- `src/host.mjs` читает `TASKBRIDGE_DATA_DIR` (не жжёт жёстко `ROOT/data`);
  диспетчер host дополнен `registerProject`.
- `scripts/start-split.mjs` — detached-лаунчер host+gateway (опт-ин,
  `npm run start:split`): поднимает host, ждёт его IPC-порт, поднимает gateway,
  пишет PIDs/порты в `data/split.json`.
- `scripts/split-acceptance.mjs` — **acceptance шага 5** (`npm run
  split:acceptance`): host+gateway как отдельные OS-процессы, создание задачи,
  SSE на gateway#1, **SIGTERM gateway#1 → host жив и держит lock, gateway#2 на
  том же эндпоинте видит ту же задачу и стримит SSE-реплей**. PASS в локальном
  прогоне.
- Дефолт не меняется: `npm start` / `taskbridge start` остаются монолитом
  (откат), split — явный выбор.

Остальное (не в этом шаге): реальная генерация Pi переживает рестарт gateway
— свойство процесса доказано acceptance'ом; финальная интеграция с реальной
моделью и переключение дефолта — за рамками текущего изменения.

## 0.9.3-dev — split в CLI (шаг 5c, операционный доступ)

CLI `taskbridge` умеет управлять split-режимом, не трогая дефолт (монолит).

- `taskbridge start --split` — поднимает host + gateway как фоновые процессы
  (через `scripts/start-split.mjs`), ждёт готовности.
- `status` — определяет режим сам: если split жив (по `data/split.json`) —
  показывает host (agent) и gateway (UI) с портом и IPC; иначе монолит.
- `stop` — гасит split (оба PID, затем `SIGKILL` при необходимости, чистит
  `split.json`) либо монолит.
- `dataRoot()` в CLI теперь чтит `TASKBRIDGE_DATA_DIR`.

Проверено вручную на одноразовом data-каталоге: start --split → status →
stop → not running. Полный набор: 333 теста зелёные.

## 0.9.3-dev — gateway: uploads и событийный контракт (split-паритет)

- Убран неиспользуемый второй `TaskStore` в gateway (события идут через IPC;
  лишнее второе соединение с SQLite не держится).

Покрытие: +2 теста в `tests/gateway.test.mjs` (upload через gateway на общий

## 0.9.3-dev — commandId/идемпотентность (этап 3 ТЗ, часть)

Команда `message` становится idемпотентной, когда клиент присылает
`commandId` (опт-ин: старые клиенты без него работают как прежде).

- Ledger команд в TaskManager: `commandId → payload-hash + результат + статус`.
  - тот же `commandId`+payload → возвращается сохранённый результат
    (не дублирует prompt при retry/двойном клике/двух клиентах);
  - тот же id с другим содержимым → `CONFLICT` без исполнения;
  - повтор идущей команды → `ACCEPTED` (не перезапуск);
  - TTL 24ч + очистка по размеру (in-memory; персистентность через рестарт —
    следующий шаг).
- `commandId` проброшен через диспетчер host, gateway и монолитный маршрут
  `/message`.

Покрытие: +2 теста в `tests/manager.test.mjs` (dedup-replay + CONFLICT, и
in-flight → ACCEPTED). Полный набор: 336 тестов зелёные.

## 0.9.2 — 2026-xx-xx

Очередь: сообщения больше не висят в ней без причины (по жалобе «встают в
очередь и долго висят, даже если модель ответила»).

- **Enter больше не паркует сообщение.** Флаг `queue` теперь значит «дождись
  своей очереди, если занято», а не «всегда в очередь». Свободная сессия
  отправляет сразу — раньше каждое сообщение мигало «В очереди» и ждало
  следующего тика насоса, даже когда машина ничего не делала.
- **Потерянные пробуждения.** `#pump()` молча выходил, если в этот момент шёл
  другой pump или машину держала сессия. Если пробуждение приходило в это окно,
  повторить его было некому: очередь стояла до следующего действия оператора.
  Теперь пробуждение запоминается, а всё, что осталось в очереди, держит
  секундный таймер — очередь чинит себя сама.
- **Блокировка головой очереди.** Насос смотрел только на `queue[0]`: сессия,
  ждущая занятую локальную модель, держала за собой всех — включая тех, кому
  локальная модель вообще не нужна. Теперь берётся первая запись, которую
  реально можно выполнить.
- **Отменённая сессия в голове очереди** останавливала насос совсем (рекурсивный
  вызов возвращался из-за флага «уже качаю»). Теперь мёртвые записи просто
  выбрасываются, и обход продолжается.
- **Неудачная доставка** больше не крутит насос в плотном цикле: повтор уходит на
  таймер.

Покрытие: `tests/manager.test.mjs` — три новых теста ровно на эти три способа
зависнуть (потерянное пробуждение, голова очереди, отменённая голова), плюс
обновлённый контракт Enter.

## 0.9.1 — 2026-xx-xx

Облако, шаг 4 из ТЗ v3 — очередь, которая переживает выключенный ПК:

- **Команда спящей машине больше не теряется.** Релей складывает `COMMAND` в
  durable-очередь (Upstash Redis по REST, если он настроен; иначе в память
  одного хоста) и отдаёт её машине сразу после подключения — в исходном порядке
  и ровно один раз. Телефон получает `COMMAND_ACK` с `queued: true`, а не отказ.
- **Что не копится:** `REQUEST` и `SYNC` — им нужен ответ сейчас, поэтому они
  по-прежнему честно отклоняются с `MACHINE_OFFLINE`.
- **Границы очереди:** 50 команд на машину и сутки жизни — сутки спустя команда
  скорее навредит.
- **Релей наконец включён в бою**: локальный облачный хост поднимает `/api/relay`
  с теми же машинами, что настроены для облачного API.
- **Починено по дороге:** отказ релея (`ERROR`) не содержал `commandId`, а клиент
  его игнорировал — «машина офлайн» приходило мгновенно, но экран ждал таймаут.
- **Починено по дороге:** сообщение с файлом, попавшее в очередь, теряло файл при
  доставке — в чате вместо вложения появлялся путь `.taskbridge-input/…`, а если
  сессия ещё не создала workspace, запрос падал с 500 и терял текст. Теперь файлы
  ждут вместе с промптом и раскладываются при доставке, ровно один раз.

Покрытие: `tests/cloud-queue.test.mjs` (5 проверок, включая поддельный Upstash и
сквозной путь «телефон → спящая машина → включение») и новый тест вложения в
`tests/queue-http.test.mjs`. Три теста релея/транспорта обновлены под новый
контракт: у офлайн-машины команда встаёт в очередь, а не отваливается ошибкой.

## 0.9.0 — 2026-xx-xx

Облако, шаг 3 из ТЗ v3 — уведомления, которые приходят с закрытым приложением:

- **Web Push прямо с машины.** ПК сам себе application server: подписывает
  VAPID-токен (RFC 8292) и отправляет зашифрованное уведомление (RFC 8291) в
  push-сервис браузера. Облако в этом пути не участвует и текста не видит.
  Шифрование сверено с примером из RFC 8291 побайтово.
- **Что присылаем:** сессия завершилась, упала, остановлена или просит
  подтверждения. Тап по уведомлению открывает саму сессию (`/session/<id>`),
  переиспользуя уже открытую вкладку.
- **Ключи и подписки** — в `data/push.json`; приватная половина VAPID никогда не
  уходит в браузер, наружу отдаются только имя устройства и хост push-сервиса.
  Мёртвые подписки (404/410 или пять ошибок подряд) забываются сами.
- **Кнопка 🔔 перестала врать**: выключение отписывает браузер от push, а не
  только гасит локальные уведомления.
- **Починено по дороге:** регистрация service worker была инлайновым скриптом, а
  сервер отдаёт `script-src 'self'` — браузер её молча блокировал, и PWA не
  устанавливался вообще. Теперь она в `web/cloud-config.js`, а тест запрещает
  инлайновые скрипты в оболочке.

Покрытие: `tests/push.test.mjs` (9 проверок, включая сквозную «завершённая сессия
доходит до рассылки») и запрет инлайновых скриптов в `tests/cloud-web.test.mjs`.

## 0.8.9 — 2026-xx-xx

Облако, шаг 2 из ТЗ v3 — паринг телефона и отзыв устройства:

- **QR на компьютере.** `POST /api/cloud/pair` выпускает device token, подписанный
  секретом машины, и складывает устройство в `data/trusted-devices.json`. QR ведёт
  на `<cloud>/pair#m=…&t=…&r=…`: ключ едет во фрагменте, который браузер никогда
  не отправляет серверу, поэтому облако его не видит и не логирует.
- **Телефон запоминает доступ сам.** `web/cloud-config.js` разбирает ссылку,
  кладёт реквизиты в localStorage и тут же убирает ключ из адресной строки
  (`history.replaceState`), после чего общий UI работает через релей.
- **Отзыв устройства работает.** Device token — подпись без состояния, релей её
  не отзывает; поэтому машина проверяет каждый кадр от клиента и отвечает
  отозванному телефону `DEVICE_REVOKED`, ничего не выполняя. Список устройств,
  «Отключить» и «Забыть» — в настройках облака (☁).
- **Realtime-коннектор наконец включается в бою**: при `cloud.realtime` машина
  сама открывает соединение с релеем (`wss://<cloud>/api/relay`), порт наружу
  по-прежнему не нужен.
- QR рисуется вендоренным `web/vendor/qrcode.mjs` (qrcode-generator, MIT), модуль
  подгружается только при открытии экрана.

Покрытие: `tests/cloud-pairing.test.mjs` — хранилище доверенных устройств (включая
битый файл), HTTP-паринг с перезапуском машины, и отзыв, проверенный через
настоящий релей с настоящим коннектором. Плюс разбор ссылки паринга в
`tests/cloud-web.test.mjs`.

  очереди до отправки; если отправка отказывала (модель занята, RPC), текст
  исчезал. Теперь очередь не «выдаёт» сообщение до успеха: отказ возвращает его
  в начало очереди и пишет событие `QUEUE_RETRY`. Это же защищает авто-доставку
  от гонок. Сам «Отправить сейчас» работает как Ctrl+Enter: пробует отправить
  (флаг «модель занята» может быть устаревшим), и при неудаче сообщение остаётся
  в очереди; если машину держит другая сессия — отказ с её именем.
- **Очередь отдавала сообщения не по порядку** («третье» раньше «второго»):
  два прохода `#pump` могли одновременно забрать сообщения. Введена защита от
  повторного входа; порядок теперь проверяется тестом.
- **Во время генерации нельзя было отправить** (в CSS «Стоп» заменял «Отправить»,
  а на телефоне Enter — перенос строки): теперь кнопки стоят рядом, отправка в
  очередь доступна всегда.
- **Работающая сессия не была видна.** Добавлена полоса состояния над полем
  ввода: `Pi работает · 12 с · qwen-27b`, `В очереди — ждёт модель · 5 с`,
  `Останавливаю…` — с живым таймером (сервер отдаёт `statusChangedAt`).
- «Стоп» больше не привязан к выбранной сессии (см. 0.8.4) и остаётся доступным.

## 0.8.4 — 2026-xx-xx

Очередь, шаг 2 (найдено на 0.8.3):

- **«Отправить сейчас» не работал.** При занятой машине он молча возвращал
  сообщение в очередь (выглядело как «кнопка ничего не делает»). Теперь отказ
  явный и называет сессию-владельца: «Машина занята сессией «X» — сначала
  остановите её», а сообщение остаётся в очереди.
- **«Стоп» останавливал только выбранную сессию.** Если генерация шла в другой
  сессии, кнопка ничего не делала. Теперь она нацелена на ту сессию, которая
  реально работает (подсказка в `title`), блокируется, когда останавливать
  нечего, и обновляется при каждом `loadTasks`, а не только при выборе сессии.

## 0.8.3 — 2026-xx-xx

Исправления очереди и облачного интерфейса:

- **Очередь работала только для уже запущенной сессии.** Решение «в очередь или
  сразу» принималось ПОСЛЕ запуска сессии, а запуск на занятой модели падал с
  «модель занята», и до очереди дело не доходило. Теперь проверка очереди идёт
  первой: сообщение (и файлы) сохраняются в `pendingPrompts` и доставляются,
  когда модель освободится. Это же убирает отказ при отправке в другую сессию,
  пока занята текущая.
- **Текст в поле ввода больше не теряется.** Черновик сохраняется на каждое
  нажатие, а при отказе «модель занята» сообщение автоматически уходит в очередь
  вместо потери.
- **Пустая плашка облачного режима.** Правило `#modeBanner { display: flex }`
  перебивало `.hidden` и оставляло пустую полосу; теперь только
  `#modeBanner:not(.hidden)` (закрыто тестом `tests/web-css.test.mjs`).
- **С телефона доступно больше.** Через релей к машине разрешены `cancel`,
  `auto-compaction`, `state`, `approvals`; кнопки, работающие только на ПК
  (импорт сессий Pi, MCP, локальные модели, настройки облака, добавление
  проектов, вложения), помечены `data-pc-only` и скрыты в облачном режиме.
- Плашка облачного режима показывает состояние машины (подключение / на связи /
  офлайн / устройство отклонено).
