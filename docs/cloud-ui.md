# Один интерфейс для локального и облачного доступа

Требование ТЗ: «Отделить PWA frontend от локального TaskBridge server. Один и
тот же frontend должен собираться для локального использования и для Vercel;
никакой бизнес-логики Pi в браузере». Плюс: PWA открывается, даже когда ПК
выключен.

Документ фиксирует, что сейчас, почему это два разных UI и как свести их в один.

## 1. Что сейчас (замер 11 сентября 2026)

| | локальный UI | облачный UI |
|---|---|---|
| размер | `web/app.js` 2344 строки, `web/index.html` 360, `web/app.css` 1099 | `cloud/web/app.js` 444, `index.html` 100, `styles.css` 150 |
| адрес сессии `/session/<id>` | есть | нет |
| импорт Pi-сессий | есть | нет |
| выбор модели Pi / thinking | есть | нет |
| MCP-серверы, локальные модели | есть | нет |
| очередь сообщений и её кнопки | есть | нет |
| список сессий группами «Активные/Недавние» | есть | нет |
| чем занят | HTTP+SSE к своему origin | `fetch` к `/api/machines`, `/api/tasks`, `/api/tasks/:id/commands`, `/api/tasks/stream` |

Вывод: облачный UI — это отдельное, сильно урезанное приложение. Хуже того, оно
говорит с **облачным хранилищем** (задачи и события живут в облаке), а новое ТЗ
требует обратного: облако — только транспорт, источник правды — ПК.

## 2. Куда идём

```
одни и те же файлы web/*  ──отдаются──►  localhost:8787   (LocalTransport)
                          ──отдаются──►  Vercel CDN       (CloudTransport)
```

1. **Единственный источник UI — `web/`.** Облако отдаёт те же файлы (Vercel
   раздаёт их как статику), а не свою копию `cloud/web/`. Копия удаляется; свои
   у облака остаются только deployment-ассеты: `manifest.webmanifest`, `sw.js`,
   иконки.
2. **В клиенте появляется Transport.** Всё, что сейчас делает `api('/api/...')`,
   уходит в интерфейс с двумя реализациями:
   - `LocalTransport` — как сегодня: HTTP + SSE к своему origin (`/api/...`);
   - `CloudTransport` — кадры протокола ([`cloud-protocol.md`](cloud-protocol.md))
     по WebSocket через релей: `HELLO/AUTH → ATTACH → SYNC{afterSeq} → EVENT`,
     команды `COMMAND` с `commandId`.
   Выбор реализации — по origin (localhost/LAN → Local, публичный адрес → Cloud).
3. **Pi-логика остаётся в Core на ПК.** Браузер только рисует состояние и шлёт
   команды; никаких решений о запуске Pi, workspace, verification в браузере.
4. **Облачный UI перестаёт читать облачные задачи.** `SESSION_LIST` (список
   сессий машины) и `EVENT` (поток с монотонным `seq`) приходят от ПК через
   релей; `SYNC{afterSeq}` добирает пропущенное. Машина офлайн → UI показывает
   «Offline», а не пустой список из облака.

## 3. Порядок работ

0a. **Запросы в облаке — готово**: транспорт отправляет `REQUEST`, машина выполняет
   его против своего локального API с белым списком (`CLOUD_ALLOWED`) и
   возвращает `RESPONSE`, поэтому общие экраны работают без второй модели API,
   а запрещённое отклоняется с `CLOUD_PATH_DENIED`.
0. **Транспорт в клиенте — готов** (`web/transport.mjs`): `createLocalTransport`
   (HTTP + SSE, как сейчас) и `createCloudTransport` (кадры протокола через
   релей: `HELLO` с токеном устройства → `ATTACH` → `SYNC{afterSeq}` → живой
   `EVENT`-поток, команды с подтверждением, переподключение с догоном).
   `selectTransport()` выбирает по origin. Покрыто тестами против **реального**
   релея и настоящего коннектора ПК: догон пропущенных событий, живой поток,
   команда с `COMMAND_ACK`, отказ аутентификации, таймаут команды. Экраны,
   которым нужен ПК (модели, MCP, импорт), получают явный `NOT_SUPPORTED`.
   Обычные запросы и поток сессии уже идут через транспорт; остались файлы
   (multipart) и облачный режим в интерфейсе.
1. **WS-слой релея** (`cloud/lib/relay.mjs` уже готов как ядро): привязка к
   WebSocket + коннектор на ПК (исходящий `wss://`, `HELLO` ролью `machine`).
2. **Transport в клиенте**: вынести сетевой слой из `web/app.js`, добавить
   `CloudTransport`, переключать по origin.
3. **Один фронтенд — готово**: `vercel.json` раздаёт `web/`, копия `cloud/web/*`
   удалена, `sw.js`/манифест/иконка переехали в общий `web/`, а
   `web/cloud-config.js` подставляет реквизиты релея на публичном адресе.
   Локальный хост облака (`cloud/server.mjs`) раздаёт тот же каталог, поэтому
   разъехаться им больше негде; проверяется `tests/cloud-web.test.mjs`.
4. **Проверка паритета**: чек-лист «локально = облако» — адрес сессии,
   очередь и её кнопки, импорт, модель/thinking, MCP, локальные модели,
   approvals; всё это должно работать в обоих транспортах.
5. **Проверка офлайна**: ПК выключен → PWA открывается, машина Offline,
   история недоступна (и это явно написано), при включении ПК сессии появляются.

Пока пункты 1–3 не сделаны, облачный UI остаётся вторичным и урезанным: править
его отдельно **не нужно** — он будет заменён.

## 4. Что нельзя потерять при объединении

- `/session/<id>`: ссылка, закладка и перезагрузка открывают ту же сессию и в
  облаке.
- Очередь сообщений: `Enter` — в очередь, `Ctrl+Enter` — сразу; кнопки у
  сообщения в очереди работают и с телефона.
- Импорт Pi-сессий и выбор модели — из облачного UI тоже (это команды к ПК).
- Никакой утечки: `payload` при E2EE — шифртекст, облако видит только
  маршрутизацию.

## 5. Паринг телефона (готово)

```
ПК (☁ → «Показать QR»)                     Телефон
  POST /api/cloud/pair                       сканирует QR
  → deviceId + device token (HMAC машины)    → открывает <cloud>/pair#m&t&r
  → запись в data/trusted-devices.json       → cloud-config.js кладёт в localStorage
                                             → history.replaceState('/') — ключ уходит из адреса
```

- **Ключ не проходит через облако.** Токен едет во фрагменте URL, а фрагмент
  браузер не отправляет серверу: облако видит только `/pair`.
- **Отзыв работает на машине.** Device token — это подпись без состояния, релей
  её отозвать не может. Поэтому каждый кадр от клиента проверяется коннектором
  (`isDeviceAllowed`): отозванному устройству приходит честный `DEVICE_REVOKED`,
  и ничего из запрошенного не выполняется.
- **Список устройств** (`GET /api/cloud/devices`) показывает, кто подключён и
  когда был на связи; `POST /api/cloud/devices/:id` отключает, `DELETE` забывает.
  Сами токены не хранятся и не показываются повторно — только в QR, один раз.
- **Realtime.** Коннектор к релею запускается, когда в настройках облака включён
  `realtime` (иначе телефону некуда подключаться: облачный API остаётся на
  опросе). Адрес релея берётся из адреса облака: `wss://<cloud>/api/relay`.

Покрытие: `tests/cloud-pairing.test.mjs` — хранилище устройств, HTTP-паринг
(включая перезапуск машины) и отзыв, проверенный через настоящий релей.

## 6. Уведомления (Web Push, готово)

```
ПК: событие сессии (TASK_SUCCEEDED / TASK_FAILED / TASK_CANCELLED / APPROVAL_REQUIRED)
  → PushCenter шифрует текст ключами подписки (RFC 8291)
  → POST прямо в push-сервис телефона с VAPID-подписью (RFC 8292)
  → sw.js показывает уведомление; тап открывает /session/<id>
```

- **Облака в этом пути нет.** Машина сама себе application server: она подписывает
  VAPID-токен и шлёт запрос в push-сервис браузера. Текст зашифрован для
  конкретного браузера — ни облако, ни push-сервис его не читают.
- **Ключи.** Пара VAPID создаётся один раз и живёт в `data/push.json`; приватная
  половина никогда не уходит в браузер. Подписки лежат там же, наружу отдаются
  только имя и хост push-сервиса.
- **Уборка.** `404/410` от push-сервиса — подписка сразу забывается; пять подряд
  других ошибок — тоже (иначе мёртвый эндпоинт опрашивался бы вечно).
- **Выключатель 🔔 честный**: он не только гасит локальные уведомления, но и
  отписывает браузер от push, иначе «выключено» приходило бы на телефон.
- Регистрация service worker вынесена в `web/cloud-config.js`: сервер отдаёт
  `script-src 'self'`, поэтому инлайновый `<script>` браузер молча блокирует.

Покрытие: `tests/push.test.mjs` — шифрование сверено с примером из RFC 8291
побайтово, VAPID-JWT проверяется настоящей подписью, разбор событий, веерная
рассылка с выбыванием мёртвых подписок, HTTP-подписка с перезапуском машины и
сквозная проверка, что завершённая сессия доходит до рассылки.

## 7. Очередь на стороне облака (готово)

«Работает, пока ПК выключен» — про одну вещь: команду, отправленную спящей
машине.

- **Что копится.** Только `COMMAND` (остановить, продолжить, отправить). Всё,
  чему нужен ответ сейчас (`REQUEST`, `SYNC`), честно отклоняется с
  `MACHINE_OFFLINE` — иначе экран крутил бы спиннер сутки.
- **Где копится.** `cloud/lib/relay-queue.mjs`: Upstash Redis по REST (serverless
  не держит TCP) при `UPSTASH_REDIS_REST_URL/TOKEN` или `KV_REST_API_*`, иначе —
  в памяти одного хоста. Список на машину: `RPUSH` + `LTRIM` + `PEXPIRE`, выдача
  — `LRANGE` + `DEL` одним пайплайном.
- **Границы.** 50 команд на машину (лишние вытесняются с головы) и сутки TTL:
  команда, пролежавшая день, скорее навредит, чем поможет.
- **Выдача.** Машина получает накопленное сразу после `AUTH_OK`, в исходном
  порядке и ровно один раз; повторный коннект ничего не переигрывает.
- **Телефон не обманут:** на офлайн-команду приходит `COMMAND_ACK` со статусом
  `ACCEPTED` и `queued: true` — «уйдёт, когда ПК включится».
- Заодно: `ERROR` от релея теперь несёт `commandId`, а клиентский транспорт по
  нему закрывает ожидание. Раньше отказ «машина офлайн» приходил мгновенно, но
  экран всё равно ждал таймаута.

Покрытие: `tests/cloud-queue.test.mjs` — семантика очереди (порядок, лимит, TTL),
Upstash-бэкенд против поддельного REST-сервиса, выбор бэкенда по окружению и
сквозной путь «телефон → спящая машина → включение» на настоящем релее.
