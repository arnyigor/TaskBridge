# Один интерфейс для локального и облачного доступа

Требование ТЗ: «Отделить PWA frontend от локального TaskBridge server. Один и
тот же frontend должен собираться для локального использования и для Vercel;
никакой бизнес-логики Pi в браузере». Плюс: PWA открывается, даже когда ПК
выключен.

Документ фиксирует, что сейчас, почему это два разных UI и как свести их в один.

## 1. Что сейчас (замер 11 сентября 2026)

| | локальный UI | облачный UI |
|---|---|---|
| размер | `web/app.js` 2344 строки, `web/index.html` 360, `web/app.css` 1099 | `cloud/web/app.js` 444, `index.html` 100, `styles.css` 150 |
| адрес сессии `/session/<id>` | есть | нет |
| импорт Pi-сессий | есть | нет |
| выбор модели Pi / thinking | есть | нет |
| MCP-серверы, локальные модели | есть | нет |
| очередь сообщений и её кнопки | есть | нет |
| список сессий группами «Активные/Недавние» | есть | нет |
| чем занят | HTTP+SSE к своему origin | `fetch` к `/api/machines`, `/api/tasks`, `/api/tasks/:id/commands`, `/api/tasks/stream` |

Вывод: облачный UI — это отдельное, сильно урезанное приложение. Хуже того, оно
говорит с **облачным хранилищем** (задачи и события живут в облаке), а новое ТЗ
требует обратного: облако — только транспорт, источник правды — ПК.

## 2. Куда идём

```
одни и те же файлы web/*  ──отдаются──►  localhost:8787   (LocalTransport)
                          ──отдаются──►  Vercel CDN       (CloudTransport)
```

1. **Единственный источник UI — `web/`.** Облако отдаёт те же файлы (Vercel
   раздаёт их как статику), а не свою копию `cloud/web/`. Копия удаляется; свои
   у облака остаются только deployment-ассеты: `manifest.webmanifest`, `sw.js`,
   иконки.
2. **В клиенте появляется Transport.** Всё, что сейчас делает `api('/api/...')`,
   уходит в интерфейс с двумя реализациями:
   - `LocalTransport` — как сегодня: HTTP + SSE к своему origin (`/api/...`);
   - `CloudTransport` — кадры протокола ([`cloud-protocol.md`](cloud-protocol.md))
     по WebSocket через релей: `HELLO/AUTH → ATTACH → SYNC{afterSeq} → EVENT`,
     команды `COMMAND` с `commandId`.
   Выбор реализации — по origin (localhost/LAN → Local, публичный адрес → Cloud).
3. **Pi-логика остаётся в Core на ПК.** Браузер только рисует состояние и шлёт
   команды; никаких решений о запуске Pi, workspace, verification в браузере.
4. **Облачный UI перестаёт читать облачные задачи.** `SESSION_LIST` (список
   сессий машины) и `EVENT` (поток с монотонным `seq`) приходят от ПК через
   релей; `SYNC{afterSeq}` добирает пропущенное. Машина офлайн → UI показывает
   «Offline», а не пустой список из облака.

## 3. Порядок работ

1. **WS-слой релея** (`cloud/lib/relay.mjs` уже готов как ядро): привязка к
   WebSocket + коннектор на ПК (исходящий `wss://`, `HELLO` ролью `machine`).
2. **Transport в клиенте**: вынести сетевой слой из `web/app.js`, добавить
   `CloudTransport`, переключать по origin.
3. **Один фронтенд**: Vercel раздаёт `web/`, `cloud/web/*` удаляется, кроме
   `sw.js`/манифеста/иконок.
4. **Проверка паритета**: чек-лист «локально = облако» — адрес сессии,
   очередь и её кнопки, импорт, модель/thinking, MCP, локальные модели,
   approvals; всё это должно работать в обоих транспортах.
5. **Проверка офлайна**: ПК выключен → PWA открывается, машина Offline,
   история недоступна (и это явно написано), при включении ПК сессии появляются.

Пока пункты 1–3 не сделаны, облачный UI остаётся вторичным и урезанным: править
его отдельно **не нужно** — он будет заменён.

## 4. Что нельзя потерять при объединении

- `/session/<id>`: ссылка, закладка и перезагрузка открывают ту же сессию и в
  облаке.
- Очередь сообщений: `Enter` — в очередь, `Ctrl+Enter` — сразу; кнопки у
  сообщения в очереди работают и с телефона.
- Импорт Pi-сессий и выбор модели — из облачного UI тоже (это команды к ПК).
- Никакой утечки: `payload` при E2EE — шифртекст, облако видит только
  маршрутизацию.
