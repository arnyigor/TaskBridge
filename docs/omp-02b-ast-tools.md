# OMP-02b — структурные инструменты OMP на четырёх задачах

**Статус: `NO-GO / evidence limited`.** Переход на OMP ради `ast_grep`, `ast_edit` и
`hashline edit` не оправдан. Ограничение доказательной базы: включённые инструменты
фактически не вызывались моделью, поэтому эффективность самих AST-операций в работе
агента этим экспериментом не проверена — проверены их доступность и влияние на
поведение OMP при включении.

Узкая проверка гипотезы из аудита OMP-02: прежний `NO-GO` не проверял главные
инструменты OMP — `ast_grep`, `ast_edit` и `edit` в режиме `hashline`. Здесь они
доступны, а прогон отвечает на два вопроса: **использует ли модель эти инструменты**
и **даёт ли это выигрыш** против Pi с тем же набором без shell.

## Что проверялось и как

Модель во всех плечах одна — `deepseek/deepseek-flash`, thinking `medium`. Различается
только ядро и доступность AST-инструментов:

| Плечо | Ядро | Инструменты |
| --- | --- | --- |
| `pi-plain` | Pi 1.3.0 | `read,write,edit,grep,find,ls` |
| `omp-plain` | OMP 18.11.0, `astGrep.enabled=false` | `read,write,edit,grep,glob` (edit = `hashline`) |
| `omp-ast` | OMP 18.11.0, `astGrep.enabled=true`, `astEdit.enabled=true` | то же + `ast_grep`, `ast_edit` |

`bash` нет ни в одном плече: иначе «структурный поиск» подменяется `grep`/`sed`, и
сравнение перестаёт отвечать на вопрос.

Доступность инструментов проверена отдельно: при `astGrep.enabled=true` модель видит
`ast_grep` и `ast_edit` (снято из `get_state` OMP), при `false` — нет. В OMP-02 их не
было, то есть прежний `NO-GO` действительно не проверял эти возможности.

Профиль для прогона:

```bash
omp --profile omp02b-ast config set astGrep.enabled true
omp --profile omp02b-ast config get astGrep.enabled   # true
```

## Сценарии и проверка

| Тест | Задача | Проверка (без участия модели) |
| --- | --- | --- |
| AST-01 | найти все вызовы `parseUnits`, не считая определение, строки и комментарии (в файлах есть 3 комментария, строковый литерал и одноимённая локальная функция) | `answer.json` сравнивается с эталонным множеством пар «файл:строка», лишнее и пропущенное считаются |
| AST-02 | среди 40 однотипных `async handleNN(req)` найти 8 функций, отвечающих `res.status(500)` в своём `catch` | множество имён в `answer.json` сравнивается с эталоном |
| EDIT-01 | починить `sliceWindow` в файле на 190 строк, не меняя остальной файл | `node verify.js` (5 случаев) + правило: вне функции файл обязан быть побайтово тем же |
| EDIT-02 | перевести 8 сервисов с `fetchUser` на `fetchUserById`, не тронув три одноимённые локальные функции | `node verify.js` + побайтовая проверка нетронутых файлов |

Правило EDIT-01 проверено отдельно на двух случаях: чистая правка тела функции
принимается, правка посторонней функции отвергается (`restOfFileUntouched=false`).
Первая версия правила (построчный диф) давала ложный провал: замена тела сдвигает
номера строк ниже, и живые строки выглядели изменёнными.

## Результаты

12 прогонов (4 сценария × 3 плеча), по одному на ячейку:

| Сценарий | `pi-plain` | `omp-plain` | `omp-ast` |
| --- | --- | --- | --- |
| AST-01 | ✅ 12.0 с, 9 вызовов, 5.7K | ✅ 14.4 с, 10, 8.0K | ✅ 12.7 с, 10, 10.3K |
| AST-02 | ✅ 6.4 с, 4, 5.3K | ✅ 13.5 с, 8, 9.0K | ✅ 10.6 с, 5, 9.9K |
| EDIT-01 | ✅ **6.6 с, 3, 5.0K** | ✅ 47.5 с, 18, 23.4K | ✅ 16.1 с, 6, 9.9K |
| EDIT-02 | ✅ 15.7 с, 29, 7.9K | ✅ 16.2 с, 18, 10.4K | ✅ 16.6 с, 15, 12.9K |

Сумма по четырём сценариям:

| Показатель | `pi-plain` | `omp-plain` | `omp-ast` |
| --- | --- | --- | --- |
| Успешность | 4/4 | 4/4 | 4/4 |
| Время | **40.7 с** | 91.6 с | 56.0 с |
| Вызовов инструментов | 45 | 54 | **36** |
| Токенов | **23.9K** | 50.7K | 43.0K |
| Вызовов `ast_grep`/`ast_edit` | — | 0 | **0** |

Меньше инструментальных вызовов у `omp-ast` дал не AST, а EDIT-02 (15 против 29 у Pi).

## Что это значит

1. **Инструменты доступны, но модель их почти не берёт.** Во втором прогоне
   `ast_grep` и `ast_edit` не вызваны ни разу из 12. В первом прогоне — по одному
   вызову (`ast01/omp-ast` → `ast_grep`, `edit02/omp-ast` → `ast_edit`), и оба
   ответа всё равно верные. То есть проблема не в доступности, а в том, что модель
   предпочитает `grep`/`read`/`edit`. Это ответ на вопрос аудита: включение AST не
   меняет поведение.
2. **Выигрыша нет ни по одному сценарию.** AST-плечо не точнее (`pi-plain` тоже
   4/4 верных) и не быстрее. На EDIT-01 `hashline`-правка OMP оказалась самой
   дорогой: 47.5 с, 18 вызовов и 23.4K токенов против 6.6 с, 3 и 5.0K у Pi —
   модель сделала 7 записей и 8 чтений вместо одной правки.
3. **Потенциал «меньше контекста» не реализовался.** Самый большой разрыв в
   токенах — в пользу Pi (EDIT-01 в 4.7 раза).

## Ограничения

- **Главное: AST-инструменты не вызывались.** Ноль вызовов `ast_grep`/`ast_edit` в
  финальной серии (в первой, до правки правила EDIT-01, было по одному вызову на
  разные сценарии, и это не изменило результат). Эксперимент показывает, что
  включённые инструменты не меняют поведение модели, но **не** показывает,
  эффективны ли сами AST-операции, — для этого нужен агент, который их вызывает.
- По одному прогону на ячейку: разброс модели не измерен, выводы — направление.
- Только облачная модель (`deepseek-flash`) по указанию оператора; локальная Qwen
  не проверялась.
- Фикстуры синтетические и небольшие: EDIT-01 — файл на 190 строк. Это мало, чтобы
  окончательно оценить `hashline` на больших файлах; вывод про EDIT-01 — только
  факт этих прогонов, не свойство инструмента.
- `bash` исключён намеренно: на задачах, где модель всё равно использует shell,
  результат может отличаться.
- Плеча «подсказка в промпте использовать `ast_grep`» не было.

## Вердикт

`NO-GO` на миграцию TaskBridge с Pi на OMP. OMP остаётся в резерве: инструменты
работают и доступны, но выигрыша в качестве или эффективности не дали, а на
точечной правке OMP оказался заметно дороже.

Что сохраняется на будущее:

- **LSP** — единственная непроверенная возможность, которая может быть полезна на
  большом Kotlin/JS-проекте (реальные ссылки, типы, реализации интерфейсов).
  Делать отдельный PoC только когда появится реальная сложная задача; не ради
  этого продолжать OMP.
- **hashline** — возвращаться при воспроизводимых ошибках точечных правок
  локальной Qwen; **ast_grep** — если обычный поиск систематически путает символы;
  **ast_edit** — только при подтверждённой потребности в массовых структурных
  правках.
- Не устанавливать AST/`hashline`-расширения для Pi «потому что они есть»: сначала
  нужен конкретный дефект, который они исправляют.

Воспроизведение:

```bash
node experiments/omp-02b/run-ast.mjs --variant all --timeout 180000
```
