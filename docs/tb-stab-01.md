# TB-STAB-01: стабильность HTTP API и жизненного цикла задач

Аудит по двум подтверждённым дефектам и регрессионная проверка жизненного цикла.
Агентное ядро, PromptBuilder, Pi-расширения и OMP не менялись; рабочий KMP, его
незакоммиченные файлы и конфигурация моделей не тронуты. Действующий сервер не
останавливался: воспроизведение — на фикстурах (`tests/server-fixture.mjs`) и на
локальном прокси из `src/proxy.mjs`.

## Задача 1. HTTP 500 на некорректном JSON — исправлено (коммит `ebfb058`)

### Как воспроизводилось

```
POST /api/tasks
content-type: application/json
[object Object]
```

Так выглядит объект, переданный в `fetch` без `JSON.stringify`. Ответ был
**500 `INTERNAL_ERROR`** с текстом парсера (`Unexpected token...`), то есть ошибка
клиента выглядела как сбой сервера и попадала в 5xx-метрики.

### Причина

`readJson()` (`src/server.mjs`) вызывал `JSON.parse(text)` без обработки. `SyntaxError`
не имеет поля `code`, поэтому общий обработчик запроса уходил в последнюю ветку —
`500`, и `errorJson` отдавал клиенту `error.message` (слова парсера). Вторая,
менее очевидная часть: тело декодировалось `Buffer.toString('utf8')`, который
**молча** заменяет битые байты на `U+FFFD`, — эндпоинт получал тело, которого
клиент не отправлял.

### Что изменено

`src/server.mjs`, только `readJson()`:

| Случай | Было | Стало |
| --- | --- | --- |
| Тело не JSON (`[object Object]`, обрезанный объект, мусор) | 500 + текст парсера | **400 `INPUT_INVALID`** «Тело запроса не является корректным JSON.»; текст парсера остаётся в логе сервера |
| Битый UTF-8 | молча `U+FFFD` → дальше как повезёт | **400 `INPUT_INVALID`** «Тело запроса не является корректным UTF-8.» (`TextDecoder(fatal)`) |
| Пустое тело | `{}` | `{}` — без изменений: так его и ждут эндпоинты (`/cancel`, `/clear`), поведение клиентов не меняется |
| Тело больше `server.maxBodyMb` | 413 `BODY_TOO_LARGE` | без изменений, покрыто тестом |
| Неверный `Content-Type` | 400 `INPUT_INVALID` (контракт `checkOrigin`) | без изменений, покрыто тестом |

Внутренние подробности наружу не уходят: у 500-ответов текст ошибки по-прежнему
свой (это операторский сервер за авторизацией), но разбор тела теперь до 500 не
доходит вовсе.

### Тесты

`tests/http-errors.test.mjs` (7, живой фикстур, сырые тела): `[object Object]`,
обрезанный JSON и мусор (все 4xx, ни одного 500), битый UTF-8, неверный
`Content-Type`, тело сверх лимита (фикстура с `maxBodyMb: 0.001` → 413), пустое
тело (обычная валидация 400), и контрольный корректный запрос — работает как
раньше. Файл включён в секцию `server` набора `scripts/regression-suite.mjs`.

## Задача 2. Редкий HTTP 502 при STOP — причина не доказана, исправления нет

### Что наблюдалось

Один раз на рабочем LAN-сервере `POST /api/tasks/:id/cancel` через прокси ответил
**502**; в `data/lan-proxy.log` — `upstream … unreachable: socket hang up`, в
`data/lan-app.log` — ничего в этот момент. Повторные STOP (через прокси и напрямую
в приложение) дали 200 и `CANCELLED`.

### Как пытался воспроизвести

Стенд `local`-скрипт на фикстуре: приложение + настоящий `createReverseProxy`,
восемь моментов отмены на 10-секундном ходе (200 мс, 2 с, 9 с, 9,9 с, 10,05 с,
12 с — включая гонку с естественным завершением), каждый раз напрямую и через
прокси, плюс повторный STOP и STOP после терминального состояния — **16 запросов,
все 200**, состояние всегда `CANCELLED`, задним числом ничего не менялось.

Отдельно проверял механизм «прокси переиспользует idle-сокет, приложение его
закрывает» (глобальный агент Node держит `keepAlive: true`): upstream с
`keepAliveTimeout = 40 мс`, 240 последовательных запросов с разными интервалами и
пачка из 20 параллельных — **ни одного обрыва**, Node корректно замечает закрытие
сокета.

### Вывод и что сделано вместо «исправления»

Причина не подтверждена, поэтому код поведения STOP не менялся (по ТЗ
предположительные правки не вносятся). Добавлена **трассировка**, которой не
хватало для следующего раза:

- `src/proxy.mjs`: на каждый запрос прокси выдаёт/переиспользует
  `x-taskbridge-request-id` (валидный от клиента сохраняется), передаёт его в
  приложение, возвращает в заголовке и в теле 502 (`requestId`), и печатает в логе
  строку `[proxy] <id> upstream … unreachable: <error> (<METHOD> <path>)`;
- `src/server.mjs`: строка ошибки приложения начинается с того же id
  (`[<id>] <message>` или `[-]`, если id нет).

`tests/proxy.test.mjs` (+2): 502 несёт id, и приложение получило **тот же** id;
валидный id клиента сохраняется, испорченный — заменяется.

Что смотреть при следующем 502: один и тот же id в `lan-proxy.log` и `lan-app.log`.
Если в приложении строки нет вовсе — сокет закрылся без обработки запроса (тогда
смотреть `lan-app.log` на `[restart]`, OOM и таймауты Node); если строка есть —
причина в самом обработчике, и её видно по тексту.

## Оставшиеся риски

1. **502 при STOP** — дефект не воспроизведён и не исправлен: следующий случай даст
   id и позволит найти причину. До этого повторный STOP безопасен (проверено:
   состояние `CANCELLED` не меняется задним числом).
2. **Пустое тело** осталось допустимым (`{}`): для эндпоинтов, которые требуют
   поля, это даёт 400 из валидации. Если понадобится строгий 400 на пустое тело —
   это отдельное решение: часть клиентов шлёт POST без тела.
3. **Текст ошибок 500** по-прежнему уходит клиенту как есть (операторский сервер за
   авторизацией). Маскировка 500 — отдельная задача: сообщения полезны в отладке и
   на них опираются существующие тесты.
4. Прогоны на реальной модели в этой задаче не делались: дефекты HTTP не зависят от
   провайдера, а живой сервер не останавливался.
