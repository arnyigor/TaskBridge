# План: синхронизация сессии и импорт свободных планов

## Шаги

### S-001 | TODO | P1 | Воспроизвести рассинхронизацию на двух клиентах и установить источник
**Критерии:** На изолированном сервере открыть один и тот же taskId в Desktop и Android, дополнительно Web; документировать несовпадения истории сообщений, статуса Pi, привязки плана, шага, revision, progress и кнопок управления. Сопоставить ответы GET task/events/plan, SSE PLAN_* и клиентские состояния; проверить совпадение адреса сервера, storeId, taskId, bootId и версий клиентов. Записать точные времена и seq событий, а не предполагать корневую причину.
**Проверка:** Воспроизводимый интеграционный сценарий и отдельный диагностический отчёт PASS/FAIL для initial open, одновременной работы, переключения сессий, foreground/reconnect и после server restart. Производственные сервер и сессии не затрагиваются.

### S-002 | TODO | P1 | Определить единый серверный контракт состояния чата и Follow Plan
**Критерии:** Сервер остаётся источником истины для истории, статуса исполнения, plan binding, revision/hash, active step, findings, pause и доступных действий. Клиенты получают одинаковые данные для одного taskId. Отличать серверные данные от локального UI: открытость модального окна, фокус, поисковая строка, прокрутка и неотправленный черновик НЕ синхронизируются принудительно. Описать источники и версии полей, инварианты и реакцию на старый API.
**Проверка:** Контрактные тесты DTO/API и тест идентичности taskId/storeId с двумя клиентами; никаких новых независимых источников состояния или второго SSE/runner.

### S-003 | TODO | P1 | Исправить первоначальную загрузку плана при открытии существующей сессии
**Критерии:** При каждом открытии чата на Desktop, Android и Web запрашивается актуальный GET /api/tasks/:id/plan, даже если план был подключён или начат на другом устройстве. Синхронизируются attached/path/status/step/progress/revision/hash/findings/capabilities. Данные предыдущей сессии или локального кеша не отображаются как актуальные. При открытом модальном окне новое серверное состояние становится видимым без его закрытия.
**Проверка:** Детeрминированные тесты: attach на A -> открыть B, detach на B -> A, завершение/пауза на A -> B; смена taskId без переноса старой карточки, корректный loading/error/offline.

### S-004 | TODO | P1 | Исправить синхронизацию истории диалога и обновлений по SSE
**Критерии:** Вторая сторона видит новые USER_MESSAGE, streaming, tool events и терминальный результат без ручного refresh. Воспроизведение и live-события дедуплицируются по seq/commandId; task snapshotSeq не откатывается старым GET; оборванные или обрезанные события восстанавливаются по доступной истории/снимку, а пропуски seq из-за prune не считаются автоматически потерей. При reconnect/foreground и смене bootId/storeId выполняется корректная ресинхронизация.
**Проверка:** Двухклиентские тесты: A отправляет -> B видит текст, прогресс и терминал, B отправляет -> A; обрыв TCP, replay cursor, pruneStreamingDeltas, быстрое переключение чатов, отсутствие дублей и потери истории.

### S-005 | TODO | P1 | Доставлять изменения Follow Plan во все открытые клиенты
**Критерии:** PLAN_ATTACHED, PLAN_STEP_STARTED, PLAN_STEP_CHECKPOINT, PLAN_REVISED, PLAN_PAUSED, PLAN_COMPLETED, PLAN_CONFLICT и PLAN_DETACHED обновляют план на обоих устройствах. Сверить реальную публикацию server events, обработчики Web/KMP и обязательный повторный GET /plan после значимых PLAN_* и reconnect; не зависеть от локального инициатора команды. Данные идут только для правильных storeId/taskId, устаревшие ответы игнорируются.
**Проверка:** Fixture и живой изолированный сервер: команды attach/start/pause/resume/stop/reconcile/detach на A -> изменение состояния и допустимых кнопок B; симметрично B -> A; PLAN_COMPLETED ровно один раз.

### S-006 | TODO | P1 | Защитить редактор и управляющие команды при двух клиентах
**Критерии:** Открытый черновик плана и позиция курсора не уничтожаются внешним SSE/GET; при несовпадении revision/hash показан конфликт с просмотром актуальной версии и без перезаписи. Два одновременных Start/Resume с разными commandId вызывают максимум один dispatch, STOP/Detach сильнее позднего продолжения. После 409 показывается актуальное серверное состояние; нет автоматического detach или повторной отправки неизвестного действия.
**Проверка:** Детерминированные barrier-тесты двух клиентов с разными commandId: параллельные Start/Resume, Resume vs STOP/Detach, CAS external edit, повтор ACK, offline -> reconnect; ни одной двойной доставки.

### S-007 | TODO | P1 | Провести нативную приёмку исправления синхронизации
**Критерии:** Desktop Compose и Android Pixel 5 API 31 одновременно открывают одну существующую сессию; новые сообщения и состояние Follow Plan синхронизируются в обе стороны. Проверены активный шаг, пауза, detach, завершение, возврат Android из фона, переоткрытие диалога, смена сессии, восстановление SSE. Web Chromium используется как третий клиент для диагностики. Нет рассинхронизации и дублей; все новые дефекты исправлены адресно.
**Проверка:** Реальные GUI smoke со скриншотами и серверной трассой (taskId, seq, revision), PASS/FAIL/NOT_TESTED по каждому действию. Не подменять GUI тестами компиляции. После S-007 запрещено считать критический баг открытым без нового воспроизведённого сценария.

### S-008 | TODO | P2 | Расширить приём свободных Markdown-планов без изменения основного Follow Plan
**Критерии:** Существующий classifyPlan различает VALID_MANAGED, CONVERTIBLE, NOT_A_PLAN, INVALID. Поддержать обычную нумерацию, заголовки с задачами, чек-листы и свободный текст с конкретными задачами как КАНДИДАТЫ на подготовку, не принимая README/AGENTS и произвольные инструкции по одному наличию списка. Не переписывать файл и не запускать Pi при выборе. Для первого этапа исходные форматы: .md/.markdown и при явном запросе .txt; PDF/DOCX/фото вне scope.
**Проверка:** Таблица позитивных и негативных фикстур: настоящий план без шаблона, заметка, README, AGENTS, пустой документ, неоднозначный список, большой текст, UTF-8/CRLF. Существующий VALID_MANAGED проходит без ИИ.

### S-009 | TODO | P2 | Добавить подготовку управляемого плана через ИИ по явной кнопке
**Критерии:** Отдельное действие «Подготовить план с помощью ИИ» превращает свободную структуру в валидированные goal, steps с ID, критериями и способами проверки. Использовать существующий askModelOnce/completeOnce, но новый валидируемый структурированный контракт вместо одного REVIEW. Модель не исполняет инструменты и не создаёт Run; результат является ПРЕДЛОЖЕНИЕМ, а не готовым сохранённым планом. Не выдумывать факты; не удалять цели, обязательства и ограничения; неоднозначности отмечать вопросами. При провайдерской ошибке исходный файл и привязка остаются неизменными.
**Проверка:** Тесты корректной и некорректной JSON-структуры, потери шага, переопределения цели, дублирующихся ID, hallucinated проверки, модели offline/timeout, отказа от структурного результата. Ограничение размера и стоимости; не обрезать молча длинные планы.

### S-010 | TODO | P2 | Реализовать предпросмотр и явное утверждение преобразования
**Критерии:** Пользователь видит исходный текст, получившийся Markdown, список добавленных/переставленных/объединённых шагов, новых критериев и нерешённых вопросов. До подтверждения нет файловой записи и изменения plan binding. Для исходного .md в workspace допустимо преобразование того же файла с восстановимой копией в служебных артефактах; для .txt/файла устройства сохранять один новый АКТИВНЫЙ управляемый .md, исходный документ остаётся исходником, а не вторым планом. Обязательны expectedHash/CAS и повторная валидация непосредственно перед сохранением/attach.
**Проверка:** Изменение исходника между preview и confirm -> 409 без потери текста; cancel -> 0 записей, old plan binding не тронут; confirm -> один валидный файл, revision/hash верны; повтор commandId -> без дублей. Проверить Windows junction и symlink.

### S-011 | TODO | P2 | Добавить проверки пригодности плана с учётом проекта без побочных эффектов

Запретить произвольный shell/запись/неизвестные MCP и обход approvals; если технически недоступен надёжный read-only режим, действие блокировать с объяснением. Предложения изменения архитектуры, расширения scope и удаления шагов требуют подтверждения. Инструкция из исходного документа рассматривается как недоверенный контент.
**Проверка:** Fixture с prompt injection в документе, попытка write/edit/bash, символические ссылки, очень большой репозиторий, модель offline/timeout. Побочных изменений и запусков исполнения плана нет.
