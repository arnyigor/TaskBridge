# TaskBridge Client Protocol (v2)

Один формат кадра для всех клиентов машины — локального браузера, телефона (PWA)
и будущего Android-клиента — и для самой машины:

```
клиент ── WSS ──► релей (Vercel) ── WSS ──► машина (ПК) ──► Pi
```

Реализация: [`src/cloud/protocol.mjs`](../src/cloud/protocol.mjs),
тесты: `tests/cloud-protocol.test.mjs`.

## 1. Что видит облако

Кадр — это конверт с маршрутизацией и непрозрачным `payload`:

```jsonc
{
  "v": 2,                       // версия протокола
  "id": "uuid",                 // id кадра
  "ts": "2026-09-11T07:00:00Z", // время отправки
  "type": "COMMAND",
  "machineId": "home-pc",       // кому (маршрутизация — видит релей)
  "sessionId": "tb_8c74",       // о какой сессии (видит релей)
  "commandId": "uuid",          // идемпотентность команды
  "seq": 18341,                 // монотонный номер события
  "status": "ACCEPTED",         // для COMMAND_ACK
  "from": "device:abc",         // кто отправил (для аудита)
  "to": "machine:home-pc",
  "payload": { }                // содержимое; при E2EE — строка-шифртекст
}
```

Правило: **в `payload` релей не смотрит вовсе**. При включённом E2EE там
шифртекст, и облако знает только `machineId`, устройство, время и размеры — ни
текста, ни кода, ни вывода инструментов.

## 2. Типы сообщений

| Тип | Кто → кому | Что несёт |
|---|---|---|
| `HELLO` | клиент/машина → релей | представление соединения (роль, версия) |
| `AUTH_OK` / `AUTH_FAIL` | машина/клиент → пир | результат аутентификации |
| `MACHINE_STATUS` | машина → клиенты | онлайн/офлайн, версия, занятость |
| `SESSION_LIST` | машина → клиенты | сессии, к которым можно подключиться |
| `ATTACH` / `DETACH` | клиент → машина | начать/прекратить получать сессию |
| `SYNC` | клиент → машина | догнать с курсора `payload.afterSeq` |
| `COMMAND` | клиент → машина | действие (никогда не исполняется повторно «слепо») |
| `COMMAND_ACK` | машина → клиент | результат: `ACCEPTED`, `DISPATCHING`, `COMPLETED`, `DUPLICATE`, `REJECTED`, `UNKNOWN_AFTER_CRASH` |
| `EVENT` | машина → клиенты | одно событие сессии с монотонным `seq` |
| `PING` / `PONG` | обе стороны | живость соединения |
| `ERROR` | обе стороны | проблема маршрутизации/протокола |

## 3. Правила, которые нельзя нарушать

1. **ПК — источник правды.** Облако не хранит историю событий, сессии и задачи.
   Телефон после reconnect просит пропущенное у ПК (`SYNC { afterSeq }`), а не у
   облака.
2. **Каждое событие несёт монотонный `seq`** (в рамках сессии). Клиент хранит
   `lastEventSeq`, дубликаты по `seq` отбрасываются. «Разрыв» `seq` — не потеря
   данных: он запрашивается заново.
3. **Каждая команда несёт `commandId`** (UUID). Повтор с тем же `commandId` и тем
   же содержимым возвращает сохранённый результат (`DUPLICATE`), а тот же
   `commandId` с другим содержимым — ошибка клиента (`protocol.sameCommand`), и
   команда не исполняется.
4. **Неизвестный исход — это состояние, а не повод повторить.**
   `UNKNOWN_AFTER_CRASH`: машина могла исполнить команду, но не успела записать
   ответ. Такое показывается пользователю явно.
5. **STOP и ответы на запросы не ждут окончания генерации.** Команды управления
   проходят вне очереди prompt'а.
6. **Кадр ограничен размером** (`MAX_FRAME_BYTES` = 256 КиБ, payload — 200 КиБ):
   большие файлы передаются ссылкой на временное хранилище, а не внутри кадра.
7. **Версия протокола обязательна.** Неизвестная версия — отказ
   (`PROTOCOL_VERSION`), а не «попробуем как-нибудь».
8. **Конверт валидируется на обеих сторонах** до записи в сокет: неизвестный тип,
   нехватка обязательного поля и некорректный `seq` отклоняются.

## 4. Соединение, reconnect, presence

```
connect ──► HELLO(+credential) ──► AUTH ──► ATTACH(machine/session) ──► SYNC{afterSeq}
                                                   │
                                            реплей пропущенного
                                                   ▼
                                              живой поток EVENT
```

- Соединение WebSocket на Vercel конечно (лимит длительности функции), поэтому
  **переподключение — штатная операция**, а не ошибка: экспоненциальный backoff с
  джиттером, затем `AUTH → ATTACH → SYNC`.
- `PING/PONG` каждые ~20 секунд; отсутствие `PONG` дольше таймаута закрывает
  соединение.
- Presence («машина онлайн») в Redis с TTL ~30 секунд: цифра должна исчезать
  сама, ложный «online» недопустим.
- Лишние повторы при офлайне ограничиваются, подписки после reconnect не
  дублируются.

## 5. Что нужно от релея

Минимум и только транспорт:

- комнаты по `machineId`: одна сторона — машина, вторая — устройства клиентов;
- кадры пересылаются как есть, без разбора `payload`;
- presence/маршрутизация — Redis (Upstash): канал, presence с TTL, rate-limit;
- ни задач, ни истории, ни файлов в облаке **нет** (см.
  [`cloud-integration-decision.md`](cloud-integration-decision.md)).

## 6. Порядок внедрения

1. **Этот документ и модуль протокола** — формат кадра, валидация,
   идемпотентность (`src/cloud/protocol.mjs`).
2. Релей: ядро (`cloud/lib/relay.mjs`) и сокетный слой (`cloud/lib/ws.mjs`,
   `cloud/lib/relay-server.mjs`) готовы и покрыты тестами — на реальных сокетах
   проверены рукопожатие, фрагментированные кадры, ping/pong, слишком большой
   кадр и разрыв машины. **Не проверено:** привязка к WebSocket на Vercel (у них
   свой API, в public beta) и адаптер general-purpose Redis (Upstash REST);
   состояние сейчас — `createMemoryRelayState`, то есть один процесс.
   **Аутентификация включена:** машина приходит со своим секретом, телефон — с
   токеном устройства, подписанным этим секретом
   (`src/cloud/device-token.mjs`: `v1.<payload>.<HMAC>`, срок действия по
   умолчанию 30 дней); релей проверяет подпись, и без неё соединение получает
   `AUTH_FAIL` и закрывается. Реестр доверенных телефонов остаётся на ПК — релею
   достаточно секретов машин своего развёртывания. Без настроенных секретов релей
   **не принимает никого** (`createOpenAuthenticator()` — явный режим для
   локальной разработки и тестов маршрутизации). Изоляция машин и невозможность
   выдать себя за машину/устройство проверены тестами.
   Кадры одного соединения обрабатываются строго по порядку: `HELLO` не может
   быть обогнан следующей командой.
3. Транспорт в PWA: `LocalTransport` (localhost) и `CloudTransport` (WSS) за одним
   интерфейсом; один и тот же интерфейс для ПК и телефона.
4. `MachineIdentity`/`DeviceIdentity`, QR-спарка, `trusted-devices.json` на ПК.
5. E2EE: `payload` становится шифртекстом, релей не меняется.

Открытый вопрос по интерфейсу (не протоколу): как показывать список команд,
когда их много — сейчас команды над ответом, под reasoning-блоком.
