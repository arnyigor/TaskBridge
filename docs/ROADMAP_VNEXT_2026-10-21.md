# TaskBridge — Roadmap vNext

**Дата:** 21 октября 2026 г.  
**Цель:** стабильная и быстрая консоль управления coding-агентами и моделями для Web, Windows Desktop и Android. **Pi остаётся стабильным ядром; OMP добавляется поэтапно как экспериментальная альтернатива, если подтвердит пользу.** Управление моделями/провайдерами становится основным продуктовым направлением, но использует уже существующие сервисы.

> Статусы ниже основаны на опубликованных отчётах и сообщениях о локальных проверках. Изменения KMP, ещё не зафиксированные в Git, сохраняются без вмешательства. Все оценки — приблизительные, не обязательства.

## A. Зафиксированный baseline

| Блок | Текущее состояние | Следующее действие |
|---|---|---|
| CORE-02, Pi 1.3.0 | `before_agent_start`, per-turn инструкции без изменения сообщений; рабочая приёмка | Оставить без дальнейшего усложнения |
| P0 Agent Policy (legacy против hook) | `GO` для `hook`: доставка инструкций подтверждена (16/16 прогонов), качество не хуже, на локальной Qwen меньше вызовов/токенов/времени; эффективность — предварительная оценка, n=1 на сценарий (см. `docs/p0-ab-results.md`) | Закрыт; строгие серии (Q3/Q4, Medium/High) — отдельно и без файловых инструментов |
| OMP-01, OMP 18.11.0 | RPC 13/13, функциональные 6/6; нет прямого сложного A/B с Pi | OMP-02 / 02b закрыты — NO-GO на миграцию |
| OMP-02b, AST/Hashline | Включённые `ast_grep` и `ast_edit` модель не вызывает (0 из 12 прогонов), качества и скорости не добавили | Не разрабатывать; LSP — отдельный PoC при реальной Kotlin-задаче |
| TB-STAB-01 | Некорректный JSON → 400, строгий UTF-8; у STOP-502 корреляционный ID, но причина не доказана | Наблюдать, исправлять только после доказательства |
| Управление провайдерами | `PiProviderProfiles`, Web-редактор, `ModelCatalog`, `ModelProbe`, статус, KMP-настройки, local models | Улучшить UX и объединить точки входа |
| KMP | Существующие Desktop/Android; незакоммиченные пользовательские правки | Не менять, пока владелец не зафиксирует базу |
| ExecutionGuard | Не нужен по текущим данным | Не разрабатывать |

### Инварианты для всех этапов

1. **Никаких изменений действующего сервера, конфигурации и активных сессий из исследовательских стендов.** Только отдельные `dataRoot`, agent profile, порты, рабочие директории и отдельные процессы.
2. **Не трогать незакоммиченные KMP-файлы** и `pi-deliveries.ndjson`; не выполнять `git add -A`, `git reset --hard` и массовую очистку.
3. Pi остаётся default; существующие сессии Pi продолжают открываться только через Pi. Двигатель фиксируется при создании сессии; **автоматический перевод истории Pi ↔ OMP не планируется**.
4. У TaskBridge одна транспортная, очередь, авторизация и UI; **сам agent loop, компактизация и выбор инструментов принадлежат ядру**.
5. Нет молчаливого fallback с OMP на Pi после возможной отправки запроса: неизвестный исход может повторить эффект. Нужно явно отобразить сбой и предложить оператору действие.
6. Провайдер, модель и агентный runtime — разные сущности; не путать `deepseek/flash` с `pi/omp`.
7. Секреты не попадают в логи, аналитику, SSE, диагностические архивы и Git. Для управления опасными инструментами нужен явный trust/approval контракт, а не только `cwd`.
8. Каждый MR ограничен небольшой областью и получает адресные тесты + `npm test`, `npm run check`, `npm run check:policy`. Все изменения контракта — обратно совместимые до отдельной версии API.

## D. OMP-02 — доказать пользу OMP именно для программирования

### Сравниваемые конфигурации

- **A: Pi 1.3.0**, без TaskBridge, минимальные сопоставимые инструменты.
- **B: OMP 18.11.0, сопоставимый набор инструментов**, если фактически можно ограничить функциональность без нарушения теста.
- **C: OMP 18.11.0, штатные специализированные инструменты**, включая доступные Hashline/AST/LSP, чтобы увидеть их добавочную пользу.

Основной выбор — между Pi и OMP в одинаковых условиях модели; сравнение B/C позволяет отделить преимущества agent loop от преимуществ инструментов. Не заявлять об использовании `ast_edit` или LSP без фактического `tool_execution_start` в журнале. Для Kotlin убедиться, что LSP запущен и поддерживает проект; иначе зафиксировать «не доступен», а не «хуже Pi».

### Сценарии (в изолированных копиях)

| ID | Сложная задача | Проверяемое свойство |
|---|---|---|
| CODE-01 | Рефакторинг KMP компонента/интерфейса, 5–8 файлов | API совместимость, сборка и тесты |
| CODE-02 | Исправление бага Node.js, затрагивающего 3–5 модулей | Поиск корня причины и минимальный diff |
| CODE-03 | Точечная правка файла на тысячи строк при параллельной смене контекста | Чтение, устойчивость якорных правок |
| CODE-04 | Массовое изменение вызовов API / импортов | Структурное редактирование без collateral changes |

Первый прогон: 4 сценария × 2 основных ядра = **8 запусков**, при необходимости отдельные B/C-проверки OMP. Повторить сомнительные результаты; не подгонять число тестов под победу одного ядра.

### Условия

- Одна облачная модель, одинаковые настройки thinking, одни и те же версии исходников/зависимостей и начальные тесты. Локальная Strata не блокирует эксперимент.
- У каждого запуска свои `cwd`, `session-dir`, git worktree/fixture, доступы, независимое состояние файлов. По завершении проверить diff и тесты вне агента.
- Собирать: taskSuccess, testPass, unauthorizedChanges, wall-clock, TTFT, toolCalls, retries, input/output tokens, first-pass edit success, реально использованные инструменты, размер итогового diff.
- При неверной интерпретации провайдером модели зафиксировать несопоставимость настроек, не сравнивать необоснованно.

### Gate OMP-02 → OMP-03

Продолжать при наличии измеримой пользы на coding-задачах (успешность, корректность правок, снижение времени/затрат или инструментальные функции, действительно нужные пользователю) **без критической регрессии стабильности**. Если результатов недостаточно, разрешён **ограниченный sandbox-only PoC OMP-03A** для проверки интеграционных рисков, но не полноценная поддержка второго ядра. При отсутствии пользы — оставить OMP доступным отдельно, Pi основным.

Артефакты: `experiments/omp-02/`, `docs/omp-02-comparison.md`, JSON результатов с фиксированными версиями/условиями.

## E. OMP-03A — минимальный адаптер процесса и RPC

**Цель:** построить надёжный изолированный транспорт OMP, а не переписывать TaskManager.

1. Ввести малый контракт `AgentRuntime` только для фактически используемых TaskBridge операций: `start`, `prompt`, `steer`, `followUp`, `abort`, `getState`, `subscribe`, `dispose`; отдельно capabilities. Существующий `PiRpcSession` сохраняется, Pi-путь не перестраивается массово.
2. Реализовать `OmpRpcSession`: ожидание `ready`, запрос `negotiate_protocol(v2)`, корреляция request ID, сборка `rpc_chunk` и ограничения на размер/время сборки, обработка потери stdin/stdout и завершения процесса.
3. Не смешивать **`prompt_result` (yield конкретного запроса)** и **`session_settled` (вся сессия освободилась)**. Правильно учитывать `agentInvoked:false`, terminal/async events, follow-up и abort.
4. Нормализовать события инструментов, stdout/stderr, model errors и usage, не теряя сырой информации для локальной диагностики. Незнакомые кадры — безопасно игнорировать или логировать без секретов, не ломая цикл.
5. Изолировать `--profile`, `--session-dir`, рабочий каталог и версию бинарника. Процесс и потомки должны завершаться по владельцу, с защитой от PID reuse.
6. Зафиксировать, что Pi-сессии и OMP-сессии **несовместимы как хранилища**, не подменять пути и не переписывать JSONL/DB.

**Gate:** ≥2 МБ `rpc_chunk` восстанавливаются байт-в-байт; параллельные запросы и поздние события не попадают в чужие ходы; terminate/abort корректны на синтетических зависаниях; одна команда не исполняется дважды после reconnect. Встроить контрактные тесты с fake OMP и отдельным живым smoke.

## F. OMP-03B — opt-in scratch-сессии в TaskBridge Web

1. Добавить **необязательное поле** `runtime: "pi" | "omp"` в создание новой сессии (по умолчанию Pi); runtime сессии после создания неизменяем.
2. В первой версии разрешить OMP только администратору на локальной машине, в **отдельном безопасном scratch-проекте**, с явным opt-in. Не распространять возможность на LAN-клиенты без проверки auth/approvals.
3. Не загружать Pi-расширения approval/media/turn-instructions напрямую в OMP: их жизненный цикл и семантика отличаются. Не включать опасные OMP-инструменты автоматически. Учесть, что `cwd` **не является sandbox**; для недоверенного кода требуется OS-level изоляция/ограничение доступа.
4. Сохранить работающие Pi: одинаковый пользовательский UI, но отдельные runtime-specific адаптеры. Выбирать модель из фактического каталога соответствующего ядра; не путать имена/форматы моделей.
5. В Web показывать runtime, текущую модель, загрузку, ошибки, доступные инструменты. STOP и статус `FAILED/CANCELLED/SUCCEEDED` должны отражать **фактическое** состояние движка.
6. Никакой автоматической миграции Pi-истории. Старые сессии — только Pi.

**Gate:** создание OMP scratch, 5–10 ходов, follow-up, streaming, abort, reload Web, процессное закрытие; Pi regression без изменений. Если approvals/изоляция не готовы — не разрешать OMP на произвольных проектах.

## G. OMP-04 — производственная надёжность и расширение использования

После успешного scratch:

- **Recovery:** restart/crash/attach, точные состояния `UNKNOWN_AFTER_CRASH` для неопределённого исхода; не выполнять повторно команды с возможными побочными эффектами.
- **STOP/queue:** гонки `prompt_result`/`session_settled`, steer/follow-up, повторный STOP, abort после yield, фоновые подагенты, отсутствие orphan-процессов.
- **Approvals/trust:** port существующей политики одобрений к OMP-инструментам, fail-closed там, где нельзя подтвердить; не использовать `--no-ui` как разрешение всех действий.
- **Media/history:** большие screenshots, компактирование, контекст 413, `toolEvidence`, границы чанков и backpressure. Ни одно поле с приватным содержимым не копируется автоматически в диагностику.
- **Models:** фактическое переключение модели/уровней reasoning без нарушения сессии; статус изменившейся конфигурации показывать клиентам.
- **Security:** защита локального RPC от внешнего доступа, ограничение чувствительных инструментов (`computer`, `browser`, `web_search`, shell), подготовка политик для доступа с телефона.
- **Acceptance:** длинная сессия, восстановление после падения, ошибки провайдера, задержки, 1–2 реальных сложных coding-задачи, KMP/API контрактные тесты.

**Gate на включение рабочих проектов:** отсутствие потерь/дублирования команд и неконтролируемых операций, гарантированная корреляция терминальных событий, работающие approvals, documented rollback. Pi остаётся default до осознанного переключения.

## H. TB-PROV-01 — единый удобный UI без нового реестра

**Фактически уже есть:** `src/providers/pi-provider-profiles.mjs`, `src/model-catalog.mjs`, `src/model-probe.mjs`, `src/provider-models.mjs`, `src/provider-status.mjs`, `web/providers.html/js`, model picker Web, `LocalModelsScreen.kt`, `SettingsScreen.kt` KMP.

2. В Web представить четыре вкладки/раздела: **Подключения**, **Каталог**, **Локальные модели**, **Диагностика**. Не дублировать existing local models экран; использовать ссылку и общий стиль.
3. Добавить глобальный поиск, фильтры (провайдер, local/cloud, tools, vision, reasoning), группировку, пакетное отображение больших каталогов, пустые состояния и понятные ошибки.

5. Сначала Web; API изменения только минимальные и additive. Существующие Pi `tb-*` профили можно изменять, сторонние профили — только читать.

**Gate:** UX-тесты большого каталога и переключения фильтров без задержки, все существующие провайдеры доступны и не перезаписываются; обратная совместимость API.

## I. TB-PROV-02 — мастер подключения провайдеров

1. Шаблоны: DeepSeek, OpenRouter, custom OpenAI-compatible; local: llama.cpp/Strata, LM Studio и поддерживаемый Ollama endpoint. **Нельзя автоматически превращать все native Pi провайдеры в OpenAI-compatible**.
2. Мастер: тип → base URL / keyEnv → `GET /models` → выбрать небольшое подмножество моделей → предпросмотр → сохранить → refresh Pi catalog → optional generation test.
3. Если `/models` отсутствует, предоставить ручное добавление ID модели и объяснить ограничение проверки.
4. Секреты пока через `$ENV_VAR` и существующую Pi credential/auth; не строить собственный plaintext vault. Статусы `configured/missing/unauthorized/rate-limited/unreachable` без раскрытия значений ключей.
5. Доступ на изменение конфигурации — только localhost-admin; запретить удалённую настройку через Android/LAN до отдельного доверенного authorization flow.
6. Защититься от SSRF: проверять URL и разрешённые IP/DNS при фактическом соединении, не следовать небезопасным redirect, соблюдать TLS для внешних хостов; не полагаться лишь на проверку введённой строки.
7. Сохранить атомарность/резервные копии/CAS (revision) существующего `PiProviderProfiles`. После изменения каталога объяснить, в каких уже работающих сессиях нужен reconnect/restart.

**Gate:** invalid URL, DNS rebinding/redirect, 401/403/404/429/5xx, timeout, тысячи моделей, concurrent `models.json` edit, чужие поля и секреты, rollback при ошибке. Не импортировать сотни моделей без отбора.

## J. TB-PROV-03 — удобный выбор и диагностика моделей

- Избранные, недавно использованные, скрытые; это **UI-предпочтения**, а не удаление моделей из Pi/OMP реестра.
- Отдельно: глобальная модель по умолчанию для **новой сессии**, модель **текущей сессии**, локальный **загруженный GGUF**. Не смешивать действия.
- Только подтверждённые `thinkingLevels` и `thinkingMap` от нужного runtime; поддержка context window, maxTokens, images/tools с явной маркировкой «неизвестно» при отсутствии метаданных.
- Два вида проб: доступность `GET /models` без генерации и платный/ресурсоёмкий TTFT-пробный запрос по явному нажатию. Ни одна проба не смешивается с рабочими метриками латентности.
- Статусы ошибки провайдера, cooldown, request ID, возможность скопировать **безопасную** диагностику. Не делать непрерывного мониторинга с платными запросами.
- Для локальных моделей показывать endpoint, PID/health (если доступен), загруженные модели, VRAM/RAM/контекст только из достоверной телеметрии. Не обещать универсальное управление процессами Strata через OpenAI-compatible API.

**Gate:** быстрое открытие model picker, отсутствие скачков UI, выбор применяется к нужной сессии, некорректная конфигурация ясно объяснена, секреты не раскрываются.

## K. TB-KMP-01 — Desktop + Android после фиксации пользовательских изменений

1. В первую очередь попросить владельца **закоммитить/отложить и проверить** текущие изменения `clients/kmp/**`. Их нельзя смешивать с внедрением OMP.
2. Расширить API модели сессии необязательным `runtime` и default Pi, не ломая старые версии клиентов. Добавить golden tests на события обоих runtimes.
3. Desktop: выбор runtime при создании scratch-сессии, понятный селектор провайдеров/моделей, favorites; Android: статус runtime, выбор моделей и диагностика только в пределах разрешений.
4. Сохранить paging истории, offline state, SSE reconnect, устойчивость к long screenshots, корректный STOP и последнюю видимую позицию чата.
5. Производственные провайдерские ключи и admin API не открывать Android/LAN без отдельной авторизации и политики.
6. Не пересобирать/не переустанавливать клиентов при чисто серверных изменениях. Пересборка APK/portable — только после реального изменения KMP.

**Gate:** JVM tests, Android debug build, Desktop portable, ручной smoke Pixel/API31 (или доступный emulator), Windows UI, восстановление после сетевого обрыва, длинная история, отсутствие регрессии Pi.

## L. TB-STAB-02 — стабильность и измерение производительности

- STOP 502: дождаться реального повторения, сопоставить `x-taskbridge-request-id` между LAN-прокси и app логами, проверить upstream-close и статус конечного хода. **Не вводить speculative fixes.**
- Media/413: подтвердить recovery на старой проблемной сессии и предотвратить повторную пересылку base64 screenshots сверх бюджета.
- Очередь и durability: не терять follow-up и не повторять неизвестный side effect после рестарта; STOP → durable CANCELLED; дубль request ID даёт идемпотентное поведение.
- История/UI: профилировать медленный рендер Web/KMP, 100+ ходов, lazy UI/chips, память и количество лишних обновлений. Оптимизировать только измеренные горячие пути.
- SQLite/recovery: выполнить crash injection и проверку атомарной публикации последнего состояния.
- Diagnostics: ограничение размера, redaction, error codes, correlation ID; полный текст internal 500 пользователю рассмотреть отдельной security-задачей.

**Gate:** наблюдаемое снижение ошибок/задержек, а не рост количества защитного кода; отсутствие регрессии в последних запусках и истории.

## M. RELEASE-01 и критерии публичного включения

1. Поддержка двух ядер заявляется как **Pi Stable / OMP Experimental**, а не как прозрачная миграция.
2. Настройка runtime должна быть явной для каждой новой сессии. При недоступности OMP fallback — только **до отправки запроса** и по явному решению оператора.
3. Установщик/документы показывают зависимости: Pi и OMP требуют своих исполняемых файлов/профилей; отдельные пути и разрешения. KMP-клиенты не включают автоматически обе среды.
4. Подготовить `docs/agent-runtime.md`, `docs/providers-and-models.md`, changelog, флаги rollout и инструкции rollback до Pi.
5. Проверки: тесты Node + policy + KMP при изменении + LAN + 502-корреляция + Scratch STOP/recovery + security review конфигурации и расширений.

## N. Что явно не делаем

- ExecutionGuard, жёсткие лимиты инструментов, собственный агентный планировщик.
- Автоматический выбор Pi/OMP по содержимому запроса (до реальных данных и контроля оператора).
- Массовый рефакторинг `task-manager.mjs` ради абстракций, не требующихся адаптеру.
- Автоматическую миграцию исторических Pi-сессий в OMP или обратно.
- Второй источник истины для моделей и API-ключей, собственный vault в plaintext.
- Автоматическую установку OMP или импорт чужих credentials из профиля Pi.
- Включение Web/browser/computer и сторонних extensions OMP с полными привилегиями без approvals.
- Непрерывные платные проверки провайдеров или автоматическое скачивание сотен моделей.
