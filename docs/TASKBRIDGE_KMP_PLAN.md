# TaskBridge KMP — план разработки (Desktop + Android)

Цель: KMP-клиент (Compose Multiplatform) для управления агентными сессиями через TaskBridge. Клиент **не управляет Pi напрямую**: он работает только с HTTP API TaskBridge и является такой же поверхностью, как браузер и `taskbridge pi`.

Зависимость: [`TASKBRIDGE_BACKEND_PLAN.md`](TASKBRIDGE_BACKEND_PLAN.md), этапы **B3 (контракт)** и **B4 (мультиклиентность)**. До их завершения можно делать K0–K1: на моках и на **текущем** API (`apiVersion = 1`, [api-contract.md](api-contract.md)), который уже пригоден для чтения списка сессий, истории и SSE.

> **Что изменилось в этой редакции.**
> - Клиент говорит с существующим `/api/*` + SSE, а не с отдельным `/v1` + WebSocket (решение backend-плана, B3).
> - Идемпотентность — существующий `commandId`, включая обработку `UNKNOWN_AFTER_CRASH`.
> - Состояния берутся из серверного `displayState`, а не вычисляются клиентом.
> - Добавлено то, чего не было: правка истории (`TURN_EDITED`/`TURN_TRUNCATED`), вложения, `storeId`, TLS с self-signed сертификатом, версия контракта, границы MVP.

**Кэш: SQLDelight, а не Room KMP.** Кэш — это журнал событий с ключом `(storeId, taskId, seq)`, постраничные выборки и массовое удаление по `seq > N` при `TURN_TRUNCATED`. Это естественнее писать на SQL, а SQLDelight проверяет запросы при компиляции. Room KMP тоже подойдёт; решение закрывается в K0 за день и дальше не пересматривается.

## 2. Модули

```
:shared:api        — DTO, TaskEvent + norm, SSE/REST-клиент, типизированные ошибки по `code`
:shared:data       — репозитории, SessionStream, outbox, кэш, uploads
:shared:domain     — модели UI-уровня, редьюсер событий в состояние сессии
:shared:ui         — общие Compose-экраны и компоненты
:androidApp        — Activity, уведомления, foreground service, pairing по QR
:desktopApp        — окно, tray, системные уведомления, горячие клавиши
```

Правила:
- `:shared:api` — только транспорт и DTO, без бизнес-логики;
- вся логика восстановления потока — в `:shared:data`;
- `:shared:domain` — чистый Kotlin без Ktor и SQLDelight, чтобы редьюсер тестировался на фикстурах без моков.

## 3. Ключевые механизмы (главные источники багов)

### 3.1 Подключение и совместимость

- При каждом подключении к daemon'у: `GET /api/info` → `apiVersion`, `storeId`, `capabilities`.
- `apiVersion` незнакомый → экран «обновите приложение/сервер», без попыток работать (правило из `api-contract.md`).
- Функции включаются по `capabilities` (`live-frames`, `ui-requests`, `presence`), а не по номеру версии. Пока backend B3 не готов, клиент работает в «режиме v1»: без live-кадров, presence и UI-запросов.
- `storeId` не совпал с сохранённым → кэш этого daemon'а сбрасывается целиком, `lastSeq` обнуляется (база пересоздана или восстановлена из бэкапа).
- Ключ кэша — `(daemonId, storeId)`, чтобы можно было переключаться между несколькими ПК.

### 3.2 SessionStream — поток событий без дыр и дублей

- Хранит `lastSeq` по каждой сессии (в памяти и в кэше).
- Подключение: `GET /api/tasks/:id/stream?after=<lastSeq>&clientId=&clientKind=` → `snapshot` → реплей истории → live.
  Сервер сам закрывает дыру между историей и подпиской (подписка до чтения БД), поэтому на одном соединении пропусков быть не должно.
- Дедупликация: событие с `seq <= lastSeq` игнорируется.
- **`seq` строго растёт, но идёт с пропусками**: сервер удаляет из журнала потоковые дельты, закрытые своим `message_end` (`src/event-trim.mjs`), и их номера не возвращаются. Поэтому «дыра» `seq > lastSeq + 1` — нормальная ситуация, а не потерянное событие, и дозапрашивать по ней нельзя (клиент зациклится). Без дыр доставку гарантирует сам сервер: подписка раньше чтения БД на одном соединении и `after=<lastSeq>` при переподключении (проверено интеграционным тестом `ChatSessionIntegrationTest`).
- **Переписывание истории** — отдельный путь, не «новое событие»:
  - `TURN_EDITED` — заменить событие с тем же `seq` в кэше и состоянии;
  - `TURN_TRUNCATED {fromSeq}` — удалить из кэша всё с `seq > fromSeq`, пересобрать состояние из кэша;
  - `TASK_FORKED` — новая сессия, обновить список.
- Live-кадры (при `live-frames`): без `seq`, с `{messageId, offset, delta}`. Применяются только к незавершённому сообщению и только если `offset` равен длине накопленного текста; иначе кадр пропускается до следующего snapshot или финального `message.assistant`, который всегда заменяет накопленный текст. В режиме v1 (без live-кадров) стриминг приходит как `PI_EVENT message_update` в истории и обрабатывается так же: финальное сообщение заменяет накопленное.
- Переподключение: экспоненциальный backoff с jitter (0.5 → 30 с), сброс после успешного snapshot; мгновенная попытка при смене сети и возврате в foreground. Молчание дольше двух интервалов heartbeat → считать соединение мёртвым.
- Один активный поток на открытую сессию + один поток списка (`/api/stream`). Закрытие экрана сессии закрывает её поток (проверяется тестом на утечки в K9).

### 3.3 Outbox промптов

- Каждый prompt получает `commandId` (UUID) **до** отправки и сохраняется локально вместе с текстом, режимом и id вложений.
- Статусы: `pending → accepted → queued → dispatched`, плюс `failed` и `unknown`.
  - `accepted` — сервер ответил `2xx` на `POST /api/tasks/:id/message`;
  - `queued` / `dispatched` — по событиям `prompt.queued` / `prompt.dispatched` (в режиме v1 — `QUEUE_*` и появление `USER_MESSAGE` с этим `commandId`).
- Повтор после обрыва — с тем же `commandId`. Дубля на стороне агента быть не может (журнал команд на сервере переживает рестарт).
- Ответы сервера:
  - повтор с тем же `commandId` → исходный результат, как успех;
  - `CONFLICT` → ошибка клиента (тот же `commandId` с другим телом), в лог, сообщение `failed`;
  - `UNKNOWN_AFTER_CRASH` → daemon упал посреди обработки. **Не** отправлять автоматически с новым `commandId`: сначала поискать в истории `USER_MESSAGE` с этим `commandId` (поле появляется в B3.3; до этого поиск невозможен); нашёлся — `dispatched`; нет — статус `unknown` и кнопка «Отправить ещё раз» (это действие пользователя, новый `commandId`).
  - `409 MODEL_BUSY` и подобные — не ошибка сети, не ретраить, показать причину.
- В UI сообщение видно сразу, со статусом. Outbox переживает убийство приложения (хранится в кэше).
- Сообщения в очереди сервера (`pendingPrompts`) показываются над полем ввода с действиями «Отправить сейчас» (`POST /pending/send`) и «Убрать» (`DELETE /pending`) — как в вебе.

### 3.4 Редьюсер состояния

- Чистая функция `(SessionState, TaskEvent) → SessionState` в `:shared:domain`, работает по полю `norm`. Сырой `data.pi` используется только в режиме v1 и только в одном адаптере `PiFrameAdapter`, который удаляется после перехода backend на `norm`.
- Неизвестный `type`/`norm.kind` → лог и пропуск, не падение.
- Покрывается тестами на фикстурах backend: прогон записанной сессии даёт ожидаемое итоговое состояние; отдельно — фикстуры с `TURN_EDITED`/`TURN_TRUNCATED`.
- UI подписан только на `StateFlow<SessionState>`, никакой логики в Composable.

### 3.5 UI-запросы расширений и approvals

- Показываются карточкой в ленте и уведомлением. В режиме v1 это только approvals (`APPROVAL_REQUIRED` / `GET /api/tasks/:id/approvals` / `POST /api/tasks/:id/approvals/:approvalId`).
- После ответа с другого устройства (`ui.resolved` / `APPROVAL_RESOLVED`) карточка закрывается с пометкой, кто ответил.
- Ответ на уже разрешённый запрос (`409 UI_REQUEST_RESOLVED`) — не ошибка для пользователя, просто закрыть карточку.
- Опасные действия (разрешить запуск инструмента) — с явным подтверждением, без «разрешить» по свайпу из уведомления.

### 3.6 Состояния в UI

Клиент показывает `displayState` с сервера и не выводит его сам. Значения и подписи:

| `displayState` | Подпись | Действия |
|---|---|---|
| `WAITING_USER` | Ждёт ответа | ответить, cancel |
| `WORKING` | Работает (+ `activity`: инструмент, `waiting_model` с позицией) | steer, в очередь, cancel |
| `QUEUED` | В очереди | отправить сейчас, убрать |
| `STARTING` | Запускается | — |
| `IDLE` | Готова | prompt, stop |
| `HIBERNATED` | Спит | prompt (поднимет сама), resume |
| `RESTORABLE` | Прервана — можно продолжить | prompt, resume, повторить последний prompt |
| `CLOSED` | Закрыта | prompt |
| `EXTERNAL` | Внешняя (только просмотр) | clone, take-over (после B9) |

В режиме v1 (без `displayState`) — маппинг из `status` по таблице backend-плана 3.1 в одном месте (`LegacyStateMapper`), с `FAILED_RECOVERY → RESTORABLE`.

### 3.7 Безопасность соединения

- Адрес daemon'а — LAN, HTTP или HTTPS с self-signed сертификатом (`tls.mjs`).
- HTTPS: QR содержит отпечаток сертификата; клиент закрепляет его (TOFU) и проверяет при каждом подключении. Проверку TLS не отключать ни в одной сборке.
- HTTP: только с явным согласием при pairing; на Android — `network_security_config` с cleartext только для адресов из частных диапазонов, а не для всего приложения.
- Токен устройства (`Authorization: Bearer`) — в Keystore; отзыв на ПК → `401` → экран повторного pairing.
- Пока backend не выдал Bearer (B3.1), клиент может работать только с `server.auth.enabled = false` — это ограничение K1–K2, указать в UI.

### K3. Локальный кэш

- [ ] Кэш списка сессий и последних N событий каждой сессии (N — по размеру, как `maxHistoryMb` на сервере, а не по количеству: одно событие инструмента может весить мегабайты).
- [ ] Открытие приложения без сети показывает последнее известное состояние с пометкой «офлайн» и временем последней синхронизации.
- [ ] `lastSeq` сохраняется, после перезапуска догружается только новое.
- [ ] Очистка кэша по размеру/возрасту; удалённая на сервере сессия удаляется из кэша при следующей синхронизации списка.

**Готово, когда:** холодный старт без сети показывает сессии; после появления сети догружается только разница.

**Готово, когда:** все действия корректно обрабатывают `409` (например, stop уже остановленной сессии) без ошибок для пользователя.

### K7. Android-специфика

- [ ] Pairing по QR-коду (`{url, pairingCode, certFingerprint}`), ручной ввод как запасной вариант.
- [ ] Уведомления:
  - `WAITING_USER` и approvals — высокий приоритет, действие «Открыть»;
  - завершение хода — обычный приоритет;
  - группировка по сессии, без спама при частых событиях (одно обновляемое уведомление на сессию).
- [ ] Фоновая работа (только LAN, без push-сервиса — web-push VAPID с сервера для нативного Android не подходит):
  - пока есть сессии в `WORKING`/`WAITING_USER` — foreground service с постоянным уведомлением и потоком `/api/stream`;
  - тип foreground service: у `dataSync` на Android 15+ лимит 6 часов в сутки, этого может не хватить для длинных задач; `specialUse` требует обоснования в Play Console; `connectedDevice` по смыслу не подходит. Решить в K0 с учётом канала распространения (Play или APK);
  - сервис останавливается сам, когда активных сессий нет;
  - fallback — периодическая проверка через WorkManager (минимум 15 минут, значит `WAITING_USER` может ждать уведомления до 15 минут — сказать об этом в настройках).
- [ ] Реакция на смену сети (Wi-Fi ↔ мобильная, потеря сети) через `ConnectivityManager.NetworkCallback`: мгновенная попытка переподключения, понятный статус «daemon недоступен» (вне домашней сети это нормальное состояние, а не ошибка).
- [ ] Разрешение на уведомления (Android 13+), поведение при отказе: баннер в приложении, фоновый сервис не запускается.
- [ ] Doze и оптимизация батареи: проверить поведение foreground service в Doze; не просить отключить оптимизацию без необходимости.

**Готово, когда:** телефон в кармане 30 минут с работающим агентом получает уведомление о `WAITING_USER`; после смены сети лента догружается без дыр.

## 5. Границы MVP

MVP — то, что закрывает сценарий «агент работает на ПК, я с телефона слежу, отвечаю и дописываю задачи».

**Используемые маршруты:** `/api/health`, `/api/info`, `/api/auth*`, `/api/projects`, `/api/models`, `/api/tasks` (GET/POST), `/api/tasks/:id` (GET/PATCH/DELETE), `/events`, `/stream`, `/state`, `/message`, `/cancel`, `/compact`, `/model`, `/thinking`, `/pending/send`, `DELETE /pending`, `/approvals*`, `/tools/:toolCallId/output`, `/api/uploads`, `/api/native-sessions*`, `/api/tasks/from-session`, `/api/commands/:commandId`, после B3 — `/resume`, `/stop`, `/api/stream`.

**Не входит:** правка истории (кнопки), артефакты/diff/apply/worktree, открытие и запуск файлов на ПК, shell, MCP, локальные модели, облако, метрики.

## 6. Порядок и зависимости

```
K0 → K1 ─────(режим v1: текущий API)─────→ K2 → K3 → K4 → K5 → K6 ─┬─→ K7 (Android)
            (B3/B4 готовы: включить capabilities)                     └─→ K8 (Desktop)
                                                                              ↓
                                                                             K9
```

K0–K1 можно делать параллельно с backend. K2 можно начать на текущем API в режиме v1 (без live-кадров, presence и UI-запросов), но **заморозить** его поведение — только после заморозки контракта B3. Pairing по токену (K7) блокируется B3.1.
