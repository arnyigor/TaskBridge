# Pi hooks: можно ли применять инструкции хода без правки сообщения (этап 1)

Исследование TASKBRIDGE-CORE-01. Вопрос: переносить ли инструкции PromptBuilder из
текста пользовательского сообщения в штатный Pi-хук `before_agent_start`, чтобы они
применялись к каждому ходу — включая follow-up — а сообщение оператора оставалось
дословным.

**Итог: да, механизм подходит.** Проверено на живом Pi 1.3.0 семью сценариями
(стенд `experiments/pi-hooks/`, отчёт прогона — `.local/pi-hooks/run5/report.json`).
Все условия приёмки этапа выполнены; миграции в этом задании не было.

## 1. Версия и API

| Что | Значение |
| --- | --- |
| Pi | `@earendil-works/pi-coding-agent` **1.3.0** (`pi --version` → 1.3.0) |
| Хук | `pi.on('before_agent_start', handler)` — событие есть в `dist/core/extensions/types.d.ts` |
| Что даёт событие | `messageType: "user" \| "custom"`, `prompt` (сырой текст после развёртывания `/skill:` и `/template`), `images`, `systemPrompt` (getter), `systemPromptOptions` (изменяемые структурированные секции) |
| Что можно вернуть | `{ message }` — добавить сообщение к ходу; `{ systemPrompt }` — заменить промпт целиком для этого хода (ставит `forceSystemPrompt`) |
| Что можно менять на месте | `systemPromptOptions`: `sections`, `promptGuidelines`, `appendSystemPrompt`, `selectedTools`, `toolGuidelines` |
| Порядок | хук вызывается в `_prepareRun` **до** добавления пользовательского сообщения; затем `_preparePromptAndToolLoadout` сравнивает секции с тем, что модель уже видит в транскрипте (`diffSystemPromptSections`) и отправляет только дельту |
| Ошибка хука | ловится (`runner.js`, `emitError`), ход продолжается; ошибка приходит клиенту отдельным RPC-событием `extension_error` |

Ключевое для задачи: `prompt` — это текст оператора, а не «сообщение + инструкции»,
поэтому журнал сессии остаётся дословным, а инструкции живут в системной секции.

## 2. Как инструкции доставляются сейчас

| Путь | Что уходит в Pi | Побочный эффект |
| --- | --- | --- |
| Новый запрос (`#buildPrompt` → `buildTurnPrompt`) | текст оператора + блок `Task instructions (<профиль>)` | текст в журнале Pi — не то, что набирал оператор; профиль фиксируется на весь ход |
| Follow-up (`#message`) | дословный текст | инструкций профиля нет: смена задачи («а теперь просто посмотри…») к ходу не применяется — это и был открытый пункт |
| Команда с ведущим слэшем | дословно | иначе Pi перестаёт видеть команду |

То есть текущая схема **правильна по осторожности** (ничего не ломает), но
инструкции привязаны к первому сообщению сессии, а не к ходу.

## 3. PoC

```
experiments/pi-hooks/
├── turn-instructions.js    расширение: хук + команда /tb-profile (для проверки команд)
├── broken-extension.js     расширение, которое падает в хуке (сценарий 7)
├── run-poc.mjs             стенд: настоящий Pi в RPC, 7 сценариев, отчёт JSON
└── README.md
```

Хук (сокращённо):

```js
pi.on('before_agent_start', async event => {
  if (event.messageType !== 'user') return;                 // не реплика оператора
  const profile = detectProfile(event.prompt);              // тот же классификатор, что в src/
  // ПЕРЕЗАПИСЬ одной именованной секции, а не дописывание:
  event.systemPromptOptions.sections = {
    ...event.systemPromptOptions.sections,
    turn_instructions: instructionsFor(profile),
  };
});
```

Что важно в реализации:

- **секция одна и та же** (`turn_instructions`), поэтому между ходами ничего не
  накапливается — Pi видит замену, а не вторую копию;
- профиль считается на каждом ходу из `event.prompt`, а не из истории;
- PoC пишет `prompt` в журнал дословно — это и есть доказательство, что хук текст
  не меняет;
- ошибка хука ничего не ломает: Pi ловит её и продолжает (сценарий 7).

## 4. Проверенные сценарии (живой Pi 1.3.0, `deepseek/deepseek-flash`)

| # | Сценарий | Результат |
| --- | --- | --- |
| 1 | Новый запрос, поиск («посмотри, есть ли файл…») | хук вызван 1 раз, профиль `quick`, `prompt` = 49 символов ровно как набрано; системный промпт 7 945 → 8 573 символов (+628 = инструкция) |
| 2 | `implement` → follow-up `quick` | два вызова хука, профили `implement`, затем `quick` — смена задачи применяется к новому ходу |
| 3 | Команда Pi (`/tb-profile`) | `disposition: handled`, хук **не** вызван, команда исполнена (свой лог), текст не превращён в промпт |
| 4 | Steering во время генерации | steer принят (`disposition: queued`), хук вызван один раз на ход; инструкции посреди ответа не добавляются |
| 5 | Compaction (`{"type":"compact"}`) | compaction выполнен, хук **не** вызван (это отдельный вызов модели, а не «старт хода») |

Вердикты стенда (все `true`, см. `report.json → verdict`): `promptVerbatim`,
`perTurnInstructions`, `noAccumulation`, `commandHandled`,

## 5. Ограничения проверки

- Модель — `deepseek-flash`, не локальная Qwen: проверялась **механика хука**, а не
  поведение модели. Для сравнения качества нужен отдельный прогон (этап 3).
- Изоляция: `PI_CODING_AGENT_DIR` в свой каталог, `--no-session`/`--session-dir` в
  каталог прогона, `settings.compaction.keepRecentTokens = 200` (иначе сессия
  «слишком мала» для compaction и сценарий 5 ничего не проверяет).
- Команды вида `/skill:…` и `/template` разворачиваются **до** хука, поэтому
  `event.prompt` содержит уже развёрнутый текст — профиль считается по нему, и это
  скорее плюс (инструкция соответствует фактическому содержимому хода).
- Числа системного промпта зависят от набора скиллов/AGENTS.md в каталоге агента.

## 6. Сравнение с текущим PromptBuilder

| Критерий | PromptBuilder (сейчас) | `before_agent_start` |
| --- | --- | --- |
| Текст оператора в журнале | первый ход обёрнут | **дословно всегда** |
| Инструкции на follow-up | нет | **есть, на каждом ходу** |
| Дублирование в контексте | инструкция один раз в первом сообщении навсегда | дельта-патч секции, заменяет предыдущий |
| Команды Pi | обходятся спецправилом в `#message` | команды до хука не доходят — правило не нужно |
| Стоимость | 0 лишних механизмов | зависит от Pi-хука; при обновлении Pi API может измениться |
| Диагностика | видно в `pi-events.jsonl` как часть prompt | видно отдельным событием `extension_error`; сами секции — в системных записях сессии |
| Риск | профиль «залипает» на сессию | риск ниже, но нужен идемпотентный набор секции (см. §3) |

Отдельный риск, который стоит держать в голове: `systemPromptOptions` — **общий
базовый объект**, который Pi передаёт в хук на каждом ходу. Дописывание
(`sections.x += …`, `promptGuidelines.push`) накапливается между ходами; возврат
`{ systemPrompt }` ставит `forceSystemPrompt` на базе и остаётся навсегда. Поэтому
в PoC — только присваивание.

## 7. Итог: переносить стоит, но отдельным шагом

Хук решает ровно ту проблему, из-за которой этап 1 затевался: инструкции
применяются к каждому ходу, сообщение оператора дословно, дублирования нет, RPC и
команды не задеты. При этом перенос — не «удалить `#buildPrompt`», а:

1. экспортировать из `src/prompt-builder.mjs` одну функцию `turnInstructions(profile)`
   (сейчас блок собирается вместе с текстом);
2. перенести расширение в `pi-extension/` (рядом с approval-расширением) и
   подключить его тем же `-e`, что и approval;
3. оставить `#buildPrompt` как fallback: если расширение не загрузилось (старый Pi,
   отключённые расширения), первый ход должен по-прежнему получать инструкции;
4. проверить обратную совместимость на импортированных сессиях (там первый ход
   уже без инструкций);
5. отдельным тестом зафиксировать, что при `messageType: 'custom'` (regenerate,
   continuation после 413) хук ничего не добавляет — иначе «продолжение ответа»
   получит второй профиль.

В рабочем коде на этом этапе **ничего не менялось**: PoC живёт в `experiments/`,
PromptBuilder и путь доставки сообщений не тронуты.
