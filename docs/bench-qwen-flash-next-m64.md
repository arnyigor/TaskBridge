# Qwen3.8-Flash-Next M64 (AtomicChat AD-3.84bpw IQ4_XS): PP/TG, предел контекста, vision

Стенд: [`scripts/bench-llama-pp.mjs`](../scripts/bench-llama-pp.mjs). Он поднимает
**отдельный** `llama-server` на свободном порту (8081) и не трогает роутер
TaskBridge на 8080, поэтому замеры не рвут Pi-сессии. PP/TG берутся из `timings`
самого сервера (`/completion`), а не из wall-clock вокруг `fetch` — HTTP и JSON не
могут завысить цифру. Отчёт печатается до и после каждой загрузки/выгрузки, JSON
с замерами остаётся в `data/runtime/bench-<label>.json` (git-ignored).

## 2. `--load-mode none` против `mmap`

`b4096/ub2048`, `ctx 65536`, `ncmoe 40`.

| режим | PP | TG | загрузка | RAM процесса |
| --- | --- | --- | --- | --- |
| `mmap` + `lazy-mode on` | 284.2 | 20.2 | 7.2 c (тёплый) / 90.4 c (холодный) | 13 774 MiB |

## 7. Уровень мышления (off / low / medium / xhigh)

Контракт живёт в шаблоне самой модели (`tokenizer.chat_template` из GGUF) — ниже
дословная выдержка оттуда:

```jinja
{%- if enable_thinking is undefined or enable_thinking is true %}
  {%- set resolved_reasoning_effort = reasoning_effort|default('xhigh') %}
  {%- if resolved_reasoning_effort not in ('xhigh', 'medium', 'low') %}
    {{- raise_exception('Unexpected reasoning effort ...') }}
```

Уровней ровно три (xhigh — дефолт, medium, low), мышление выключается
`enable_thinking = false`. При этом **«medium» не добавляет в промпт ничего**:
инструкция есть только у xhigh («think carefully… validate assumptions…») и у low
(«keep your thinking brief»).

Замерено по 3 прогона на уровень, temperature 0, задача-ловушка на CRT
(наименьшее N: N≡2 mod 3, N≡3 mod 5, N≡2 mod 7 → 23):

| уровень | верно | thinking-токены | токенов всего | wall |
| --- | --- | --- | --- | --- |
| off | **0/3** | 0, 0, 0 | 4, 4, 4 | 0.3–2.1 c |
| low | 3/3 | 172, 172, 172 | 360, 360, 360 | 18.0–19.8 c |
| medium | 3/3 | 253, 253, 253 | 543, 543, 543 | 26.9–27.0 c |
| xhigh | 3/3 | **139**, 139, 139 | 228, 228, 228 | 11.5 c |

- **`off` на этой модели нерабочий** для чего-либо, кроме однозначных вопросов:
  3/3 провала там, где все «думающие» уровни дали 23.
- **Уровень не управляет бюджетом мышления.** Это одна фраза в промпте, и длина
  размышления выходит какой угодно: «medium», который не добавляет ничего,
  размышлял вдвое дольше «xhigh». На второй задаче (улитка, ответ 8) порядок был
  low 275 > medium 212 > xhigh 181 — то есть **xhigh стабильно думает меньше всех
  и при этом не ошибается**.
- Размен практически только по времени: 0.3 c (off) → 11.5 c (xhigh) → 27 c (medium).

Оговорка: temperature 0 — жадное декодирование, три прогона совпали побитово, так
что это проверка детерминированности, а не разброса при семплинге. Задачи мелкие;
на больших ранжирование может быть иным.

### Ловушка: llama.cpp принимает больше уровней, чем шаблон

`--reasoning-effort` умеет `minimal/low/medium/high/xhigh/max`, но шаблон этой
модели принимает только три. Проверено запросами:

| `reasoning_effort` | результат |
| --- | --- |
| `medium` | HTTP 200 |
| `high`, `minimal`, `max` | **HTTP 500**, Jinja `raise_exception` (line 49 шаблона) |

Поэтому в `models.ini` у `[*]` стоит `reasoning-effort = medium`; менять его на
`high` нельзя — каждый запрос будет падать с 500.

### Запрос per-request — работает

```json
{"model":"qwen-flash-next-m64","messages":[...],
 "chat_template_kwargs":{"enable_thinking":true,"reasoning_effort":"xhigh"}}
```

Pi шлёт ровно это (`~/.pi/agent/models.json`, секция провайдера `llama.cpp`):

```json
"compat": { "thinkingFormat": "chat-template",
  "chatTemplateKwargs": { "enable_thinking":   {"$var":"thinking.enabled"},
                          "reasoning_effort":  {"$var":"thinking.effort", "omitWhenOff":true} },
"thinkingLevelMap": {"off":"none","low":"low","medium":"medium","xhigh":"xhigh",
                     "minimal":null,"high":null} }
```

### ⚠️ Новые пресеты в Pi ещё не «думающие»

`pi --list-models`:

```
llama.cpp  qwen-flash-next-m64        128K  128K  reasoning: no
llama.cpp  qwen-flash-next-m64-128k   128K  128K  reasoning: no
llama.cpp  qwen-flash-next-m64-256k   128K  128K  reasoning: no
llama.cpp  qwen-flash-next-m64-vision 128K  128K  reasoning: no   images: yes
```

`reasoning: no` — Pi не предложит уровни и не пошлёт `chat_template_kwargs`. Плюс
contextWindow у всех 128K, хотя у пресетов 64K/128K/256K: провайдер берёт дефолт,
потому что записей про эти модели в `models.json` нет вообще. Думающие записи там
есть только у `qwen-27b-*` — и именно они единственные показывают `reasoning: yes`.

## 9. Как этим пользоваться

`models.ini` — preset-файл роутера, путь задан в `config.json`
(`localRuntime.router.args → --models-preset`). Имя секции = id модели.

```
taskbridge models                 # список пресетов и статусов
taskbridge models load <id>       # загрузить (блокирующе)
taskbridge models unload <id>     # выгрузить
taskbridge models reload          # stop+start: перечитать models.ini
taskbridge models stop
```

**ini читается при старте роутера и вживую не перечитывается** — проверено:
при 7 секциях в файле запущенный роутер отдавал 5. Поэтому после правки
`models.ini` нужен `models reload` (или перезапуск TaskBridge). Осторожно: если
роутер пережил процесс TaskBridge, он числится `EXTERNAL_RUNNING`, и `reload`
откажется его убивать — команда скажет об этом прямым текстом.

Способы вообще не думать о загрузке:

1. **Автозагрузка** (`--models-autoload` включён по умолчанию) — запрос с нужным
   `model` поднимает его сам; проверено на vision-тесте.
2. **Pi**: `/llama` — встроенный селектор моделей с действиями load/unload/stop.
3. **HTTP**: `POST /api/local/load|unload|start|stop` (TaskBridge) или
   `POST /models/load` (роутер напрямую).

## Воспроизводимость

Два прогона с идентичными аргументами дали PP 286.12 и 284.16 при совпадающей до
MiB VRAM — разница между конфигами от ~3% уже осмысленна.

## Открытые вопросы

- `ncmoe 45` для 128K + `b8192/ub4096` (между «смертью» на 46 и работой на 48) не
  проверялся: 48 уже даёт 1.2 GB запаса, выигрыш был бы косметический.
- При `ncmoe ≤ 42` на 128K свободной VRAM после загрузки то 61, то 47 MiB — цифры
  не монотонны, поэтому точная граница «сколько именно надо» не калибрована; сам
  факт (≤42 падает, ≥43 работает) воспроизведён на четырёх конфигурациях.
- `-ctk/-ctv` кроме `q4_0` не пробовал: q8_0 удвоит KV и, вероятно, потребует
  ещё шаг `ncmoe`.
