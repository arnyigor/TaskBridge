# TaskBridge — подробный план доработок

Дата сверки: 11 сентября 2026 года.
Статус: план реализации. Пункты с [ ] — оставшиеся работы, а не выполненные изменения.

## 1. Цель

Основной сценарий: начать работу на ПК через TaskBridge, закрыть терминальный клиент, продолжить ту же сессию с телефона и вернуться на ПК с общей историей и состоянием.

TaskBridge владеет процессом агента, историей, рабочей копией и результатами. Терминал, локальный браузер и облачный интерфейс — клиенты. Отключение клиента не останавливает агента.

Вторая цель: довести работу до проверенного изменения в репозитории — просмотр diff, verification, ограниченные исправления, явное применение или сохранение результата.

Сначала этот сценарий реализуется на Pi. Другие runners, параллельность, reviewer и Android-клиент развиваются отдельными этапами. Сохраняются Node.js, Pi RPC, локальный SQLite, артефакты на диске и LAN. Vercel уже реализован; новый relay с нуля не проектируется.

### 2.2. Подтверждённые ограничения

1. TaskManager напрямую создаёт PiRpcSession и совмещает задачу, сессию, запуск, verification и runtime.
2. activeTaskId ограничивает выполнение одной inference-задачей. Новая задача при занятости может отклоняться, несмотря на наличие queue.
3. После restart активные задачи получают FAILED_RECOVERY. Историю можно продолжить; непрерывное исполнение после сбоя не обеспечено.
4. Нет taskbridge pi с attach/detach.
5. LAN API сообщений не имеет общего устойчивого commandId-контракта. Cloud-дедупликация не закрывает все аварийные окна.
6. Импорт использует исходный native session-файл; sidecar-lock обычный Pi не соблюдает.
7. Нет ограниченного repair loop. Patch собирается до verification и может устареть, если проверки меняют файлы.
8. Patch сравнивается с текущим HEAD workspace. Полноту результата после коммитов агента относительно baseCommit необходимо доработать.
9. Apply доступен для FAILED/CANCELLED: успешные проверки не обязательны для применения.
10. Очистка сирот существует; нужен аудит сохранности результатов, а не ещё один механизм удаления.
11. Cloud-реализации расходятся по хранилищу, API, конфигурации и Root Directory.
12. Видимые несовпадения cloud-ветки и рабочей копии: createTask передаёт id в input вместо options.requestedId; setModel вызывается с объектом вместо provider/modelId; setThinking отличается от setThinkingLevel.

## 3. Правила реализации

- SQLite остаётся источником локального состояния исполнения. Облако хранит транспортные данные выбранного варианта; отсутствие отдельной облачной БД не означает отсутствие облачного состояния.
- Каждый этап завершается пользовательским сценарием. Массовую перестановку каталогов не совмещать с изменением поведения.
- Сохранять taskId, пути артефактов и существующие seq при миграции.
- Disconnect/detach, abort/cancel, archive/delete имеют разные действия и семантику.
- STOP и ответы агенту не ждут завершения генерации в очереди управления.
- Не обещать exactly-once для внешнего Pi RPC без доказанной поддержки; неопределённый результат после сбоя показывается явно.
- PID — диагностическое поле, а не способ подключения к потерянному stdio.
- Неприменённый результат не удаляется только из-за возраста или терминального статуса задачи.
- AUTO выбора профиля сохраняется. Выбор runner/платного провайдера — отдельная функция с явной политикой пользователя.

## 6. Этап 2 — Session, Run и минимальный Runner

Результат: управление Pi отделено от задач, существующий UI продолжает работать.

### Модель данных

| Сущность | Назначение | Минимальные поля |
| --- | --- | --- |
| Task | Цель, проверки, результат | id, projectId, sessionId, status, resultRevision |

1. Запустить taskbridge pi, отправить задачу, меняющую файл A.
2. Во время работы закрыть терминал: Pi продолжает выполнение.
3. Подключиться с телефона, увидеть историю и отправить изменение файла B.
4. Вернуться через taskbridge pi, увидеть оба запроса и продолжить работу.
5. Без сбоя процесса сохраняются тот же native sessionId и единственный процесс-владелец.
6. Повторить с одновременным CLI/PWA, обрывом сети и повтором команды.

До прохождения этого сценария не расширять проект несколькими новыми runners.

Приоритет: P1. Зависимости: этапы 2–4.
Результат: restart HTTP/cloud gateway не прерывает генерацию; сбой host обрабатывается отдельно.

- [ ] Вынести AgentHost в фоновый процесс с защищённым локальным IPC. Он владеет Pi, SessionManager и очередями управления.
- [ ] Gateway становится клиентом host. Host — единственный исполнитель команд; gateway не меняет задачи напрямую и не конкурирует за старый server-lock.
- [ ] Runtime descriptor: instanceId host, IPC endpoint, session/run, native reference, workspace, PID, время запуска.
- [ ] Restart gateway подключается к живому host по IPC; stdio по одному PID не восстанавливается.
- [ ] После crash host выявлять осиротевшие процессы, проверять владельца перед освобождением ресурсов, согласовывать незавершённые команды.
- [ ] Различать «история восстановлена», «готово к продолжению», «выполнение возобновлено». Автоматический resume — для доказуемо безопасных случаев.
- [ ] Для прерванного Run/неизвестного исхода команды дать явное действие продолжения.
- [ ] Добавить опциональный Windows autostart в контексте пользователя без обязательной системной службы.

Приёмка:

- [ ] Restart gateway при генерации не меняет Pi PID и не теряет сообщения.
- [ ] Crash host не создаёт второго писателя в native session и не повторяет неоднозначную команду молча.
- [ ] После перезагрузки ПК доступны история, результаты и понятное продолжение.
- [ ] Graceful shutdown сохраняет принятые команды/outbox; ошибки IPC/startup видны через doctor.

## 10. Этап 6 — актуальный результат, review diff и repair

Приоритет: P1. Зависимости: этапы 2–3. Исправления patch и UI diff можно выполнять раньше отдельного host.
Результат: применяемое изменение соответствует реально проверенному состоянию файлов.

### 10.1. Результат и Apply

- [ ] Собирать финальный patch после verification либо повторно после изменяющих файлы проверок.
- [ ] Связать resultRevision, baseCommit, patch hash, verification и Run с одним снимком результата.
- [ ] Перед Apply выявлять устаревание после follow-up, внешнего изменения worktree и форматирования.
- [ ] Просмотр по файлам/hunks, статистика, binary/deleted/renamed, скачивание patch.
- [ ] Сохранить временный Git index; не заменять его git add -N в пользовательском индексе.
- [ ] Сохранить dirty/HEAD/git apply --check. Force не должен незаметно обходить отдельный verification gate.
- [ ] При настроенных проверках обычный Apply — для актуального успешного результата. FAILED/CANCELLED — отдельное явное действие с причиной и журналом.
- [ ] NOT_CONFIGURED показывать отдельно от PASSED: отсутствие проверок не означает успешные тесты.

### 10.2. Ветка, повторное применение и очистка

- [ ] Keep branch: явное сохранение результата в именованную ветку с коммитом, без автоматического push/merge.
- [ ] После коммитов агента diff включает изменения относительно сохранённого baseCommit, а не только текущего HEAD worktree.
- [ ] Повтор Apply возвращает уже применённый статус. Follow-up после Apply получает новую revision и определённую базу сравнения.
- [ ] Archive не уничтожает workspace; delete — отдельное действие.
- [ ] Проверить sweepOrphans: неизвестный каталог сначала инвентаризируется/показывается пользователю, а не признаётся заведомо ненужным.
- [ ] Автоочистка — явно включённая политика при доказанном сохранении результата. Неприменённые/несохранённые изменения сохраняются.
- [ ] Перед удалением закрыть использующий каталог процесс, проверить границы путей и отсутствие других владельцев Session.

### 10.3. Verification и ограниченный repair

- [ ] Сохранить совместимость с массивом verification-команд; расширенный формат добавляет имя шага, timeout и признак изменения файлов.
- [ ] Проверки берутся из доверенной конфигурации; агент не может убрать обязательный gate правкой проектного файла.
- [ ] После провала отправлять в ту же сессию ограниченный фрагмент лога, команду и exit code; полные логи сохранять.
- [ ] Ввести autoRepair/maxRepairAttempts: первоначально максимум два исправления при явно включённой функции.
- [ ] Каждый repair — отдельный Run со своей verification, длительностью и результатом.
- [ ] STOP отменяет процесс verification и будущие попытки, а не только меняет флаг.
- [ ] Ошибки инфраструктуры, auth и недоступной модели не направлять в бесконечное исправление кода.
- [ ] После лимита сохранить patch/evidence, показать причину остановки и ручное продолжение.

Приёмка:

- [ ] Форматтер меняет файл во время проверки: UI/Apply используют обновлённый patch.
- [ ] Коммит агента в worktree входит в результат относительно baseCommit.
- [ ] Тест падает, repair исправляет причину; отдельный сценарий доказывает предел попыток.
- [ ] STOP во время verification завершает дочерний процесс и не запускает repair.
- [ ] Обработаны устаревший результат, изменившийся source HEAD, повтор Apply, binary, новый файл.
- [ ] Неприменённые результаты переживают archive, restart и очистку.

Области: src/git.mjs, TaskManager/Run lifecycle, артефакты, API, diff UI и тематические тесты.

## 11. Этап 7 — постоянная очередь и ресурсы

Приоритет: P1. Зависимости: этапы 2–3 и определённое восстановление Run; параллельный repair — этап 6.
Результат: следующая задача принимается, даже когда текущая выполняется.

- [ ] Сначала сохраняемая очередь с capacity=1: добавление, отмена, порядок, причина ожидания, восстановление после restart.
- [ ] Заменить activeTaskId учётом ресурсов: local endpoint/GPU, remote provider/account, verification и workspace.
- [ ] Capacities настраиваются; одинаковую пропускную способность провайдеров не предполагать.
- [ ] Для одной Session/workspace разрешать одного изменяющего файлы исполнителя. Разные задачи в общем checkout также блокируют запись друг для друга.
- [ ] Согласовать загрузку/смену/выгрузку модели с занятостью ресурса: не обрывать чужой Run.
- [ ] Освобождать ресурсы после STOP, ошибки запуска, timeout, verification; зависший lock не блокирует очередь навсегда.
- [ ] WAITING_INPUT удерживает необходимые ресурсы, сохраняя защиту workspace от другого писателя.
- [ ] Таймауты ожидания/исполнения, ограниченный retry транспорта; retry не смешивается с repair кода.

Приёмка:

- [ ] Три задачи идут по порядку при capacity=1; вторую принимают во время первой.
- [ ] Локальная и удалённая модель через Pi работают параллельно на независимых ресурсах.
- [ ] Restart не запускает один Run дважды и не оставляет ресурс навечно занятым.
- [ ] Два писателя в workspace не допускаются.

Зависимости задач — отдельное расширение: одного dependsOn недостаточно, нужно определить, какой commit/patch получает зависимая задача.

## Я бы зафиксировал новый приоритет так

1. **Persistent TaskBridge sessions в браузере.**
2. **PC browser → phone → PC browser без потери состояния.**
3. **Красивый импорт native Pi sessions с автоматическим поиском, группировкой и preview.**
4. Safe clone/import вместо одновременного владения native session.
5. AgentHost/recovery.

Так архитектура получается проще и точнее соответствует твоему реальному сценарию: **терминал нужен для старых/существующих Pi-сессий, а после импорта вся дальнейшая работа идёт из TaskBridge с любого устройства.**


Да. В твоём случае я бы **не начинал с Android-клиента**. Правильная схема — **публичная PWA на Vercel + локальный TaskBridge Agent Host на ПК + облачный relay**. # Но здесь есть важный нюанс Vercel

Vercel теперь официально поддерживает WebSocket в Functions — функция появилась в public beta 22 июня 2026 года. ([Vercel][2])

Но нельзя сделать:

```text
PC WebSocket ──┐
               │ random Vercel instance
Phone WS ──────┘
```

и надеяться, что оба всегда попадут в один process.

Fluid Compute может обслуживать несколько запросов одним instance, но Vercel всё равно масштабирует Functions и не гарантирует единственный глобальный process. ([Vercel][3])

И официальный WebSocket пример Vercel отдельно отмечает проблему: **без shared cross-instance layer устройства, попавшие в разные instances, могут не видеть сообщения друг друга**. ([Vercel][4])

Это важная поправка к первоначальной идее «Vercel совершенно без state».

**Нет.**

TaskBridge не нужна традиционная БД:

```text

```

Но cloud relay желательно иметь **небольшой shared realtime state/pub-sub**.

Я бы использовал:

```text

```

через Vercel Marketplace.

Vercel сейчас прямо предлагает Redis/Upstash как serverless key-value/realtime storage; старый Vercel KV уже заменён интеграциями Marketplace. ([Vercel][5])

Но использовать Redis здесь нужно совсем не как базу TaskBridge.

**Не хранить:**

source code

tasks

# WebSocket reconnect обязателен

Vercel WebSocket connection не бесконечен. Официальный starter прямо реализует reconnect, потому что Function соединение закрывается при достижении максимальной duration. ([Vercel][7])

На Hobby Fluid Compute стандартный максимум сейчас 300 секунд; более длинные режимы доступны на более высоких планах. ([Vercel][3])

Но это не проблема.

Нужно:

```text
connected
   ↓
heartbeat
   ↓
disconnect
   ↓
reconnect
   ↓
AUTH
   ↓
ATTACH machine/session
   ↓
SYNC lastEventSeq
   ↓
continue
```

Пользователь этого практически не видит.

# Session protocol уже должен поддерживать replay

Например телефон последний раз видел:

```text

```

Пока он был offline:

```text
18342
18343
...
18487
```

После reconnect:

```text
SYNC {
    sessionId,
    afterEventSeq: 18341
}
```

PC возвращает:

```text
18342...18487
```

И только затем live stream.

# Cloud relay не должен хранить event history

Вот важный архитектурный момент:

```text
WRONG

Phone
 ↓
Vercel DB
 ↓
session history
 ↓
PC
```

Нужно:

```text
RIGHT

Phone
 ↓
Vercel transport
 ↓
PC
 ↓
EventJournal
```

Если phone reconnect:

```text
PC = source of truth
```

# Что делать, если ПК выключен

PWA всё равно открывается.

Показывает:

```text
Igor-PC
○ Offline

Sessions unavailable while machine is offline.
```

В первой версии этого достаточно.

Позже можно добавить:

```text
Queue task while offline
```

И вот только для этого понадобится небольшой durable cloud inbox:

```text
pending command
```

Но это можно сделать после MVP через Queue/Redis/Blob, не создавая полноценную application database.

# Что делать с файлами

Не гонять большие файлы через JSON WebSocket.

Маленькие:

```text
< ~1 MB
→ binary WS frames
```

Большие позже:

```text
Phone
 ↓ encrypted upload
temporary Blob
 ↓
PC downloads
 ↓ hash verification
 ↓ delete Blob
```

Cloud Blob должен быть **temporary transport**, а не storage TaskBridge.

# Подробный порядок разработки

Я бы теперь закрепил roadmap так:

1. **Отделить PWA frontend от локального TaskBridge server.** Один и тот же frontend должен собираться для локального использования и для Vercel; никакой бизнес-логики Pi в браузере.

2. **Ввести TaskBridge Client Protocol.** `HELLO`, `AUTH`, `MACHINE_STATUS`, `SESSION_LIST`, `ATTACH`, `SYNC`, `COMMAND`, `COMMAND_ACK`, `EVENT`, `PING/PONG`; каждому command — UUID, каждому event — monotonic `seq`.

3. **Закончить Persistent SessionManager.** Сессия должна принадлежать Core, а не WebSocket/browser. Закрытие всех браузеров не должно останавливать Pi.

4. **Сделать cloud PWA на Vercel.** Страница должна открываться даже при выключенном ПК. Добавить manifest, service worker, install UI и offline shell.

5. **Добавить MachineIdentity.** `machineId`, key pair, display name; private key только локально.

6. **Добавить DeviceIdentity в PWA.** При первом запуске генерировать device identity; credential сохранять локально, не использовать email/password.

7. **Сделать QR pairing.** QR должен содержать публичный Vercel URL + одноразовый token, а не LAN IP. Token короткоживущий и single-use.

8. **Сделать TaskBridge outbound connector.** ПК сам устанавливает `wss://...` к Vercel. Никаких входящих портов, DDNS или проброса NAT.

9. **Сделать WebSocket relay на Vercel.** Развести namespaces/rooms по `machineId`, а phone connection привязывать к доверенному device.

10. **Добавить минимальный Upstash Redis только для relay/pub-sub/presence.** Не хранить там tasks/sessions/messages. Это не TaskBridge DB, а cross-instance transport state. Vercel сам поддерживает Marketplace-интеграцию Redis/Upstash. ([Vercel][5])

11. **Добавить heartbeat/presence.** ПК обновляет presence TTL; PWA показывает `ONLINE/OFFLINE`; ложный online должен исчезать за десятки секунд.

12. **Реализовать reconnect.** Exponential backoff, желательно с jitter; пересоздание connection после Vercel Function expiration должно быть нормальной штатной операцией.

13. **Реализовать session replay.** Клиент хранит `lastEventSeq`; после reconnect Core возвращает пропущенные события.

14. **Добавить idempotency.** Повтор `commandId` никогда не должен повторно отправлять prompt, stop, apply или другую опасную команду.

15. **Реализовать multi-device.** PC browser и Android PWA одновременно видят одну session; команды проходят через один sequencer.

16. **Реализовать E2EE.** Cloud relay должен передавать ciphertext; ключ TaskBridge session/transport выводится из device/machine identities.

17. **Сделать Machines → Sessions UX.** Сначала выбирается компьютер, затем active/recent sessions; native Pi importer находится там же.

18. **Добавить Pi session importer.** Сканировать Pi sessions локально, группировать по проекту, показывать preview и `Continue in TaskBridge`; безопасный clone — default.

19. **Добавить remote security controls.** Revoked devices, permissions, pairing reset, `Disable remote`, event audit; опасные операции вроде регистрации нового project root отдельно ограничить.

20. **Добавить notification layer.** Сначала Web Push для `DONE/FAILED/INPUT_REQUIRED`; Android native notifications оставить на будущее.

21. **Только после стабилизации PWA сделать Android client.** KMP/Compose клиент использует тот же wire protocol; никакого второго backend.

# Мой итоговый выбор

**Для TaskBridge сейчас: PWA first. Android later.**

И самое важное — PWA должна быть не:

```text
установленной копией страницы
http://192.168.x.x
```

а полноценным **cloud entry point**:

```text
TaskBridge PWA
     ↓
public Vercel origin
     ↓
secure relay
     ↓
outbound connection
     ↓
your PC
```

Тогда пользователь может впервые открыть TaskBridge хоть из мобильной сети, хоть из другой страны — UI всегда существует. Единственное, что требуется заранее, — **один раз спарить конкретный телефон/браузер с ПК**, либо позже добавить механизм безопасного подключения нового устройства.

И я бы пересмотрел тезис «совсем без БД»: **без application database — да, однозначно. Без любого shared cloud state — лучше нет.** Минимальный Redis pub/sub с TTL только для маршрутизации делает Vercel relay надёжным и практически не усложняет архитектуру, при этом весь ценный state остаётся локальным.
