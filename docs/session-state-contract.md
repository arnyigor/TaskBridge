# Контракт состояния сессии: чат и Follow Plan

Этот документ отвечает на один вопрос: **что клиент обязан считать серверной
истиной, а что остаётся его локальным делом.** Он дополняет `docs/api-contract.md`
(там — формы ресурсов и маршруты) и `docs/follow-plan-ux-acceptance.md` (там —
приёмка). Машиночитаемая часть маршрутов — `src/api-contract.mjs`, проверка —
`tests/api-contract.test.mjs` и `tests/session-state-contract.test.mjs`.

## 1. Источники истины

| Что видит оператор | Источник | Маршрут / поле |
|---|---|---|
| История сообщений | журнал событий задачи (SQLite), воспроизведение + live по SSE | `GET /api/tasks/:id/events` (`?after=`, `?tail`/`&before`), `GET /api/tasks/:id/events` (SSE) |
| Текст идущего ответа | события стрима того же журнала | `PI_EVENT`/`TEXT_*`, `task.assistantText` в снимке |
| Статус исполнения | задача | `task.status`, `task.turnState`, `task.runId` |
| Очередь промптов | сервер | `task.pendingPrompts`, `PROMPT_QUEUED` |
| Привязка плана | SQLite (binding) | `GET /api/tasks/:id/plan` → `attached`, `path`, `state`, `planId` |
| Ревизия и хэш файла | файл плана + binding | `plan.revision`, `plan.hash` |
| Текущий шаг | файл плана + binding | `plan.stepId`, `plan.progress`, `plan.file` |
| Находки | файл плана | `plan.findings`, `plan.file.blocking` |
| Пауза / разбор | binding | `plan.state` (`IDLE`, `RUNNING_STEP`, `REVIEWING`, `PAUSED`, `PAUSED_REVIEW`, `COMPLETED`) |
| Доступные действия | сервер | `plan.actions` (см. `web/follow-plan-view.mjs`, `FollowPlan.kt` — те же правила) |
| Возможности сервера | сервер | `GET /api/info` → `followPlan.enabled`, `followPlan.capabilities`, `apiVersion` |

Правило: если значение можно пересчитать из ответа сервера, клиент его не хранит
как «своё». Кеш допустим только как ускорение отрисовки и обязан сбрасываться по
`storeId`/`bootId`/`seq` (см. §4).

## 2. Что НЕ синхронизируется (локальное состояние клиента)

Эти вещи принадлежат человеку за конкретным устройством и не должны
подтягиваться, перезаписываться или «исправляться» сервером и вторым клиентом:

- открытость диалога/панели и выбранная вкладка;
- фокус, позиция курсора, выделение;
- строка поиска и позиция прокрутки списка (в т.ч. в сканировании плана);
- несохранённый черновик сообщения и черновик редактора плана (он живёт до
  явного сохранения или отмены и при конфликте показывается рядом с серверной
  версией);
- локальная очередь ещё не подтверждённых отправок (она отображается отдельно
  от истории и снимается по `USER_MESSAGE`/отказу).

Следствие: «рассинхронизация» в этих полях — не дефект. Дефект — если
расходится что-то из §1.

## 3. Версии и идентичность

| Поле | Где | Смысл |
|---|---|---|
| `apiVersion` | `GET /api/info` | версия HTTP-контракта (`src/api-contract.mjs`), меняется только при несовместимом изменении формы/смысла |
| `storeId` | `GET /api/info` | идентичность истории этой базы; изменился — курсоры и кеш недействительны |
| `bootId` | `GET /api/info` | идентичность запуска процесса; меняется при рестарте сервера |
| `followPlan.capabilities` | `GET /api/info` | какие маршруты Follow Plan этот сервер реально обслуживает |
| `seq` / `snapshotSeq` | события / снимок задачи | монотонный номер события; `snapshotSeq` — до какого `seq` снимок актуален |
| `plan.revision` / `plan.hash` | `GET /api/tasks/:id/plan` | CAS-пара для правки и для привязки предпросмотра к подключению |

## 4. Инварианты

- **I-1. Один `taskId` — одно состояние.** Два независимых клиента (разные
  `clientId`, разные соединения) для одного `taskId` получают одинаковые
  `status`, `snapshotSeq` и одинаковый `plan` (`attached`, `path`, `revision`,
  `hash`, `state`, `progress`, `stepId`, `findings`).
  Проверка: `tests/session-state-contract.test.mjs` (два клиента).
- **I-2. Привязка плана серверная.** `attach`/`detach`, сделанные одним клиентом,
  видны другому через `GET /plan` без клиентского «пуша».
  Проверка: тот же тест.
- **I-3. `seq` строго монотонен и одинаков для всех читателей.** Клиенты не
  переупорядочивают историю и не откатывают `snapshotSeq` старым `GET`.
  Проверка: тот же тест (`/events?after=`), плюс `docs/api-contract.md` §Гарантии.
- **I-4. Смена `storeId` обнуляет курсоры.** Разные базы дают разные `storeId`;
  клиент, увидев новый, сбрасывает кеш и историю.
  Проверка: тот же тест (две фикстуры), KMP `Connection.storeId`, web `api/info`.
- **I-5. Один runner на задачу.** Второе SSE-соединение не создаёт второй
  запуск Pi: `runs` не растёт, доставка промптов не дублируется.
  Проверка: тот же тест (два открытых потока, число run'ов неизменно).
- **I-6. Локальный UI не пишется сервером** (§2). Проверкой служит отсутствие
  маршрутов, принимающих эти поля: контракт их не описывает.
- **I-7. Старый сервер не ломает клиента.** Нет маршрута `/plan*` → клиент
  показывает `PLAN_API_UNAVAILABLE`, остальной чат работает; неизвестная
  возможность в `capabilities` → функция просто не показывается.
- **I-8. Ответ на команду — терминален.** `409 CONFLICT` / `UNKNOWN_AFTER_CRASH`
  не повторяются автоматически (см. `docs/api-contract.md` §Гарантии).

## 5. Реакция на старый или чужой сервер

- `GET /api/info` без `followPlan` → режим считается выключенным, иконка «По плану»
  серая с подсказкой, а не исчезает.
- `404` на `/api/tasks/:id/plan*` → в интерфейсе `PLAN_API_UNAVAILABLE`
  («сервер не поддерживает этот API»), подключение не выполняется.
- `storeId` не совпал с сохранённым → кеш истории и курсоры сбрасываются,
  история перечитывается с нуля.
- `bootId` не совпал → SSE переподключается; пропуски `seq` из-за prune не
  считаются потерей (см. `docs/api-contract.md`).
- `apiVersion` больше клиентского → клиент продолжает работать по известным ему
  полям и не пытается угадывать новые.
