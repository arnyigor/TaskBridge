# TaskBridge HTTP API — контракт

Машиночитаемый список маршрутов — [`src/api-contract.mjs`](../src/api-contract.mjs).
Он не «документация рядом с кодом»: тест `tests/api-contract.test.mjs` поднимает
живой сервер и падает, если хоть один маршрут из списка перестал отвечать. Эта
страница — то, что нужно знать, чтобы написать клиент (веб уже написан; следующим
будет Android/KMP).

Текущая версия: **`apiVersion = 1`**, её отдаёт `GET /api/info` → `apiVersion`.

## Правило версий

- добавили маршрут — дописали сюда и в `src/api-contract.mjs`, версия не меняется;
- меняется форма или смысл существующего — поднимаем `API_VERSION` и пишем здесь, что изменилось;
- клиент обязан прочитать `apiVersion` и отказаться работать с незнакомой версией, а не угадывать.

## Адрес и авторизация

Базовый адрес — откуда загружен сервер (`http://<host>:8787`). Все ответы — JSON,
кроме помеченных как бинарные.

Авторизация выключена, пока `server.auth.enabled = false` (по умолчанию), и тогда
сервер слушает только `127.0.0.1`. Когда включена:

- `GET /api/auth/pairing` отдаёт текущий код и данные QR **только на самом
  компьютере**: loopback-адрес сокета, loopback в последнем `X-Forwarded-For`,
  loopback в `Host` и нет заголовка `Tailscale-User-Login`. Поэтому ни свой
  LAN-прокси, ни `tailscale serve` не делают удалённый запрос «локальным»;
- `POST /api/auth/pair` `{code, deviceName?, clientKind?}` создаёт устройство
  `{deviceId, token}`. Браузер получает токен только в HttpOnly-cookie
  `taskbridge_session=<token>`; клиент с `clientKind` `android` / `desktop` / `cli` —
  ещё и в теле ответа (`token`), один раз;
- нативные клиенты шлют `Authorization: Bearer <token>`. Изменяющий запрос с
  cookie, но без `Origin`, отклоняется (`401`): cookie — только для браузера;
- `GET /api/auth` сообщает `deviceTokens: true`; клиент, у которого есть только
  cookie старого формата, должен спариться заново;
- `GET /api/auth/devices` — список устройств, `DELETE /api/auth/devices/:id` —
  отзыв (только с ПК); отозванный токен перестаёт работать сразу;
- без учётных данных закрытые маршруты отвечают `401` с `code: "AUTH_REQUIRED"`,
  чужой `Origin` (не свой хост и не из `server.auth.allowedOrigins`) — `403 ORIGIN_FORBIDDEN`.

Cookie старого формата `<expires>.<nonce>.<sig>` принимаются до истечения срока.

## Ошибка

Любой неуспех — один и тот же конверт:

```json
{ "error": "Сессия не найдена.", "code": "NOT_FOUND" }
```

Важно различать два `404`: несуществующий **маршрут** отвечает
`{ "error": "Not found" }`, а несуществующая **сессия** — другим текстом. Клиент
не должен считать «Not found» обычной ошибкой ресурса: это признак расхождения
версий.

## Поток работы (модель для клиента)

1. `POST /api/tasks` — создать задачу в проекте. Ответ содержит `id`.
   К первому запросу TaskBridge дописывает короткий блок `Task instructions (<профиль>)`:
   границы (рабочая папка, «только то, что просят») и форма ответа. Профиль
   (`quick` — поиск факта, `explore` — разбор по умолчанию, `implement` — изменения)
   определяется по тексту запроса без отдельного вызова модели; отчёт об изменениях
   требуется только в `implement`. Follow-up уходит дословно: правила уже лежат
   в транскрипте Pi, а очередь и восстановление после перезапуска читают текст как есть.
2. `GET /api/tasks/:id/stream` (SSE) — живая лента. При обрыве клиент
   переподключается и передаёт `Last-Event-ID: <последний seq>`.
3. `GET /api/tasks/:id/events?after=<seq>` — то же самое, но «пачкой»: этим
   закрывается разрыв, если лента не поднялась (фон, Doze, потеря Wi-Fi).
4. `POST /api/tasks/:id/message` — follow-up/steering. `{ "now": true }` минует
   очередь: во время ответа текст уходит steering'ом в текущий ход (команды не
   останавливаются, модель отвечает на него после текущей команды), в свободную
   сессию — новым сообщением. Остановить работу может только сама модель или
   `/cancel`. `POST /api/tasks/:id/pending/send` делает то же с сообщением из очереди.
5. `POST /api/tasks/:id/cancel` — STOP.
6. `POST /api/tasks/:id/session/restart` — перезапустить сессию: убивает Pi-процесс
   этой сессии, следующее сообщение перезапускает её из сохранённого файла сессии.
   Рутинный выход для зависшей сессии (Pi жив, но не отвечает) — рестарт сервера
   здесь аварийный выход, он затрагивает все сессии. История не теряется; сообщение,
   которое Pi принял, но не успел обработать, перепоставляется в очередь. Ответ:
   200, задача в `FAILED_RECOVERY` («Прервана — можно продолжить»); для уже
   завершённой или стоящей в очереди сессии — no-op.
7. `POST /api/tasks/:id/workspace/trust` с `{ "confirm": true }` — сохранить папку
   сессии в `~/.pi/agent/trust.json` как доверенную, совместимо с интерактивной
   командой Pi `/trust`. Запущенный Pi этой сессии перезапускается, чтобы
   проектные ресурсы перечитались; история сохраняется. В управляемом MCP-режиме
   TaskBridge по-прежнему использует свой MCP-конфиг вместо `.pi/mcp.json` проекта.

**Ключевое свойство для мобильного:** задача живёт часами и **не держит HTTP**.
Клиент может уйти в фон и вернуться — он догоняет историю по `seq`.

## Ресурсы

### `GET /api/info`: статусы аккаунтов провайдеров

Поле `providerStatuses` — объект по точному `model.provider`. Клиент не должен
угадывать провайдера по имени модели: например, `wormsoft/deepseek-*` использует
подписку WormSoft, а не отдельный баланс DeepSeek. Сейчас нормализованы:

- `deepseek`: `kind: "balance"`, валюты, рублёвый эквивалент и прогноз расхода;
- `wormsoft`: `kind: "subscription"`, тариф, оставшиеся/общие кредиты и лимиты окна;
- `routerai`: `kind: "credits"`, оставшиеся credits без придуманной валюты.

`/api/info` отдаёт только последнее известное состояние и не запрашивает провайдеров.
Если данных ещё нет, запись содержит `available: false, reason: "not-fetched"`.
`POST /api/providers/refresh` с `{ "provider": "wormsoft" | "deepseek" | "routerai" }`
обновляет только выбранный аккаунт по нажатию на строку статуса и возвращает
`{ [provider]: status }`. Повторные нажатия в течение 20 секунд используют
результат предыдущего запроса. После завершения хода модели WormSoft остаток
также считывается автоматически (не чаще раза в минуту).
Отсутствующий ключ даёт `available: false`; старое поле `deepseek` временно
сохранено для совместимости.

### `POST /api/providers/check` (TB-PROV-01B)

Проверка соединения с провайдером: один бесплатный `GET {baseUrl}/models`.
Тело — `{ "provider": "<id>", "id": "<model>"? }` (модель необязательна: без неё
проверяется провайдер целиком). Работает и для управляемых `tb-*`, и для записей,
которыми TaskBridge не владеет.

Адрес резолвится **только на сервере** — из каталога Pi (`models.json`) или из
настроенных локальных серверов; URL из тела не принимается, поэтому проверка не
становится SSRF-ручкой. Redirect не выполняется (`redirect: "manual"`): ответ 3xx
возвращается как `code: "REDIRECT"` и `status: "UNSUPPORTED"` с пояснением, потому
что переход по `Location` на внутренний адрес превратил бы проверку в запрос от
имени сервера. DNS rebinding при этом не закрыт: соединение идёт по имени из
конфигурации, разрешение адреса не пиннится. Ничего не пишется в `models.json`,
токены не тратятся, генерация модели не выполняется.

Ответ: `{ provider, id, status, ok, code, httpStatus, latencyMs, models, checkedAt, message, requestId }`,
где `status` — один из `AVAILABLE` | `UNAUTHORIZED` | `RATE_LIMITED` | `TIMEOUT` |
`UNREACHABLE` | `UNSUPPORTED` | `UNKNOWN`. `UNSUPPORTED` означает «так проверить
нельзя» (нет адреса в каталоге, нет `/models`), а не «сломано». HTTP 200 от `/models`
не доказывает, что модель умеет генерировать — для этого отдельная проба
`POST /api/models/probe` с `mode: "latency"`. Повторная проверка того же провайдера
в течение 5 секунд возвращает `code: "COOLDOWN"` без запроса к провайдеру.

### `GET /api/quick-actions`

Возвращает список slash-команд для нативных клиентов: skills из Pi, prompts из
Pi/project folders и встроенные команды. Элемент: `{ id, type, title, description, insertText }`.
Клиент показывает список при вводе `/` и вставляет `insertText` в composer.

### `GET /api/models`

`{ models, thinkingLevels, defaultModel, defaultThinkingLevel, latency }` — каталог Pi
плюс накопленная задержка ответа. `latency` — объект по ключу `provider/id` (тот же
ключ, что у клиента): `{ count, avgMs, p50Ms, lastMs, samples: [{ ttftMs, at }] }`.
Это TTFT (отправка промпта → первый токен), по одному замеру на ответ ассистента,
для локальных и облачных моделей одинаково — у облачных API других таймингов нет.
Ключа может не быть: замеров по модели ещё нет.

Ответ несёт `freshness`: `refreshed` — каталог только что получен от Pi, `partial` —
получен, но часть провайдеров не ответила или не была проверена из-за общего бюджета
прохода, `cache` — Pi не ответил, отдан последний известный каталог (строки
`models` в нём прежние; при `refresh=1` в ответе появляется `sync`
`{ changed, conflict, expired, providers[] }`). Клиент обязан показать это словами
(`web/model-picker-view.mjs`, `catalogStateText`), а не выдавать кэш за свежий
каталог. Если каталога ещё не было и Pi не ответил, `/api/models?refresh=1` отвечает
ошибкой, а не пустым списком.

Общий бюджет синхронизации — `config.modelSync.budgetMs` (по умолчанию 12 000):
провайдер, до которого бюджет не дошёл, попадает в `sync.providers[]` с
`skipped: "deadline"` и не опрашивается, а не молча считается здоровым.

`?refresh=1` дополнительно синхронизирует списки моделей провайдеров, включённых в
`config.modelSync.providers` (сегодня wormsoft): сервер опрашивает их собственный
OpenAI-совместимый `GET {baseUrl}/models` и ДОБАВляет недостающие модели в
`~/.pi/agent/models.json` (существующие записи и их compat-метаданные не
переписываются, id с префиксом самого провайдера — его внутренние алиасы — не
добавляются). Затем запускается свежий Pi-probe, который отдаёт каталог с новыми
моделями. Синхронизация opt-in per provider: openrouter и routerai отвечают
сотнями моделей, и их включать не стоит без отдельной настройки.

Запись в `models.json` идёт с проверкой ревизии (пункт 2.4 плана): файл читается
один раз до сетевых вызовов, а перед `rename` его байты сравниваются с прочитанными
ещё раз. Если за время запроса файл изменил редактор провайдеров, запись
отменяется, ничего не перезаписывается, в журнал идёт `provider model sync:
models.json изменён во время запроса, запись отменена`. Временный файл уникален
(`.tb-<pid>-<hex>.tmp`, `wx`, режим 0600), бэкап — исходные байты через
`COPYFILE_EXCL`.

### `POST /api/provider-profiles/draft-check` — мастер подключения, шаги 3–4

Проверка **ещё не сохранённого** подключения: `{ baseUrl, keyEnv }` (тело), ответ
`{ ok, status, code?, httpStatus?, latencyMs, baseUrl, models[], note }`.

`models` — каталог провайдера (до 300 записей с `id`, `name`, `contextWindow`), из
которого оператор отмечает нужное; сервер при сохранении принимает не больше 100.
Ручной ввод ID остаётся для API без discovery.

Защита входа (адрес приходит от клиента, поэтому проверяется до сети):

- только `http(s)`, без логина, пароля, query и fragment;
- `http` разрешён только для `localhost`/`127.0.0.1`/`::1` и локальных IPv4;
- служебные диапазоны запрещены целиком — link-local `169.254/16` (metadata-сервис
  облака), `0.0.0.0/8`, multicast, IPv6 `fe80::/fc/fd/ff`;
- `redirect` не выполняется: ответ 3xx возвращается как `status: "REDIRECT"`;
- в `keyEnv` принимается только имя переменной окружения (`[A-Z][A-Z0-9_]*`),
  значение ключа отклоняется с `INPUT_INVALID`;
- облачному адресу имя переменной обязательно; если переменная не задана в процессе
  сервера — `status: "NO_KEY"` без сетевого запроса.

Маршрут доступен только локальному администратору (как и запись профилей), файл
`models.json` этим запросом не меняется. DNS rebinding остаётся непокрытым: имя из
конфигурации разрешается обычным порядком.

### `Task`

`id`, `title`, `prompt`, `projectId`, `status`, `createdAt`, `updatedAt`,
`model: { provider, id }`, `requestedModel`, `thinkingLevel`, `workspacePath`,
`queueReason`, `current`, `errorCode`, `error`, `files[]`, `compaction`, `lastUsage`,
`metrics`, `speeds`, `outputFiles[]`, `nativeSource`, `applied`, `worktree`,
`runId`, `snapshotSeq`, `runtime`, `turnState`.

`runId` — идентификатор текущего прогона (одного хода, включая ожидание
подтверждения) или `null`, когда ход закончен. Прогон живёт в журнале
`GET /api/tasks/:id/runs` (`id, kind, status, startedAt, finishedAt, data`) и после
завершения остаётся там со статусом хода; повторное открытие закрытого прогона
запрещено на уровне записи (`ON CONFLICT ... WHERE status NOT IN (terminal)`).
Прогоны, не закрытые предыдущим процессом, при старте получают `FAILED` с
`errorCode: UNKNOWN_AFTER_CRASH` — их исход неизвестен, и он не повторяется.

`metrics` — числа последнего хода (PP/TG, размер промпта, TTFT), `speeds` — по всей
сессии: `{ turns, ppMax, ppAvg, ppTurns, tgAvg, tgTurns }`. В средние входят только
те ходы, где число было: PP на кеш-попадании Strata не публикует, и такой ход не
тянет среднюю вниз.

Полный набор полей — в ответе `GET /api/tasks/:id`; сервер вправе добавлять поля,
поэтому клиент должен игнорировать незнакомые, а не падать.

`queueReason` объясняет, чего ждёт сессия в статусе `QUEUED` (в `data.reason` события
`QUEUE_WAITING` — тот же код): `MODEL_BUSY` — локальная модель занята другой сессией,
`MODEL_LOADING` — модель ещё загружается, `WORKSPACE_BUSY` — рабочая папка занята другой
сессией (только при `queue.maxSessionsPerDirectory` > 0: проект без worktree отдаёт всем
сессиям свою папку), `BUSY` — занят общий лимит или слот провайдера, `RESTORED` —
восстановлено после перезапуска. Клиент показывает подпись, а не код; тексты — в
`WAIT_TEXT` (`src/task-manager.mjs`) и `DisplayState.activityOf` (KMP).

### Лимиты параллельности (`GET /api/info` → `scheduler`)

- `maxConcurrentSessions` (`queue.maxConcurrentSessions`, 1…16, по умолчанию 4) — сколько
  сессий работают одновременно на всём компьютере;
- `maxSessionsPerDirectory` (`queue.maxSessionsPerDirectory`, 0…16, по умолчанию 0) — сколько
  сессий одной рабочей папки допустимо одновременно. `0` — своих ограничений нет: проект
  без worktree (общая папка) работает как остальные, и число сессий решает только
  `maxConcurrentSessions`; `1` — строгая очередь «один писатель на папку», вторая сессия
  ждёт с `WORKSPACE_BUSY`. Worktree сессии и разные проекты этим лимитом не задеваются;
- `providerConcurrency[provider]` — свой лимит на провайдера (по умолчанию равён
  `maxConcurrentSessions`), `providers` в ответе показывает `active`/`limit`/`cooldownUntil`.

### Статусы

`QUEUED` · `PREPARING` · `PREFLIGHT` · `RUNNING` · `WAITING_USER` · `VERIFYING` ·
`CANCELLING` · `SUCCEEDED` · `FAILED` · `CANCELLED`

Активные: всё до `CANCELLING` включительно. Терминальные: `SUCCEEDED`, `FAILED`,
`CANCELLED`. Показывать пользователю нужно подписи, а не коды (в вебе это
`TASK_STATUS_LABELS`).

### `TaskEvent`

```json
{ "taskId": "…", "seq": 412, "type": "TASK_SUCCEEDED", "message": "Done", "data": {} }
```

Типы, которые клиенту нужно понимать:

- поток: `USER_MESSAGE`, `PI_EVENT` (в `data.pi` — сырой кадр Pi), `STATUS`, `PROMPT_QUEUED`, `PROMPT_ACCEPTED`;
- итог: `TASK_SUCCEEDED`, `TASK_FAILED`, `TASK_CANCELLED`, `VERIFICATION`, `VERIFICATION_ERROR`;
- правка истории: `TURN_EDITED` (текст сообщения перезаписан, `seq` тот же),
  `TURN_TRUNCATED` (ходы после `fromSeq` убраны — в том числе в живом чате);
- прочее: `MODEL_SWITCH`, `THINKING_LEVEL`, `COMPACT_REQUESTED`, `QUEUE_*`,
  `APPROVAL_REQUIRED`, `APPROVAL_RESOLVED`, `LOCAL_MODEL_PROGRESS`, `RUNTIME_*`,
  `WORKSPACE_READY`, `OUTPUT_FILES`, `TOOL_OUTPUT`, `CHANGES_APPLIED`, `WORKTREE_REMOVED`,
  `TASK_FORKED`, `SESSION_RESTORED`, `SESSION_SHRUNK`, `SESSION_TOO_LARGE`, `SESSION_INVALID`, `ENGINE_SWITCH`, `PI_STDERR`, `PI_PROTOCOL_ERROR`,
  `ABORT_TIMEOUT`, `QUEUE_DROPPED`.

`USER_MESSAGE` и `TASK_FAILED` несут `data.turn` — номер хода, к которому событие
относится. По нему клиент привязывает запоздавшее терминальное событие к своему
ходу: у такого события и `at`, и `seq` больше, чем у сообщения, которым оператор уже
начал следующий ход, поэтому ни время, ни порядок событий этот случай различить не
могут. Клиенты, которым поле не нужно, его игнорируют.

`TASK_FAILED` при ошибке модели (`errorCode: MODEL_ERROR`) несёт `data.toolEvidence`:
до 10 подтверждённых выводов инструментов этого хода (`{toolName, target, excerpt}`,
`target` — до 160 символов, `excerpt` — одна строка до 240 символов).
`task.error` при этом остаётся строкой провайдера — подтверждённое лежит рядом, а не
внутри неё; то же содержимое есть в result.md, раздел `## Tool evidence`.
Web показывает выжимки оператору и в LAN: это подмножество того, что уже отдаёт
`TOOL_OUTPUT`, то есть интерфейс считается доверенной поверхностью и не маскирует
содержимое автоматически. В копируемый бандл «Скопировать диагностику» выжимки
не попадают: там остаются только число записей и имена инструментов.

`SESSION_SHRUNK` — перед запуском Pi (и повторно после ответа 413) история сессии
восстановлена: base64 старых скриншотов перенесён в `data/media/<sha256>.<ext>`, в
истории осталась ссылка на оригинал, новейшие изображения оставлены. id сообщений,
`parentId`, tool calls и настройки модели не меняются, рядом с файлом лежит
`.bak-<timestamp>`. `SESSION_TOO_LARGE` — файл больше бюджета (`pi.sessionMaxMb`,
по умолчанию 24 МБ), но изображений в нём уже нет: не тронут, сессию надо
сжимать или клонировать. `SESSION_INVALID` — файл не разбирается как JSON или
проверка целостности после восстановления не прошла: сессия оставлена как есть.

Список открытый: **неизвестный тип клиент обязан игнорировать**, а не падать.

## Гарантии

- **`seq` строго монотонен** в пределах задачи и сохраняется между перезапусками.
  Курсоры `after` и `Last-Event-ID` поэтому не ломаются.
- **Идемпотентность.** `POST /api/tasks`, `/message`, `/cancel`, `/apply` принимают
  `commandId` (+ `clientId` устройства). Повтор с тем же `commandId` не создаёт
  вторую задачу — критично для мобильной сети. Итог команды доступен через
  `GET /api/commands/:commandId`.
  Два ответа журнала команд — окончательные, повторять их нельзя, поэтому они
  приходят как `409`, а не `5xx`: `CONFLICT` (тот же `commandId` с другим телом)
  и `UNKNOWN_AFTER_CRASH` (команда принята, но сервер упал до её завершения).
  Повтор команды, которая ещё выполняется, — тоже `409`, с кодом `ACCEPTED`:
  его можно повторить позже и получить сохранённый результат.
  После `UNKNOWN_AFTER_CRASH` клиент ищет в истории `USER_MESSAGE` с этим
  `commandId`: нашлось — сообщение дошло; нет — предложить отправить заново
  с новым `commandId`.
- **Кто отправил.** `USER_MESSAGE` несёт `commandId` и `clientId` исходной
  команды (если они были), а сообщение, доставленное из очереди, — ещё и
  `pendingId` своей записи в `pendingPrompts`. Каждое сообщение, поставленное в
  очередь, отмечается событием `PROMPT_QUEUED { pendingId, commandId?, clientId?, deviceId? }`.
  Сопоставлять своё сообщение нужно по этим полям, а не по тексту.
  `deviceId` — спаренное устройство, которое сервер сам опознал по токену
  (`clientId` клиент называет сам, `deviceId` подделать нельзя). Задача, созданная
  устройством, несёт `source: { clientId?, deviceId? }`; с самого ПК поля нет.
  `USER_MESSAGE.data.mode` — как сообщение дошло до Pi: `prompt` / `steer` / `follow_up`.
- **Очередь видна сразу, беседа — только когда сообщение дошло.** Сообщение, отправленное
  с `queue: true` к работающей сессии, до `USER_MESSAGE` в беседе не находится: клиент
  показывает его очередью (телефон — строкой отправки над полем ввода, веб — строкой
  очереди) и рисует пузырь только по `USER_MESSAGE`. Иначе сообщение сначала висело
  пузырём в ленте, а через некоторое время «переезжало» в очередь (2026-10-12).
- **Первое сообщение.** Оно хранится в `task.prompt`, поэтому отдельного
  `USER_MESSAGE` для него нет. `PROMPT_ACCEPTED {initial:true}` появляется
  только после подтверждения Pi RPC. Это подтверждает передачу в Pi, но ещё
  не доказывает обращение к провайдеру или получение ответа.
- **Heartbeat.** SSE-поток задачи шлёт комментарий `: heartbeat` каждые
  `server.sse.heartbeatSec` (по умолчанию 15 с); клиент считает поток мёртвым
  после трёх пропущенных интервалов.
- **Идентичность базы.** `GET /api/info` → `storeId`: случайный id истории этой
  базы. Если он изменился (база пересоздана или восстановлена из бэкапа — у
  копии из `npm run backup` всегда свой `storeId`), `seq` начались заново и
  закэшированные клиентом курсоры недействительны: кэш нужно сбросить.
- **Версия Pi.** `GET /api/info` → `pi: { version, supported, supportedRange, error }`
  (`null`, пока проверка при старте не завершилась). Неподдерживаемая или
  ненайденная версия — предупреждение `PI_VERSION_UNSUPPORTED` в `warnings`, а не
  отказ в работе.
- **Курсоры истории.** `after` — «дай после seq», `tail` (+`before`) — постраничная
  выдача, выровненная по ходам, для длинных сессий.
- **Ограничение размера.** Один запрос отдаёт не больше `maxEventsPerRequest`
  событий (по умолчанию 20000); глубже — через `tail`/`before`. Страница истории
  ещё ограничена по байтам (`server.maxHistoryMb`, по умолчанию 6 МБ) — иначе
  браузер задыхается на разборе. Кап всегда оставляет самое свежее событие, каким
  бы большим оно ни было, поэтому окно, которое в бюджет не влезло, перед выдачей
  облегчается (`lightenEvent` в `src/event-trim.mjs`: выбрасываются только те
  поля фреймов Pi, которые не читает ни один клиент, — прежде всего `agent_end`
  с копией всей переписки и картинками, до 16.3 МБ на фрейм). Без этого тело
  ответа могло превысить 16 МБ, а клиент такой ответ отвергает целиком
  («Ответ сервера слишком большой (16 МБ)»), и сессия не открывалась вовсе.
- **Вложения.** `POST /api/uploads` (multipart, потоково) возвращает `token` и
  `files[].id`; в задачу/сообщение передаётся `uploadToken` и `ids`. Клиентские
  имя/размер не принимаются на веру.
- **Долгие задачи не держат соединение.** Ни один HTTP-запрос не остаётся открытым
  на время работы агента.

## Маршруты

Полный список с методами и назначением — в `src/api-contract.mjs` (и в
[README](../README.md#http-api) в человекочитаемом виде). Группы: статус и метрики,
авторизация, проекты и файлы, сессии/модели, задачи (создание, управление,
переписывание истории, approvals, артефакты), локальный runtime, администрирование
сервера, MCP, push, облако.

MCP дополнительно поддерживает безопасную диагностику (`POST /api/mcp/health`)
и CRUD управляемых server definitions (`POST /api/mcp/definitions`). Статус
возвращает latency/последнюю ошибку, OAuth scopes без секретов и конфликты имён
инструментов. Изменения пишутся в `data/mcp-audit.jsonl`.

`POST /api/server/restart` перезапускает **сам процесс** TaskBridge (не профиль
модели) и требует тела `{ "confirm": true }` — без флага отвечает `400
INPUT_INVALID`, при занятой машине — `409 MODEL_BUSY`. Ответ `202` приходит
раньше, чем сервер останавливается: перезапуск выполняет отдельный отсоединённый
процесс, поэтому клиент успевает получить ответ.

`POST /api/system/shutdown` выключает **машину**, на которой живёт сервер, и
требует того же тела `{ "confirm": true }` (иначе `400 INPUT_INVALID`). Ответ
`200 { "shuttingDown": true }` уходит прямо перед запуском системной команды
(`shutdown /s /t 0` на Windows, `osascript` на macOS, `shutdown -h now` на
Linux). Обратного отсчёта и отмены на сервере нет — 10-секундный таймер отмены
живёт в клиенте: если приложение умрёт до конца отсчёта, выключение просто не
уйдёт, а не сработает без присмотра.

`POST /api/system/reboot` перезагружает **машину** и требует того же тела `{ "confirm": true }` (иначе `400 INPUT_INVALID`). Ответ `200 { "rebooting": true }` уходит прямо перед запуском системной команды (`shutdown /r /t 0` на Windows, `osascript` на macOS, `shutdown -r now` на Linux). Таймер отмены — клиентский, как у shutdown.

Потоковые (`SSE`) маршруты — только два: `GET /api/tasks/:id/stream` и
`GET /api/local/events`.

### Project Dashboard (MR-01, 2026-10-11)

#### Run Recipes (MR-05, 2026-10-11)

Рецепт — это **как** делать повторяющуюся работу: шаблон промпта, схема
параметров, агент и модель, профиль контекста, стратегия рабочей папки, проверка.
**Когда** запускать — это расписание (MR-06), а факт запуска — созданная сессия;
отдельной таблицы о запуске нет, иначе об одном и том же было бы два источника
правды.

- `GET /api/recipes?projectId=`, `POST /api/recipes`, `GET/PATCH/DELETE /api/recipes/:id`.
- `POST /api/recipes/:id/run` `{parameters, trigger: manual|schedule}` — запустить
  сейчас: создаётся новая сессия, её промпт — отрендеренный шаблон, в метаданных
  `recipeRun` (рецепт, параметры, триггер), а сессия связывается с задачей рецепта
  связью `implementation`, если рецепт её называет.

Параметры — то, ради чего это существует: `{{area}}` в промпте превращается в
список на телефоне, а не в правку стены текста. Правила:

- схема параметров: `string`, `enum` (со `values` и `default` из них),
  `boolean`, `number`; значение по умолчанию обязано соответствовать типу;
- `{{параметр}}` подставляется **только** в поля из фиксированного списка
  (шаблон промпта, `runtime.model/thinking`, `verification.command`) — это не
  шаблонизатор общего вида и не подстановка в произвольную команду;
- `context`, `workspace` и `limits` рецепт **не применяет** (AUTO-01A): запуск не
  собирает контекст, не создаёт отдельную рабочую папку и не ограничивает время.
  Непустые значения этих полей отклоняются при сохранении (`400 INPUT_INVALID`) —
  обещанная, но не исполняемая настройка хуже отсутствующей. Пустые объекты и
  старые записи читаются как есть;
- `runtime.id` — только `pi`: второго ядра в TaskBridge нет;
- placeholder, которого нет в схеме, отклоняется при сохранении (`400
  INPUT_INVALID`): опечатка должна падать при операторе, а не в 03:00;
- неизвестное имя параметра в запуске — тоже отказ, а не молчаливое игнорирование.

`POST /api/recipes/:id/run` и предпросмотр (`renderRecipe`) используют одну и ту
же функцию: показанное и запущенное не могут разойтись.

#### Schedules и Invocations (MR-06, 2026-10-11)

Планировщик живёт **на ПК** — ни на телефоне, ни в relay: телефон выключен, а
09:00 всё равно наступает, и результат потом приходит на устройство. Иерархия
уровней не смешивается: `schedule → invocation → session → run(s)`; `runs`
остаются историей исполнения внутри сессии.

- `GET /api/schedules?recipeId=`, `POST /api/schedules`, `GET/PATCH/DELETE /api/schedules/:id`,
  `POST /api/schedules/:id/run` (запустить сейчас — расписание при этом не сдвигается).
- Спецификация: `daily` с `at: "ЧЧ:MM"`, `weekly` с `weekday` (`mon`…`sun`) и `at`,
  `interval` с `everyMinutes` (5…10080). Время — **локальное для машины**: там
  живёт планировщик, и оператор задаёт «09:00» по своим часам. День недели задаётся
  именем: число требовало бы конвенции (0 — воскресенье или понедельник?), а
  молчаливый выбор одной из них — это ошибка на сутки.
- `misfirePolicy`: `SKIP` | `RUN_ONCE` (по умолчанию) | `CATCH_UP`. Дефолт выбран
  осознанно: ПК, простоявший три дня, не должен запустить три независимых аудита.
  В `SKIP`-случае всё равно появляется запись инвокации со статусом `SKIPPED` —
  «не запускалось» это тоже информация.
- `concurrencyPolicy`: `SKIP_IF_RUNNING` (по умолчанию, тоже с записью `SKIPPED`) |
  `QUEUE` | `PARALLEL` | `REPLACE` (последний останавливает предыдущий запуск и
  помечает его инвокацию `FAILED` с причиной).
- `notify`: `action-required` (по умолчанию) | `always` | `errors-only` | `never`.
  При `action-required` push уходит на ошибки, отмены, запросы подтверждения и на
  успешный запуск **с изменениями** или **не прошедшей проверкой**; чистый пустой
  успех ночного аудита никого не будит.
- `approvalMode`: только `pause` — подтверждение, которое просит агент, ждёт
  человека, как и в ручной сессии. Обходить существующую approval policy
  расписанию нельзя.
- Секреты в расписании не хранятся: параметр с именем вроде `token`/`api_key`
  отклоняется с указанием на `secretRef`.

Инвокация — это запись о факте запуска: `scheduledAt`, `startedAt`, `finishedAt`,
`status` (`RUNNING` | `SUCCEEDED` | `FAILED` | `SKIPPED`), `reason`, `misfire`,
`parameters`, `sessionId`, `verification`, `workspaceRef`, `resultArtifact`.
Статус **догоняется по сессии** (`RUNNING` → итог сессии), поэтому перезапуск
сервера не оставляет «вечно идущий» запуск. Если рецепт требует проверку
(`verification.required`), а она не `PASSED`, инвокация помечается `FAILED`:
«запустилось» не должно читаться как «получилось».

Тик планировщика в сервере включается ключом `schedules` (`{enabled, tickSec}`),
намеренно не `scheduler`: этим именем уже называется очередь сессий (`/api/info.scheduler`).
Ручной тик — `POST /api/scheduler/tick` (только на самой машине), он же используется тестами,
чтобы проверить политики пропусков, не ожидая трёх дней.

`verification.command` в рецепте — это **имя профиля** из
`config.verificationProfiles` (`android-smoke: [":client:jvmTest", ":shared:jvmTest"]`),
поэтому промпт не содержит shell-команд.

#### Resume Engine (MR-04, 2026-10-11)

`resumeContext` **вычисляется** и никогда не хранится: это то, что нужно новой
сессии прямо сейчас — задача, её сессии с их recap, состояние Git и результаты
проверок. Транскрипты не копируются: ради этого всё и делается.

- `GET /api/work-items/:id/resume?strategy=&memory=` — предпросмотр: чек-лист того,
  что попадёт в новую сессию (`Goal`, критерии, сессии с recap, Git, проверки), что
  **не** попало (у сессии нет recap, список файлов обрезан Git'ом, рабочая папка
  удалена), какую рабочую папку и режим памяти выбрали, сколько это токенов, и
  `fingerprint` — те факты, которые запуск обязан найти снова.
- **Прерванная попытка (2026-10-12).** Сессия, остановившаяся НЕ успешно
  (`FAILED`/`CANCELLED`), попадает в предпросмотр как `interrupted[]` и в бриф
  отдельным блоком `## Прерванная попытка`: статус, ошибка, последнее событие,
  база чекпоинта (`startHead`, `startedAt`), текущий `head`, коммиты между ними
  (`commitsSince`) и незакоммиченные файлы. Живые сессии (`QUEUED`/`RUNNING`)
  сюда не попадают: они ещё идут.

  Базу чекпоинта пишет **TaskBridge, а не модель**: при готовности рабочей папки и
  до первого запроса к LLM в записи сессии появляется `checkpoint`
  `{ at, head, workspacePath, worktree, baseCommit }`. Модель об этом не знает и не
  тратит на это ни токена, ни вызова инструмента; журналом «на ходу» служит тот же
  поток событий сессии (SQLite: `WORKSPACE_READY`, `TOOL_OUTPUT`, `TASK_*`) плюс
  живое состояние Git, читаемое в момент предпросмотра. Поэтому блок не может
  устареть: это не копия лога, а чтение фактов.
- `POST /api/work-items/:id/resume` `{strategy, memory, preview, sessionIds?}` —
  запуск. Сервер **повторно** читает факты и сравнивает их с `fingerprint` из
  предпросмотра: `HEAD` сдвинулся, рабочая папка исчезла, сессия или артефакт из
  превью пропали — это `409 CONTEXT_CHANGED` с полем `changes` (что именно
  изменилось), а не запуск «на удачу». При совпадении создаётся **новая короткая
  сессия**: её промпт — отрендеренный бриф, в метаданных `resumeFrom` (задача,
  сессии, commit, стратегия, режим памяти), а сама сессия связывается с задачей
  связью `resume`.
- Стратегии рабочей папки: `fresh-worktree` (по умолчанию) и `reuse` (только
  worktree, которым управляет TaskBridge, и только после подтверждённого
  предпросмотра). «Применить патч» из эскиза роадмапа не реализовано осознанно:
  автоматически применять чужую работу — разрушительное действие, а кнопка,
  которая на самом деле означает «сделай это руками», врёт.
- Режим памяти: `native` (долговременная память проекта подключается сама, а
  релевантные выдержки из неё — см. MEM-01 ниже) или `off`. Копий памяти в
  `resumeContext` нет.

Исчезнувшая сессия не подменяется основным checkout'ом проекта: связь остаётся
видимой (`available: false`), а предпросмотр говорит, что состояние работы взять
неоткуда.

#### Память проекта: ProjectMemoryProvider (MEM-01, 2026-10-12)

TaskBridge не знает внутренностей `pi-memory-md`: он знает только два вопроса —
«что проект помнит» и «что из этого относится к текущей работе». Граница —
`src/memory/project-memory-provider.mjs`; `src/task-manager.mjs` работает с этой
абстракцией, поэтому другой backend можно подключить, не переписывая Resume.

**Canonical project identity.** Имя проекта в памяти — это имя каталога, который
`pi-memory-md` считает корнем проекта, а не то, как проект назван в TaskBridge.
Корень определяется по Git, а не по папке сессии:

1. `git rev-parse --git-common-dir` внутри рабочей папки проекта;
2. если это `<main>/.git` — проект **linked worktree**, и корнем считается
   основной checkout (`dirname`), а не сам worktree: `C:\repo\TaskBridge` и
   `C:\worktrees\feature-x` — одна память, а не две;
3. иначе — `git rev-parse --show-toplevel`;
4. не Git-каталог (или сломанный `.git`) — корнем становится путь проекта как он
   зарегистрирован. Угадывания чужого корня нет.

Коллизия возможна: два **разных** репозитория с одинаковым именем каталога
получают одну папку памяти — так `pi-memory-md` называет проекты, и fix через
переименование папки означал бы чтение каталога, который Pi не инжектит. Поэтому
TaskBridge не молчит: `collisions` в инспекторе и предупреждение в Resume
называют оба репозитория, если это разные корни с общей папкой памяти. Один и тот
же корень, зарегистрированный дважды, коллизией не считается.

**Список сессий и его бюджет.** `GET /api/tasks` — строка сессии, а не сессия:
`prompt`/`assistantText`/`compaction.last.summary`/`git.status` обрезаются до 300
символов, `thinkingText`/`metrics`/`speeds`/`lastUsage`/`parameters` приходят как
`null`, модель — только подписью (`provider`/`id`/`name`), а списки файлов и правок
заменены сэмплом (3 записи) и счётчиками (`outputFileCount`, `attachmentCount`,
`fileCount`, `git.changedFileCount`/`changedFilesTruncated`). Полная сессия — только
в `GET /api/tasks/:id`. Причина: телефон грузит список каждые 5 с, и 1.1 МБ JSON
(70 сессий) по Wi-Fi не успевали — список «тормозил». Вместе с gzip-сжатием JSON-ответов
(при `Accept-Encoding: gzip`, тела ≥ 1 КБ) 1315 КБ превратились в 44 КБ (2026-10-14).

**Жизненный цикл заметки (этап M3).** `modified` в frontmatter — когда знание менялось
по существу (mtime двигает любой редактор), проставляется при принятии предложения.
`supersedes: <путь заметки>` — замена: заменённая заметка **выпадает из инъекции** (её
знание уже неверно), но **остаётся в поиске** с пометками `superseded: true` и
`supersededBy`; в ответе `relevant` это число (`superseded`). Предложение может нести
`supersedes`, и тогда цель проверяется: несуществующая или лежащая вне `core/` заметка
отвергается кодом `SUPERSEDES_UNKNOWN`.

**Консолидатор.** `GET /api/projects/:id/memory/consolidation` (`?threshold=`, `?limit=`) —
пары заметок, которые стоит слить, по сходству значимых слов (Jaccard, порог по умолчанию
0.35). Только чтение и только `action: "propose"`: `POST` того же маршрута с `{first,
second}` оформляет пару **предложением** через общий гейт (`NOT_SIMILAR` для непохожих,
`NOT_FOUND` для отсутствующих), в `core/` ничего не пишется до явного «Принять».

**Метрики памяти** в `GET /api/metrics` → `memory`: `searches`, `search_ms_total`,
`search_ms_max`, `notes_total`, `proposals_pending`, а также счётчики инъекций
(`injections`, `injected_notes`, `injected_tokens`, `injected_global_*`) и переполнения
бюджета (`budget_overflows`, `budget_dropped_*`).

**Автоматический перезапуск.** `config.server.autoRestart` (`enabled`, `at: 'HH:MM'`
или `everyHours`, `minUptimeMinutes`, `onlyWhenIdle`, `tickSec`) — сервер сам
перезапускается по расписанию тем же путём, что и кнопка (`POST /api/server/restart` →
отделённый воркер поднимает сервер и проверяет, что он жив). Решения принимает
`src/auto-restart.mjs`: свежий процесс не перезапускается раньше `minUptimeMinutes`
(защита от цикла), наступивший момент считается «съеденным» последним перезапуском,
при `onlyWhenIdle` живая работа дожидается, а не обрывается. План и причина последнего
тика видны в `GET /api/info` → `autoRestart` (`enabled`, `at`, `nextAt`, `lastRestartAt`,
`state.reason`: `idle` | `not-due` | `too-young` | `busy` | `due`).

**Где физически лежит память.** `config.memory.projectMemoryRoot` (если `null` или
не задан — `~/.pi/memory-md`, переопределяется `TASKBRIDGE_PROJECT_MEMORY_ROOT`),
далее `<root>/<projectName>/core/**/*.md`. Инжектится Pi только содержимое `core`:
`<root>/<projectName>/notes/…` на диске есть, до модели не доходит — поэтому
инспектор честно говорит `status: unavailable`, если нет каталога `core`, а не
показывает пустой список как «памяти нет».

**Как выбираются выдержки.** `GET /api/projects/:id/memory?q=…` — только чтение
(записи в память нет ни у одного маршрута). Выбор для Resume:

- запросы строятся из самой работы (`goal`, критерии готовности, `remaining`,
  изменённые файлы), а не одним «дай всю память»;
- каждое поле записи: `id`, `text`, `category` (`architecture` | `decision` |
  `constraint` | `pattern` | `known-issue` | `other`), `source` (путь относительно
  папки проекта в памяти), `score`, `updatedAt`, `provenance.file`,
  `estimatedTokens`, `reason` («matched: …» — почему запись здесь);
- совпадение считается по **словам** (имя файла, `description`, `tags`, текст), а
  не по подстроке: «not» не должно находить «monotonic». Слово засчитывается и
  при совпадении по началу — так «курсор» находит «курсора»;
- порядок детерминированный: `score` → категория (не `other` раньше) → `updatedAt`
  → `source`. Одинаковый запрос при неизменной памяти даёт одинаковый список;
- дубликаты (одинаковый нормализованный текст) схлопываются;
- бюджет: не более 8 записей и `memory.indexBudgetTokens` токенов (дефолт 2000,
  оценка `длина / 4`); запись, которая в бюджет не влезает, **не** добавляется —
  одна огромная запись не проходит как «бюджет соблюдён», потому что считается до
  добавления. Не влезшее остаётся доступным поиском, а причина называется в
  `overflow` и `warnings` (счётчик — в `/api/metrics` → `memory`);
- ранжирование (этап M1): `pinned: true` в frontmatter → вес категории
  (`decision` > `constraint` > `architecture` > `pattern`/`known-issue` > `other`)
  → релевантность BM25 → давность использования (`useCount`/`lastUsedAt` из
  индекса, обновляются при попадании записи в инъекцию или выдачу);
- **`_global/`** — общие знания оператора (`<memoryRoot>/_global/**`), инжектятся
  во все проекты со своим мини-бюджетом `memory.globalBudgetTokens` (дефолт 400);
  в ответе такие записи помечены `scope: 'global'` и не вытесняют знание проекта.

Копия памяти в `resumeContext` ограничена: `memory.hits` (до 20),
`memory.estimatedTokens`, `memory.globalTokens`, `memory.warnings`,
`memory.overflow`, `memory.overview`.

**Индекс (этап M1).** Поиск идёт через FTS5-индекс `data/memory-index.db` (кэш, не
источник правды: файлы `.md` остаются единственным источником, удаление индекса
ничего не теряет). Инвалидация — по `mtime + size` при чтении каталога; индекс
выбирает кандидатов по BM25, и с диска читаются только они. Индекс открывается
лениво и закрывается вместе с сервером; при недоступном индексе память работает
прежним обходом файлов. Ключ проекта — `слаг-sha256[:8]` от канонического корня
(`src/memory/project-key.mjs`), `scratch` — для черновиков; совпадение имён
каталогов двух репозиториев сообщается как коллизия, а не разрешается угадыванием.

**Предложения памяти (MEM-08, 2026-10-12).** Один путь записи — и он не агентский:

```
сессия/агент → POST /memory/proposals → буфер <memory>/.memory-proposals/
                                        ↓ (детерминированные проверки)
                                     POST …/accept — человек
                                        ↓
                                     core/project/*.md  →  читает pi-memory-md
```

- `GET /api/projects/:id/memory/proposals` — очередь и счётчики
  (`pending`/`accepted`/`rejected`); они же видны в инспекторе в поле `proposals`.
- `POST /api/projects/:id/memory/proposals` `{text, category?, reason?, paths?,
  sourceSessionId?, sourceWorkItemId?}` — 201 с `{ proposal, problems }`: `problems`
  показывают сразу, что помешает принятию, но предложение уже лежит в буфере.
- `POST /api/projects/:id/memory/proposals/:proposalId/accept` — **единственный**
  способ что-то записать в память. Проверки, каждая из которых — факт, а не оценка:
  `EMPTY_TEXT`, `TOO_LONG` (>4000), `UNKNOWN_CATEGORY`, `MISSING_PATHS` (ни одного
  из объявленных путей нет), `DUPLICATE` (такой же текст уже есть среди живых
  записей), `SECRET_SHAPE` (текст похож на ключ/токен). Отказ — `400` с массивом
  `problems`, и **на диске не меняется ничего**; повторное принятие — `400`
  (`уже accepted`), неизвестное — `404`.
- `POST /api/projects/:id/memory/proposals/:proposalId/reject` `{reason?}` — файл
  остаётся как запись о том, что и почему отклонено.
- **Отказ при принятии не закрывает предложение.** Он записывается в тот же файл
  (`refusals`, `lastRefusalAt`), поэтому `GET …/proposals` отдаёт
  `counts: { pending, accepted, rejected, refused, reasons }`, где `reasons` — частоты
  кодов гейтов. Это телеметрия качества памяти: видно, какой гейт срабатывает чаще
  всего, то есть на каком месте агент чаще всего выдумывает.
- **Инспектор в терминале** (офлайн, ничего не пишет):
  `node scripts/memory-inspect.mjs --project <id|имя|путь> [--query <текст>]
  [--work-item <wi-…>] [--root <repo>]` — показывает записи, устаревшие с причиной,
  результаты поиска, очередь предложений с приговором гейтов и (для Work Item) какие
  выдержки попадут в Resume и почему (`matched: …`).
- Принятие кладёт заметку в `core/project/<категория>-<слаг>.md` с `tags: [suggested]`,
  `sourceSessionId`/`sourceWorkItemId` и объявленными `paths:`; существующий файл
  никогда не перезаписывается — коллизия имени разрешается суффиксом.
- `SAVE_DISABLED` у провайдера остаётся правдой: чтение памяти ничего не пишет, а
  предложение само по себе — файл **вне** `core`, который `pi-memory-md` не сканирует.
  Поэтому непринятое предложение физически не может попасть в контекст модели.

**Устаревание по путям (`paths:`).** Заметка может объявить файлы, о которых она:
`paths: src/chat/cursor.mjs`. Поддерживаются шаблоны: `*` (не перешагивает `/`),
`**` (любая глубина), `?` — например `paths: src/**/*.mjs`; сравнение регистронезависимое.
Точные имена проверяются по файловой системе, шаблоны — по списку файлов проекта
(`git ls-files --cached --others --exclude-standard`). Если **ни одного** из объявленных
путей не осталось — заметка считается `stale`: она не удаляется и не правится, но в
выдачу (`search`/`relevant`) не попадает, потому что описывает проект, которого больше
нет. `GET /api/projects/:id/memory` показывает `stale: { count, sources }` и
`liveEntries`; `includeStale` в провайдере позволяет достать их осознанно (для разбора).
Заметка без `paths:` устаревшей не считается никогда; шаблон без списка файлов (вне git)
тоже не считается мёртвым — спрятать живое знание хуже, чем показать старое.

**Если память недоступна.** Это не ошибка запуска: `status: unavailable`,
`hits: []`, предупреждение в `memory.warnings` — и Resume работает дальше. Память
полезна, но не является точкой отказа.

**Одинаковая папка у двух репозиториев — память НЕ читается.** `status: ambiguous`,
`hits: []`, предупреждение с обоими корнями. Выборка не фильтруется, а именно не
делается: неизвестно, чьи это записи, а смешать знания двух проектов хуже, чем
начать без долговременной памяти. То же правило в инспекторе — он показывает
причину и пустой список, а не «знания проекта». Этот случай в fingerprint попадает
как `memoryStatus: "ambiguous"`, поэтому предпросмотр с ним нельзя подтвердить
молча.

**`SAVE_DISABLED`.** Запись долговременной памяти не реализована и не появится до
MEM-08: провайдер её не делает, инспектор это сообщает явным полем, а не молчанием.
Никакой автоматической выгрузки recap в память проекта нет — recap это
эпизодическая память сессии (см. ниже), кандидат в долговременную память
предлагается человеку отдельно.

**Fingerprint памяти.** Кроме `HEAD`, рабочей папки, стратегии, сессий и артефактов
запуск сверяет: `memory` (режим `native`/`off`), `memoryStatus` (появилась,
пропала, сломалась) и `memoryHits` (идентификаторы выбранных записей). Изменение
нерелевантной записи запуск **не** блокирует: в fingerprint попадает только то,
что реально уйдёт в новую сессию. Изменилась сама выбранная запись или её
набор — это `409 CONTEXT_CHANGED` с `field: memory.hits`.

#### Session Recap (MR-04, «Этап 2»)

`GET/PUT/DELETE /api/tasks/:id/recap` — `recap.json` + `recap.md` в артефактах
сессии. В SQLite про recap не хранится ничего, кроме факта наличия артефактов: это
документ, а не ещё одна база.

- `source: saved` — recap написал агент или оператор (семантические поля:
  `accomplished`, `decisions`, `remaining`, `blockers` придумать нельзя);
- `source: derived` — что TaskBridge знает точно: цель сессии, изменённые файлы из
  Git, результаты проверок. Пустые поля остаются пустыми.

**Проверки в recap: слова сессии ≠ результат (2026-10-12).** Каждая запись
`verification` — это `{ text, status }`, и статус говорит, кто это утверждает:

| status | кто говорит |
|---|---|
| `passed` | TaskBridge сам запустил эту команду, она прошла |
| `failed` | TaskBridge сам запустил, она упала |
| `contradicted` | сессия утверждает успех, а TaskBridge видел провал этой команды |
| `reported` | так говорит сессия; TaskBridge этого не наблюдал |

Сопоставление — по имени команды: `PASS: npm test`, `npm test` и
`тесты прошли: npm test` — одно и то же утверждение о `npm test`. Всё, что не
сопоставилось с наблюдением, остаётся `reported` — в брифе это
`[со слов сессии]`, в `recap.md` — `[reported]`. Старые `recap.json` со строками
читаются как `reported` (обратная совместимость).

`GET /api/tasks/:id/recap` дополнительно отдаёт `observed` — то, что TaskBridge
проверил сам, без участия слов: `{ head, changedFiles, verification: [{ command, ok }] }`.
Это факты, а не мнение сессии: recap никогда не считается истиной проекта, приоритет —
состояние репозитория и наблюдённые проверки.

Resume предпочитает `saved` и явно предупреждает про сессии без recap: иначе новый
агент не узнает, что в них решено.

### Work Items (MR-02, 2026-10-11)

#### Связь задачи с сессиями (MR-03, 2026-10-11)

Одну задачу разработки делают **несколько независимых сессий**, и это **не** таблица
`runs`: `runs` принадлежат одной сессии (в сессии много прогонов), а work item
группирует сессии. Смешивать эти иерархии нельзя — на различии держится MR-04
(«продолжить работу чистой сессией»).

- `GET /api/work-items/:id` отдаёт саму задачу **вместе** с `sessions` — одного
  вызова хватает экрану, и показать задачу без её сессий всё равно нельзя;
  `GET /api/work-items/:id/sessions` — тот же список отдельно.
- `POST /api/work-items/:id/sessions` `{sessionId, relation?}` — связать сессию.
  Обе стороны обязаны существовать (`404 SESSION_NOT_FOUND` / `404 NOT_FOUND`),
  `relation` — одна из `implementation` (по умолчанию), `investigation`, `review`,
  `verification`, `resume`; неизвестная — `400 INPUT_INVALID`. Повторная связка тех
  же двух **обновляет** relation, а не создаёт вторую строку.
- `DELETE /api/work-items/:id/sessions/:sessionId` — снять связь; сессия при этом
  не трогается, а отсутствие связи — не ошибка (`{removed: false}`).
- `GET /api/tasks/:id/work-items` — обратный взгляд: к каким задачам относится
  сессия (их может быть несколько).

Связи не остаются висячими: удаление сессии убирает её связи (иначе задача
ссылалась бы на то, что нельзя открыть), удаление задачи — все её связи. Факты о
сессии в задачу не копируются: список отдаёт `status`, `title`, `updatedAt`,
`events` и `available` (сессия могла исчезнуть с другого устройства — это видно, а
не молча пропадает).

Задача разработки — **семантическое состояние работы**, а не контейнер: заголовок,
цель, критерии готовности, статус, приоритет, теги. Сюда **не** складываются
prompt, история чата, diff, вывод инструментов, дампы памяти и `resumeContext` —
иначе задача превращается в мусорку, а память проекта теряет смысл. Сессии,
которые эту работу делали, связываются отдельно (MR-03); сам TaskBridge
work item переживает удаление проекта из реестра, как и сессия.

- `GET /api/work-items?projectId=&status=&includeClosed=0` — список, новые сверху.
- `POST /api/work-items` — `{projectId, title, goal?, status?, priority?, acceptanceCriteria?, tags?}`.
  `title` обязателен, проект должен быть **зарегистрирован** (`404 PROJECT_NOT_FOUND`) —
  задача, которую неоткуда открыть, хуже отказа. Статус по умолчанию `BACKLOG`.
- `GET /api/work-items/:id`, `DELETE /api/work-items/:id` — чтение и удаление;
  удаление задачи **не** трогает её сессии.
- `PATCH /api/work-items/:id` — частичное обновление: отсутствующее поле сохраняет
  значение, `null` очищает nullable-поле. Переход в `DONE` проставляет
  `completedAt` один раз, выход из `DONE` его снимает.

Статусы: `BACKLOG`, `READY`, `IN_PROGRESS`, `BLOCKED`, `DONE`, `CANCELLED`;
приоритет — целое 0..9 (или `null`). Неизвестное значение — `400 INPUT_INVALID`, а
не молчаливая замена на значение по умолчанию.

Дашборд (`GET /api/projects/overview`) показывает по проекту `workItems` и
`activeWork` — то самое «Active work» из роадмапа: открытые задачи, то есть все,
кроме `DONE` и `CANCELLED`.

Три маршрута дают проектно-ориентированную навигацию поверх того, что уже
существует: реестра проектов и сессий. Второго источника истины нет — в SQLite
лежит **только** то, что оператор изменил в отображении.

- `GET /api/projects/overview` — по строке на каждый зарегистрированный проект:
  `sessions`, `working` (статус не терминальный), `needsAttention` (сессии,
  которые без оператора не сдвинутся: `FAILED` или `WAITING_USER`),
  `lastActivityAt`, `pinned`, `archived`; плюс `unassignedSessions` — сессии проектов, удалённых из реестра
  (их история не удаляется, поэтому они считаются, а не исчезают).
  Сортировка: закреплённые, затем по последней активности, затем по имени.
- `GET /api/projects/:id/sessions?q=&status=&sort=&limit=&offset=` — сессии одного
  проекта, отфильтрованные на сервере: `sort` ∈ `recent` (по умолчанию),
  `created`, `title`, `size`; `limit` 1..500 (по умолчанию 50). Ответ —
  `{ projectId, registered, items, total, offset, limit, endReached }`.
  **Неизвестный реестру id — не 404**: `registered: false` и его сессии, иначе
  история удалённого проекта стала бы недостижимой.
- `PATCH /api/projects/:id/preferences` `{ pinned?, archived? }` — закрепить или
  отправить в архив. Отсутствующее поле сохраняет своё значение (PATCH одного
  флага не сбрасывает второй), не-булево — `400 INPUT_INVALID`, неизвестный
  проект — `404 NOT_FOUND`. Значения читаются с диска при каждом запросе, поэтому
  переживают перезапуск сервера.

Архивация — только про список: она **не** удаляет ни каталог, ни сессии, ни
worktree и **не** мешает создавать в проекте новые сессии и работать с уже
открытыми. Старые клиенты и веб ничего не замечают: `/api/projects` и `/api/tasks`
остались прежними и не знают о архиве.

### Размер контекста и состояние файлов локальной модели

`GET /api/local` — то же состояние, что видит панель: `models[]` содержит `external`,
`contextWindow`, `contextEditable`, `filesPresent` и `missingFile`. `?fresh=1` отвечает
без пятисекундного кэша — это кнопка «Обновить»: только так видно то, что изменилось
на диске (удалённые веса), не дожидаясь следующего опроса.

`filesPresent: false` — файлов, из которых сервер поднимает модель (`exe` и пути из
`args` его конфига: `--pack`, `--native`, `--ple-gguf`, `--expert-profile`, `--mtp`,
`--mmproj`, `--model`), больше нет на диске; `missingFile` — первый отсутствующий.
`null` — конфиг не про файлы, о них ничего не утверждается.

У пресетов роутера llama.cpp файлы берутся из их секции `models.ini` (те же ключи
без дефисов: `model`, `mmproj`, `pack`, `native`, `ple-gguf`, `expert-profile`, `mtp`),
и такая строка дополнительно несёт `vision` (`mmproj` есть и не выключен `no-mmproj`),
`visionEditable` (секция есть — её можно править отсюда) и `removable` (секция есть —
строку можно убрать). Строка, которой в `models.ini` нет (роутер поднят с `--models-dir`),
остаётся без этих полей: конфига TaskBridge у неё нет.

`removable` — запись есть в конфиге, которым владеет TaskBridge: `localRuntime.externalServers`
в `config.json` — или секция пресета в `models.ini` роутера. Убрать её можно через
`POST /api/local/forget` с телом `{ "model": "qwen3.8-flash-next-iq2-xs" }`. Удаляется **только запись**
(её же список и возвращается в ответе), а `config.json` переписывается сразу — иначе строка вернулась бы
после перезапуска. Файлы модели, конфиг движка и запущенный процесс не трогаются; запущенный пресет
роутера сервер убирать отказывается (`400 MODEL_BUSY` — сначала «Остановить»). Строка, найденная
автоматически в Pi (`~/.pi/agent/models.json`), помечена `removable: false`: `400 INPUT_INVALID`, потому что
владелец этой записи — Pi.

`POST /api/local/vision` с телом `{ "model": "qwen-27b-q3", "vision": true }` включает и
выключает vision **пресета роутера** llama.cpp. Vision — это ключ `mmproj` его секции
`models.ini`. Выключение **комментирует** строку проектора (`; mmproj = <файл>`) и
дописывает `no-mmproj = true`: явный `mmproj` сильнее `no-mmproj` (= `--no-mmproj-auto`,
измерено на живом роутере), поэтому без комментария vision остался бы включённым, а так
путь проектора остаётся в файле и включение обратно не ищет его по диску. Включение
раскомментирует строку и убирает флаги автоподбора; если строки не было, путь берётся из
другой секции с теми же весами, иначе — из файла `*mmproj*.gguf` рядом с весами. Ничего
не нашлось → `400 LOCAL_VISION_UNSUPPORTED`, файл не трогается. Ответ: `{ provider, model,
file, vision, previous, mmproj, changed, restartRequired }` (`mmproj` — путь активного
проектора, у выключенного `null`). Запущенный роутер читает `models.ini` при старте:
`restartRequired: true` означает, что правка подхватится следующей загрузкой пресета.
У внешних серверов (Strata) и строк из Pi тот же `400 LOCAL_VISION_UNSUPPORTED`:
их vision задаётся их собственным конфигом.

`POST /api/local/context` с телом `{ "model": "qwen3.8-flash-next-iq3-s", "context": 131072 }`
меняет размер контекста **внешнего** локального сервера (Strata).

Контекст — параметр загрузки, а не сессии: у каждого движка он лежит в своём файле,
и у Strata это `--max-context` в `strata-<модель>.json`, который `serve/server.py`
передаёт движку при старте (своего флага CLI или HTTP-ручки у него нет: `/health`
отдаёт уже прочитанное `max_context`). TaskBridge меняет **только это число**: файл
правится текстом (CRLF, отступы и порядок `args` остаются как были) и записывается
атомарно; если `--max-context` в файле нет, ответ `400 LOCAL_CONTEXT_UNSUPPORTED`,
и файл не трогается.

Ответ: `{ provider, model, file, context, previous, changed, kvResident, restartRequired }`.
`restartRequired: true` означает, что сервер сейчас отвечает и продолжает работать
со старым контекстом — новое значение подхватит следующая загрузка. Пресеты роутера
llama.cpp получают тот же `400 LOCAL_CONTEXT_UNSUPPORTED`: их `ctx-size` живёт в
`models.ini`, и TaskBridge его не правит (в списке моделей у таких строк просто нет
признака `contextEditable`).

### Откуда берётся контекст и лимит контекста сессии

`GET /api/tasks/:id/context` отвечает на вопрос «из чего собран запрос к модели»:

```json
{
  "taskId": "…",
  "model": { "provider": "wormsoft", "id": "gpt-6-luna", "contextWindow": 1000000 },
  "contextWindow": 1000000,
  "usage": { "tokens": 60000, "contextWindow": 1000000, "percent": 6, "source": "pi" },
  "totalTokens": 60000,
  "sources": [
    { "id": "system-prompt", "label": "Системный промпт (SYSTEM.md)", "detail": "…", "chars": 2230, "tokens": 558, "known": true },
    { "id": "instructions", "label": "Инструкции проекта (AGENTS.md)", "detail": "…", "chars": 21770, "tokens": 5443, "known": true, "count": 2 },
    { "id": "skills", "label": "Навыки (описания)", "chars": 440, "tokens": 110, "known": true, "count": 11 },
    { "id": "mcp-tools", "label": "MCP-инструменты", "chars": 21000, "tokens": 5250, "known": true, "count": 120, "servers": ["web-search", "mcpServer"] },
    { "id": "builtin-tools", "label": "Встроенные инструменты Pi", "tokens": null, "known": false },

  "note": "Размеры источников — оценка (символы / 4, как считает Pi)…"

```

Источники читаются с диска: `SYSTEM.md`/`APPEND_SYSTEM.md` (агентский каталог, проектный
`<проект>/.pi/` важнее), цепочка `AGENTS.md`/`AGENTS.override.md`/`CLAUDE.md` от рабочей
папки вверх, описания навыков из `skills/*/SKILL.md`, объявления MCP-инструментов из кэша
адаптера. Их размер — **оценка** `chars/4` (та же эвристика, что у Pi), поэтому она
подписана как оценка. `totalTokens`, `conversation` и остаток `unaccountedTokens`
(`totalTokens − measuredTokens`, не меньше нуля) взяты из `get_session_stats` самого Pi:
так честнее, чем показывать нулём то, чего снаружи не видно (базовые инструкции Pi,
объявления встроенных инструментов, текст, который дописывают расширения). `known: false`
означает «источник есть, размер не измеряется», а не «источник пуст». Если сессия не
запущена, `totalTokens` = `null`: числа выдумывать нечем.

`POST /api/tasks/:id/context` с телом `{ "limit": 40000 }` ставит лимит контекста
сессии, `{ "limit": null }` — снимает. Лимит — настройка TaskBridge, а не Pi: Pi знает
только окно своей модели и своё сжатие по нему. Когда ход закончен и Pi оценивает
контекст выше лимита, TaskBridge сам сжимает историю (то же сжатие, что делает Pi при
подходе к окну) — до публикации `TASK_SUCCEEDED`, чтобы следующее сообщение из очереди
не ушло в модель с переполненным контекстом. Событие `CONTEXT_LIMIT_REACHED` несёт
`{ used, limit }`; неудача сжатия — `CONTEXT_LIMIT_FAILED` и на исход хода не влияет.
Ответ обоих маршрутов — тот же отчёт, поле `limit.tokens` хранится в задаче
(`contextLimit`).

### Чтение файла рабочей папки

`GET /api/tasks/:id/workspace-file?path=` отдаёт файл сессии (`?download=1` — как
вложение). Путь внутри рабочей папки задачи читается как есть. Файл **вне** неё
открывается только тогда, когда его назвала сама сессия:

- путь, переданный аргументом инструмента (`path`, `file_path`, `filePath`);
  относительный считается от рабочей папки задачи, а не от каталога сервера;
- путь, названный в записи сессии — в ответе агента, в команде, в выводе инструмента.
  Именно эти пути оператор видит в чате и по ним жмёт: до 2026-10-12 считались только
  аргументы инструмента, и половина путей из ответов отвечала «путь выходит за
  пределы рабочей папки» (в веб-чате абсолютный локальный путь выглядел ещё и как
  внешний URL: «G:…» похоже на схему);
- файл должен существовать и быть файлом (иначе `404 NOT_FOUND`), а приватные пути
  (`.git`, `.pi`, `.ssh`, `node_modules`, `data`, `.env*`, `config.json`, `secret*`,
  `*.pem` …) не выдаются никогда — `403 FILE_FORBIDDEN`, даже если сессия их называла.

### Размер сессии на диске

`GET /api/tasks/:id/storage` отвечает `{ id, bytes, files, partial, computedAt,
thresholdBytes, warn }` — сколько места занимает каталог сессии
(`data/tasks/<id>`: журнал `pi-events.jsonl`, `diff.patch`, вложения `files/`),
плюс нативная сессия pi и рабочая копия. Это **только измерение**: сервер ничего
не удаляет, не обрезает и не ограничивает. `warn: true` — размер перешёл порог
`storage.warnSessionMb` (по умолчанию 1 ГБ). Предупреждение нужно потому, что
сырой журнал кадров (вывод bash, содержимое файлов) и вложения растут незаметно:
на 2026-10-20 одна из сессий занимала 3,7 ГБ. Замер кэшируется на 5 минут на
сессию, обход дерева ограничен 20 000 записей (`partial: true` — предел
достигнут, цифра неполная).

### Открытие файла на компьютере

`POST /api/tasks/:id/files/:fileId/open`, `POST /api/tasks/:id/artifacts/:name/open`
и `POST /api/tasks/:id/workspace-file/open` (тело `{ "confirm": true, "reveal": false }`)
открывают файл приложением, зарегистрированным в ОС для его расширения, а при
`reveal: true` — показывают его в файловом менеджере. Это действие на самой машине:
маршруты отвечают только клиенту, чей **адрес — сама машина** (loopback или один из
её собственных адресов интерфейсов). Телефон в той же сети и облако не подходят
(`403 FILE_OPEN_LOCAL_ONLY`). За LAN-прокси адрес клиента приходит в последней
записи `X-Forwarded-For` (её дописывает прокси, подделать её клиент не может), так
что ПК, открывший UI по своему LAN-адресу, распознаётся как машина, а телефон —
нет. Флаг `confirm` обязателен
(без него `400 INPUT_INVALID`) — он же не даёт пробнику контракта запускать окна на
сборочной машине. Действие доступно только у сессии с рабочей папкой (или у
вложения/артефакта этой сессии).

`POST /api/tasks/:id/workspace/open` (то же тело, без `reveal` — цель и есть папка)
открывает **папку сессии** файловым менеджером: ту самую, в которой работает агент
(`workspacePath`). Гейты те же (`403 FILE_OPEN_LOCAL_ONLY` у телефона и облака,
`400 INPUT_INVALID` без `confirm`). У свежей сессии рабочей папки ещё нет — `404
NOT_FOUND` («Рабочая папка не найдена»), а не открытие каталога задачи. Ответ:
`{ opened: true, name, path }`.

`POST /api/tasks/:id/files/:fileId/run`, `POST /api/tasks/:id/artifacts/:name/run` и
`POST /api/tasks/:id/workspace-file/run` (то же тело) запускают файл-скрипт на
машине и возвращают `{ command, exitCode, stdout, stderr, timedOut }`. Интерпретатор
выбирается по расширению (`.bat/.cmd`, `.ps1`, `.sh/.bash`, `.py`, `.js/.mjs/.cjs`,
`.rb`, `.pl`); для незнакомого расширения — `400 SCRIPT_NOT_RUNNABLE` (не угадываем).
Ненулевой код выхода и таймаут — это результат скрипта, а не ошибка сервера. В отличие
от `/open`, запуск разрешён не только на самой машине, но и **авторизованному клиенту**
(спаренному телефону): работать выполняет ПК, а телефон получает вывод. Требуется
`confirm: true`; при выключенной авторизации (`server.auth.enabled = false`) это
означает любого клиента, дотянувшегося до API.

`POST /api/tasks/:id/shell` (тело `{ "confirm": true, "command": "…" }`) выполняет
строку команды оболочкой машины (`cmd.exe /c` или `sh -c`) в рабочей папке сессии и
возвращает `{ exitCode, stdout, stderr, timedOut }`. Это тот же случай: строку
команды запускает кнопка «Выполнить» на блоке кода в ответе, с подтверждением в UI.
Запуск разрешён на машине и авторизованному клиенту (телефону), но требует
`confirm: true`; пустая или слишком длинная (>65536 символов) команда —
`400 INPUT_INVALID`.

Вывод нормализуется в UTF-8 (на Windows команда запускается в кодовой странице 65001,
иначе cmd/PowerShell пишут в OEM-кодировке и кириллица превращается в мусор). Полный
вывод всегда сохраняется артефактом сессии `cmd-output-<время>.log` (виден в разделе
Artifacts); в ответ уходит только ограниченный хвост (около 16 КиБ, `truncated: true`),
а `outputName`/`outputBytes` называют файл. Файл можно скачать или прикрепить к
сообщению (кнопка «В чат» в UI) — так большой вывод не забивает чат и не упирается в
лимит поля ввода, но его можно передать агенту целиком.

### Связь глазами клиента: свой push и эпизоды DEGRADED (4.3, фаза 4)

`POST /api/clients/wake` (тело `{ "port": 41234 }`) — регистрация своего push-приёмника
в локальной сети: клиент (телефон) держит `ServerSocket` на этом устройстве, а сервер
стучится в него при завершении хода (`TASK_SUCCEEDED`/`TASK_FAILED`/`TASK_CANCELLED`),
чтобы клиент сделал обычный refresh, не дожидаясь опроса. Адрес берётся из сокета
(`req.socket.remoteAddress`), а не из тела: **публичные адреса отклоняются** (только
private IPv4, loopback, IPv6 ULA), порт — 1..65535. Доставка — at‑most‑once без
повторов; после 5 неудачных попыток устройство забывается. Пропущенный wake — не
ошибка: опрос остаётся запасным каналом.

`POST /api/clients/link` (тело `{ "state": "live"|"degraded"|"reconnecting", "reason"?, "attempt"?, "clientId"? }`)
сообщает **переход** связи у клиента. Зачем: обрыв потока при живом сервере раньше
замечает клиент (его двухуровневый health), а не сервер, и без этих сообщений
«часто отваливается» остаётся воспоминанием. Считаются **эпизоды**, а не попытки:
переход из `live` в нерабочее состояние даёт +1 к `degradedEpisodes`, обратный
переход — к `recoveredEpisodes`; повторы ретраев не считаются (иначе метрика мерила
бы шум). Присылать можно только состояние и причину — никакого содержимого промптов
и истории; за этим следит и тест. Числа видны в `GET /api/metrics` →
`server.degradedEpisodes`, `server.recoveredEpisodes`, `server.lastDegradedAt`,
`server.degradedClients` (кто именно сейчас не в `live`, с `since`, `reason`,
`attempt`).

## Чего пока нет

- **OpenAPI/Swagger-схемы.** Пока контракт — это список маршрутов + эта страница +
  проверяющий тест. Схему (и генерацию Kotlin-клиента) можно добавить поверх
  `src/api-contract.mjs`, когда появится второй клиент.
- **Push для нативного клиента.** Есть web-push (VAPID) — он работает только в
  браузере; приложению нужен FCM или foreground-сервис.
- **Версионирования ответов.** `apiVersion` описывает весь API целиком; частичных
  версий по маршрутам нет.


## Удаление ответа и диагностика доставки (2026-09-26)

`POST /api/tasks/:id/turns/:turnId/delete` дополнительно принимает
`assistant-initial` и `assistant-<seq USER_MESSAGE>`. Удаляется ответ и последующая
история; вопрос сохраняется. Для этого `TURN_TRUNCATED` содержит `keepUser: true`,
`reason: "delete"`, `fromSeq: userSeq + 1` (для initial — 1).
Клиент при таком маркере удаляет ответ без создания активного placeholder.
Прежняя семантика `user-*` сохранена. Идентификаторы вариантов пока не принимаются.

## Ветка сессии в обе стороны (2026-10-09)

`POST /api/tasks/:id/fork` с `{ turnId }` копирует разговор **до** выбранного
сообщения включительно: `user-N` — по само сообщение, `assistant-N` — по ответ на
него (оба id называют один и тот же обмен). У собственного первого промпта сессии
события нет, поэтому `user-initial` даёт пустую копию (промпт и так в задаче), а
`assistant-initial` — первый обмен.

С `direction: "from"` копия начинается **с** выбранного сообщения: его текст
становится собственным промптом новой сессии, а всё, что шло ниже, переносится с
исходными курсорами `seq` — на них ссылаются сами события
(`TURN_VARIANT_START.turnSeq`, `TURN_TRUNCATED.fromSeq`), поэтому копия не
перенумеровывается. `USER_MESSAGE` выбранного сообщения при этом не копируется:
клиент строит этот ход из записи задачи ровно так же, как первый ход сессии,
созданной с этим промптом (иначе строка показалась бы дважды), а ссылки на старый
seq этого сообщения переписываются на первый обмен копии
(`turnSeq`/`variantId` → `0`/`"initial"`, `id` → `assistant-initial`).

Ответ — задача ветки, как и раньше; `TASK_FORKED` содержит `fromSeq` (выбранный ход,
`0` — собственный первый промпт сессии) и `throughSeq` (последний скопированный
seq, `null` — до конца журнала). Исходная сессия не меняется.

`USER_MESSAGE` означает подтверждённую передачу RPC-команды агенту, а не
подтверждение обращения к провайдеру. Для `mode: steer` инструкция ещё может ждать
окончания текущего шага. `message_start` / `message_update` показывают начало
следующего ответа / поступление данных. Heartbeat подтверждает только связь с
TaskBridge. KMP показывает эти различия и копируемые сведения: время контакта,
последнее событие, seq, статус runtime, модель и код ошибки.

`PI_RPC_HUNG` / `PI_RPC_EXITED` при отправке или смене модели освобождают runtime и
слот сессии; следующий запрос восстанавливает процесс обычным путём. `PI_RPC_SLOW`
не уничтожает процесс, который продолжает выдавать события.
`RUNTIME_STATE`, вызванный завершением хода, публикуется перед `TASK_SUCCEEDED` /
`TASK_FAILED` / `TASK_CANCELLED`: терминальное событие завершает этот ход.

### Провайдер держит ход: `PROVIDER_WAIT` и `task.providerWait`

Отказ провайдера — не ошибка сессии и не событие чата: Pi жив, объявляет повтор и
ждёт. Ждать приходится долго (2026-10-09: HTTP 429 «user reached the limit» с
`retry-after-ms 5452000`, то есть 1 ч 31 мин), а объявление приходит каждые 15 с.
Поэтому событие публикуется **один раз на эпизод ожидания** — на каждый отказ, а не на
каждый тик: иначе 1,5 часа тишины выглядят как обычная работа модели, а чат получает
360 одинаковых строк. Эпизод называет сам машинный кадр расширения (`periodId`): внутри
эпизода Pi успевает сменить и причину (`retry` ↔ `network`), и объявленный срок (5 с →
15 с), поэтому ни причина, ни дедлайн раундом быть не могут (2026-10-12: три источника
одного отказа давали три заметки в чате). Прозу без `periodId` (уведомление самого Pi)
привязывают к текущему эпизоду по виду отказа и модели; новый `periodId` — новый эпизод.

- `PROVIDER_WAIT` — эпизод ожидания начался (новый отказ, а не тик); `data` = поля
  `task.providerWait` ниже плюс `waiting: true`;
- `PROVIDER_WAIT_END` — провайдер ответил (`data.reason` — первый кадр модели),
  Pi завершил ход или ушёл;
- `task.providerWait` заполнено, пока Pi ждёт: `kind` (`rate-limit` | `retry`),
  `provider`, `model`, `httpStatus`, `reason` (словами провайдера), `waitMs` и
  `retryAt` (абсолютный момент повтора — счётчик считает клиент, а не сервер),
  `periodId` (эпизод ожидания из машинного кадра; `null` — источник был прозой),
  `since`/`at`. Поле не переживает процесс: без живого Pi оно не отдаётся;
- `runtime.activity = waiting_model` вместо `streaming`, пока ждём: байтов нет;
- конец ожидания без повтора — отдельный случай: расширение говорит «<модель> failed and
  pi-limits-wait is not retrying: <причина>» и присылает кадр `event: "give_up"`.
  Ожидание после него снимается (обещать повтор, которого не будет, нельзя), а в чат
  уходит одна строка «Провайдер <модель> не принял запрос и повторять не будет: <причина>.»
  (`UI_NOTIFY`, `data.giveUp`) вместо сырой английской строки расширения;
- кадр объявления остаётся в `pi-events.jsonl`, но в чат строкой `UI_NOTIFY` не
  попадает — оттуда он читается как ошибка агента, которой нет.
