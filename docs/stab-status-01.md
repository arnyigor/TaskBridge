# STAB-STATUS-01: корректная индикация стадии обработки запроса моделью

**Приоритет:** P1 (важная UX/observability-регрессия, не критический дефект данных).  
**Порядок:** после TB-STAB-02 (STOP/reconnect), в рамках финальной клиентской стабилизации Web/Desktop/Android, до TB-PROV-02/03 при нехватке ресурсов. Не смешивать с MEDIA-10 и PERF-03.  
**Статус:** backlog / NOT_STARTED. Новая функциональность ради этой задачи не добавляется.

Документ фиксирует дефект индикации и технический план. Код, зависимости, конфигурация
сервера и активные сессии этим документом не изменены; гипотезы по исходникам ниже
не подтверждены прогоном на установленной сборке.

## Воспроизведение

22.10.2026: Strata показывает `Reading prompt`, 73 728 / 185 025 токенов (40%), загрузка GPU 99%, prefill ~2 336 tok/s. В это время KMP TaskBridge отображает «Сообщение передано · ожидается ответ агента» / «Агент принял сообщение · ожидается начало работы». В строке статистики показаны TTFT 1,7 с, PP 133, TG 59 — источник этих чисел и их отношение к текущему ходу необходимо обозначить. Пользовательские скриншоты: 20261022-115102 и 20261022-115109.

Это не просто неправильная подпись: пользователь не может отличить работу модели от
ожидания провайдера или зависшего запроса.

## Что проверить до изменений

1. Снять для одного **текущего** хода идентификатор сессии, provider/model/endpoint, `turn`, `attemptId` (если есть), время последнего события Pi, состояние ответного сообщения, фактический ответ `/api/info` (с redaction) и состояние Strata за те же секунды. Две активные сессии нельзя автоматически отождествлять с глобальной телеметрией одного GPU/движка.
2. В `clients/kmp/shared/src/commonMain/kotlin/ru/arny/taskbridge/ui/chat/ChatScreen.kt`: `externalRow` выбирается по provider ИЛИ id (стр. 1264), `readingPrompt` — `metrics.phase.contains("read")` (стр. 1286), `readsPromptNow = answerSilent && (readingPrompt || livePp != null)` (стр. 1956), а `answerSilent` берётся у `lastOrNull()` assistant из всей истории (стр. 1249). Проверить, не принадлежит ли `answer` предыдущему ходу, не пропала ли фаза в сериализации, не выбрана ли чужая модель.

   Статическое чтение этой копии (не прогон на установленной сборке) объясняет
   наблюдаемое: если на новом ходе `livePp` приходит из `/api/info`, а последний
   assistant предыдущего хода уже содержит текст, `answerSilent = false`, и
   `readsPrompt` не включается на всём prefill. Дополнительно `livePp` /
   `externalMetrics.pp` — снимок текущего PP движка, не привязанный к ходу.
   Оба факта требуют подтверждения телеметрией шага 1.
3. Проверить частоту и freshness `SessionListState.info`, преобразование `LocalModelMetrics`, поле `phase`, `busy`, `promptRead`, `promptTotal` на сервере и KMP.
4. Если живых сигналов нет, сообщать «Запрос принят Pi · ожидаем данные от модели», а не утверждать, что модель не начала работу.

### Три кандидатные причины (сохранены до воспроизведения)

Ни одна не доказана; менять `ChatScreen.kt` до синхронного снятия данных шага 1 нельзя.

| # | Причина | Где | Приоритет доказательства |
|---|---|---|---|
| H1 | `answerSilent` анализирует последний ответ **всей** истории, а не текущего хода | `ChatScreen.kt:1249`, `:1332`, `:1956` | Наиболее конкретная гипотеза: прошлый ответ гасит «читает промпт» на всём prefill нового хода |
| H2 | `externalRow` сопоставляет телеметрию по провайдеру **или** модели | `ChatScreen.kt:1264` | При нескольких локальных моделях возможна атрибуция чужой строки (`phase`, `promptRead`, PP) |
| H3 | `readingPrompt` зависит от фазы движка, обновляемой опросом `/api/info` | `ChatScreen.kt:1286`, `:1295` | Фаза может приходить с задержкой или относиться к другому запросу |

## Целевая индикация

| Фактическое состояние      | Что показывает TaskBridge       |
| -------------------------- | ------------------------------- |
| Pi принял запрос           | «Запрос принят Pi»              |
| Strata выполняет prefill   | «Модель читает промпт · 40%»    |
| Модель начала reasoning    | «Модель генерирует размышления» |
| Модель выдаёт ответ        | «Модель генерирует ответ»       |
| Агент запустил инструмент  | «Агент выполняет команду»       |
| Нет достоверной телеметрии | «Ожидаем данные от модели»      |

Отдельно: TTFT, PP и TG предыдущего хода не должны выглядеть как скорость текущего запроса.

## План изменения

- **STAB-STATUS-01A (evidence):** добавить тестовый сценарий Strata prefill (0→40→100%), промпт без новых output tokens, при наличии старого завершённого assistant в истории. Проверить, что статус «Читает промпт» показывается по живым подтверждённым метрикам именно текущего хода. Сначала красный тест, затем минимальный фикс.
- **STAB-STATUS-01B (state priority):** задокументировать приоритет: ошибка/отмена → явный отказ или ожидание провайдера → compaction → running tool → подтверждённый prefill → генерация текста/reasoning → очередь → ACK без данных. `PROMPT_ACCEPTED` означает только принятие Pi, не завершение prefill и не начало вывода токенов.
- **STAB-STATUS-01C (correlation/freshness):** связь метрик с provider+model+endpoint и текущим запросом; если источник агрегированный и нельзя надёжно сопоставить сессии, показывать источник и неопределённость. Старые значения после нового хода, STOP, `FAILED`, `SUCCEEDED`, переключения модели/endpoint не могут служить доказательством текущей фазы. При отсутствии подтверждения — не выдумывать prefill.
- **STAB-STATUS-01D (numbers):** разделить `TTFT текущего хода` и `типичный TTFT (исторический)`; PP/TG прошлого хода помечать «последний ход», live PP — как текущий. Текущий `promptRead/promptTotal` показывать только когда сигнал свежий и привязан к активной модели.
- **STAB-STATUS-01E (UI):** обновлять фазу не чаще, чем приходят свежие данные движка; не вводить высокочастотный polling и новые бесконечные анимации. Сохранить обратную совместимость API и режим облачных провайдеров, где нет отдельной телеметрии prefill.

## Проверки и приёмка

| ID | Сценарий | Критерий |
|---|---|---|
| ST-01 | Strata реально читает большой промпт | «Читает промпт», достоверный прогресс или статус без процентов |
| ST-02 | Старый ответ есть, новый ход в prefill | Старый assistant не маскирует prefill |
| ST-03 | Нет live-телеметрии | Нейтральная подпись ACK/ожидания данных, без выдуманного состояния |
| ST-04 | Стримятся thinking/output tokens | «Генерирует», без ложного «Читает промпт» |
| ST-05 | Активна команда инструмента | «Выполняет инструмент», без ложного prefill |
| ST-06 | Две сессии на одном провайдере или модели | Данные одного запроса не приписываются другому |
| ST-07 | STOP, смена модели, повторный ход | Старые `phase`/PP/TG не используются как текущие |
| ST-08 | Долгий prefill (2–5 минут), медленные опросы | Статус не возвращается в «ожидаем начала работы» при живом сигнале |
| ST-09 | Нет output при 429/413 | Явная диагностическая ошибка/ожидание имеет приоритет |
| ST-10 | Desktop и Android-эмулятор | Одинаковая семантика; без регрессии FPS, polling и батареи |

**Границы:** не изменять agent loop, Pi/Strata, управление GPU, MEDIA recovery, scheduler, конфигурацию работающего сервера или активные сессии. Изменения компактные и отдельно коммитятся после адресных тестов; при изменении KMP прогнать JVM-тесты, Desktop smoke и Android-эмулятор (Pixel 5/API31 или доступный аналог). Результаты маркировать PASS/FAIL/NOT_TESTED.

## Условие возобновления

Работа возвращается к этой задаче только после завершения TB-STAB-02: STAB-02A — STOP после
постановки продолжения в очередь, но до его выполнения; STAB-02B — реальный SSE reconnect,
включая пропущенные события отмены и повторную доставку `commandId`. Первый шаг при
возобновлении — синхронное снятие данных Pi, `/api/info`, Strata и интерфейса TaskBridge в
рамках одного конкретного хода; только по нему правится `ChatScreen.kt`.
