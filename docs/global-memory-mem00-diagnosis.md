## 2. Предупреждение и причина

В проверенных Python-исходниках установленного MCP (`src/**/*.py` и корневые `*.py`) точная фраза `Глобальная память переполнена` отсутствует. Она также не найдена в проверенных исходниках TaskBridge `src`, `web`, установленных Pi extensions и JS-файлах установленного Pi dist. Происхождение именно этой формулировки **не установлено**; считать её дословным ответом MCP нельзя.

Подтверждённый близкий источник — `manage_project_memory`, ветка `action == 'save'`, `core.py:792–797`:

```text
code: MEMORY_LIMIT_EXCEEDED
Тем больше лимита (15): <число превышения> сверх (...). Файлы НЕ удалены. Убери лишние через action='delete'.
```

`_check_storage_limits()` (`core.py:325`) сортирует `MEMORY_DIR.glob('*.md')` по mtime и возвращает имена после первых 15. `MAX_ACTIVE_PROJECTS = 15` — константа `core.py:40`, не параметр конфигурации и не токен-бюджет. Других присваиваний этому имени в AST модуля не найдено.

Проверка вызывается **после записи save**, до best-effort git-коммита; превышение не блокирует запись. В проверенных ветках list/load/index/budget нет этой проверки. Это порог предупреждения о числе legacy-тем, а не ограничение объёма инъекции.

## 4. Политика записи/очистки и риски

- Автоудаления активных тем при превышении 15 в текущем `_check_storage_limits` нет.
- Save допускается сверх 15. Для отдельного content действует другой предел: 2000 токенов. При успешном подсчёте и превышении возвращается `MEMORY_TOO_LARGE` до записи, без автоматической обрезки тела под бюджет.
- `_compose_slice` нормализует обрамление: trim, удаление повторных legacy-заголовков, создание актуального заголовка; это не побайтовое сохранение входа.
- `_backup_topic` перед изменением существующей темы сохраняет снимок и **автоматически удаляет старые снимки сверх `HISTORY_KEEP = 5`**. Это реальная автоматическая очистка истории, не активных тем.
- Ошибка OSError при резервировании подавляется, возвращается None; save/delete продолжаются. Запись темы — прямой `write_text`, не атомарная замена. Поэтому нельзя гарантировать сохранность при сбое диска/процесса или конкурирующих writer.
- Явный `delete` удаляет активный файл после попытки резервирования; archive переносит его; restore восстанавливает. Эти операции не запускались.
- Git-коммит стора best-effort, не гарантия восстановления. Существующие `.history` и git нельзя считать проверенной резервной копией.
- Load/search меняют `.access.json`; для read-only диагностики они намеренно не использовались.

**Риск:** превышение количества тем само по себе не удаляет знания в проверенном исходнике. Но есть ограниченное хранение истории, неблокирующий сбой backup и неатомарная перезапись. Указание «убери лишние через delete» необоснованно подталкивает к удалению.
