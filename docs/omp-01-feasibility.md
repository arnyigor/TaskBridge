# OMP-01: изолированная проверка Oh My Pi

Проверка OMP (форк Pi) как возможного альтернативного агентного ядра TaskBridge.
Ничего в рабочем TaskBridge не менялось: ни `config.json`, ни `data/`, ни KMP, ни
Pi-расширения. Адаптер не разрабатывался — сначала технические доказательства.

**Итог: OMP 18.11.0 на Windows работает, RPC-протокол пройден целиком (13/13), все
шесть функциональных сценариев выполнены успешно. Преимуществ перед Pi, ради
которых стоило бы менять ядро, по этим прогонам не видно — рекомендация оставить Pi
и не начинать адаптер.**

## 1. Версия и установка

| Параметр | Значение |
| --- | --- |
| Версия OMP | **`omp/18.11.0`** (уже установленная на машине, `~/AppData/Local/omp/omp.exe`, 2026-10-15) |
| Актуальная в npm | `@oh-my-pi/pi-coding-agent` **18.12.5** (не устанавливал, см. ниже) |
| Платформа | Windows, git-bash; Node 24.16.0 |
| Bun | **не установлен** (`bun` отсутствует в PATH); `engines` пакета требует `bun >= 1.3.14` |
| Как запускался | `omp --mode rpc --no-ui --profile omp01 --session-dir <эксперимент> --model deepseek-flash` |

Решение по установке: новая версия не ставилась. На машине уже есть рабочий
standalone-бинарник 18.11.0 (официальный установщик, без Bun), а второй глобальный
install ради проверки добавил бы риск и ничего не дал бы: вопрос задачи — «можно ли
использовать OMP и полезнее ли он Pi», а не «какая из 18.1x свежее». Версия
зафиксирована этим отчётом и попадает в каждый прогон (`summary.json → omp`).

Изоляция от Pi: `--profile omp01` (свой agent-db, models-db, сессии, кэши) плюс
`--session-dir` внутри каталога эксперимента. Рабочий каталог Pi (`~/.pi/agent`),
его сессии и `models.json` не читались и не менялись. Ключ провайдера берётся из
окружения (`DEEPSEEK_API_KEY`), в отчёт и в репозиторий не попадает. Профиль живёт
вне репозитория: `~/.omp/profiles/omp01/`.

## 3. RPC (13 проверок, стенд `experiments/omp-01/rpc-checks.mjs`)

| # | Проверка | Результат |

| 6 | `session_settled` | ✅ пришёл после `prompt_result` |
| 7 | `steer` / `follow_up` во время генерации | ✅ `queue_update { steering: 1, followUp: 0 }`, вторая команда — `completed` |
| 8 | `abort` | ✅ `prompt_result.status: aborted`, `isStreaming: false`, `isSettled: true` |
| 9 | Сохранение и повторное открытие сессии | ✅ файл сессии создан, `open_session` → `resumed: true`, продолжение отвечает |
| 10 | `rpc_chunk` (крупные кадры) | ✅ ответ `get_available_models` = **2 063 149 байт** при лимите кадра 1 МиБ пришёл одной последовательностью сегментов и собрался в валидный JSON |

Отличия протокола OMP от Pi, важные для будущего адаптера (по `docs/rpc.md` и по
наблюдению):

- `prompt_result` (конец конкретного запроса) и `session_settled` (сессия больше не
  может себя разбудить) — **разные вещи**; Pi присылает только `agent_settled`.
  Хост обязан ждать оба, иначе «ответ показан, а сессия живёт».
- `prompt` подтверждает **admit**, а не завершение; при `data.agentInvoked: false`
  запроса к модели не было вовсе.
- `rpc_chunk` — только при согласованном protocol v2; в v1 крупный ответ приходит
  ошибкой `RPC response exceeded the transport limit`, крупные события обрезаются.
- Есть команды, которых у Pi нет: `open_session`, `new_session`, `set_host_tools`,
  `set_host_uri_schemes`, `get_subagents`, `cancel_subagent`, `steer_subagent`,
  `goal`, `set_todos`, `set_event_filter`, `promote_queued_message` и др.

## 5. Обнаруженные несовместимости и подводные камни

- **Bun в требованиях.** Пакет объявляет `engines.bun >= 1.3.14`; на машине Bun нет.
  Работает standalone-бинарник, но `npm i -g` или `omp install` без Bun — отдельная
  проблема (issue #15480 про это же). Для TaskBridge это значит: ставить OMP надо
  установщиком, а не как npm-пакет, и фиксировать бинарник.
- **Крупные кадры.** Без `negotiate_protocol v2` ответ на 2 МБ приходит ошибкой, а
  события обрезаются. Любой адаптер обязан согласовать v2 и реализовать сборку
  `rpc_chunk` (проверено на 2 063 149 байт).
- **Две точки завершения** (`prompt_result` + `session_settled`) — при наивном
  переносе Pi-логики на OMP ответ будет показан раньше, чем сессия освободится, и
  STOP/очередь разъедутся.
- **`before_agent_start` в OMP срабатывает и на entreged steer/follow-up батчи**
  (docs/extensions.md), а не только на «новый ход». Наш TaskBridge-хук инструкций
  написан под Pi-семантику; в OMP его поведение надо перепроверять отдельно.
- **Профиль и история.** `--profile` создаёт свои `agent.db`/`models.db` — это удобно
  для изоляции, но означает, что «просто переиспользовать» настройки Pi нельзя.
- Мелочь: `node --test test/` (каталог) в Node 24 на этой фикстуре ведёт себя
  странно; в фикстуре команда задана явными файлами.

## 6. Отличия от Pi (архитектурный обзор)

| Аспект | Pi 1.3.0 | OMP 18.11.0 |
| --- | --- | --- |
| Происхождение | самостоятельный агент | форк Pi; API расширений почти совпадает (`before_agent_start`, `pi.zod`, hooks) |
| Инструменты | ~10 базовых (read/write/edit/bash/grep/glob + MCP) | **31** встроенный: `ast_grep`/`ast_edit`, `lsp`, `debug` (DAP), `eval` (Python/JS с возвратом в инструменты), `browser`, `computer`, `web_search`, `task` (подагенты), `todo`, `ask`, `github`, `generate_image`, `tts` и др. |
| LSP | нет | 14 операций (диагностика, навигация, renames, code actions) |
| Отладка | нет | 28 операций DAP (lldb-dap и др.) |
| Подагенты | расширением (`subagent`) | первый класс: `task` с изоляцией по worktree и типизированным результатом, `agent://` доступ к их выводу |
| Compaction | ручная (`/compact`) + пороги | такое же + `set_auto_compaction`, `compaction` в RPC, учёт async-работы при settle |
| Хуки/расширения | `pi.on(...)`, `-e` | те же + `--hook`, `hooks.md`, правила с инъекцией в поток |
| RPC | JSONL, `agent_settled` | JSONL, `prompt_result` + `session_settled`, protocol v2 с `rpc_chunk`, host-tools/URI, event filter |
| Провайдеры | каталог из `models.json` | 60+ «из коробки», свои `models.yml`, роли smol/slow/plan |
| Длинные сессии | зависят от хоста | `--restore` (перезапуск прерванного хода и подагентов), agent hub, `wait` |

Ради чего действительно стоило бы менять ядро: `ast_edit`/`ast_grep` (структурные
правки вместо построчных), `lsp` и `debug` (диагностика и отладка на уровне IDE),
подагенты с изоляцией по worktree и типизированным результатом. Это ровно те
возможности, которых у Pi нет, и которые TaskBridge сейчас не даёт.

Чего у OMP **нет** и что TaskBridge пришлось бы дублировать/адаптировать: его RPC
не похож на Pi-шный (см. §3), а семантика завершения другая. Плюс TaskBridge-специфика
(очередь, approvals, media-policy, `toolEvidence`, resume) живёт на уровне хоста и
переносу не подлежит.

## 7. Предварительная оценка стоимости интеграции

Если бы решение было «интегрируем»:

| Работа | Оценка |
| --- | --- |
| `agent-runtime.mjs` + `pi-runtime.mjs` (обёртка нынешнего `pi-rpc.mjs` под общий интерфейс) | 1–2 дня, риск низкий |
| `omp-runtime.mjs`: `start/prompt/steer/followUp/abort/getState/subscribe/dispose`, две точки завершения, `open_session`, v2 + `rpc_chunk` | 3–5 дней, риск средний (протокол проверен, но краевые случаи — очередь, ретраи, async-работа) |
| Согласование с хостом: очередь TaskBridge ↔ `prompt_result`/`session_settled`, STOP, resume после рестарта, approvals | 2–3 дня, риск высокий (это места, где нынешние баги проявляются как «зависло») |
| Media-policy и `toolEvidence` под OMP-события | 1–2 дня, риск средний |
| Инструкции хода: перенос `before_agent_start`-расширения на семантику OMP (steer-батчи) | 0,5–1 день, риск низкий |
| Тесты: контракт рантайма + регрессия на fake-ядре | 1–2 дня |
| **Итого** | **~9–15 дней** без учёта сравнения на локальной модели |

Плюс постоянная цена: два ядра в поддержке, два набора поведения при отладке сессий
и два способа объяснять «почему агент сделал не то».

## 8. Решение

**Оставить Pi. OMP Adapter не разрабатывать.**

Основания:

1. OMP на Windows стабилен и протокол у него аккуратный — технических препятствий
   нет, вопрос только в выгоде.
2. На шести задачах выгоды не видно: 6/6 успешно, 0 повторов, 0 лишних правок;
   время 7–18 с, токены 10,8–14,3 тыс. — это те же порядки, что TaskBridge + Pi на
   аналогичных сценариях (`bench/agent-behavior`, смоук).
3. Разница — в инструментах (LSP, DAP, AST-правки, подагенты), а не в качестве на
   простых задачах. Пока эти инструменты не проверены на задачах разработки, платить
   9–15 дней адаптера и постоянную цену второго ядра не за что.

Что имело бы смысл сделать до любого пересмотра решения:

- сравнить Pi и OMP на **задачах разработки** (D01/D02-подобные), где у OMP есть
  `ast_edit`, `lsp` и `task`: если OMP там заметно аккуратнее, аргумент появится;
- то же на локальной Qwen через Strata (после восстановления StrataPanel): важнее
  всего не число вызовов, а `task success` и wall-clock.
- отдельно проверить восстановление прерванного хода (`--restore`) — у Pi аналога нет.

## 9. Что проверено и что нет

Проверено на живых прогонах: установка и запуск на Windows, DeepSeek Flash,
13 проверок RPC (включая `rpc_chunk` на 2 МБ), шесть функциональных сценариев с
проверкой фактического состояния файлов и тестов.

Не проверено: локальная Qwen (Strata не готова — по ТЗ это не требовалось),
отказ провайдера и поведение `prompt_result.error`, длинные сессии (compaction на
живом объёме), `--restore` после падения, подагенты `task`, LSP/DAP-инструменты,
производительность на задачах разработки в сравнении с Pi.

## 10. Воспроизведение

```bash
node experiments/omp-01/rpc-checks.mjs --model deepseek-flash
node experiments/omp-01/run-functional.mjs --model deepseek-flash
# отчёты: .local/omp-01/rpc-*/rpc-report.json, .local/omp-01/functional/summary.json
```

Скрипты пишут только в `.local/omp-01/` (не в git); профиль OMP — `~/.omp/profiles/omp01`,
сессии эксперимента — внутри `.local`. Рабочий TaskBridge, его `config.json`, `data/`
и KMP не затрагивались.
