# План: продолжение существующих Pi-сессий из TaskBridge (в т.ч. с телефона)

## Цель
Дать пользователю выбрать уже существующую сессию Pi (созданную из терминала
или из TaskBridge) и продолжить её как задачу TaskBridge — с телефона в том числе.

## Что уже есть (переиспользуем как есть)
- `src/pi-rpc.mjs`: `PiRpcSession` уже поддерживает `sessionFile` → флаг
  `--session <path>` (+ `--session-dir`). Ядро процесса менять не нужно.
- `src/session-history.mjs`: уже умеет восстанавливать/реконструировать
  сессию по `task.piSessionFile`. Это фолбэк-путь, для нативных сессий не
  нужен — там валидный v3-файл уже есть.
- Формат `SessionHeader` (`type, version, id, timestamp, cwd, parentSession`)
  стабилен и достаточен, чтобы сгруппировать файлы по проекту.

## Разведка (выполнена)
- Pi хранит сессии в `~/.pi/agent/sessions/<encoded-cwd>/*.jsonl`, ключ —
  `cwd` из заголовка файла. На машине пользователя найдено 658 сессий в
  105 папках проектов, все заголовки читаются без ошибок — формат стабилен,
  парсить его напрямую (без RPC) безопасно.
- В RPC-режиме Pi (`rpc-mode.js`) команды листинга сессий нет (`new_session`,
  `switch_session`, `get_session_stats`, `get_messages` есть, `list_sessions`
  нет). Значит перечисление файлов TaskBridge должен делать сам через `fs`.
- Алгоритм кодирования `cwd` → имя папки сессий у Pi внутренний, не
  экспортирован в public API. Проще и надёжнее не повторять его, а сканировать
  `~/.pi/agent/sessions/**/*.jsonl` и фильтровать по `cwd` из заголовка.

## Что нужно добавить

### 1. Листинг внешних сессий (сервер)
Новый модуль (например `src/pi-session-index.mjs`):
- вход: путь проекта (`project.path`).
- сканирует `~/.pi/agent/sessions/**/*.jsonl`, читает только первую строку
  каждого файла (заголовок), фильтрует по `cwd === project.path`.
- отдаёт список `{ file, id, name?, cwd, mtime, messageCount? }`, сортировка
  по `mtime`. Не парсит весь файл ради списка.

### 2. API-эндпоинт (server.mjs)
- `GET /api/projects/:id/pi-sessions` → список сессий для проекта (модуль п.1).
- `POST /api/tasks/from-session` `{ projectId, sessionFile }` → создаёт задачу
  в task-manager с `piSessionFile = sessionFile` и `workspacePath = project.path`
  (без git-worktree — см. риск №2).

### 3. Импорт истории для отображения в чате (task-manager.mjs / task-store.mjs)
Чтобы веб-чат сразу показал прошлые сообщения, а не пустой экран, нужно один
раз при создании задачи прогнать сообщения из `.jsonl` (role: user/assistant/
toolResult) через тот же путь, что и обычные live-события от Pi
(`pi.message_start` / `pi.message_end` кадры), и записать их в `task-store`
как обычные события.
- Функция `importNativeSession(file) → events[]`, читает `SessionMessageEntry`,
  для каждого `message` формирует `message_end`-кадр с этим `message`
  (формат уже знаком `ChatState.apply`), пишет через `store.appendEvent`.
- `ChatState` (web/chat-state.mjs) менять не нужно — она уже понимает такие
  кадры (видно из `addUser`/`apply`, которые сейчас питаются такими же
  событиями из `session-history.mjs`).
- Общую логику построения кадра из `AgentMessage` стоит вынести в шаред-хелпер
  и переиспользовать из `session-history.mjs` (там уже есть похожий код).

### 4. UI (web/app.js)
- В экране проекта/новой задачи — кнопка "Продолжить существующую сессию",
  список из п.2 (имя/дата/кол-во сообщений), выбор →
  `POST /api/tasks/from-session`.
- Дальше это обычная задача TaskBridge — открывается тот же чат-экран.

## Риск №1 — конкурентная запись в один файл (главное ограничение)
Если пользователь на компьютере ещё держит открытым интерактивный `pi` на
этой же сессии, а TaskBridge параллельно запускает
`pi --mode rpc --session <тот же файл>` на телефоне — два процесса пишут в
один JSONL → гонка/порча файла. В `session-manager.js` файлового лока нет.

Варианты (по возрастанию сложности):
1. **MVP**: предупреждать в UI — "закройте pi в терминале перед продолжением
   с телефона". Дёшево, ответственность на пользователе.
2. **Проверка занятости**: эвристика через `handle.exe`/`Get-Process` на
   Windows — ненадёжно кроссплатформенно, не стоит усложнений.
3. **Правильный лок**: TaskBridge сам пишет lock-файл рядом (`*.lock` с
   pid/host) при старте RPC-сессии на этом файле, снимает при штатном
   завершении; при старте — если lock свежий, отказывать с понятной ошибкой.
   Не спасает от стороннего `pi` в терминале, но защищает от двух
   TaskBridge-сессий одновременно (комп + телефон на одну задачу).

Рекомендация: (1) сразу, (3) — только если реально появится сценарий
"комп и телефон одновременно", а не "сначала комп, потом телефон".

**Реализовано (2026-09-09):** (1) и (3) сделаны — `native-sessions.mjs`
(`acquireNativeLease`) даёт файловый лок между процессами TaskBridge, диалог
в UI перед импортом явно объясняет риск и просит закрыть терминал вручную.
Автоматического обнаружения занятости терминального `pi` по-прежнему нет и
не планируется как MVP (см. пункт 4 ниже) — это осознанное ограничение, а не
недосмотр.

### Вариант 4 (отложено) — удалённо прибить терминальный `pi` с телефона

Идея пользователя: раз TaskBridge не может определить, открыта ли сессия в
терминале, дать кнопке "продолжить" самой найти и завершить соответствующий
процесс `pi` перед импортом — по аналогии с тем, как `runtime-control.mjs`
уже умеет безопасно останавливать `llama-server`.

Ключевое отличие от кейса с моделью, из-за которого это отложено: у
`llama-server` есть надёжный якорь для поиска — порт, который он слушает
(`Get-NetTCPConnection` даёт однозначный PID). У терминального `pi` такого
якоря нет: это интерактивный процесс без сетевого порта. Пришлось бы
перебирать процессы `pi`/`node` и сопоставлять их командную строку с путём к
файлу сессии — это:
- ненадёжно, если `pi` запущен через обёртку/алиас/`npx`, или в
  интерактивном режиме без явного пути сессии в аргументах;
- рискует задеть не тот процесс при нескольких открытых терминалах с `pi`
  для разных проектов/сессий;
- убивает интерактивную пользовательскую сессию (в отличие от безголового
  сервера модели) — заметнее и неприятнее при ошибке.

Если всё же понадобится: реализовывать по тому же паттерну, что и
`identifyExternal()`/`stopWindowsExternal()` в `runtime-control.mjs` — найти
кандидатов через `Get-CimInstance Win32_Process` с фильтром по имени
исполняемого файла (`config.pi.command`), сопоставить `CommandLine` с путём
файла сессии, показать пользователю полную командную строку найденного
процесса для ручного подтверждения перед остановкой (никогда не убивать
автоматически без подтверждения, в отличие от модели, где решение принимает
конфигурация профилей, а не догадка по командной строке).

## Риск №2 — workspace/worktree
Нативные сессии создавались с `cwd` = сам рабочий проект, без git-worktree.
Для "продолжить существующую сессию" `workspace.useGitWorktreeByDefault`
нужно отключать — работать прямо в `project.path`, т.к. история из `.jsonl`
привязана к конкретным путям файлов на диске.
