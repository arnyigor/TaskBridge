# Анализ доставки сообщений и «зависаний» TaskBridge

Дата проверки: 2026-10-06. Объект: текущее рабочее дерево, включая существовавшие незакоммиченные изменения. Проверка ограничена этим репозиторием; установленный Pi, внешние расширения, пользовательские сессии и работающий сервер модели не исследовались.

## Вывод

Проблема не сводится к «локальная модель медленная». Между Pi и интерфейсом есть несколько независимых мест, где теряется наблюдаемость прогресса. Некоторые дефекты подтверждены исполнением, другие — чтением кода; причина конкретного пользовательского зависания без трассы пока не установлена.

Основные результаты:

1. **Связь с TaskBridge может быть исправна, когда Pi уже не делает видимой работы.** SSE heartbeat не проверяет модель. После подтверждения команды ожидание завершения хода имеет предел 12 часов.
2. **Начало сжатия не гарантирует немедленное обновление индикатора KMP.** Клиент не запрашивает metadata по событию начала, а сервер не публикует изменение activity, если общий runtime state остался прежним.
3. **Обновление metadata может отбрасываться при непрерывном потоке.** Защита от устаревшего ответа GET отбрасывает весь снимок при изменении cursor, включая свежие поля активности.
4. **Интерфейс не эквивалентен Pi console.** Часть сообщений расширений намеренно фильтруется; поддерживается лишь узкий вариант статусных сообщений smart-compaction.
5. **После успешного сжатия может оставаться текст его последней стадии.** Это поведение даже закреплено существующим тестом.
6. **В нормализованном cloud-пути отсутствует начало автосжатия.** Минимальный вызов нормализатора подтвердил потерю события.
7. **При большом backlog SSE replay может пропустить начало истории после cursor.** Минимальная проверка хранилища подтвердила, что при лимите выбирается хвост, а не первая страница.

Это объясняет возможное расхождение с консолью без предположения о поломке самой модели. Но не доказывает, что все наблюдавшиеся зависания имеют одну причину.

## 1. Как проходит сообщение

```text
Клиент: отправка / outbox
  → HTTP-команда TaskBridge
  → проверка живой Pi-сессии и локальной модели
  → очередь ИЛИ непосредственная доставка
  → старт/восстановление Pi RPC, get_state
  → prompt / steer / follow_up
  → ACK RPC
  → сохранение USER_MESSAGE, освобождение барьера событий
  → Pi stdout JSONL
  → последовательный обработчик TaskManager
  → журнал событий / SSE
  → reducer клиента + отдельный GET metadata
  → agent_settled
  → проверка результата и терминальный статус TaskBridge
```

Точки реализации:

- [TaskManager](../src/task-manager.mjs): доставка 3655–3822, обработка кадров 2184–2326, последовательная цепочка 1314–1345.
- [PiRpcSession](../src/pi-rpc.mjs): JSONL 93–146, запросы и таймеры 218–288.
- [SSE server](../src/server.mjs): публикация 235–256, heartbeat 278–285, replay 1311–1334.
- [ChatSession](../clients/kmp/core/client/src/commonMain/kotlin/ru/arny/taskbridge/core/client/session/ChatSession.kt): получение событий и metadata 240–335.

**Три разных подтверждения:** HTTP-успех/постановка в очередь, ACK Pi, завершение хода — не одно и то же. Аналогично heartbeat означает доступность транспортного соединения, а не наличие ответа модели.

## 2. Находки по приоритету

### P1. После ACK отсутствует короткий предел ожидания завершения хода

**Подтверждено кодом.** `PiRpcSession.#settle` удаляет запрос из pending и очищает его таймеры при ACK. Дальнейшие токены уже не контролируются idle timeout этой команды.

`TaskManager` ожидает settle до `12 * 60 * 60 * 1000` мс как для первоначального запуска (около строки 1204), так и для последующего сообщения (3767). Обычный путь завершения опирается на `agent_settled`, не просто `agent_end`. Закрытие/ошибка процесса также обрабатываются; проблема относится прежде всего к живому, но молчащему процессу или отсутствующему ожидаемому событию.

SSE при этом может продолжать выдавать heartbeat каждые 15 секунд. KMP выставляет `LinkState.Live` после получения данных/heartbeat. Его 45-секундный таймаут чтения проверяет молчание SSE, а не Pi.

**Симптом:** связь зелёная, задача RUNNING, но ответа и понятной причины ожидания нет.

**Для локальной модели:** загрузка, обработка большого prompt до первого токена и многостадийное сжатие могут быть долгими и законными. Поэтому простое сокращение 12 часов и автоматическое убийство процесса — небезопасное исправление.

**Рекомендация:** отдельное состояние «нет прогресса N секунд», основанное на времени последнего кадра Pi/токена/смены стадии. Показывать отдельно связь, принятие команды, очередь, загрузку, сжатие и генерацию. Проверку живости выполнять ограниченным probe; не считать её доказательством прогресса генерации. STOP/диагностика должны оставаться доступны. Совместимость `agent_settled` с реально установленным Pi нужно проверить трассой, а не заменять его на `agent_end` вслепую.

### P1. Начало сжатия не сразу обновляет индикатор KMP

**Подтверждено кодом и минимальной проверкой runtime-функции.**

- TaskManager обрабатывает оба `compaction_start` и `auto_compaction_start`, устанавливает `_compacting`, `_compactingSince`, `current` (2210–2220).
- `#runtimeChange` сравнивает только `.state` (4148–4154).
- [deriveRuntimeState](../src/runtime-state.mjs), 40–64: переход может быть `WORKING/streaming → WORKING/compacting`; state не меняется.
- ChatSession, 319: metadata запрашивается по окончанию сжатия, но не по началу.

Без дополнительного STATUS/UI_NOTIFY начало может ждать следующего heartbeat и GET metadata — при штатных настройках примерно до 15 секунд плюс сетевое время. При отбрасывании GET-снимка ожидание может быть ещё дольше.

**Важно:** это не утверждение, что событие начала полностью потеряно в локальном SSE: reducer может показать заметку. Речь об отдельной полоске активности и её таймере.

**Рекомендация:** запускать refresh по обоим событиям начала; отдельно решить доставку изменений activity/compactingSince. Не менять публичный формат RUNTIME_STATE без тестов его потребителей.

### P1. GET metadata конкурирует с SSE и может не применяться

**Подтверждено условие в коде; starvation на реальном UI не воспроизведён.** ChatSession, 324–331:

1. Запоминает cursor.
2. Загружает task по HTTP.
3. Если за это время обработано новое SSE-событие — отбрасывает весь результат.

Это полезная защита от ситуации «старый завершённый снимок остановил новый ход». Но вместе с terminal status отбрасываются runtime/current/compactingSince. При частых событиях и медленном GET несколько обновлений подряд могут не примениться.

**Рекомендация:** не удалять проверку cursor просто так. Нужна проверяемая версия снимка/хода либо явное применение runtime-событий; тест на гонку старого terminal snapshot с новым ответом обязателен.

### P1. Часть информации Pi console не доходит до пользователя

**Подтверждено кодом.** TaskManager, 4193–4220:

- `notify` превращается в UI_NOTIFY, кроме распознанных retry-in-progress notices;
- `setStatus` используется для прогресса только при `statusKey`, начинающемся с `smart-compaction`;
- прочие terminal decorations, включая widgets, не отображаются этим обработчиком.

[ChatReducer](../clients/kmp/core/client/src/commonMain/kotlin/ru/arny/taskbridge/core/client/chat/ChatReducer.kt) содержит фильтр `^Smart compaction: `: такие notices намеренно скрываются, поскольку стадии предполагается показывать через task.current.

Если конкретная версия расширения сообщает стадии через notify, другой statusKey или widget, консоль покажет их, а TaskBridge может не иметь видимой замены. Протокол реального расширения в этой проверке не установлен.

**Рекомендация:** сначала записать реальные кадры расширения. Скрывать повторяющиеся notices только при наличии работающего альтернативного индикатора; ошибки и изменения стадии не должны исчезать вместе с секундным шумом.

### P2. Успешное сжатие оставляет видимость незавершённой стадии

**Подтверждено кодом и существующим ожиданием теста; отдельный серверный тест здесь не запускался.**

- Пустой `setStatus` не очищает `current`: условие требует непустой text (4210).
- `compaction_end` очищает только точную строку `Pi сжимает контекст…`, не `Smart compaction: ...` (2222–2230).
- [server.test.mjs](../tests/server.test.mjs), 317–327, после успешного сжатия ожидает сохранённый `Smart compaction: final merge (...)`.
- Повторные ticks одной стадии отбрасываются после удаления суффикса секунд; время в сохранённом тексте не является живым таймером.

**Симптом:** сжатие закончилось, но в current всё ещё final merge. При этом runtime.activity может уже быть не compacting: поля противоречат друг другу визуально.

**Рекомендация:** активную стадию очищать по явному end/clear, а последнюю стадию, если нужна для диагностики, показывать как историческую, не как текущую. Различать успех, отмену и ошибку. Обновить тест, который сейчас закрепляет старое поведение.

### P1 для cloud-пути. Потерян `auto_compaction_start`

**Воспроизведено исполнением.** [EventNormalizer](../src/events/event-normalizer.mjs), 260–274:

- `compaction_start → compaction_started`;
- `auto_compaction_start → []`;
- оба варианта окончания поддерживаются.

Минимальная проверка вызвала `normalizePiFrame` для каждого начала: ручное дало событие, автоматическое — пустой массив.

**Область:** нормализованный поток; нельзя переносить этот вывод на прямой локальный SSE, который передаёт исходные PI_EVENT.

**Рекомендация:** симметричная обработка alias начала и regression-тест двух вариантов lifecycle.

### P2. Большой reconnect может пропустить накопившиеся события

**Семантика хранилища воспроизведена; большой end-to-end replay не запускался.**

SSE вызывает `readEvents(taskId, maxEventsPerRequest, after)`, затем отправляет результат и переключается на live. Стандартный предел — 20 000 событий.

[TaskStore](../src/task-store.mjs), 462–479, выбирает `ORDER BY seq DESC LIMIT ?`, затем разворачивает массив. Это последние N событий после cursor, не первые N.

Минимальный пример: записано 1…5; `readEvents(id, 2, 0)` возвращает `[4, 5]`. Если аналогичное превышение произошло при replay, события 1…3 не попадут в этот поток, а cursor продвинется до 5.

Обычный reconnect на небольшом объёме работает — это подтвердили существующие HTTP/SSE-тесты. После финального сообщения часть streaming deltas штатно удаляется, поэтому разрывы seq сами по себе ещё не доказывают потерю полезных данных.

**Рекомендация:** отдельная forward-pagination для replay либо явный snapshot/reset-протокол при усечении. Нельзя просто глобально изменить семантику readEvents: интерфейсу истории нужен хвост.

### P2, нагрузочная гипотеза. Буферы и последовательная обработка

`sendSse` не учитывает false от `res.write`; pending во время replay — массив без видимого лимита. Pi-события последовательно проходят через eventChain и запись raw/event данных до публикации.

Это сохраняет порядок, но медленный диск, большой вывод инструментов или медленный клиент могут увеличивать задержку и память. Нагрузочное воспроизведение не выполнено, поэтому это **не установленная причина** текущих зависаний.

Измерять прежде всего: время получения кадра, длину/возраст очереди обработки, время записи, время публикации и применения клиентом. Не вводить batching до измерений.

## 3. Особенности локальных моделей

В [TaskManager](../src/task-manager.mjs), 3669–3733, уже есть специальная логика:

- проверка состояния живой Pi-сессии перед отправкой;
- отказ BUSY при сжатии;
- проверка занятости модели;
- очередь с причинами MODEL_BUSY/MODEL_LOADING;
- cold-model parking только когда `loaded === false`, кроме immediate/fromQueue;
- подтверждение постановки в очередь отдельным PROMPT_QUEUED.

Это полезные механизмы, а не доказательство поломки очереди. Существующие комментарии описывают прошлые исправления; их нельзя выдавать за воспроизведённые текущие дефекты.

[LocalModels.getBusyStatus](../src/local-models.mjs), 547–584, при недоступном `/models` возвращает `unknown: true, busy: false, loaded: null`; при недоступных slots также возможна неопределённость. Неопределённость не равна подтверждённой свободе модели. В таком состоянии ветка парковки cold-model может не сработать, и отправка пойдёт по более долгому пути. Проверить нужно с реальным router/обычным llama-server.

Проба `get_state` в доставке использует 60 секунд; при кадрах RPC idle timer продлевается до hard cap `timeout × 8`. Поэтому «ничего не отправляется» может происходить ещё до prompt/ACK, а не во время генерации. Внешний HTTP-таймаут или отмена клиента могут завершить ожидание раньше; их фактическое взаимодействие здесь не воспроизводилось.

Отдельно доставка удерживает `runtime.eventChain` до ACK и сохранения USER_MESSAGE (3751–3804). Это обеспечивает правильный порядок истории. Если Pi долго не подтверждает prompt, входящие события этой цепочки задерживаются, хотя Pi уже мог их испустить. Raw `pi-events.jsonl` записывается внутри обработчика цепочки, то есть это не независимое измерение времени прихода stdout. Для диагностики такого случая нужен timestamp на входе PiRpcSession, до барьера. Менять барьер без проверки порядка USER_MESSAGE/ответа нельзя.

## 4. Почему консоль выглядит исправной

Консоль получает вывод и интерфейс расширений напрямую. TaskBridge добавляет:

- admission/очередь и проверки занятости;
- отдельный RPC-процесс и ACK;
- последовательную запись событий;
- преобразование событий, а для cloud — отдельную нормализацию;
- фильтрацию terminal UI;
- SSE/reconnect/replay;
- два источника клиентского состояния: события и GET metadata.

Следовательно, нормальная работа консоли не гарантирует нормального отображения RPC-сессии. Но и обратный вывод «виноват только UI» преждевременен: RPC-процесс, его расширения и сервер модели должны быть сопоставлены на одном конкретном ходе.

## 5. Что собрать при следующем зависании

Не запускать повторный prompt автоматически: неизвестно, был ли первый принят, и повтор может создать вторую работу.

Для одного taskId/хода собрать с временными отметками, предварительно удалив секреты и содержимое приватных prompt:

1. Режим подключения: direct/LAN/cloud, тип и версия клиента, модель/provider.
2. Отправку команды, её commandId (если есть), HTTP-результат и постановку в очередь.
3. Отправку RPC prompt/steer и получение ACK.
4. Последний stdout frame Pi и отдельно последний токен/стадию.
5. `compaction_start/auto_compaction_start`, setStatus/notify, соответствующий end, `agent_end` и `agent_settled`.
6. Снимок task: status, current, runtime, compactingSince, очередь, pending UI request, error.
7. Существующие `pi-events.jsonl`, `pi.stderr.log`, события задачи; учитывать задержку raw-журнала за eventChain.
8. Состояние процесса Pi и локального сервера, health/slots без принудительной загрузки другой модели.
9. Последний опубликованный SSE seq и последний применённый cursor клиента.

Развилка диагноза:

| Наблюдение | Где искать |
|---|---|
| Нет ACK и нет кадров | старт Pi / RPC / расширения до prompt |
| Кадры есть, ACK нет, UI молчит | ACK-барьер и контракт prompt |
| ACK есть, далее молчание | модель / prefill / compaction / ожидание инструмента |
| Pi прогрессирует, журнал отстаёт | eventChain / запись / backpressure |
| В журнале прогресс есть, в SSE нет | публикация / replay / транспорт |
| В SSE есть, UI не показывает | фильтрация / reducer / metadata race |
| Есть end сжатия, но виден final merge | устаревший current |
| Есть agent_end, нет agent_settled | проверить контракт окончания реального Pi |

## 6. Рекомендуемый порядок исправлений

1. Небольшие подтверждённые разрывы: auto_compaction_start в нормализаторе, refresh KMP по началу, очистка активной стадии по end/clear.
2. Тесты гонок metadata и доставки activity без смены state; сохранить защиту от старого terminal snapshot.
3. Прозрачные состояния ожидания и время последнего реального прогресса. Не использовать heartbeat как индикатор работы модели.
4. Реальная трасса Pi RPC со smart-compaction и локальной моделью: холодный старт, длинный prefill, ручное и автоматическое сжатие, STOP, следующий ход.
5. Forward replay/snapshot при превышении лимита; затем нагрузочные проверки.

Критерии приёмки: начало сжатия видно без ожидания heartbeat; стадия не остаётся активной после end; поток токенов не блокирует metadata навсегда; долгое молчание показано явно, STOP доступен; reconnect больше лимита восстанавливается без молчаливой потери; новый ход не завершается старым GET-снимком.

## 7. Выполненные проверки и ограничения

Запущены последовательно на Node.js v24.16.0:

```text
node --test --test-concurrency=1 \
  tests/rpc-timeout.test.mjs \
  tests/pi-rpc-faults.test.mjs \
  tests/event-stream.test.mjs \
  tests/runtime-faults.test.mjs
```

TEMP/TMP/TMPDIR перенаправлены внутрь `.local/delivery-analysis-tmp`, чтобы временные fixture оставались в текущем репозитории.

**Результат: 21 тест, 20 passed, 0 failed, 1 skipped; около 40 секунд.** Пропущен платформенный тест убийства дочерних процессов, помеченный как покрытый `taskkill /T` на Windows; это не отдельное подтверждение его поведения этой проверкой. Были предупреждения Node DEP0190 о shell+args, не ошибки тестов.

Проверено: обычный SSE reconnect и join посреди потока; heartbeat; классификация RPC timeout; crash, повреждённый JSONL, UTF-8; STOP; восстановление и повторная постановка steer; фильтрация retry notices; существующий сценарий скоростей локальной модели. Все эти сценарии используют fake Pi, не настоящую генерацию.

Дополнительные минимальные проверки:

- EventNormalizer: ручное начало даёт compaction_started, автоматическое — пустой массив.
- deriveRuntimeState: state остаётся WORKING при смене streaming на compacting.
- TaskStore: пять событий, limit=2, after=0 → [4,5]. Первая попытка fixture без записи задачи упала на FOREIGN KEY; после правильного создания задачи проверка прошла. Это ошибка подготовки проверки, не дефект хранилища.

Не запускались: KMP/Compose tests, сборка desktop/Android, реальная модель, установленный Pi, внешние расширения, длительный нагрузочный replay, полноценный cloud end-to-end. Живой пользовательский сбой не воспроизведён.
