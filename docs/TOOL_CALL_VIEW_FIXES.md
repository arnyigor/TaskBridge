# TaskBridge — универсальное отображение вызовов инструментов

**Приоритет:** P0 — потеря параметров и недоступный вывод; P1 — улучшение интерфейса.  
**Область:** Pi RPC, MCP, Node backend, Web, KMP Desktop, Android.  
**Цель:** каждый инструмент отображается одинаково корректно независимо от имени, набора аргументов, формата результата и размера вывода.

## 1. TOOL-01 — диагностика исходной ошибки

Проверить один реальный вызов `mcpServer_execute_python_code` во всех слоях:

1. Исходный кадр Pi `tool_execution_start`.
2. Объект `frame.args` и фактическое поле с Python-кодом.
3. Кадры `tool_execution_update`.
4. Финальный кадр `tool_execution_end`.
5. Объект `frame.result`.
6. Запись `tool-<id>.log`.
7. Ответ `GET /api/tasks/:id/tools/:callId/output`.
8. Отображение Web и KMP.

Собрать диагностический отчёт по восьми вызовам со скриншота: ID, состояние, названия полей аргументов, тип результата, размер вывода, наличие файла и результат API.

Не выводить в диагностические журналы содержимое секретных аргументов.

**Критерий:** установлено, на каком конкретно слое теряется информация.

## 2. TOOL-02 — единая модель инструмента

Создать общий контракт представления вызова, например:

```text
ToolCallView
  id
  name
  status
  startedAt
  endedAt
  durationMs

  summary
  argumentsPreview
  argumentsFormat
  argumentsAvailable

  outputPreview
  outputFormat
  outputStatus
  outputBytes
  truncated

  errorCode
  errorMessage
```

Это предварительная схема; сначала сверить существующие DTO и API.

Принципы:

- `summary` — краткое человекочитаемое описание.
- `argumentsPreview` — безопасный ограниченный фрагмент.
- `outputPreview` — ограниченный видимый результат.
- Полные данные подгружаются по отдельному запросу, когда они действительно сохранены.
- Нельзя подменять отсутствие вывода сообщением об ошибке сохранения.
- Все новые поля необязательные для совместимости с историческими событиями.

**Критерий:** неизвестный MCP-инструмент отображается без специального обработчика под его имя.

## 3. TOOL-03 — универсальные аргументы

Основные файлы:

- `src/task-manager.mjs`
- `web/chat-state.mjs`
- `ChatReducer.kt`
- `ChatModel.kt`

Сейчас используются преимущественно `command`, `path` и `file_path`.

Доработать формирование краткого описания.

Для известных форматов:

| Инструмент | Что показывать |
|---|---|
| `bash` | Команду, cwd, exit code |
| `read` | Путь и запрошенный диапазон |
| `edit` | Путь и краткое описание изменения |
| `write` | Путь и размер записываемого содержимого |
| `grep` | Шаблон и область поиска |
| `find` / `ls` | Целевой каталог и фильтр |
| `execute_python_code` | Фрагмент Python-кода |
| HTTP/API | Метод, URL и безопасные параметры |
| MCP с JSON | Структурированные аргументы |
| `subagent` | Задачу, имя агента и прогресс |
| Неизвестный инструмент | Автоматически сформированный JSON-preview |

Для неизвестных инструментов не выводить только `tool: name`. Если аргументы доступны, показывать их ограниченный структурированный preview.

Разделять метку и полные параметры.

Содержимое `code`, `script`, `python_code` и других возможных полей определять по фактической схеме инструмента, а не угадывать единственное имя поля.

### Безопасность

Выполнять редактирование или маскирование потенциальных секретов до формирования публичного preview. Не сохранять полные чувствительные параметры в новых логах только ради улучшения интерфейса.

**Критерий:** восемь вызовов одного Python-инструмента можно различить по аргументам.

## 4. TOOL-04 — надёжное сохранение вывода

**Приоритет:** P0

Основные файлы:

- `src/task-manager.mjs`
- `src/tool-output.mjs`
- `src/server.mjs`

Проверить весь жизненный цикл сохранения.

### Выявленные риски

1. Результат `tool_execution_end` исключается из сохраняемого события.
2. Полный вывод переносится в отдельный artifact.
3. Запись artifact производится асинхронно без ожидания завершения.
4. Ошибки записи местами подавляются.
5. Восстановление вывода из истории может не сработать, поскольку `result` из события уже удалён.
6. `toolResultText()` обрабатывает текстовые части и изображения, но не все варианты структурированного MCP-ответа.

### Требуемые изменения

- Ввести гарантированный порядок `tool_execution_end → сохранение результата → доступность результата через API`.
- Не делать финальную доступность вывода зависимой от незавершённой фоновой записи.
- Проверять и фиксировать ошибки сохранения.
- Поддерживать `content` с текстовыми частями, `structuredContent`, допустимые поля `details` и прочие форматы после проверки фактических контрактов Pi/MCP.
- Не сериализовать изображения или бинарные данные в текстовый вывод; хранить их отдельно и предоставлять метаданные/просмотр.
- Сохранять связь результата с `toolCallId` и сессией.
- Не допускать коллизии файлов инструментов по именам.
- Ограничивать использование памяти и размер передачи по SSE.

Для восстановления исторических результатов сначала проверить существующий `tool-*.log`, затем доступный исходный Pi session record, если он действительно содержит результат. Не обещать восстановление там, где данные уже утрачены.

**Критерий:** после успешного завершения инструмента API либо возвращает сохранённый результат, либо сообщает точную причину его недоступности.

## 5. TOOL-05 — корректные состояния вывода

Вместо одной надписи «Полный вывод не сохранён» реализовать состояния:

| Статус | Отображение |
|---|---|
| `RUNNING` | Инструмент выполняется, вывод формируется |
| `AVAILABLE` | Вывод доступен |
| `EMPTY` | Инструмент завершён без текстового вывода |
| `TRUNCATED` | Показана часть вывода, доступна загрузка остального |
| `MISSING` | Сохранённый результат не найден |
| `SAVE_FAILED` | Ошибка сохранения результата |
| `LOAD_FAILED` | Не удалось загрузить, можно повторить |
| `INTERRUPTED` | Выполнение прервано |

Не трактовать HTTP 404 одинаково для ещё работающего инструмента, пустого вывода и повреждённой старой истории.

**Важно:** в KMP `ToolRow` результат загрузки кешируется. Если пользователь раскрыл команду до её завершения, ошибка может остаться на экране. После завершения инструмента нужно обновлять статус и позволять повторно запросить вывод.

## 6. TOOL-06 — потоковый вывод

Доработать вывод инструментов во время работы.

Требования:

1. При старте сразу отображать название и параметры.
2. По поступлении данных обновлять окно stdout/stderr.
3. Для длинного вывода поддерживать ограниченный rolling buffer.
4. Не дублировать накопительные `partialResult`, принимая их за новые дельты.
5. При завершении синхронизировать итоговый результат.
6. Не перерисовывать всю историю чата при поступлении каждого блока вывода.
7. Поддерживать вывод без перевода строки, ANSI-последовательности, Unicode и многострочные ошибки.
8. После перезапуска клиента показывать сохранённое состояние.

Для встроенного `bash` и MCP-инструментов без streaming-поддержки предусмотреть корректное отображение только финального результата.

**Критерий:** UI показывает прогресс, если Pi его предоставляет, и не изображает streaming там, где его нет.

## 7. TOOL-07 — улучшить Web и Compose UI

Основные файлы:

- `clients/kmp/shared/.../chat/ChatItems.kt`
- `clients/kmp/shared/.../chat/ToolGroups.kt`
- `clients/kmp/shared/.../chat/ChatScreen.kt`
- `web/app.js`

### Свёрнутый вид

Отображать:

- Состояние.
- Название инструмента.
- Краткие параметры.
- Продолжительность.
- Признак результата или ошибки.

### Раскрытый вид

Отдельные секции:

**Аргументы:** код с подсветкой синтаксиса либо форматированный JSON.

**Результат:** stdout, stderr, текстовые данные, JSON или метаданные мультимедиа в зависимости от формата.

**Диагностика:** код завершения, время выполнения, статус, размеры, сведения об усечении.

Действия:

- Скопировать аргументы.
- Скопировать вывод.
- Повторить загрузку вывода.
- Раскрыть весь вывод.
- Сохранить вывод в файл.
- Открыть изменённый файл, если инструмент его действительно затронул.

При большом выводе использовать ограниченное окно с прокруткой, а не размещать весь текст в длинной Compose-колонке.

### Группировка

Сохранить возможность сворачивать несколько одинаковых вызовов, как восемь Python-команд на скриншоте.

Но внутри группы каждая команда должна иметь собственный ID, параметры, состояние и результат.

Отдельно исправить возможную перестановку вызовов при группировке по типу: хронологический порядок команд должен сохраняться. Не объединять разнесённые во времени группы, если между ними выполнялись другие инструменты.

## 9. Порядок реализации

**Коммит 1 — TOOL-DIAG:** реальный воспроизводимый тест MCP Python, классификация потери информации.

**Коммит 2 — TOOL-MODEL:** универсальное краткое описание аргументов и совместимый контракт.

**Коммит 3 — TOOL-PERSIST:** надёжное сохранение результатов и корректный API.

**Коммит 4 — TOOL-STATE:** разделение пустого, ожидаемого, недоступного и ошибочного вывода.

**Коммит 5 — TOOL-KMP:** интерфейс Desktop/Android и повторная загрузка.

**Коммит 6 — TOOL-WEB:** аналогичное поведение Web.

**Коммит 7 — TOOL-STREAM:** ограниченный streaming без роста памяти.

**Коммит 8 — TOOL-E2E:** реальные MCP, Pi, переподключение, compact и длинная история.

После каждого коммита выполнять соответствующие тесты и проверять, что остальные функции агента не затронуты.

## Definition of Done

Задача считается завершённой, если:

- Все известные и неизвестные инструменты имеют осмысленный заголовок.
- При наличии аргументов пользователь может их просмотреть.
- Доступный текстовый или структурированный результат отображается.
- Отсутствие вывода отличается от сбоя его сохранения.
- Результаты не смешиваются между вызовами.
- Порядок команд сохраняется.
- Большие результаты не раздувают SSE и память клиентов.
- Вывод остаётся доступным после перезапуска.
- Web, Desktop и Android показывают сопоставимые данные.
- Реальный тест с восьмью вызовами `mcpServer_execute_python_code` проходит полностью.
