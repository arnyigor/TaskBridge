# TaskBridge 2.0 — LAN-first: стабильность → производительность → провайдеры → OMP

**Дата:** 18 октября 2026  
**Статус:** проектный план, код репозитория не изменён; тесты в рамках подготовки документа не запускались.  
**Репозиторий:** https://github.com/arnyigor/TaskBridge  
**Исходная база для проверки:** ветка `codex/stabilize-taskbridge-20261015`, commit `bf3f26c1a73edd4a1ea7ac34c453c6a3d19f4992` (релиз 1.2.3 по отчёту стабилизации); перед разработкой перепроверить HEAD, CI и фактические версии локальной установки.

## 1. Итоговое решение

**Цель:** простой, быстрый и исключительно надёжный инструмент управления агентом на Windows из Desktop, браузера и Android по домашнему Wi-Fi. Через него удобно работать с локальными и облачными моделями, Git, проектами, сессиями и долгими задачами.

### Жёсткие границы

1. **Доступ к TaskBridge только по loopback и домашней LAN.** Не проектировать Relay/VPS/Tailscale, мобильный интернет, публичные endpoints, Cloudflare-туннели, автоматическую смену LAN/WAN. Не открывать порт на роутере. Оставить авторизацию/попарное подключение устройств в LAN.
2. **Обращение из домашнего ПК к облачным провайдерам моделей допустимо.** «LAN-only» относится к управлению TaskBridge, а не к запрету OpenAI, OpenRouter и других API.
3. **Не интегрировать Codex CLI / app-server / ACP.** Модели OpenAI доступны как провайдеры через текущий Pi, затем OMP, при соответствующей авторизации и тарифе. Это не означает импорта нативных Codex-сессий.
4. **Pi остаётся исполняющим ядром до самого финала плана.** После стабилизации, оптимизации и удобной настройки провайдеров проводится безопасный OMP-пилот, сравнительные тесты и управляемое переключение.
5. **Никакой переписи с нуля.** Переиспользовать существующие SQLite, HTTP/SSE, KMP, локальное хранилище Android, outbox, ModelCatalog, ModelProbe, ProviderStatus, управление локальными моделями, избранные модели и Git/worktree.
6. **Новые функции — только с тестами и проверенным rollback.** Не объединять произвольные улучшения в один коммит; не изменять существующие сессии Pi/OMP напрямую.

## 2. Что уже существует — не дублировать

| Область | Фактическая основа | Что улучшать |
|---|---|---|
| Сервер | Node 22+, SQLite, `src/task-manager.mjs`, `src/server.mjs` | декомпозиция, восстановление, границы ответственности |
| Стабилизация | В отдельной ветке исправлены идемпотентность команд, состояния после крашей, обработка RPC/SSE, Android state | перенос с проверкой, регрессии и устойчивость |
| Android KMP | ChatCache, сохранённый outbox, восстановление черновиков, `ChatSession`; Wi-Fi SocketFactory для RFC1918 | длинная история, расход батареи, лаги, быстрый reconnect |
| Модели | `src/model-catalog.mjs`, `/api/models`, фавориты, ModelPicker | упорядоченный каталог, быстрый поиск, фильтры, режимы, настройки |
| Диагностика моделей | `src/model-probe.mjs`, `/api/models/probe`, измерение TTFT | понятные статусы, безопасные тесты, раздельные ошибки |
| Состояние провайдеров | `src/provider-status.mjs`, `/api/providers/refresh`; часть балансов | покрытие, честная свежесть, отсутствие ложных цен/остатков |
| Синхронизация моделей | `src/provider-models.mjs` умеет opt-in добавлять модели к Pi `models.json` | лимиты каталога, дедупликация, пользовательское управление |
| Локальные модели | llama.cpp/Strata, сведения о GPU/RAM, загрузка и пресеты | отдельный ясный UX без лишнего ручного редактирования JSON |
| Git и проекты | Project/Work Item/Session/Run, рабочие каталоги/worktrees | визуальный diff, контроль файлов, последовательные коммиты |
| Сеть | LAN HTTP/SSE, pairing и сетевые проверки | простота, безопасная авторизация, стабильная работа в домашнем Wi-Fi |

**Известная проблема UX:** экран настроек KMP содержит и сведения о компьютере, и мониторинг, и каталог моделей, и балансы; сценария «Добавить → Проверить → Выбрать → Использовать» как последовательного мастера нет. Вместо ещё одного backend провайдера нужен единый пользовательский слой.

## 3. Правильный порядок релизов

**Фаза A → B → C → D → E.** Внутри фазы маленькие независимые merge requests. Не начинать E до зелёных контрольных испытаний A–D.

### Фаза A. Стабилизация (P0)

#### MR-A00 — принять проверенную стабилизацию

- Проверить расхождение `master` и `codex/stabilize-taskbridge-20261015`; переносить существующие исправления, не повторять их.
- Запустить `npm ci`, `npm run check`, `npm test`, поддерживаемые KMP JVM tests, полноценную сборку Android APK; проверить Windows portable.
- Зафиксировать точные версии Node, Gradle, Android, Pi и модели; документировать известные проблемы.
- Сделать копию `data/`, конфигов и сессий без секретов в публичном отчёте; проверить восстановление на копии.
- **Приёмка:** стабильный воспроизводимый baseline + таблица пройденных/пропущенных проверок. Не заявлять PASS без реального прогона.

#### MR-A01 — восстановление и идемпотентность

- Ключ команды (`commandId`) устойчив при повторе после обрыва связи; не исполнять side effect второй раз без новой команды.
- Развести `QUEUED`, `ACCEPTED`, `RUNNING`, `COMPLETED`, `FAILED`, `UNKNOWN_OUTCOME`; сделать точные UI-статусы.
- Восстановление SQLite/сессии после отключения сервера и завершения Pi; атомарность важнейших переходов; foreign key / миграции.
- **Приёмка:** kill в момент отправки, tool call, записи результата, перед ACK; повтор не создаёт двойных действий; восстановление корректно.

#### MR-A02 — lifecycle процессов и безопасность

- Ограничить управление PID только процессами, принадлежащими данной установке; исключить `taskkill /IM node.exe` и подобное.
- Устойчивый STOP и timeout, неоставление осиротевших runtime; защита от двойной записи одного session file.
- Подтверждения операций и файловые пути проверяются на стороне Windows-сервера, не на клиенте.
- **Приёмка:** тесты orphan/STOP/ownership, отмена не затрагивает чужие процессы.

#### MR-A03 — сохранность и диагностика

- SQLite backup/restore с корректным checkpoint и проверкой целостности; ротация логов с маскированием ключей.
- Health-раздел: состояние базы, Pi, моделей, занятых задач, последней ошибки, версий; копирование диагностического пакета без секретов.
- Проверить LAN pairing/revoke, смену IP, Wi-Fi reconnect и VPN, не ломая прямой локальный маршрут.
- **Приёмка:** восстановление из резервной копии и диагностика без приватных токенов.

### Фаза B. Производительность и UX (P1)

#### MR-B01 — измерение перед оптимизацией

- Synthetic fixtures: 100/1000 сессий, 10 000/100 000 событий, длинный reasoning/tool output, большие файлы и много проектов.
- Замерять startup, открытие сессии, scroll jank, пиковую память, запросы к серверу, нагрузку CPU, TTFT провайдера и задержку UI отдельно.
- Сохранять baseline; не принимать «стало быстрее» без повторяемых замеров на том же железе.
- **Приёмка:** отчёт p50/p95 + CI-регрессия для основных измерений (с реалистичными допусками).

#### MR-B02 — Android/Desktop: длинные чаты

- Paging/виртуализация по требованию, устойчивые ключи, правильная загрузка более старых страниц, dedup.
- Длинный Markdown, tool output, большие блоки кода, изображения и reasoning: предварительный просмотр + раскрытие по требованию, без потери текста при копировании.
- Черновик и положение скролла переживают поворот/перезапуск/переход между экранами.
- **Приёмка:** длительная прокрутка и многократное переключение сессий без OOM, скачков и дублей.

#### MR-B03 — сервер: горячий путь и SSE

- Ограниченный поток событий и backpressure; replay с cursor/seq при разрыве; не опрашивать Pi и аккаунты провайдеров на каждом `/api/info`.
- Кешировать дорогие статусы с TTL/stale-while-revalidate; отменять старые запросы при смене сессии; не пересоздавать полный snapshot при каждой текстовой дельте.
- Декомпозировать крупные файлы вокруг уже стабилизированных интерфейсов, без большого rewrite.
- **Приёмка:** корректность SSE под нагрузкой, предсказуемая RAM и отсутствие повторного запуска RPC из-за refresh UI.

#### MR-B04 — удобство выполнения задач

- Понятная очередь и её позиция, статусы thinking/tool/provider wait, STOP/continue/retry, причины ожидания и recovery action.
- Минимум лишних экранов: быстрый доступ к сессии, проекту, модели, журналу команд, diff и логам.
- Git workflow: отображение изменённых файлов, diff, проверка тестов и ручное подтверждение коммита; никогда auto-commit при провале проверки.
- **Приёмка:** сценарий «дать правку → дождаться → проверить diff → коммит → следующая задача» полностью понятен в UI.

### Фаза C. Провайдеры: простое и надёжное управление (P1, главный продуктовый акцент)

**Принцип:** пользователь настраивает подключение и выбирает модели, а TaskBridge знает, как представить их текущему агентному ядру. Не заставлять пользователя редактировать `models.json` или будущий `models.yml` для типовых провайдеров.

#### MR-C01 — ProviderProfile / ModelProfile и контракт

Ввести engine-neutral настройки, не привязанные к Pi JSON или OMP YAML:

```text
ProviderProfile:
  id, displayName, kind, baseUrl?, authRef?, enabled,
  discoveryMode, connectionHealth, lastCheckedAt,
  modelsFilter, visibility, source, revision
ModelProfile:
  providerId, modelId, displayName?, favorites,
  defaultThinking?, defaultContext?, settingsOverrides?,
  lastWorkingAt?, pinned
```

- Секреты — только серверный защищённый storage или специализированное хранилище ядра; в профиле хранится ссылка, не plaintext-токен.
- Единственный источник истины для пользовательских настроек; версия схемы и миграции; изменения применяются атомарно.
- Под текущий Pi создать `PiProviderConfigAdapter`: генерация/изменение корректных настроек с резервной копией и rollback; не писать одновременно в одно место из TaskBridge и Pi без блокировки.
- Авторизационные и модельные capabilities, errors и billing отделить от идентичности провайдера.
- **Приёмка:** можно сохранить/удалить/изменить профили, перезапустить сервер и получить те же данные без утраты авторизации.

#### MR-C02 — экран «Провайдеры» с мастером настройки

Три понятные зоны: **Облачные**, **Локальные**, **Пользовательские OpenAI-compatible**.

Путь добавления: `Добавить` → выбрать из готовых шаблонов → задать метод входа → `Проверить соединение` → выбрать модели → `Сохранить`.

- Для OAuth/ChatGPT показать «Войти на компьютере» / «Вход подтверждён» / «Требуется повторный вход». Не пытаться выдавать терминальный login за волшебный браузерный OAuth на телефоне.
- Для API key маскированное поле с раскрытием по удержанию, проверка без логирования и кнопка замены; не выводить секрет в `/api/info`, JSON ответа или crash report.
- Для Ollama/llama.cpp/Strata — адрес, локальная доступность, обнаруженные модели, проверка; не просить фиктивный API key.
- Для custom: URL, тип API (Completions/Responses, если поддерживается ядром), токен, заголовки (advanced), discovery.
- По умолчанию простой режим, продвинутые настройки скрыты.
- **Приёмка:** новое подключение к стандартному провайдеру настраивается из UI без правки файла конфигурации.

#### MR-C03 — честная диагностика и тестирование

- Разделять `URL reachable`, `Credentials configured`, `Authentication verified`, `Models discovered`, `Generation verified`.
- `GET /models` не доказывает, что генерация работает; для end-to-end проверки нужна отдельная явная проба модели, способная потребить платные токены.
- Читабельные статусы: 401/403 invalid key/permissions, 404 wrong model, 429 rate limit, 402 funds, 5xx provider, TLS/DNS timeout, unreachable LAN engine.
- Сбор timings: connection, time to first token, total, дата; кэш TTL; запрет автоматической платной пробы из-за открытия настроек.
- **Приёмка:** все ошибки воспроизводятся моками и выводят конкретную рекомендацию.

#### MR-C04 — управление каталогом моделей

- Быстрый поиск, группировка, favourites, recent, скрытые, pinned; фильтры code, reasoning, vision, context, cost, provider, local/cloud.
- Истинное `provider/modelId`, никакой путаницы имён локальных пресетов; неиспользуемые сотни моделей не затрудняют работу.
- `/models` discovery cache; ручной refresh и выборочные обновления, сохранение ручных override; показ количества скрытых моделей.
- Метаданные `contextWindow`, `maxTokens`, `thinking` и image capabilities показывать как advertised/verified/unknown, без выдуманных лимитов.
- **Приёмка:** выбрать нужную модель за несколько действий при сотнях моделей, без задержки на опрос всех облаков.

#### MR-C05 — настройки вызовов и fallback

- Разделить модель/провайдер от **профиля задачи**: «Быстро», «Точно», «Локально», «Для кода», «Проверка» — пользовательские пресеты вместо жёстко зашитого выбора.
- Настройки по model capabilities: thinking, контекст, температура только когда разрешено, max output, timeout, concurrency.
- `Fallback` не должен незаметно отправлять конфиденциальные файлы другому провайдеру или повышать стоимость: явное согласие; никакого автоматического переключения после побочных действий инструмента.
- Строго отделять ошибку модели от ошибки harness и от локальной сети Android.
- **Приёмка:** выбранный профиль корректно сохраняется и применяется к новым сессиям; смена модели во время выполнения блокируется или безопасно откладывается.

#### MR-C06 — балансы, лимиты, производительность

- Использовать существующий `provider-status.mjs`; где API баланс не возвращает, явно показывать «провайдер не предоставляет данные», а не 0.
- Не смешивать валюту, кредиты, подписочные окна, лимиты RPM/TPM. Всегда дата последней проверки и единица измерения.
- Никаких ложных цен; неизвестная цена = неизвестная. Ручной refresh по умолчанию; optional ограниченный фоновый refresh только при реальной пользе и безопасном API.
- Показ текущего ожидания по 429, времени до retry если provider сообщил, и реальных локальных pp/tg от Strata/llama.cpp.
- **Приёмка:** ложные остатки/лимиты не появляются, UI не создаёт платных запросов для обновления балансов.

#### MR-C07 — удобство локальных движков

- Не объединять **запуск локального движка** и **авторизацию облачного провайдера** в один сложный экран.
- Strata и llama.cpp: presets, loaded/offline, RAM/VRAM, ctx, запуск/остановка, копирование диагностик, отмена операций, изменения с preview.
- Если движок уже запущен извне — только подключаться и диагностировать, не запускать дубликат.
- Отображение реальных ошибок backend, не бесконечные spinner'ы и не придуманные метрики.
- **Приёмка:** минимальные действия для перехода между локальной и облачной моделью, без редактирования raw JSON.

### Фаза D. Закрепление качества и релиз (P0/P1)

#### MR-D01 — тестовая матрица

- Unit / API / KMP / end-to-end для CRUD профилей, импорта legacy конфигов, защиты секретов, тестов провайдера, model switching.
- Fault injection: Pi отказал, провайдер не ответил, ключ истёк, LAN Wi-Fi исчезла, Windows перезапустился, SQLite блокировка, каталог содержит 1000 моделей.
- Обязательный KMP Android APK build, smoke на устройстве, Windows portable release/upgrade.
- **Приёмка:** зелёный набор тестов и явный список остаточных известных ошибок.

#### MR-D02 — release/operability

- Мастер первого запуска: папка проектов → pairing → подключение модели → тест → первый промпт.
- Диагностический экспорт без секретов, лог ротация, поиск ошибок, версия и понятные способы восстановиться.
- Документация: один актуальный Quick Start, без исторических рекомендаций включать облачный транспорт. Убрать из стандартной навигации устаревшие cloud-настройки; не удалять код в рамках рискованного rewrite.
- **Приёмка:** чистая установка и миграция старой без ручных исправлений в конфиге.

### Фаза E. OMP — только в конце (P2 → P0 перед переключением)

**Не переписывать интерфейс провайдеров под OMP.** Переиспользовать `ProviderProfile`, `ModelProfile`, диагностику и UI, изменив backend-адаптер.

#### MR-E01 — контрольный A/B бенчмарк

- Сравнить последнюю проверенную Pi-версию и зафиксированную OMP-версию на одинаковой Windows-машине, локальной Qwen/Strata и одном облачном провайдере.
- Отдельно сравнивать базовые одинаковые инструменты и полный набор OMP: не приписывать улучшения edit/LSP «скорости движка».
- Тестовые задания: поиск в проекте, 1-file fix, multi-file refactor, Kotlin/Gradle, тест, ошибка инструмента, долгий reasoning, cancel/restart.
- Метрики: success rate, время, tokens, tool calls, ошибки, p95, RAM, crash/restore. Не покупать платные пробы без согласованного бюджета.
- **Gate:** решение о внедрении после отчёта, не заранее.

#### MR-E02 — OmpRpcAdapter

- Задокументировать и реализовать границу `AgentRunner`: start / prompt / steer / followUp / abort / state / events / models / thinking / compact / session / approvals / shutdown.
- Отдельный процесс `omp --mode rpc` на Windows, без обязательного перехода сервера TaskBridge на Bun.
- Обработка `ready`, negotiation RPC v2, `rpc_chunk` с проверками размера/порядка, `prompt_result`, `session_settled`, subagent frames, UI requests; нормализация в существующую TaskBridge event model.
- Не вызывать Pi-specific `get_commands` для OMP: использовать `get_available_commands`; mapping возможностей строго по feature flags.
- Ограничить memory и frame sizes, защититься от огромных логов, таймаутов и event storms.
- **Приёмка:** контрактные тесты и настоящие Windows smoke с локальной и облачной моделью.

#### MR-E03 — конфигурация и безопасная миграция провайдеров

- OMP имеет собственную конфигурацию `~/.omp/agent/models.yml`, OAuth/credential store и провайдеры. Преобразовывать только безопасные известные поля ProviderProfile; API-key не копировать в открытый YAML.
- Предусмотреть re-login, если учётные данные нельзя безопасно перенести, не обещать импорт OAuth.
- Предпросмотр преобразования Pi модели → OMP provider/model, конфликтов идентификаторов и capabilities; отдельное подтверждение на каждый спорный случай.
- Сохранить старые Pi JSONL в режиме read-only; при продолжении старой задачи создавать новую OMP-сессию с кратким handoff summary, не переписывать историю in place.
- Интеграцию «Продолжить из Markdown» выполнить здесь как независимый от engine импорт новой задачи.
- **Приёмка:** возможность вернуться к Pi без изменения/порчи исходных сессий и auth.

#### MR-E04 — staged rollout

- Pi остаётся fallback. OMP доступен за feature flag и только для новых сессий; старые продолжают работать по Pi.
- Испытания: длинная генерация, tools, approvals, cancel, switch model, restart, Android reconnect, high-load, duplicate send и локальные ограничения памяти.
- Default переключать только после повторяемого PASS. При провале — rollback без миграции/потери хранилища.
- **Приёмка:** нет регрессий P0, сохранены настройки пользователей и понятный выбор модели.

## 4. Проектное правило для провайдеров

```text
KMP/Desktop/Web (показывают одни и те же настройки)
      │ local REST/SSE
      ▼
TaskBridge ProviderService
      ├── ProviderProfileStore (не хранит открытые ключи)
      ├── CredentialRef / Secret resolver
      ├── Catalog + Capability + Health + Usage
      └── AgentConfigAdapter
            ├── PiProviderConfigAdapter   [пока]
            └── OmpProviderConfigAdapter  [в конце]

TaskBridge Orchestrator: Session / Run / Command (SQLite)
      └── Pi RPC пока → OMP RPC после испытаний
```

**Избегать двух источников истины.** Если OMP автоматически обнаруживает локальные модели/учётные данные, ProviderService должен читать и отражать его состояние, а не перезаписывать OMP без разбора. UI TaskBridge хранит только управляемые им настройки; imported/external записи помечаются источником и имеют ограниченный CRUD.

## 5. Пример целевого пользовательского сценария

**Настройки → Провайдеры → Добавить → OpenRouter.** Указать ключ один раз, увидеть `Доступен`, нажать `Обновить каталог`, отметить 3–5 избранных моделей. Открыть сессию, выбрать «Для кода», получить подтверждённую активную модель и изменить уровень thinking, если он поддерживается. При ошибке 429 UI показывает «Лимит запросов — повтор через …» (только если реальный Retry-After известен). При ошибке auth — «Ключ отклонён» и безопасная ссылка на настройки.

**Настройки → Провайдеры → Локальные → Strata.** TaskBridge показывает, что процесс уже запущен, его endpoint, живые метрики с временем последнего обновления и загруженную модель. Пользователь выбирает модель, контекст и стартует сессию; дублирующий сервер не поднимается.

**На Android:** те же провайдеры, что на Windows, без переноса API-ключей на телефон. Ключи остаются на домашнем ПК. Соединение TaskBridge — только домашняя Wi-Fi сеть, API провайдеров вызывается от сервера Windows.

## 6. Обязательные стандарты выполнения каждого MR

1. Перед началом `git status` и проверка baseline; отдельная рабочая ветка/worktree.
2. Короткое описание проблемы и reproduction до редактирования.
3. Один MR — один контролируемый логический результат. Не менять одновременно KMP UI, SQLite schema и AgentRunner без тестового стыка, если этого можно избежать.
4. Сначала unit / contract tests, затем минимальная реализация; после — regression tests.
5. Если затрагивается сессия/очередь, проверить kill/restart/disconnect, duplicate commands, source of truth.
6. Если затрагиваются креденшлы, проверить masked UI, server storage, sanitization, запрет раскрытия в логах и ответах API.
7. Документировать совместимость конфигураций и rollback; только после PASS — отдельный коммит.
8. Не использовать `git add -A` при работе агента; не убивать все `node.exe`; не перезаписывать работающий portable EXE.
9. Когда агент выполняет задачу, новая просьба пользователя идёт в очередь на следующий MR, а не смешивается с незавершённым diff.
10. Фиксировать реальное тестирование и не выдавать проектные решения за уже готовую функцию.

## 7. Итоговый порядок для исполнительного агента

| Очередь | MR | Цель |
|---:|---|---|
| 1 | A00–A03 | Стабилизация и достоверная база |
| 2 | B01–B04 | Производительность, интерфейс, надёжные операции |
| 3 | C01–C03 | Профили и мастер подключения, диагностика |
| 4 | C04–C07 | Каталог, модели, пресеты, балансы и локальные движки |
| 5 | D01–D02 | Release quality и проверка всей системы |
| 6 | E01 | Доказательная оценка OMP |
| 7 | E02–E04 | OMP-адаптер и только затем переключение |

**Definition of Done:** стабильное приложение, понятное пользователю управление провайдерами и моделями, быстрый список и чат, надёжное сохранение команд/сессий, работа Android по Wi-Fi, поддержка локальных моделей и облачных APIs, возможность обновления/отката без потери данных. OMP — замена исполняющего ядра после всех предыдущих работ, а не повод переписывать TaskBridge.
