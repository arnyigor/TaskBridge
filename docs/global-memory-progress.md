Ограничение консистентности: повторные обходы/хеши выявляют наблюдаемый дрейф, но не обеспечивают атомарный point-in-time snapshot при любых параллельных записях (включая ABA/изменение уже перепроверенного файла). Без сотрудничества writer или файлового snapshot нельзя честно гарантировать такую консистентность. Перед изменением рабочей установки нужен согласованный повторный snapshot с блокировкой writer либо механизмом snapshot ОС. Остановка MCP не выполнялась. Это также пока не полный MEM-01 основного плана: отдельные pi-memory-md, SQLite TaskBridge и конфигурации не резервировались.

Скрипт дополнительно отказывает при существующем каталоге назначения, вложении backup/source, непроверенном манифесте и небезопасных путях восстановления; не должен перезаписывать ранее существующие файлы. Тесты имитируют дрейф, исчезновение файла, подмену копии и traversal. Последняя проверка памяти: 65 PASS, 0 FAIL, 0 SKIP.

## MEM-01B — изолированная разработка legacy persistence

Базовая копия сохранена как `.local/mem01b/core.original.py` (SHA-256 `a1ab3f84ad5cb6de8e60c54b486d8021271fec10f4079939eb0650474372820b`). Разработка выполнена в `.local/mem01b/core.py`, без подключения копии к действующему MCP и без второго writer. Финальный SHA-256 после проверки NTFS и нормализации LF: `4ee74c0a09844fd92f034bc1ae23bbc354de410eea1b357393c07c7f856fb4e8`.

Root cause подтверждён на исходной реализации: из пяти целевых проверок четыре FAIL (продолжение после сбоя backup, преждевременный retention, обход replace, потеря конкурентной версии), одна PASS (успешное резервирование). Лог `.local/mem01b/baseline-reproduction.log`.

Подготовлен последовательный патч `docs/patch-memory-atomic-save.diff` к существующему `src/mcp_tools/core.py`, а не отдельная система хранения. Существующая ветка save и `_backup_topic` доработаны:

- Межпроцессный неблокирующий byte lock Windows / flock POSIX; SHA-CAS до записи и повторная проверка перед replace.
- Backup создаётся эксклюзивно, flush/fsync и проверка байтов обязательны; отказ блокирует изменение оригинала.
- Запись temp в том же каталоге, flush/fsync, `os.replace` без unlink-fallback; проверка результата.
- Один локальный журнал операции на тему: prepared/committed/aborted, старый/новый SHA, путь backup и имя temp. После process-crash состояние определяется по SHA; неизвестная версия не переписывается.
- После replace ошибки bookkeeping возвращают `MEMORY_COMMIT_UNCERTAIN`, до replace — `MEMORY_WRITE_FAILED`/`MEMORY_CONFLICT`.
- Retention выполняется только после подтверждённого commit, сохраняет непосредственный backup; ошибка cleanup не отменяет успешную запись, но видна в ответе.
- Независимый reviewer обнаружил P1: delete/archive/restore обходили lock. Все эти операции теперь используют тот же lock/recovery; восстановление версии использует тот же atomic persistence. Добавлены регрессии interleaving save с каждой операцией.
- Уникальные timestamp+nanosecond+UUID имена исключают коллизии архива и обеспечивают хронологическую сортировку снимков.

Тесты: `tests/test_legacy_memory_persistence.py` (AST-only: без импортов реального MCP, git и внешнего токенизатора). Финальная копия: **35 PASS, 0 FAIL, 0 SKIP**, включая настоящий Windows sharing violation через открытый handle без FILE_SHARE_DELETE, ENOSPC/partial temp/fsync/backup/replace, два процесса, аварийный выход до и после replace, recovery, безопасный restore, защищённый NTFS DACL и read-only attributes. Патч MEM-01B отдельно: 31 PASS, четыре проверки новой политики count ещё не применимы. Два обновлённых патча применены к отдельной исходной копии через GNU patch, результат побайтово совпал с финальным SHA; эта копия также прошла 35 тестов. Проверки выполнялись с fixture-каталогами в `.local/mem01b`, PYTHONDONTWRITEBYTECODE=1.

### NTFS — подтверждённый дефект и исправление

Нативный тест сначала FAIL: `os.replace` подменял защищённый DACL исходной темы наследуемым DACL временного файла. В изолированной копии добавлен `_copy_file_security`: owner/group проверяются на совпадение (при несовпадении отказ, а не попытка смены владельца); DACL и защита наследования переносятся и проверяются через Win32. ACL применяется к ещё пустому backup/temp ДО записи приватных байтов. Информационный флаг AUTO_INHERITED может сбрасываться Windows; проверяются фактические ACE, owner/group и защищённость DACL. На POSIX копируется mode, но эта ветка не проверена нативно в данном Windows-окружении.

Обычные/archive Windows-файлы поддержаны; read-only, hidden/system, compressed/encrypted, sparse/reparse и другие специальные атрибуты дают безопасный отказ до замены оригинала вместо молчаливой потери атрибутов. Проверены отказ изменения security descriptor и неизменность SHA, read-only и отсутствие записи содержимого до установки ACL.

### MCP transport — отдельная интеграционная проверка PASS

`.local/mem01b/integration-server` содержит копию memory-domain модуля и точных зависимостей его импортов из установленного MCP. Запуск через установленный `.venv/Scripts/python.exe`; реальный FastMCP, Pydantic-схема инструмента и stdio ClientSession. Проверены initialize/list_tools/save/load/search/history/restore-version/archive/restore/delete, сохранение при 30+ темах и байтовое восстановление backup. Лог `.local/mem01b/mcp-integration.log`.

Ограничения integration: зарегистрирован memory-domain инструмент, не все 31 инструмента общего сервера; внешний токенизатор и git заменены тестовыми функциями; память, индекс pi-memory-md, access-журнал и логирование направлены только внутрь изолированного дерева. Рабочий MCP не вызывался и не перезапускался.

**Оставшиеся ограничения перед развёртыванием:** power-loss durability не доказана (нет platform-specific sync метаданных каталогов); SACL/аудит, integrity labels и альтернативные NTFS streams не сохраняются и требуют отдельной поддержки/проверки применимости к реальному store. Установку на произвольные файлы с такими метаданными безопасной не объявляем. Полная общая сборка всех MCP-инструментов и реальные токенизатор/git пока не проверены. Lock защищает участвующие writer, не чужие редакторы между последним SHA-check и replace. CAS фиксирует наблюдаемую сервером версию, не версию прочитанного ранее клиентом текста. При раннем crash могут остаться temp/неполные backup; они не воспроизводятся поверх данных и не удаляются автоматически. Поведение при реальном полном диске имитировалось, диск не заполнялся. До рабочей установки нужны свежий согласованный backup, проверка применимости указанных ограничений к реальным файлам и отдельное разрешение пользователя.

**Оставшиеся риски/незавершённость:**

- Для точного eligible/total после динамической stale-проверки и дедупликации читаются тела всех совпавших кандидатов, не только возвращённой страницы. Это сознательная стоимость точного total без новой схемы хранения. FTS выбирает совпадения, чтение выдачи и контекст ограничены; fallback дороже и честно помечен. Бесконечный рост во время запроса ограничен исходным числом индексных кандидатов.
- Страницы стабильны для неизменённых данных. При одновременном редактировании между отдельными запросами offset не является snapshot/cursor; запрос может увидеть уже обновлённые данные.
- Во время первой синхронизации индекс читает все заметки; ограничено число возвращаемых результатов, не стоимость полной переиндексации.
- globalStats.stored — число файлов, не классификация active/archive/superseded.
- Глобальный путь `_global` пока не конфигурируемый (MEM-04 отдельно).

## Python .venv / системный executable

Read-only диагностика pyvenv.cfg: CPython 3.12.10, virtualenv 20.31.2, base-executable `C:/Program Files/Python312/python.exe`, include-system-site-packages=false. `.venv/Scripts/python.exe` — отдельный Windows launcher (274424 байта), системный executable — 104952 байта.

Отдельный диагностический процесс через ту же команду .venv показал:

- sys.executable: `.venv/Scripts/python.exe`;
- sys.prefix: `.venv`;
- sys.base_prefix: `C:/Program Files/Python312`;
- импорт mcp: `.venv/Lib/site-packages/mcp/__init__.py`.

Это согласуется с нормальным redirector Windows virtualenv: системный дочерний Python не доказывает обход окружения. На момент этой диагностики активный MCP не перезапускался. sys.prefix действующего PID напрямую не считывался, поэтому результат диагностического процесса нельзя выдавать за снимок globals живого сервера.

### Свежий backup и гарантия durability

Создан `.local/mem01/backup-20261029-145425`, SHA-manifest внутри; восстановлен отдельно в `.local/mem01/restore-20261029-145425`. **1255 файлов, 1587335 байт**, все восстановлены; ошибок и наблюдаемого дрейфа 0. Лог `.local/mem05-final/fresh-backup-20261029-145425.json`. Это наблюдаемый согласованный снимок по повторным хешам, не доказанная атомарная копия при любой гонке writer. До развёртывания всё ещё нужен snapshot ОС или согласованная пауза/блокировка writer, не фиктивный advisory lock, который старый writer игнорирует.

Гарантия текущей реализации ограничена протестированными сбоями процесса: replacement, journal recovery и проверенные backup. **Power-loss durability не заявляется**: нет подтверждённой синхронизации directory metadata/аппаратного кэша, питание не отключалось, несколько файлов не объявляются транзакцией. Для такой гарантии нужен отдельный дизайн и испытание; увеличение MAX_ACTIVE_PROJECTS её не даёт.

Защищённый DACL, memory-domain stdio, deep pagination и счётчики проверены. До развёртывания нужны полное резервирование и согласованный snapshot. Пользователь отдельно разрешил перезапуск MCP в предыдущем ходе, и он был выполнен; в ходе разработки MEM-01B/MEM-02 новых перезапусков не было. Установленный модуль, конфигурация, память, writer и миграция не менялись.
