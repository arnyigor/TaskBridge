## Часть 1. Решения и границы

### 1.1 Принятые решения

| # | Решение | Почему |
|---|---|---|
| D1 | Развиваем TaskBridge, а не переходим на OpenClaw | OpenClaw читает сессии Pi из JSONL и умеет только `pi --session <id>` в терминале; к живому процессу Pi он не подключается |
| D2 | Один живой Pi-процесс на сессию, все клиенты — поверхности к нему | Главное отличие TaskBridge: телефон, браузер и терминал видят один и тот же runtime |
| D3 | Основной клиент — KMP (Android + Desktop), веб-UI остаётся запасным | KMP уже почти готов и удобнее |
| D4 | Доступ из интернета — через Tailscale, без Vercel и без проброса портов | Нет публичной точки входа; доступ к TaskBridge = доступ к shell на ПК |
| D5 | KMP ходит на Tailscale-IP ПК (`100.x.y.z`) по HTTP | Не зависит от кастомного DNS телефона; трафик уже зашифрован WireGuard; нативному приложению не нужен secure context |
| D6 | Транспорт событий остаётся SSE | `id` + `Last-Event-ID` дают ту же гарантию, что `fromSeq` в WebSocket; переписывать транспорт не нужно |
| D7 | SQLite откладываем | Файловое хранилище пока не блокер; переход — когда начнёт мешать |

### 1.2 В объёме

1. Удалённый доступ через Tailscale и безопасность при нём.
2. Надёжный поток событий: `seq`, `Last-Event-ID`, heartbeat, idempotency.
3. Явная state machine runtime и защита от двойной записи сессии Pi.
4. Параллельные сессии и ограничение нагрузки на локальную модель.
5. Жизненный цикл: idle-таймаут, закрепление, авто-resume.
6. CLI `taskbridge pi` — attach к живой сессии из терминала.
7. KMP: сеть (LAN/tailnet), синхронизация, уведомления, pairing по QR.

### 1.3 Вне объёма (сознательно)

- Мессенджеры (Telegram и др.), облачные воркеры — это ниша OpenClaw.
- Раннеры Codex / Claude Code — отложено на неопределённый срок.
- WebSocket-транспорт, отдельный daemon `agentd`, мультипровайдерная абстракция.
- Take ownership внешней сессии с остановкой чужого процесса — только view/clone.

## Часть 2. Спецификация доработок

### 2.1 Удалённый доступ (Tailscale)

#### Схема

```
Телефон (Tailscale always-on) ──WireGuard──► ПК (Tailscale)
      │                                          │
      │ KMP:     http://100.x.y.z:8787  ─────────┤ TaskBridge :8787
      │ Browser: https://pc.<tailnet>.ts.net ────┤ tailscale serve → 127.0.0.1:8787
      │ Дома:    http://192.168.x.x:8787 ────────┘ (опционально, LAN)
```

#### Требования

- **R1.1 Авторизация обязательна**, если слушаем не только loopback. При `server.host != 127.0.0.1` и `auth.enabled = false` — сервер не стартует, либо стартует только на loopback с явным предупреждением в консоли.
- **R1.2 Bearer-токен для нативных клиентов.** Сейчас pairing даёт cookie. Добавить выдачу токена устройства:
  - `POST /api/auth/pair` с `{code, deviceName, clientKind}` возвращает `{deviceId, token}`;
  - запросы с `Authorization: Bearer <token>`;
  - хранение: `data/server-auth.json` → список устройств `{deviceId, name, kind, tokenHash, createdAt, lastSeenAt}`;
  - отзыв: `DELETE /api/auth/devices/:id` (только с localhost или от устройства с правом admin);
  - токен хранится только в виде хэша, сравнение timing-safe (как сейчас).
- **R1.3 Origin.** Добавить `server.allowedOrigins` (включить `https://pc.<tailnet>.ts.net`). Правило:
  - запрос с заголовком `Origin` — Origin обязан быть в allowlist (защита браузера от CSRF);
  - запрос без `Origin` (нативный клиент, CLI) — допускается только с Bearer-токеном.
- **R1.4 ⚠ Ловушка `tailscale serve`.** За reverse proxy все запросы приходят с `127.0.0.1`. Сейчас `GET /api/auth/pairing` отдаёт код «только с localhost», а rate limit, вероятно, считает по IP. Через `serve` это значит:
  - pairing-код станет доступен любому устройству tailnet;
  - rate limit станет общим на всех.

  Решение:
  - ввести флаг `server.behindLocalProxy`; при нём «localhost-only» эндпоинты проверяют не IP, а отсутствие заголовков проксирования (`X-Forwarded-For` / `Tailscale-User-Login`) — либо проще: pairing-код показывать **только в консоли сервера и в QR на экране ПК**, а эндпоинт `/api/auth/pairing` удалить;
  - rate limit считать по `X-Forwarded-For`, только если запрос пришёл с loopback и флаг включён.
- **R1.5 Firewall Windows.** Правило входящих для порта 8787 только с `100.64.0.0/10` (Tailscale) и домашней подсети. Пример (сверить с текущей политикой):
  ```powershell
  New-NetFirewallRule -DisplayName "TaskBridge" -Direction Inbound -Protocol TCP `
    -LocalPort 8787 -RemoteAddress 100.64.0.0/10,192.168.1.0/24 -Action Allow
  ```
  Проброс портов на роутере и UPnP — не включать (как и сейчас в README).
- **R1.6 HTTPS для браузера** — через `tailscale serve` на loopback-адрес TaskBridge (точный синтаксис сверить с `tailscale serve --help` установленной версии). Self-signed HTTPS TaskBridge для tailnet не нужен.
- **R1.7 Pairing по QR.** Экран на ПК (localhost-страница веб-UI и/или вывод в консоль) показывает QR с JSON:
  ```json
  {
    "v": 1,
    "name": "HOME-PC",
    "endpoints": [
      {"kind": "lan", "url": "http://192.168.1.42:8787"},
      {"kind": "tailnet", "url": "http://100.101.102.103:8787"},
      {"kind": "tailnet-https", "url": "https://pc.tailnet-xxx.ts.net"}
    ],
    "pairingCode": "482913",
    "expiresAt": "2026-09-25T21:10:00Z"
  }
  ```
  Tailscale-IP определять автоматически (адрес интерфейса из `100.64.0.0/10`) с возможностью переопределить в конфиге.

#### Кастомный DNS на телефоне

- Системный «Частный DNS» не конфликтует с Tailscale, но может мешать резолву имён `*.ts.net`. Поэтому KMP использует IP (D5).
- DNS через приложение (AdGuard, NextDNS и т.п.) занимает VPN-слот Android — с Tailscale одновременно не работает. Зафиксировать в README.

### 2.2 Надёжный поток событий

#### Модель события

Каждое сохраняемое событие задачи получает монотонный `seq` внутри задачи (если в `events.jsonl` уже есть порядковый id — использовать его).

```json
{
  "seq": 1284,
  "ts": "2026-09-25T20:14:03.120Z",
  "type": "tool_execution_start",
  "source": {"kind": "pi"},
  "data": { }
}
```

Пользовательские сообщения дополнительно несут источник:

```json
"source": {"kind": "client", "clientKind": "android", "deviceId": "d_7f2a"}
```

`clientKind`: `android` | `desktop` | `web` | `cli`.

#### Требования

- **R2.1** `seq` выдаётся и событие дописывается в `events.jsonl` **до** рассылки клиентам. Запись в файл сериализована (одна очередь записи на задачу).
- **R2.2** SSE (`GET /api/tasks/:id/stream`):
  - каждое сохраняемое событие отправляется с полем `id: <seq>`;
  - поддержка заголовка `Last-Event-ID` и параметра `?after=<seq>` (приоритет у заголовка);
  - алгоритм подключения без дыр:
    1. подписаться на внутренний bus задачи и буферизовать;
    2. прочитать из `events.jsonl` события с `seq > after`;
    3. отправить snapshot (см. R2.4), затем историю;
    4. из буфера отправить только события с `seq` больше последнего отправленного;
    5. дальше — live.
- **R2.3 Стриминговые дельты** (текст ассистента по кусочкам) — эфемерные: отправляются без `id`, в историю не пишутся (логика `event-trim.mjs` уже отбрасывает устаревшие дельты — согласовать). Финальное сообщение сохраняется как обычное событие.
- **R2.4 Snapshot** при подключении: `{task, state, activity, lastSeq, partialAssistantText, pendingUiRequest?, queuedMessages}`. Клиент после обрыва сразу видит незавершённый текст.
- **R2.5 Heartbeat**: комментарий SSE `: ping` каждые `server.sse.heartbeatSec` (по умолчанию 15 с). Клиент считает соединение мёртвым после 3 пропущенных интервалов.
- **R2.6 Idempotency**: `POST /api/tasks` и `POST /api/tasks/:id/message` принимают `clientRequestId` (UUID).
  - Хранение: последние N ключей на задачу в `task.json` (или отдельный `requests.json`), TTL 24 ч.
  - Повтор с тем же ключом → `200` с исходным результатом, без повторной отправки в Pi.
  - Тот же ключ с другим текстом → `409`.
- **R2.7 Статусы отправки** в событиях: `message_queued {clientRequestId, position}` → `message_dispatched {clientRequestId, mode: prompt|steer|follow_up}`.

### 2.3 State machine runtime и защита сессий

#### Состояния runtime задачи

| Состояние | Смысл |
|---|---|
| `STARTING` | запускается `pi --mode rpc` |
| `IDLE` | Pi жив, turn не идёт |
| `WORKING` | идёт turn; `activity` уточняет (`tool`, `streaming`, `compacting`, `waiting_model`) |
| `WAITING_USER` | Pi ждёт ответа на UI-запрос расширения |
| `ABORTING` | идёт STOP (`clear_queue` + `abort`, затем kill по таймауту) |
| `SLEEPING` | Pi остановлен по idle-таймауту, сессия восстанавливается автоматически |
| `RESTORABLE` | Pi упал / TaskBridge перезапущен; следующее сообщение поднимет процесс с тем же файлом сессии |
| `STOPPED` | остановлен пользователем |

Отдельно — статус задачи для пользователя (`RUNNING / DONE / CANCELLED / FAILED …`) остаётся как есть; state runtime — это слой ниже.

#### Требования

- **R3.1** Все переходы — через одну функцию с таблицей допустимых переходов; недопустимый переход → лог с `taskId` и текущим состоянием, состояние не меняется. Каждый переход — событие `runtime_state {from, to, reason}`.
- **R3.2** Все команды к Pi (prompt, steer, follow_up, abort, compact, get_state, ответ на UI-запрос, graceful stop) проходят через **одну очередь на задачу**. Параллельная запись в stdin невозможна.
- **R3.3** Каждая RPC-команда с ожиданием ответа имеет таймаут; по таймауту — ошибка клиенту, лог, сессия не зависает.
- **R3.4** Чтение stdout Pi: буферизация по `\n`, корректная склейка строк на границе чанков, декодирование UTF-8 через `TextDecoder` в потоковом режиме (кириллица на границе чанка). Проверить, что текущий «строгий LF-JSONL parser» это покрывает; добавить тест.
- **R3.5 Защита от двойной записи сессии Pi (ownership guard).** Перед запуском `pi --session <file>` (resume, импорт, авто-resume):
  1. в своих runtime'ах нет живого процесса с этим файлом;
  2. нет чужого процесса `pi`, запущенного с этим файлом (Windows: командные строки процессов через `Get-CimInstance Win32_Process` / WMI — вызывать с таймаутом, результат кэшировать на несколько секунд);
  3. файл сессии не менялся последние `pi.sessionQuietMs` (по умолчанию 10 с).

  Если проверка не прошла → `423 SESSION_BUSY` с вариантами: **View** (только чтение) или **Clone** (копия JSONL в новый файл сессии, работа с копией). Импорт через `native-sessions.mjs` помечает такие сессии как `EXTERNAL_ACTIVE`.
- **R3.6** При старте TaskBridge — reconciliation: задачи, которые были `WORKING/IDLE`, переходят в `RESTORABLE` (вместо текущего `FAILED_RECOVERY` для случаев, когда файл сессии Pi цел); осиротевшие процессы Pi из прошлого запуска (PID + время старта в `task.json`) завершаются деревом.

### 2.4 Параллельные сессии и нагрузка на модель

- **R4.1** Снять ограничение «одна активная inference-задача». Настройки:
  ```json
  "runtime": {
    "maxLive": 6,
    "maxWorking": 3
  }
  ```
  `maxLive` — сколько процессов Pi может жить одновременно; `maxWorking` — сколько одновременно в `WORKING`.
- **R4.2 Лимит на endpoint модели.** Первая версия — без прокси: TaskBridge знает, какой провайдер у задачи (из `pi.args` / профиля / `get_state`), и не даёт одновременно больше `maxConcurrent` задач в `WORKING` на один endpoint. Остальные ждут с `activity: waiting_model` и позицией в очереди.
  ```json
  "modelEndpoints": [
    {"id": "llama-local", "match": {"provider": "llama.cpp"}, "maxConcurrent": 2},
    {"id": "qwen-web",    "match": {"provider": "qwen-local"}, "maxConcurrent": 1}
  ]
  ```
  Для llama-server `maxConcurrent` = число слотов `-np`. Напоминание: контекст делится между слотами (`ctx / np` на слот).
- **R4.3** Задача, ожидающая модель, не держит «пустой» turn в Pi: промпт стоит в очереди TaskBridge и отправляется в Pi, когда освобождается слот.
- **R4.4** Параллельные задачи в одном проекте безопасны при включённом worktree (уже есть: worktree на задачу). Без worktree — предупреждение в UI/API при второй живой задаче в том же `cwd`.
- **R4.5 (позже, при необходимости)** — локальный HTTP-прокси перед llama-server для точного учёта in-flight запросов.

### 2.5 Жизненный цикл

- **R5.1** `runtime.idleTimeoutMin` (по умолчанию 30; `0` = никогда). По таймауту — graceful stop Pi через очередь команд, состояние `SLEEPING`.
- **R5.2** Закрепление задачи (`pinned: true`, `PATCH /api/tasks/:id`) отключает idle-таймаут.
- **R5.3** Сообщение в `SLEEPING` / `RESTORABLE` → авто-resume: поднять Pi с тем же файлом сессии (с ownership guard), дождаться `IDLE`, отправить сообщение. Гонка «сообщение пришло во время засыпания» закрывается очередью команд (засыпание — тоже команда в очереди).
- **R5.4** Graceful shutdown TaskBridge (Ctrl+C / закрытие `start.cmd`): не принимать новые команды, остановить Pi-процессы деревом, дописать состояния.

### 2.6 CLI `taskbridge pi`

Тонкий клиент к тому же HTTP API. **Сам Pi не запускает.**

| Команда | Действие |
|---|---|
| `taskbridge pi` | attach к задаче текущего `cwd` (путь проекта или его worktree); если несколько — выбор; если нет — предложить `new` |
| `taskbridge pi list` | задачи: id, проект, state, activity, последняя активность |
| `taskbridge pi attach <id>` | attach к конкретной задаче |
| `taskbridge pi new ["текст"]` | новая задача в проекте текущего `cwd` |
| `taskbridge pi stop [<id>]` | остановить runtime |

Внутри attach:

- Ctrl+C: в `WORKING` → STOP текущего turn; в `IDLE` → detach (Pi продолжает жить).
- `/detach`, `/stop`, `/compact`, `/state`, `/pin` — маппинг на API.
- При attach — хвост истории (последние N turn'ов через `event-window.mjs`), сообщения с других устройств помечены: `── from Android ──`.
- UI-запросы расширений — интерактивный выбор в терминале.
- Авторизация: CLI на том же ПК берёт токен из `data/cli-token` (создаётся сервером при старте, права только для текущего пользователя).
- Реализация: `bin` в `package.json`, Node ESM, без зависимостей; рендер — `readline` + минимальный ANSI. Проверить позже возможность использовать `pi-tui`.

### 2.7 KMP-клиент

#### Сеть

- **R7.1** Устройство хранит список endpoint'ов из QR (`lan`, `tailnet`, `tailnet-https`).
- **R7.2** Выбор endpoint'а:
  - при старте, при `ConnectivityManager.NetworkCallback` (`onAvailable` / `onLost` / смена транспорта) и при обрыве потока;
  - параллельно пингуем `GET /api/health` по всем endpoint'ам с таймаутом ~1 с;
  - приоритет: `lan` → `tailnet` → `tailnet-https`;
  - выбранный endpoint кэшируется до следующего события сети.
- **R7.3** Android `network_security_config`: cleartext разрешён **только** для IP ПК в LAN и Tailscale-IP; глобально cleartext запрещён.
- **R7.4** Tailscale на телефоне — «Постоянный VPN» в настройках Android. В приложении — понятная ошибка «ПК недоступен: проверьте Tailscale», если не отвечает ни один endpoint.

#### Синхронизация

- **R7.5** SSE-клиент (Ktor SSE или OkHttp EventSource):
  - хранит `lastSeq` по задаче (в памяти и в кэше);
  - переподключение с `Last-Event-ID`, backoff с jitter (0.5 → 1 → 2 → … → 30 с), мгновенно — при смене сети или возврате в foreground;
  - watchdog heartbeat: 3 пропуска → переподключение;
  - дедуп: `seq <= lastSeq` игнорируется; дыра (`seq > lastSeq + 1`) → дозапрос `GET /events?after=`.
- **R7.6** Outbox: каждое сообщение получает `clientRequestId` до отправки, сохраняется локально, статусы `pending → sent → queued → dispatched`. Повторная отправка — с тем же ключом.
- **R7.7** Редьюсер состояния задачи — чистая функция, покрытая тестами на записанных событиях.

#### Уведомления и фон

- **R7.8** Уведомления: `WAITING_USER` (высокий приоритет), завершение turn/задачи, ошибка. Группировка по задаче, без спама.
- **R7.9** Фон: пока есть задачи в `WORKING`/`WAITING_USER` — foreground service с подключением к лёгкому общему потоку статусов (см. R7.10). Тип foreground service и лимиты времени проверить для целевых API Android (14/15). Fallback — периодический опрос через WorkManager.
- **R7.10 Новый эндпоинт** `GET /api/stream` — SSE только со сменами состояний всех задач (`runtime_state`, `task_status`, `ui_request`), без содержимого. Для списка задач и фоновых уведомлений.

#### UI

- **R7.11** Список задач: проект, заголовок, state, activity (`pytest tests/…`), время; `WAITING_USER` сверху; индикатор `waiting_model` с позицией.
- **R7.12** Экран задачи: метки источника сообщений, статусы outbox, режим follow-up/steer при `WORKING`, кнопка STOP только в активных состояниях, ответ на UI-запросы, pin.
- **R7.13** Экран «Устройства/Подключение»: текущий endpoint, тип сети, пинг, повторный pairing, отзыв устройства.

| DELETE | `/api/auth/devices/:id` | новый — отзыв |
| GET | `/api/auth/pairing` | удалить или ограничить (R1.4) |
| GET | `/api/pairing-qr` | новый — QR, только localhost без прокси-заголовков |
| POST | `/api/tasks` | + `clientRequestId` |
| POST | `/api/tasks/:id/message` | + `clientRequestId`; ответ + `position` |
| PATCH | `/api/tasks/:id` | + `pinned` |
| GET | `/api/tasks/:id/stream` | `id:` у событий, `Last-Event-ID`, snapshot, heartbeat |
| GET | `/api/tasks/:id/events` | события содержат `seq`, `source` |
| POST | `/api/tasks/:id/ui-response` | новый (если сейчас UI-запросы расширений не прокинуты) |
| POST | `/api/tasks/:id/clone` | новый — клон сессии (R3.5) |
| GET | `/api/stream` | новый — общий поток статусов |
| GET | `/api/health` | + версия TaskBridge, версия Pi, `apiVersion` |

Ошибки — единый формат `{code, message, state?}`; новые коды: `SESSION_BUSY` (423), `INVALID_STATE` (409), `DUPLICATE_REQUEST_MISMATCH` (409), `CAPACITY` (429).

## Часть 4. Порядок, риски, правила

### 4.1 Порядок

```
Этап 0 → Этап 1 → Этап 2 ─┬─→ Этап 3 → Этап 4 ─┬─→ Этап 6 → Этап 7
                          │                    │
                          └─→ Этап 5 (KMP) ────┘
```

Первая заметная польза для повседневной работы — после этапов 1 и 2: телефон работает вне дома, и переподключения не теряют события.

### 4.2 Риски

| Риск | Что делаем |
|---|---|
| Через `tailscale serve` все запросы выглядят как localhost | R1.4 — убрать localhost-only выдачу кода, учесть прокси-заголовки |
| Частный DNS мешает `*.ts.net` | KMP по IP (D5) |
| DNS-приложение занимает VPN-слот | Документировать; альтернатива — системный Частный DNS |
| Формат RPC-событий Pi меняется между версиями | Проверка версии (этап 0), fixtures, контрактные тесты |
| WMI-проверка процессов медленная | Таймаут, кэш, fallback на «тишину» файла |
| Фоновые ограничения Android режут поток | Foreground service только при активных задачах + WorkManager fallback |
| Отказ relay Tailscale / проблемы доступности | Запасной вариант — свой WireGuard или Headscale; код TaskBridge не меняется |

### 4.3 Правила разработки

- Каждый баг, найденный руками, сначала превращается в тест (fake-pi или MockEngine), потом чинится.
- Логи: в каждой строке `taskId`, `seq` (если есть), `deviceId` (если есть), state runtime.
- Изменения API — только обратно совместимые; `apiVersion` в `/api/health`, KMP проверяет его при подключении.
- Любая новая точка входа в запуск `pi --session` проходит через ownership guard.
