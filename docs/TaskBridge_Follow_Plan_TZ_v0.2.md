# TaskBridge — Follow Plan (PLAN-FOLLOW-01)

**Статус:** архитектурное ТЗ v0.2, до фиксации неоговорённых продуктовых решений.  
**База:** TaskBridge `master` / стабильный baseline `taskbridge-stable-2026-10-22`.  
**Не путать с:** будущим read-only Plan Mode, который составляет планы без изменения проекта.

## 1. Цель и границы

Follow Plan — режим исполнения **существующего пользовательского плана**, выбранного как один главный Markdown-файл, в обычной Pi-сессии с доступом к инструментам. После каждого завершённого хода контроллер проверяет результаты, состояние файла и оставшиеся шаги. Если задачи остаются, формирует целевой следующий запрос; при найденном связанном с задачей дефекте допускает контролируемое уточнение файла; при выполнении всех критериев объявляет завершение плана. Ход Pi `SUCCEEDED` сам по себе **не равен** `PLAN_COMPLETED`.

Применимо к Web, KMP Desktop и Android в локальной сети, с одним сервером-владельцем состояния. Не входит в первую версию: генерация плана с нуля, read-only планирование, DAG-параллелизм, автоматические коммиты, фоновые независимые агенты, сложные мультипроектные планы, микросервисы.

### Рабочие входы

- Выбранная Pi-сессия, её workspace, модель и действующие правила безопасности.
- Путь к **одному** файлу плана, например `docs/IMPLEMENTATION_PLAN.md`. Файл может быть существующим; при несовместимом свободном формате требуется явный импорт в управляемый Markdown, без тихого уничтожения исходного текста.
- Существующий пользовательский текст/прикреплённые материалы, настройки режима исполнения и ограничения автоматических циклов.

### Выходы

- Обновлённый **тот же** Markdown-план со стабильными ID и статусами задач.
- Обычные изменения проекта, результаты команд и тестов в существующих Runs/Pi-сессии.
- События прогресса/ошибок в существующем SSE, карточка плана в чате, сводка по завершении.

## 2. Основные инварианты

1. **Один файл — источник истины для содержания и состояния шагов.** Никаких параллельных `TODO.md`, `progress.json`, `plan2.md`. В SQLite допустима служебная запись исполнения: привязка сессии/файла, хэш, активный цикл, ключ команды, stop epoch, lease и лимиты; она не заменяет план.
2. **План не выполняется по одному текстовому ответу «готово».** Проверяются все открытые пункты и критерии.
3. **Один активный цикл на сессию.** Управление из двух клиентов не даёт параллельных запусков.
4. **Нет повтора неизвестных побочных действий.** После краша/UNKNOWN_AFTER_CRASH или неопределённого завершения Pi переход в `PAUSED_REVIEW`, оператор сверяет результат.
5. **STOP сильнее auto-continue.** После принятого STOP отменённый цикл не запускает новый ход.
6. **Каждый цикл ограничен.** При отсутствии прогресса, проблеме провайдера, бюджете или повторном отказе — пауза и отчёт, не бесконечный loop.
7. **При внешнем изменении файла не перетирать его автоматически.** Проверять ревизию + SHA-256, конфликт останавливает автоматическое продолжение до согласования.
8. **Не менять основную задачу без согласия человека.** Допустима автоматическая декомпозиция, добавление блокирующего связанного дефекта и переупорядочивание незавершённых шагов; изменения цели, удаление обещанных результатов, новые опасные операции требуют подтверждения.

## 3. Минимальный управляемый Markdown-формат

```markdown
---
taskbridge_plan: 1
plan_id: p-uuid
revision: 7
goal: "Стабилизировать загрузку истории"
---

# План: стабилизация истории

## Шаги

### S-001 | DONE | P1 | Воспроизвести проблему
**Критерии:** сценарий воспроизведён в тесте.
**Проверка:** `node --test tests/history.test.mjs`.
**Результат:** failing-тест до исправления; run abc.

### S-002 | IN_PROGRESS | P1 | Исправить пагинацию
**Критерии:** нет дублей и потери событий.
**Проверка:** адресные тесты + UI smoke.

### S-003 | TODO | P1 | Прогнать приёмку Android
**Критерии:** повторный вход восстанавливает состояние.
**Проверка:** эмулятор + журнал событий.

## Обнаруженные проблемы
- F-001 | P1 | OPEN | При тестировании обнаружено дублирование событий.
```

В первой версии поддерживается только фиксированный, валидируемый шаблон. Плановый parser должен работать по Markdown AST / устойчивой структурированной схеме, не regex-угадыванию произвольного текста. `revision` увеличивает только сервис при санкционированной записи; ручную правку файл может принести с несинхронизированной ревизией — это обнаруживается по хэшу. Все идентификаторы шагов стабильны.

Служебные статусы: `TODO`, `IN_PROGRESS`, `BLOCKED`, `DONE`, `SKIPPED` (последний только по явной политике/подтверждению). Критерии должны быть наблюдаемыми; `DONE` хранит краткое evidence. История отдельных попыток/Runs не дублируется в файл полностью, а даётся ссылками.

**Запись:** сервисный `taskbridge_plan_update` с `planId`, `expectedRevision`, `expectedHash` и изменениями; проверка schema, scope и transitions; атомарная замена файла с Windows-safe retry. Прямое внешнее редактирование допускается и требует импорта изменившейся ревизии, но не может тихо переписать автоматическую текущую версию. Временные файлы допустимы только как механизм атомарной записи; пользователь не обязан вести второй план.

## 4. Цикл выполнения и подтверждение завершения

```
ATTACHED -> IDLE
  START -> RUNNING_STEP
  Pi turn settled -> REVIEWING
  REVIEWING + checkpoint CONTINUE -> update plan -> dispatch next step -> RUNNING_STEP
  REVIEWING + checkpoint REPLAN -> validate patch -> update same file -> dispatch next step
  REVIEWING + checkpoint COMPLETE -> final validation -> COMPLETED
  REVIEWING + NEED_INPUT/BLOCKED/NO_PROGRESS -> PAUSED_REVIEW
  user PAUSE -> PAUSE_REQUESTED -> PAUSED (at safe boundary)
  user STOP -> cancel Pi + increment cancel epoch -> PAUSED_REVIEW
  restart with unknown in-flight effects -> PAUSED_REVIEW, never auto-resend
```

Каждый нормальный шаг — обычная отправка в `TaskManager`, связанная с существующим Run и детерминированным `commandId`; `PlanFollower` **не** реализует второй Pi runner, собственный scheduler или отдельную очередь команд. Событие `TASK_SUCCEEDED` закрывает **ход**; `PLAN_COMPLETED` — только после общей проверки. Успешный ход может завершить несколько шагов при достаточных подтверждениях; один шаг может потребовать несколько ходов.

### Checkpoint-протокол

Лучше специальный Pi extension tool `taskbridge_plan_checkpoint` с машинным JSON, привязанным к `planId`, `planRevision`, `stepId`, `cycleId`, `runId`, чем парсинг «да/нет» или фразы `всё выполнено`. Расширение не переносит политику решений из TaskBridge в модель. Результат подтверждается контроллером **после settled**, не во время последующего tool call.

Пример:

```json
{
  "planId": "p-uuid",
  "revision": 7,
  "cycleId": "c-12",
  "decision": "REPLAN",
  "completedStepIds": ["S-002"],
  "evidence": [{"stepId":"S-002","kind":"test","ref":"run-123","summary":"29/29 pass"}],
  "findings": [{"id":"F-002","priority":"P1","blocking":true,"summary":"Новый баг обнаружен в reconnect"}],
  "proposedChanges": [{"op":"insert_after","after":"S-002","stepId":"S-004","title":"Исправить reconnect","priority":"P1"}],
  "nextStepId": "S-004"
}
```

Решения: `CONTINUE`, `REPLAN`, `COMPLETE`, `BLOCKED`, `NEED_INPUT`, `NO_PROGRESS`. Отсутствие валидного checkpoint не равнозначно завершению. Контроллер создаёт **не более одного** короткого проверочного хода: «Сверь файл плана, результаты и незавершённые пункты; передай checkpoint». При ещё одном пропуске/невалидном checkpoint — `PAUSED_REVIEW`, а не бесконечные уточнения. Отдельный проверочный ход может быть ограничен без побочных действий, если Pi 1.4.0 подтверждает требуемый механизм защиты.

`COMPLETE` принимается, только если файл распарсен, хэш/ревизия согласованы, нет открытых обязательных шагов/блокирующих findings, критерии выполнены, нет незавершённых или неизвестных побочных действий. `model says COMPLETE` без этих условий отклоняется с причиной. Когда строгую машинную проверку критерия реализовать нельзя, шаг получает `UNVERIFIED` и требует принятой политики подтверждения — **не** маркируется автоматически тестированным.

### Почему не бесконечные вопросы после ответа

Проверочный вопрос реализуется логически на каждом settle. Если модель уже отдала структурированный checkpoint, лишний запрос к провайдеру не делается. Если не отдала — отправляется одна контрольная инструкция. Это сохраняет требуемую самопроверку, но не удваивает стоимость всех ходов.

## 5. Автокоррекция плана

**Приоритеты:**

- `P0` блокирующий дефект / безопасность / потеря данных: вставить перед дальнейшим выполнением (если изменение цели или рискованная операция — запросить согласование).
- `P1` препятствие выполнению текущего шага или приёмке: автоматически добавить конкретный проверяемый шаг и поставить следующим.
- `P2` тесно связанная полезная правка: добавить в «Обнаруженные проблемы» или будущие шаги без тихого расширения объёма.
- `P3` косметика/новая функция: сохранить как наблюдение, не выполнять автоматически.

Каждый новый шаг содержит `originFindingId`, критерии, проверку и связь с обнаружившим Run. До `DONE` на исходном шаге не переходить без критериев. Старые `DONE` не переписывать; уже выполненные шаги можно пометить «требуется повторная проверка» отдельным шагом, если изменения их затронули. Дедупликация findings по устойчивому ключу и близости смысла; обнаружение одной и той же ошибки дважды не добавляет бесконечные копии шага. Нельзя бесконтрольно увеличивать число шагов.

Если файл плана был изменён человеком, автоматический patch модели должен либо примениться к новой ревизии после явного merge, либо вернуть `409 PLAN_REVISION_CONFLICT` и остановить auto-continue.

## 6. Короткий управляющий промпт следующего цикла

Пример **не системного универсального промпта**, а специфической инструкции конкретного шага, передаваемой один раз через текущий механизм `turn_instructions`/Pi extension или обычную управляемую команду (не одновременно двумя путями):

> Режим FOLLOW PLAN. Источник истины: `docs/IMPLEMENTATION_PLAN.md` (planId p-uuid, revision 7). Перед действиями перечитай этот файл, проверь незавершённые шаги и результаты прошлого хода. Цель плана неизменна. Текущий приоритет: S-003. Если найден относящийся к выполнению дефект, которого нет в плане, зарегистрируй finding с доказательством и предложи минимальный новый шаг с приоритетом P0/P1/P2. Для блокирующего P0/P1 — обнови **тот же** файл через `taskbridge_plan_update` с ожидаемой ревизией; не создавай второй план и не теряй существующие ID. Не считай шаг завершённым без его критериев проверки. Выполни ближайший допустимый шаг, затем вызови `taskbridge_plan_checkpoint` с подтверждениями, следующим шагом или причиной блокировки. Не делай автоматических git-коммитов, не выполняй несогласованных разрушительных действий. При отсутствии прогресса или неопределённом результате сообщи BLOCKED, а не повторяй попытку бесконечно.

Контроллер не должен пересылать полный Markdown-контент на каждом цикле, если агент может прочесть его как файл; достаточно пути, ревизии, активного шага и коротких результатов. При отсутствии доступного read-инструмента — ограниченный фрагмент файла, с учётом токен-бюджета.

## 7. Управление в чате

Небольшой переключатель около вложений и меню действий: **«По плану»** (а не «Plan Mode», зарезервированного для будущего read-only сценария). При первом включении выбрать файл из workspace либо указать относительный путь; показать валидность и возможность импорта. Включение без кнопки «Старт/Продолжить» **не** запускает модель и не тратит токены.

В чате — компактная карточка: `PLAN.md • 3/7 • выполняется S-004`, текущая цель, последний проверенный результат, новые проблемы и кнопки **Пауза после шага / STOP сейчас / Продолжить / Открыть файл / Изменить план**. Кнопка «По плану» управляет выбранным режимом отправки и автоматическим продолжением, но не заменяет STOP. Выключение во время работы ставит запрос паузы на ближайшей безопасной границе — не убивает уже работающий Pi без отдельного STOP.

Состояние обязательно серверное; Web/Desktop/Android используют одинаковый DTO и SSE. Сжатая карточка не вставляет полный план или служебный JSON в чат; подробный план открывается в диалоге по требованию. Два клиента видят один прогресс и одну revision; конфликтные изменения возвращают 409.

## 8. Архитектура TaskBridge

- `src/application/plan-follower.mjs`: конечный автомат, правила ревизий/циклов, next-step, бюджет и pause. **Без собственного runner**.
- `src/application/plan-file.mjs`: чтение/валидация/атомарные изменения одного Markdown-файла, хэш, конфликты. Проверка symlink/realpath и workspace-scope.
- `src/task-store.mjs`: только runtime-запись plan binding, `cycleId`, dispatch intent, lease, last settled seq, `cancelEpoch`, бюджет, expected hash/revision. Содержимое/шаги — в файле.
- `pi-extension/taskbridge-follow-plan.js`: `taskbridge_plan_update` и `taskbridge_plan_checkpoint`, hooks после проверки совместимости с Pi 1.4.0; фактическая авторизация обновлений — на стороне TaskBridge.
- `src/task-manager.mjs`: точечное подключение к существующим методам отправки, исходам Run и STOP; не дублировать STOP/QueuePump.
- `src/server.mjs`: API чтения, attach, start, pause, stop, resume, patch/reconcile. Изменяющие операции через существующий command ledger; `expectedRevision` и 409.
- `web/`, `clients/kmp/core/api`, `clients/kmp/core/client`, `clients/kmp/shared`: DTO, синхронизация, toggle, карточка, плановый редактор.

**Атомарность файловой системы и SQLite:** единой ACID-транзакции нет. Перед выдачей нового хода сохранить durable dispatch intent (cycleId, idempotent commandId, expectedRevision/hash); файл менять атомарным rename. После старта сравнивать фактический file hash и данные intent, восстанавливать только однозначные случаи. Если побочные действия могли состояться или файловый hash расходится — пауза, никакого слепого автовозобновления.

## 9. API (предварительный контракт)

```text
GET    /api/tasks/:taskId/plan
POST   /api/tasks/:taskId/plan/attach       {path,commandId}
POST   /api/tasks/:taskId/plan/start        {expectedRevision,commandId}
POST   /api/tasks/:taskId/plan/pause        {commandId}
POST   /api/tasks/:taskId/plan/resume       {expectedRevision,commandId}
POST   /api/tasks/:taskId/plan/stop         {commandId}
PATCH  /api/tasks/:taskId/plan              {expectedRevision,changes,commandId}
POST   /api/tasks/:taskId/plan/reconcile    {expectedRevision,action,commandId}
```

Статусы и доступные действия возвращает API. Должны быть различимы `PLAN_NOT_ATTACHED`, `PLAN_INVALID`, `PLAN_REVISION_CONFLICT`, `PLAN_BUSY`, `PLAN_BLOCKED`, `PLAN_BUDGET_EXCEEDED`, `PLAN_UNKNOWN_OUTCOME`. Events `PLAN_ATTACHED`, `PLAN_STEP_STARTED`, `PLAN_STEP_CHECKPOINT`, `PLAN_REVISED`, `PLAN_PAUSED`, `PLAN_COMPLETED`, `PLAN_CONFLICT`. Не дублировать многомегабайтные тексты плана в SSE.

## 10. Надёжность, лимиты и безопасность

- Версионирование: binding принадлежит одной сессии; один active follower на `taskId`, workspace conflicts наследуются TaskManager. Один файл не должен одновременно контролироваться двумя независимыми автоматическими followers.
- Защита от зацикливания: предложение по умолчанию **3 подряд цикла без измеримого прогресса**, максимум **20 автоматических циклов** до контрольной паузы, **1** проверочный extra-turn, плюс настраиваемые budget времени/токенов/стоимости. Эти числа — предложения для утверждения, не жёсткие продуктовые требования.
- Снижение затрат: не отправлять дополнительный audit-запрос, если checkpoint уже передан; не опрашивать модель для status; UI обновлять по SSE, fallback GET.
- При 413/429/временных сбоях учитывать существующие MEDIA-09/10, provider wait и command ledger. Follow Plan **не создаёт свой retry loop**.
- STOP должен инвалидировать epoch до начала await; поздний checkpoint/ACK/settled с другим epoch игнорируется.
- Указанный план — данные задачи, не разрешение обходить approvals, workspace-policy и безопасность. MCP неизвестного поведения требует прежней политики подтверждения. Скрытые shell-записи в файл плана обнаруживаются по hash; без sandbox нельзя обещать абсолютную блокировку внешних процессов, но неконсистентный файл не должен запускать следующий шаг.
- Изолировать плановый путь внутри workspace с realpath-проверкой, запретом traversal, контролем symlink и разрешениями, запретом секретов и подробных tool outputs в metadata.
- Логи содержат planId, revision, cycleId, runId, commandId, stepId, контекст transitions, без содержимого секретов или мегабайтов истории.

## 11. Матрица тестирования

**Поведение и UX**: attach существующего файла, невалидный Markdown, пустой план, старт без генерации на toggle, Web/KMP toggle в обе стороны, мобильный компактный вид, ручная правка шага, переключение сессий, два клиента одновременно.

**Автоматический цикл**: обычный шаг DONE→следующий, несколько DONE за ход, длительный шаг за несколько ходов, COMPLETE только при всех done, одно fallback-уточнение при отсутствующем checkpoint, невалидный JSON → пауза, NO_PROGRESS → пауза после заданного лимита, новый P1 баг вставляет шаг следующим, дубликат finding не размножается, P3 не расширяет scope, смена цели требует согласования.

**Гонки**: STOP в окнах до/после постановки следующего сообщения и после ACK, pause/STOP во время REVIEWING, повтор `commandId`, новый ручной запрос, restart при отправленном shell-tool, crash между fs rename и SQLite фиксацией, правка Markdown одновременно с checkpoint, битый/удалённый/заблокированный файл, Windows rename failure, второй follower того же файла.

**Проверки**: негативные тесты поддельного COMPLETE, ошибочно отмеченных checkbox, устаревшего evidence, незапущенного теста, failed verification, missing approval, попытки редактировать чужой путь, prompt-injection в плане; полнота SSE после прунинга, restore по курсору. Реальный Pi 1.4.0 — отдельно: регистрируется tool, приходят tool_call/settled, нет дублирования из hook, долгий reasoning/compaction и STOP; затем Desktop + Android Pixel 5 API 31 + Web browser smoke.

Не повторять все тесты по нескольку раз: unit/адресные для каждой части; один полный Node и соответствующие KMP-тесты/сборки на финальном gate. Рабочий сервер, Strata и внешние пользовательские Pi-сессии не трогать.

## 12. Этапы реализации и критерии GO/NO-GO

| Этап | Результат | Gate |
|---|---|---|
| FP-00 | Совместимость Pi 1.4.0, end-of-turn события, extension-tool, mapping STOP/queue, contract file | Тест на настоящем Pi без пользовательских данных |
| FP-01 | Markdown schema/parser, импорт, CAS/atomic write, runtime SQLite binding | Конфликты и аварийное восстановление без порчи файла |
| FP-02 | Checkpoint tool и строгая валидация завершения | Поддельный COMPLETE не заканчивает план |
| FP-03 | Durable follower + автоход, отсутствие checkpoint, прогресс и budgets | Нет дублей после STOP/restart, нет бесконечного loop |
| FP-04 | Автопоправка связанных дефектов, приоритет и аудит | P1 баг становится следующим шагом; P3 не расширяет scope |
| FP-05 | API + Web + KMP composer toggle и карточка | Консистентный режим в двух клиентах; Android background |
| FP-06 | Полная изолированная интеграционная приёмка, rollback/flag | PASS негативных тестов, baseline не повреждён |

Каждый этап отдельными коммитами; feature flag `followPlan.enabled=false` по умолчанию до интеграционной приёмки. Не изменять ветку пользователя принудительно; не push без разрешения.

## 13. Непринятые продуктовые решения (не маскировать догадками)

1. **Файл:** разрешить произвольный Markdown или требовать управляемый формат (предложено: импорт существующего в управляемый Markdown после preview).
2. **Автономность:** default автопродолжения или подтверждение каждого шага (предложено: авто с паузой на риске/лимите).
3. **Новые обнаруженные задачи:** автоматически выполнять только P0/P1 блокеры или все связанные улучшения (предложено: P0/P1 блокеры, P2/P3 отдельные findings).
4. **Политика проверок:** требуется строгое подтверждение каждого пункта или допускается отмеченный `UNVERIFIED` для субъективных критериев (предложено: явные уровни verified/claimed/manual-accepted).

Эти решения необходимо закрепить до изменения рабочего контракта/UX, а не предполагать, что они уже согласованы.
