## Исправления чата в этой работе

- Удаление `assistant-initial` / `assistant-<seq>` сохраняет USER выше. Удаляются ответ и последующая история. KMP передаёт идентификатор ответа; сервер и оба редьюсера понимают `keepUser + reason: delete` без новой анимации. Удаление произвольного варианта по его UUID пока не поддерживается.
- Доставка различает отправку на сервер, подтверждение сервера, передачу агенту и применение инструкции. Серверная очередь остаётся отдельной строкой с действиями.
- 27 сентября метка доставки перенесена внутрь пузыря USER в KMP Desktop/Android: прежняя мелкая строка под пузырём оказалась слишком незаметной. Для первого сообщения сервер теперь публикует `PROMPT_ACCEPTED` только после ответа Pi RPC; до него видны «В очереди» / «Сервер готовит сессию» / «Ожидает подтверждения Pi». Начало ответа модели — отдельный этап, не равный доставке к провайдеру.
- Диагностика раскрывается над composer: соединение, последний контакт, последнее событие и время, seq, runtime, модель, код ошибки; сведения можно скопировать.
- Steering не убивает инструменты. Предыдущий ответ перестаёт анимироваться при переходе к следующему ответу. Ошибка/abort заканчивает анимацию даже без `agent_settled`.
- Heartbeat подтверждает живое соединение и запускает сверку состояния. У HTTP-чтения лимит 30 с, у команд — 180 с; ожидание `ACCEPTED` ограничено 30 проверками. Обычная отмена coroutine сохраняется.
- Устаревший HTTP-ответ не перезаписывает более новые SSE-события. Статус RUNNING/terminal обновляется из событий, а старый terminal не завершает ещё не подтверждённый optimistic bubble.
- `PI_RPC_HUNG` / `PI_RPC_EXITED` при отправке и смене модели освобождают runtime и слот. Последующие команды могут восстановить сессию. `PI_RPC_SLOW` сохраняет работающий процесс.
- Runtime-переход публикуется перед терминальным событием хода: клиент, завершивший чтение на `TASK_*`, не теряет последнее изменение состояния.
- По примеру локального Pi Desktop добавлен прямой селектор моделей из шапки и composer: каталог показывается из памяти сразу, обновляется в фоне, провайдеры свёрнуты, поиск раскрывает совпадения. Выбор ждёт ответа RPC, затем сразу обновляет модель в чате; при ошибке окно остаётся открытым, чат не блокируется.

Это устраняет воспроизводимые ошибки состояния и восстановления. Без трассы конкретного зависания нельзя утверждать, что найден каждый случай «ответ не получен».
Подтверждение RPC не доказывает обращение к провайдеру: для точной диагностики провайдера нужны отдельные события попытки запроса, первого токена, retry и timeout из Pi.

### Уточнение 27 сентября: параллельные сессии

Сейчас TaskBridge хранит несколько сессий и отдельные Pi-процессы в `runtimes`
по `taskId`, но **параллельных работающих ходов нет**. Глобальный
`activeTaskId` и `#pump()` допускают только один turn на весь сервер: пока A
генерирует ответ, выполняет инструменты или ждёт UI-подтверждения, сообщение в B
сохраняется как `pendingPrompts` с причиной `BUSY` и начнёт исполняться после A.
Это относится и к разным облачным провайдерам. Тесты `manager.test.mjs`
проверяют очередь другой сессии и новую сессию во время работы; 52/52 проходят.

KMP отображает несколько сессий и опрашивает их статусы, но не принимает решение
о запуске: ограничение находится в `src/task-manager.mjs`. В дополнение к
`activeTaskId`, глобальный `#admit()` временно отвечает `BUSY` на одновременные
изменяющие запросы. Его также надо заменить или сузить при реализации R4.
В локальном `config.json` на момент проверки у всех шести настроенных проектов
`useWorktree: false`; при одновременной записи файлов в одном проекте это риск
конфликтов. Этот локальный конфиг не менялся.

Параллельность технически возможна без замены KMP и HTTP/SSE: процессы Pi уже
разделены по сессиям. Для R4 нужен планировщик с лимитами `maxWorking` и
`maxLive`, квотами по endpoint, независимой диспетчеризацией и блокировкой
команд внутри каждой сессии. Запускать две задачи в одном `cwd` следует через
разные worktree; для локального llama.cpp лимит ограничивать реальной ёмкостью
сервера. Тесты должны доказать фактическое перекрытие двух turn'ов и отсутствие
перекрытия при лимите endpoint=1, а также корректную отмену и восстановление.

Важные расхождения: начало roadmap описывает файловый store и отложенный SQLite,
но этап 2 и реализация уже используют SQLite. Этапы 3 и 5 нельзя считать ни полностью
отсутствующими, ни завершёнными. В KMP outbox пока живёт в памяти; ручной retry создаёт
новую команду и не восстанавливает байты вложений — это отдельный оставшийся пункт.

## Референс Pi Desktop

Скриншот подходит как визуальный ориентир существующего UI-плана.
Переписывать KMP, транспорт или хранение для такой компоновки не требуется.
Локальный `G:\AIModels\pi-app` проверен по исходникам: Electron/React-приложение
`pi-desktop` 0.5.8 с `@earendil-works/pi-coding-agent` 0.83.0. Его код UI напрямую
в Compose не переносится, но компоновку и поведение можно воспроизвести.
`MainLayoutShell` делает три изменяемые колонки с узкой правой полосой при сворачивании;
`ComposerDock` держит ввод отдельным нижним слоем и измеряет его высоту для ленты;
`RightPanelTabs` и каталог задают вкладки Review/Run/Context/Tree/Files.
Его `model-picker.tsx` использует кэш моделей, свёрнутые группы провайдеров,
поиск и подтверждённое RPC-переключение. Эти принципы повторены в KMP Compose,
без переноса React-кода.
На узком окне Pi сворачивает правую панель, а ширину пользовательских панелей
ограничивает. Для KMP это подтверждает адаптивную компоновку P3, а не необходимость
замены текущей архитектуры. Референс использует другую версию Pi, чем установленная
в TaskBridge 0.87.1, поэтому поведение RPC нельзя копировать без проверки.

В worker референса `steer` вызывает `session.steer`, `abort` отдельно вызывает
`clearQueue` и `session.abort`; обычный prompt во время streaming по умолчанию
передаётся как `followUp`. Это дополнительно подтверждает необходимость
раздельных действий «В очередь», «Вклиниться» и «Stop» в KMP.

1. Стабилизировать отправку/завершение/восстановление и закончить P0.
2. P1/P2: компактная боковая панель, спокойные метаданные, composer и лента одной ширины, ясные статусы. Сложность умеренная: преимущественно Compose.
3. P3: правый инспектор. Начать с уже доступных файлов/артефактов и вывода команд.
4. Добавить дерево workspace, полноценный diff/review, Git и Context отдельными частями. Это заметная работа по API и моделям данных, а не только вёрстка вкладок.
5. На Android показывать те же данные отдельным экраном/sheet; три колонки оставлять для широкого Desktop.

Вкладка Run не должна случайно создавать второй независимый Pi-процесс: действия
остаются командами существующей серверной сессии. Широкий редизайн в эту правку не включён.

## Семантика действий

- **В очередь:** после завершения текущей работы.
- **Вклиниться:** принять инструкцию сейчас, применить на границе шага; текущая генерация и уже запущенные инструменты могут продолжаться до этой границы.
- **Stop:** явно отменить текущую работу, включая команды; это не откатывает уже сделанные изменения.
- **Остановить и отправить:** возможное отдельное будущее действие, не скрытая семантика steering.

Основание: [Pi Agent Core — Steering and Follow-up](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md#steering-and-follow-up).
Это описание текущего upstream; совместимость установленного Pi проверяется отдельными RPC-тестами.
