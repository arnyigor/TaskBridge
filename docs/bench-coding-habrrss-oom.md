# Эталонный бенчмарк кодирования: HabrRSS OOM на больших архивах

Задача взята из реальной истории коммитов проекта
`G:\Android\AndroidStudioProjects\HabrRSS\` — с известной первопричиной, которую
можно сверить объективно. Ниже: правила, подготовка стенда, результаты прогонов и
что из них следует.

## 1. Правила, чтобы модель не подсмотрела

1. Дерево собирается через `git archive <pre-fix-commit>` — **без `.git`**.
   История с фиксом модели не видна (`git log` в дереве отвечает
   `not a git repository` — проверено на прогонах).
2. Дерево лежит отдельно от этого описания:
   `G:\AIModels\LLMBenchmarks\MyTests\habrrss-oom-<model>\`, а бенчмарк и ground
   truth — в репозитории TaskBridge.
3. **Нельзя запускать бенчмарк с `cwd`, где лежит ответ** (из TaskBridge или из
   клона HabrRSS с историей).
4. Проверочные скрипты модели не показываются: они применяются к её дереву уже
   после прогона.

## 2. Что за баг (ground truth)

**Состояние без фикса:** `02de21b` в HabrRSS (`feat(branding): … (v1.0.6)`).

Коммит `1a6c140` (v1.0.7), дословно:

> `TechReaderRepository.changedRemoteEntities` used to call
> `feedDao.getAllCachedOnce()` on every page, materializing the full `feed_items`
> table (including `cachedArticleJson` TEXT) just to merge in a small page. On a
> 5-10k+ article hub archive that crashed the import after 2-3 pages with OOM.

```kotlin
// было
val currentById = feedDao.getAllCachedOnce().associateBy { it.id }
// стало
val pageIds = map { it.id }
val currentById = feedDao.getByIds(pageIds).associateBy { it.id }
```

Коммит `dc543e2` (v1.0.8) добавил вторую половину: список ленты читал **все**
хранимые статьи (до 22k строк) вместе с тяжёлой колонкой `cachedArticleJson` и
перестраивал с копированием весь смапленный список на каждую эмиссию DAO.
Лечение: проекция без `cachedArticleJson` + лимит `FEED_LIST_LIMIT = 3000`,
`countByFeed` для честного счётчика, `conflate` на потоках.

Затронутые файлы (набор важен — по нему удобно сверять, «куда пошла» модель):
`TechReaderRepository.kt`, `FeedDao.kt`, `RoomFeedDao.kt`, `InMemoryFeedDao.kt`,
`FileBackedFeedDao.kt`, `FileBackedFeedDao.android.kt`.

**Почему задача хорошая.** Реальная, воспроизводимая на устройстве, требует
понимания слоёв (DAO → репозиторий → flow) — и **не ловится юнит-тестами**: на
дефектном дереве `:composeApp:jvmTest` даёт 130/130 зелёных.

## 3. Подготовка стенда

### 3.1. Дерево

```bash
SRC=G:/Android/AndroidStudioProjects/HabrRSS
TREE=G:/AIModels/LLMBenchmarks/MyTests/habrrss-oom-<model>
git -C "$SRC" archive 02de21b | tar -x -C "$TREE"      # без .git
cp "$SRC/local.properties" "$SRC/secret.properties" "$TREE/"
cd "$TREE" && ./gradlew :composeApp:jvmTest            # прогрев Gradle + baseline
```

Прогрев обязателен: кэш `~/.gradle` общий, и без него первая модель платит за
холодную сборку. Базовая линия после прогрева — ~10–40 с.

### 3.2. Правка харнесса (не подсказка модели)

Debug-сборка получает отдельный `applicationId`, чтобы ставиться **рядом** с
боевым приложением и не трогать его данные:

```kotlin
// composeApp/build.gradle.kts
buildTypes {
    getByName("debug") { applicationIdSuffix = ".oomtest" }
    …
}
```

На телефоне после этого живут два пакета: боевой `com.arny.habrrss` (не трогаем) и
тестовый `com.arny.habrrss.oomtest` (он **debuggable**, поэтому работает `run-as`).

### 3.3. Фикстура — самое важное

**Почему она нужна.** Первопричина — материализация всей таблицы на каждой
странице, но тяжёлая в ней только одна колонка: `cachedArticleJson` (полное тело
статьи). Тело кэшируется **не при загрузке страниц**, а при полнотекстовом чтении
статьи. Проверено на живом приложении: после импорта 20 страниц programming-хаба в
базе было **1 940 строк и 0 тел** (9.0 МиБ) — падать нечему, сколько страниц ни
загружай. У пользователя архив на 39 996 статей накоплен месяцами, с телами, —
вот это состояние и воспроизводит падение.

**Как готовится.** `scripts/bench-habrrss-fixture.mjs` берёт снятую с устройства
базу, вытаскивает из неё настоящий `cachedArticleJson` (образец) и размножает
строку до нужного количества под нужный фид, сохраняя схему и Room-хэш:

```bash
# снять базу с телефона (приложение debuggable)
adb exec-out run-as com.arny.habrrss.oomtest cat databases/habr_rss.db > pulled.db
node scripts/bench-habrrss-fixture.mjs --source pulled.db --out fixture.db \
     --rows 12000 --blocks 12 --feed habr-hub:programming:alltime
```

Результат проверенного варианта: 12 100 строк, из них 12 000 с телами, **75 МиБ
тел**, база 149.5 МиБ, сборка 2.3 с.

**Заливка на устройство** (крупный файл через stdin ломается на Windows, поэтому
сначала `push`, потом пайп внутри устройства):

```bash
adb push fixture.db /data/local/tmp/habr_rss.db
adb shell "am force-stop com.arny.habrrss.oomtest"
adb shell "run-as com.arny.habrrss.oomtest rm -f databases/habr_rss.db-wal databases/habr_rss.db-shm"
adb shell "cat /data/local/tmp/habr_rss.db | run-as com.arny.habrrss.oomtest sh -c 'cat > databases/habr_rss.db'"
```

**Контроль воспроизведения.** С фикстурой дефектная сборка на OnePlus 6T падает
сразу при открытии локального архива:

```
ApplicationExitInfo: reason=4 (APP CRASH(EXCEPTION)), pss=154MB, rss=250MB
```

250 МБ RSS при лимите heap 256 МБ — та самая смерть из отчёта. В `logcat` её нет
(падение нативное/системное), поэтому достоверный источник — `dumpsys activity
exit-info <pkg>`.

### 3.4. Между прогонами

`adb shell pm clear com.arny.habrrss.oomtest` → заново залить фикстуру → запускать
следующую модель. Иначе вторая стартует с архива, накопленного первой.

Эмулятор как альтернатива устройству: поднимать **только** программным
рендерингом (`-gpu swiftshader_indirect`) — модель занимает ~15 ГБ из 16 ГБ VRAM,
аппаратный рендеринг эмулятора туда не влезает. Плюс нужен `ANDROID_SDK_ROOT`, иначе
эмулятор падает с `Cannot find AVD system path`.

### 3.5. Стенд на эмуляторе (предпочтительный для прогонов)

Эмулятор лучше телефона: он не занят человеком, состояние сбрасывается до эталона и
на нём нет чужой истории падений.

```bash
node bench/emulator.mjs --wipe    # поднять с чистого листа и дождаться загрузки (~40 c)
node bench/emulator.mjs           # повторный запуск (если уже поднят — просто скажет)
node bench/emulator.mjs --kill    # погасить
```

| флаг | зачем |
| --- | --- |
| `-gpu swiftshader_indirect` | **обязательно**: модель занимает ~15.6 ГБ из 16 ГБ VRAM; программный рендеринг VRAM не трогает вообще |
| `-wipe-data` | пустой dropbox: иначе модель находит ЧУЖОЙ крах. В одном прогоне она нашла падение боевого приложения (`com.arny.habrrss v5 (1.0.4)`, `growth limit 268435456`) и приняла его за своё воспроизведение |
| `ANDROID_SDK_ROOT=G:/Android/SDK` | без него эмулятор падает с `Cannot find AVD system path` (проверено) |
| `-no-snapshot -no-boot-anim -no-audio` | быстрее и без лишнего шума |
| `-memory 2048` | как в самом AVD Pixel_5 |

Heap эмулятора — **192 МБ** (у телефона 256), то есть с фикстурой падает даже легче;
абсолютные времена прогонов на телефоне и эмуляторе несравнимы.

#### Полный рецепт «модель + эмулятор»

```bash
# 1. эмулятор с чистого листа
node bench/emulator.mjs --wipe

# 2. свежий applicationId на прогон (.b1, .b2 …) — иначе старые краши в dropbox
#    совпадут с нашим пакетом. Правка харнесса в дереве:
#    getByName("debug") { applicationIdSuffix = ".b1" }
cd <дерево> && ./gradlew :composeApp:assembleDebug
adb -s emulator-5554 install -r composeApp/build/outputs/apk/debug/composeApp-debug.apk

# 3. эталонное состояние: очистка → база с архивом → настройки с хабом
node bench/preflight.mjs --app com.arny.habrrss.b1     # код 0 = стенд готов

# 4. прогон модели в упряжке
B="G:/Android/AndroidStudioProjects/Taskbridge/bench"
cd <дерево>
BENCH_APP=com.arny.habrrss.b1 \
BENCH_SCENARIO="$B/verify-scenario.mjs" \
BENCH_SUPERVISOR_LOG=data/runtime/supervisor.log \
pi -p --mode json --model "llama.cpp/qwen-27b-q3" --thinking medium \
  --mcp-config "$B/mcp-bench.json" -e "$B/supervisor.ts" -e "$B/verify-tool.ts" \
  "$(cat задача.txt)" > run.jsonl 2>&1

# 5. разбор и независимая проверка правки
node scripts/bench-pi-metrics.mjs run.jsonl                # шаги, токены, размышления, инструменты
node bench/verify-scenario.mjs --app com.arny.habrrss.b1   # CRASH / OK / NOT_RUN
```

Порядок шагов важен: фикстуру нельзя залить в несуществующий пакет, а `--wipe`
после установки стирает и приложение, и фикстуру.

`verify-scenario.mjs` без аргументов работает и как самостоятельная проверка
(его же вызывает инструмент `verify`): он запускает приложение, идёт Хабы →
programming → «Загрузить все страницы», проверяет живость процесса между шагами и
судит по `exit-info` + `logcat`. Вердикт `NOT_RUN` («сценарий не состоялся»)
умышленно отделён от `OK` — иначе занятое устройство выглядит как успех.

### 3.6. Инструменты: почему правило про ast-index не работало

Требование «пользуйся ast-index» лежало строкой в системном промпте (глобальный
`SYSTEM.md`, 7 упоминаний) и **не выполнялось**: за четыре прогона — ноль обращений,
весь поиск шёл через grep/read. При этом инструмент почти бесплатный:

```
ast-index rebuild   → 0.31 c, 127 файлов, 2476 символов, индекс 1.86 МБ
ast-index class FeedDao → 3 мс
```

Причины две, и обе — про обвязку, а не про модель:

1. **Это правило, а не инструмент.** В списке инструментов его нет, а в системном
   промпте оно конкурирует с описаниями 80+ инструментов. Ровно тот же провал, что с
   проверкой на устройстве: пока проверка была просьбой — 0 обращений, стала
   инструментом `verify` — 31.
2. **Скрытый предварительный шаг.** Структурные запросы (`class`, `symbol`, `refs`)
   без индекса отвечают `Index not found. Run 'ast-index rebuild' first.` — агент
   утыкается в это и возвращается к grep. При этом `rebuild` — доли секунды.

Что сделано в стенде:

| что | файл |
| --- | --- |
| `rebuild` индекса в пре-флайте (больше не надо догадываться) | `bench/preflight.mjs` |
| Инструмент `ast` с типизированными операциями (class/symbol/usages/refs/outline/…) | `bench/ast-tool.ts` |
| Напоминание в момент, когда агент пошёл искать текстом (grep/find → инъекция «есть ast») | `bench/supervisor.ts` |
| Флаг `--with-ast`, чтобы эффект мерился отдельно от остальной обвязки | `bench/run-benchmark.mjs` |

Проверено: модель вызывает `ast` и получает `FeedDao [interface]: …FeedDao.kt:11`.
Метрика для A/B — та же, что для канонических инструментов: число обращений к `ast`
и число шагов до первого из них (у `artemis_mobile_run_task` это было 102 шага,
у `screencap` — 128).

### 3.7. Другие языки: что вместо ast-index для JS, Python, HTML

ast-index работает по Kotlin и Java. Для остальных языков искались отдельные быстрые
способы — с замерами, а не по рекламе.

**Что уже есть, и это важно:** встроенный `grep` в pi **уже использует ripgrep**
(в бандле 19 ссылок, `rgPath`). То есть модель и так грепала быстрым rg, отдельный
инструмент для текста не нужен — дублировать не стали.

**Замер (331 сессия Claude Code, 4 репозитория) — rg выигрывает 9 классов запросов
из 12.** ast-grep выигрывает ровно один: структурные запросы в React/TSX, где rg даёт
**0 %** попаданий, а ast-grep — 66.7 %. Отсюда правило:

| запрос | чем искать |
| --- | --- |
| точная строка, имя, токен | **rg** (уже внутри grep) |
| шаблон кода (JS/TS/TSX, Python, Go, Rust, …) | **ast-grep** |
| символы/классы Kotlin, Java | **ast-index** (инструмент `ast`) |
| «где определено / кто вызывает», типы, наследование | **LSP** (rg и ast-grep этого не умеют) |
| запрос по смыслу без общих слов | индексирующий семантический поиск (asgrep/sgrep) |

**Почему расширение, а не MCP.** Тот же бенчмарк: MCP-инструменты быстрее по стенным
часам (2–5×), но платят фиксированный «load tax» ~1576 токенов за сессию, который не
окупается — на 5, 11, 27 и 79 вызовах MCP дороже, чем bash+grep. Поэтому обвязка
живёт расширением pi и дёргает бинарь напрямую.

Что сделано:

| что | где |
| --- | --- |
| Инструмент `sg`: `search` (структурный шаблон) и `outline` (структура файла) для 21 языка | `bench/ast-tool.ts` |
| Проверка бинаря в пре-флайте (предупреждение, не отказ: для Kotlin он не нужен) | `bench/preflight.mjs` |

Грабли, найденные при проверке (все учтены в обёртке):

1. **npm-обёртка `ast-grep` — shell-скрипт.** `execFile` на Windows его не запускает:
   ENOENT → код 1 и пустой вывод, что **выглядит как честное «ничего не найдено»**.
   Исправлено двумя способами: берём нативный `@ast-grep/cli/ast-grep.exe`, а любой
   сбой запуска (`ENOENT`/`EACCES`) печатается в выводе явно, отдельно от нуля совпадений.
2. **`sg` — устаревшее имя**, бинарь требует `ast-grep`.
3. **Сломанный паттерн даёт код возврата 0** и лишь предупреждение `ERROR node`.
   Обёртка распознаёт это и пишет «результат недостоверен», а не «0 совпадений».
4. **Грамматика -l должна совпадать с расширением** (`tsx` ≠ `jsx`): иначе тихо ноль
   без ошибки — обёртка предупреждает об этом прямо в тексте ответа.
5. **POSIX-путь (`/tmp/…`) Windows-бинарь не резолвит** — путь приводится к нативному.

Проверено от лица модели: `sg outline web/chat-state.mjs` → структура файла;
`sg` с `console.log($A)` по каталогу → **114 совпадений** с файлом и строкой;
`sg outline` на настоящем `FeedDao.kt` → интерфейс и все 38 методов;
а `ast class FeedDao` продолжает отвечать за 3.45 мс.

### 3.8. Глобальная установка: почему проектной недостаточно

Обвязку можно ставить в проект (`.pi/extensions/bench-harness`) или глобально
(`~/.pi/agent/extensions/bench-harness`). Для чужого проекта подходит только
второй вариант — и это не предпочтение, а следствие механики pi:

1. `.pi/extensions` входит в `TRUST_REQUIRING_PROJECT_CONFIG_RESOURCES`, то есть
   наличие проектных расширений делает проект «требующим доверия».
2. Решение о доверии: флаг `--approve/-a`, иначе запись в `trust.json`, иначе
   `defaultProjectTrust` (по умолчанию `ask`).
3. **При отсутствии UI (а `pi -p` — это отсутствие UI) недоверенный проект даёт
   «не доверять»** → проектные расширения **пропускаются молча**, без сообщения.

То есть проектная установка в незнакомом каталоге просто не загрузится, и выглядеть
это будет не как ошибка, а как «модель почему-то пошла в grep». Проверено: в каталоге
`C:\temp\instest` инструмент не появился, и модель ушла в bash — ровно в
`Index not found. Run 'ast-index rebuild' first.` — ту самую ловушку, из-за которой
и затевался инструмент. Глобальные расширения (`agentDir/extensions`) грузятся всегда.

```bash
node bench/install.mjs --global --tools-only   # ast + sg глобально, без стендовых инструментов
node bench/install.mjs --global --uninstall
```

`--tools-only` ставит **только поиск по коду**. `verify`/`repro` из глобальной
установки исключены намеренно: они требуют эмулятора, фикстуры и `BENCH_APP` и в
обычном проекте были бы мусором в списке инструментов. Надзиратель тоже не ставится:
его инъекции и гейт — логика стенда, а не инструмент; сначала проверяем, хватает ли
одного описания инструмента, и только потом добавляем напоминания.

**Самозапуск индекса.** В новом проекте индекса нет, и первый же `ast class X` без
самозапуска вернул бы «Index not found». Теперь инструмент сам строит индекс
(лениво, на первом запросе) и повторяет запрос. Проверено на чистом кэше
(`%LOCALAPPDATA%\ast-index` удалён) в каталоге с одним Kotlin-файлом:

```
ast class Foo → 2 строк
(индекса не было — построен автоматически, запрос повторён)
Classes matching 'Foo':
  Foo [class]: A.kt:3
stderr: Time: 3.1573ms
```

Индекс живёт в `%LOCALAPPDATA%\ast-index\<хеш>` и **в проект ничего не пишет** —
проверено: после `rebuild` в каталоге не появилось ни одного нового файла. Это снимает
главный риск глобальной установки.

## 4. Промпты

Отдаются дословно, диагноз не подсказывается (правило: **в промпте не должно быть
причины**, только наблюдаемое поведение).

**v1 — как спросил бы пользователь** (использовался в прогонах 27B Q3 и Flash):

```
Привет!

Есть проблема с большими хабами. Открываю хаб, жму «Загрузить все страницы» —
прогружает две-три страницы, и приложение закрывается. На маленьких хабах всё
нормально. Запускаю заново, снова жму — опять две-три страницы и вылет.
Телефон OnePlus 6T.

Посмотри, в чём там дело, и почини. Хочется убрать саму причину, а не заглушить.
```

**v2 — плюс требование самопроверки** (использовался в прогоне IQ4_XS): к v1
добавлено «проверь сам на устройстве, а не только по коду: Android SDK и AVD на
месте… Хочу видеть подтверждение, что на моём сценарии оно больше не падает».

**v3 — плюс критерий готовности** (A/B против v2, прогон не состоялся): к v1
добавлены правила «не перечитывай, что уже читал», «нашёл причину — сразу правка»,
«проверка = запуск сценария, а не чтение», «5 шагов без правки — действуй»,
«задача закрыта, когда сценарий перестал падать».

Что сознательно **не** попадает в промпт: `OutOfMemoryError`, строка лога
`updateState items=14611 … elapsed=1702ms` (цитата из коммита), лимит heap,
диапазон размеров архива, `./gradlew`. Всё это — подсказки диагноза.

### Обвязки: одна модель, разная упряжка

Раннер `bench/run-benchmark.mjs` прогоняет всё одной командой; обвязка выбирается
профилем:

```bash
node bench/run-benchmark.mjs --model llama.cpp/qwen-27b-q3 --harness full --verify-fix
```

| профиль | что включает |
| --- | --- |
| `bare` | ничего (базовая модель) |
| `verify` | только инструмент `verify` |
| `supervisor` | только надзиратель (инъекции) |
| `full` | `verify` + надзиратель + сужение инструментов |
| `gate` | `full` + надзиратель ЗАБИРАЕТ `verify`, пока нет ни одной правки |

Замерено на одной модели (27B Q3_K_XL, эмулятор, одна и та же фикстура):

| профиль | время | шагов | правок | `verify` | результат |
| --- | --- | --- | --- | --- | --- |
| `bare` (прогон v1) | 27.6 мин | 70 | 36 | 0 | правка есть, но не проверена |
| `full` (v4) | **57 мин** | 118 | **97** | **31** | **фикс работает** (проверено контролем) |
| `gate` (v4) | 12.4 мин | 46 | **0** | 0 (спрятан) | обходной путь, правок нет |

**Три вывода, которые стоят больше самих цифр:**

1. **Обвязка превращает «умеет» в «сделал».** Без неё модель ни разу за три прогона
   не подошла к устройству; с `verify` — 31 обращение и работающий фикс. Разница не в
   уме, а в обратной связи и в цене проверки.
2. **Заблокировать инструмент ≠ заблокировать способность.** В режиме `gate`
   `verify` был убран из активного набора — и модель ушла в ARTEMIS
   (`mobile_run_task` 12 раз) через прокси `mcp`. Прямые инструменты были сужены, а
   прокси остался открыт. Отнимать надо класс действий, а не один инструмент.
3. **Собственной проверке модели верить нельзя.** Получив `OK`, она на самом деле
   снесла данные приложения и переписала список хабов — то есть убрала то, на чём
   падает. Правду установил только контрольный прогон на том же стенде (дефектное
   дерево → `CRASH`, её дерево → `OK`).

### Осторожно с выводом «тесты зелёные»

`jvmTest` **не является доказательством** починки: на дефектном дереве он также
даёт 130/130 (проверено на baseline до прогонов). Зелёные тесты после правки
означают только, что код компилируется и не ломает существующее поведение — не
что ушёл OOM. Именно поэтому в критериях проверки (раздел 6) стоит запуск сценария
на устройстве.

### Что показали прогоны

1. **Ни одна модель не воспроизвела баг на устройстве.** Ни `adb`, ни эмулятора,
   ни `logcat` — ни в одном из трёх прогонов. Все работали с кодом и юнит-тестами.
2. **Сборкой проверяли двое из трёх.** 27B Q3 прогнала `jvmTest`/`testDebugUnitTest`/
   `compileDebugKotlinAndroid` по 7 раз, Flash — `testDebugUnitTest` 11 раз (с фильтром)
   и получила `BUILD SUCCESSFUL`. IQ4_XS не запустила ни одной gradle-команды, хотя
   дала лучший диагноз.
3. **Правки реальные, не пустые:** у 27B Q3 в `TechReaderRepository.kt` изменено
   44 строки, в `FeedDao.kt` 8, в `RoomFeedDao.kt` 3 — и `jvmTest` после них зелёный.
4. **27B Q3** к 27-й минуте правила ровно те шесть файлов, что и настоящий фикс, но
   накрутила 36 правок по кругу, перепроверяя одно и то же тестами.
5. **Flash M64** — самая долгая и самая «залипшая»: 41 минута, первая правка почти
   в конце, 0 упоминаний `adb`/эмулятора.
6. **IQ4_XS** — лучший диагноз при худшей динамике. В размышлениях она на пятом
   шаге сформулировала **и первопричину, и обе половины настоящего фикса**:

   > `changedRemoteEntities` … loads the entire `feed_items` table via
   > `getAllCachedOnce()` — including `cachedArticleJson` … O(pages × archive size)
   > … Fix: add a DAO query `getByIds(ids)`

   …и после этого ещё десять минут читала, сделала ноль правок и делегировала
   разведку субагенту `scout`.
5. **Инструкции из системного промпта игнорируются**: `ast-index` (код-поиск,
   описан в глобальном `SYSTEM.md`, 7 упоминаний) не вызван ни разу — модель
   грепала вручную.

### Диагноз: это описанный failure mode, а не случайность

- **Cuadron et al., 2025, «The Danger of Overthinking: Examining the Reasoning-Action
  Dilemma in Agentic Tasks»** ([arXiv:2502.08235](https://arxiv.org/abs/2502.08235)):
  на SWE-bench Verified, 4018 траекторий. Паттерн **Analysis Paralysis** — «models
  focus on heavy planning instead of interacting with the environment» — ровно наш
  случай. Чем выше overthinking, тем **хуже** результат; отбор решений с низким
  overthinking даёт +30 % к успеху и −43 % вычислений. Reasoning-модели склонны к
  этому сильнее нерассуждающих.
- **TACT, 2026** ([arXiv:2605.05980](https://arxiv.org/html/2605.05980v1)) делит
  провал на два: **overthinking** («repeatedly reasons over information it already
  has» — IQ4_XS) и **overacting** («repeats searches, re-reads files» — 27B Q3).
  Калиброванный шаг определяется тем, что он **добавляет новое знание**. Лечат
  они это на уровне активаций и подчёркивают: «without fine-tuning or **prompt
  changes**».
- Родственное: [«Do NOT Think That Much for 2+3»](https://arxiv.org/abs/2412.21187),
  [L1: Controlling How Long a Reasoning Model Thinks](https://arxiv.org/abs/2503.04697),
  [Snap Out of It: Dual-Process Mitigation](https://aclanthology.org/2025.realm-1.16/).

Практические рычаги по силе: уровень/бюджет размышлений → внешний оркестратор и
лимит шагов → native function-calling → и только потом промпт. По промпту помогает
не «думай меньше», а **смена критерия готовности**: не «понять», а «сценарий
перестал падать».

## 6. Как проверять результат модели

1. `./gradlew :composeApp:jvmTest` в её дереве — компиляция и регрессии
   (порог: 130/130, как в baseline).
2. **Проверка первопричины** (модели не показывается): после её правки то же
   устройство с той же фикстурой не должно падать на том же сценарии. До фикса —
   `APP CRASH(EXCEPTION), rss=250MB`, после фикса — не падает.
3. Сверка по существу с настоящим фиксом: перестал ли `changedRemoteEntities`
   тянуть всю таблицу на каждой странице; убрана ли тяжёлая колонка из запросов
   списка; не перестраивается ли весь список на каждую эмиссию.

Ограничение: **сам `OutOfMemoryError` юнит-тестом не воспроизводится** — он про
256-МБ heap устройства. Поэтому «фикс работает» утверждается по
`exit-info`/отсутствию падения на устройстве, а не по зелёным тестам.
