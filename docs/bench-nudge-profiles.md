# Профили надзирателя: оси задачи, триггеры, как подгонять

Документ фиксирует договорённость: **поведение обвязки задаётся осями задачи, а не её названием**,
и у каждого класса свои триггеры. Числа — из замеров; там, где замера нет, это прямо помечено.

Реализация: `bench/supervisor.ts`. Настройка: `env` → `<проект>/.pi/harness.json` → умолчания.
Живая правка в сессии: команда `/nudge` (`/nudge`, `/nudge off`, `/nudge profile=existing-bug`, `/nudge after=14`).

## 1. Оси, от которых зависит смысл триггеров

| ось | значения | что меняется |
| --- | --- | --- |
| **результат задачи** | изменение кода ↔ ответ на вопрос | `staleNudges` осмысленны только для изменения; для поиска **выключены** (правок нет по определению) |
| **есть ли уже сборка/тесты** | новый проект ↔ существующий | в новом проверять нечего до скелета (фаза «разведка»); в существующем сборка есть с первой минуты — фаза «работа» **сразу** |
| **что делаем** | фича ↔ баг ↔ рефакторинг | баг: сначала **воспроизведение**, потом правка; рефакторинг: проверять сборкой и использованиями символа |
| **есть ли исполняемая проверка** | тесты / сборка / устройство / артефакт | определяет, что запускает автопроверка |

## 2. Фазы вместо одного счётчика

Ключевое изменение по итогам прогона `kmp_app`: **бюджет напоминаний привязан к фазе проекта**.

* `phase = recon` — скелета ещё нет (ни `settings.gradle.kts`, ни `pom.xml`, ни `package.json`…).
  Здесь правок ждать рано: идёт обязательная разведка. Порог `nudgeAfter` (для нового проекта 24 —
  по замеру: 26 шагов / 20 минут законной разведки).
* `phase = work` — скелет появился. Разведка кончилась, теперь 24 шага без правки — это уже застой.
  Порог `workNudgeAfter` (6). **При смене фазы бюджет напоминаний сбрасывается.**

Почему это понадобилось: в прогоне `kmp_app` профиль `build-project` имел `maxNudges: 2`, и оба
напоминания сгорели на 4-й и 5-й минуте — **до** скелета. На 13-й минуте скелет появился, и в самый
нужный момент надзиратель молчал. Счётчик за весь прогон — неверная модель.

## 3. Профили (финальный набор)

Решение после замера: `research-first` **убран** — его роль целиком выполняет фаза `recon`
профиля `build-project` (там порог 24, автосборка отложена до скелета). Меньше профилей —
меньше поводов ошибиться в выборе.

| профиль | для чего | stale | проверка | автосборка | особое |
| --- | --- | --- | --- | --- | --- |
| `build-project` | новый проект с нуля | 24 / 6 | через 6 шагов | да, 2× | фаза `recon` → `work` |
| `existing-feature` | существующий проект, фича | 6 / 6 | через 3 шага | да, 3× | фаза сразу `work` |
| `existing-bug` | существующий проект, баг | 6 / 6 | через 2 шага | да, 3× | **сначала воспроизведение** |
| `fix-first` | правка по проверяемому симптому (устройство) | 8 / 6 | через 4 шага | — | гейт: `verify` спрятан до первой правки |
| `search-only` | только поиск/анализ | **выкл** | выкл | — | правок не будет по определению |
| `generate-artifact` | длинная генерация одного артефакта | выкл | через 4 шага | — | проверять надо артефакт, а не сборку |

«24 / 6» = порог в фазе разведки / в фазе работы.

### Ось «баг»: воспроизведение до правки (`requireRepro`)

В профиле `existing-bug` включено требование: если правки идут, а симптом ни разу не воспроизведён
(не прогонялся падающий тест, сценарий, не запускалось приложение) — надзиратель напоминает:
«ты чинишь то, что тебе показалось». Основание — урок стенда OOM: собственная «проверка» модели
оказалась ложной (она отчиталась «готово» на стёртой фикстуре).

Что считается воспроизведением: вызов инструмента `repro`, либо команда с `test` / `run` /
`connectedAndroidTest` / `am instrument` / `adb` / `install` (`reproPatterns`, настраивается).

## 4. Автопроверка силами обвязки (P2)

Как только появляется скелет, надзиратель **сам** запускает сборку и вбрасывает модели **вердикт**,
а не лог:

| результат | что делает |
| --- | --- |
| `BUILD SUCCESSFUL` | говорит: версии и окружение рабочие |
| не разрешаются зависимости | говорит **немедленно** — это провал подбора версий |
| проблема окружения (SDK/JDK) | говорит |
| задача не найдена | говорит (модуль не подключён в `settings.gradle.kts`) |
| ошибки компиляции из-за ещё не написанного кода | **молчит** — на этой стадии это норма |

Правки при этом **не блокируются**: заставлять собирать на середине нельзя (ломает стратегию
«снизу вверх» и провоцирует заглушки ради зелёной сборки). Проверять и сообщать ≠ заставлять.
Классификатор покрыт тестами: `node bench/test-measure.mjs` (5 случаев вердикта).

## 5. Что измерено, а что нет

| класс | статус | ключевые числа |
| --- | --- | --- |
| правка по проверяемому симптому (стенд OOM) | **измерено** | `verify` как инструмент: 0 → 31 обращение; порог 8 подошёл |
| новый проект с нуля (`kmp_app`) | **измерено частично** | разведка 26 шагов / 20 мин; первая правка 8–20 мин; сборка моделью поздно (~1600 строк); лимит напоминаний сгорал до скелета → отсюда фазы |
| только поиск (экзамены anwap/tivi/python) | **измерено** | 0–2 правки на задачу → stale-напоминание бессмысленно |
| длинная генерация артефакта (`moon_mission`) | **измерено** | порога «шагов без правки» нет; нужна проверка артефакта (песочница) |
| **существующий большой проект: фича** | **НЕ измерено** | ожидание: фаза `work` с первой минуты, автопроверка после первой правки |
| **существующий большой проект: баг** | **НЕ измерено** | ожидание: сначала воспроизведение (инструмент `repro`), потом правка |
| рефакторинг через модули | **НЕ измерено** | проверка: сборка + использования символа |

## 6. Как подгонять (протокол)

1. **Числа глобальны, триггеры — по осям.** Механизмы («после скелета», «после первой правки»)
   переносятся между проектами; подгонять заново нужно только пороги.
2. **Один прогон на клетку, а не три** — когда проверяем детерминированный механизм (автосборка
   вбросила вердикт или нет; видно с первого раза). Три повтора нужны там, где решает поведение модели.
3. **Проверять перенос, а не повтор.** Один профиль на 2–3 репозиториях того же класса
   (`anwapvideoplayer`, `tivi`, `AI-Reasoning-Lab`) информативнее, чем 3 прогона на одном.
4. **Каждый прогон даёт калибровку**, даже провальный: `bench/timeline-run.mjs` всегда пишет
   `timeline.json` с порогами — «первая правка», «первая сборка моделью», «автопроверка»,
   «модель увидела результат сборки», плюс все напоминания с шагом и `stale`.
5. **Правка в профиль — только по факту.** Пример: порог 8 → 24 сделан **после** того, как увидели
   26 шагов законной разведки; фазы — **после** того, как увидели сгоревший до скелета бюджет.

## 7. Запуск и измерение

```bash
# запуск (одна сессия, свои пути, проверка после старта)
node bench/launch-run.mjs --cwd <каталог> --prompt-file <файл> --profile existing-bug --max-minutes 60 --tag bug1

# статус и таймлайн порогов
node bench/status-run.mjs  <каталог>/runs/<tag>
node bench/timeline-run.mjs <каталог>/runs/<tag>

# проверка самих измерителей (детекторы, классификатор, сверка с сессией pi)
node bench/test-measure.mjs <каталог>/runs/<tag>
```

Ключевая метрика A/B «автосборка против пинания»: **когда модель впервые увидела результат сборки**.
В плече с автосборкой это момент появления скелета; в плече «только напоминания» — если модель
послушалась, позже, иначе не наступит вовсе.

## 8. Проверка механизмов вне прогона (обязательный шаг)

Перед каждым экспериментом механизм проверяется отдельно — иначе получим «измеряли фигню»:

| проверка | команда | что даёт |
| --- | --- | --- |
| детекторы и классификатор | `node bench/test-measure.mjs <каталог прогона>` | 11 случаев записи в bash, 9 случаев сборки, 5 вердиктов сборки, 3 случая скелета, сверка с сессией pi |
| запуск `.bat` для автосборки | прогон `cmd.exe /c gradlew.bat …` вручную | на Windows `execFile('*.bat')` даёт **синхронный EINVAL** и автосборка молча не работает |
| готовность полигона | прогон целевого теста до задачи | например, `anwap_bug`: **25 тестов, 1 падает** — воспроизведение есть, критерий «не сломать» проверяем |

Первые два пункта уже спасли два недействительных замера: сборка через `cmd //c "gradlew.bat …"`
не распознавалась, а `python - <<EOF` считался записью файла.

## 9. Открытые вопросы

1. Нужен ли отдельный тип напоминания «правка есть, воспроизведения нет» для класса `existing-bug`
   (аналог `nudge_verify`, но про `repro`).
2. Стоит ли автопроверке запускать **тесты модуля** (а не сборку) там, где они есть
   (`src/test`, `*Test.kt`) — сейчас выбирается самая дешёвая сборка.
3. Порог `workNudgeAfter` (6) взят по аналогии с `fix-first`, замера на фазе «работа» пока нет.
