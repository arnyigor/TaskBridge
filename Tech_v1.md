## Правила выполнения

- Выполнять этапы по порядку. `[x]` означает реализовано и проверено; `[ ]` — осталось. Начатое описывать в журнале, не отмечать выполненным.
- Разработка только в отдельной рабочей копии и на соседнем сервере. Основной сервер, его config.json, models.ini, SQLite, Pi-сессии и процессы моделей не изменять до итоговой приёмки.
- Рабочая копия: `C:/Users/ArnyPC/.codex/worktrees/taskbridge-v1/Taskbridge`.
- Этот файл в основном каталоге — доступный пользователю журнал. Его копия в рабочем каталоге должна обновляться одновременно.
- Отдельные порты, данные, тестовые проекты и настройки Pi обязательны. Для детерминированных проверок использовать fake Pi; реальную модель подключать отдельно, не перезапуская основной runtime.
- Не копировать секреты в отчёты. Не переносить незакоммиченные изменения пользователя (`bench/supervisor.ts` и существующие untracked-файлы).
- Перед переносом: узкие регрессии, полный npm test, npm run check, браузерная приёмка ПК/телефона, проверка восстановления и длительный прогон. Не выдавать fake Pi за проверку реальной модели.
- Перенос на основной разрешён пользователем только после проверок. Сначала backup и проверка активных задач, затем перенос проверенных файлов и контролируемый перезапуск. Не обрывать активную работу.

## 1. Чат: очередь, команды, состояния ответов — P0

Цель: сообщение не теряется, принудительная доставка не отменяет инструменты, старый ход не завершает новый.

- [x] 1.1. Воспроизвести «Отправить сейчас» во время генерации и инструмента; зафиксировать регрессию.
- [x] 1.2. Разделить доставку уточнения (steer) и явную отмену (STOP). Принудительная доставка должна использовать штатный Pi RPC, без скрытого abort. Если Pi не поддерживает действие — явная ошибка/очередь.
- [x] 1.3. Поздние agent_settled/message_end/abort/TASK_FAILED относятся к своему ходу (turn-токен на сервере, маршрутизация по времени в reducer) и не помечают свежий ответ отменённым/прерванным. Добавлены тесты на поздний abort, поздний settle и поздний TASK_FAILED.
- [x] 1.4. Очередь адресуется по pendingId: одинаковые тексты не смешиваются, устаревший повтор не затрагивает другую строку, отмена одного элемента не удаляет остальные; вложения ждут в pendingFiles и переживают рестарт (есть тест).
- [x] 1.5. Клиентские commandId/clientId на createTask/message/cancel/apply; повтор при потерянном ответе использует прежний ID, при двойном сетевом провале клиент сверяет серверный журнал `/api/commands/:id`. Повтор отклонённой команды снова отдаёт ту же ошибку; смена now/queue при том же ID — CONFLICT.
- [x] 1.6. Черновик текста хранится в localStorage по сессии и восстанавливается после перезагрузки; неоднозначная отправка показывается отдельным сообщением и не стирает оптимистичный ход.
- [x] 1.7. Состояния ожидания различаются (подготовка/очередь и её причина/работа/инструмент/сборка результата, счётчик времени, текущее действие); молчащий ход с работающим инструментом остаётся ожиданием, а не ошибкой (тест).
- [x] 1.8. Узкие HTTP/DOM-тесты: быстрые сообщения, send-now, STOP, ошибка модели, повтор запроса, переключение сессии в полёте — есть в наборе и проходят.

Примечание по 1.2: после согласования с пользователем принудительная доставка (Ctrl+Enter и «Отправить сейчас» из очереди) снова прерывает текущий ход вместе с выполняющимся инструментом — это осознанное решение оператора. Обычная отправка (Enter → очередь) по-прежнему не прерывает работу.

Приёмка: на каждый принятый ввод понятный результат; STOP — единственный неявно не запускаемый путь отмены; нет потерянных сообщений, дублей и залипших состояний.
