# TaskBridge Backend — план доработок (agentd)

Цель: превратить TaskBridge в центральный supervisor агентных сессий, к которому одновременно подключаются браузер, CLI (`taskbridge pi`) и KMP-клиенты (Desktop/Android). Все клиенты работают с **одним и тем же** живым runtime Pi, без повторного запуска и без потери контекста.

Документ по клиентам: `TASKBRIDGE_KMP_PLAN.md`. Он зависит от этапов B3–B4 этого плана (API v1 должен быть заморожен до начала активной разработки KMP).

---

## 1. Целевая архитектура

```
                    ┌──────────────────────── agentd (TaskBridge) ───────────────────────┐
                    │                                                                     │
  Browser ──┐       │  API v1 (REST + WS)                                                 │
  CLI ──────┼──────►│    │                                                                │
  KMP ──────┘       │    ▼                                                                │
                    │  SessionRegistry ── LeaseManager ── Discovery                       │
                    │    │                                                                │
                    │  RuntimeSupervisor ── ModelScheduler                                │
                    │    │                                                                │
                    │  PiRpcSession (per conversation) ── command queue ── state machine  │
                    │    │                     │                                          │
                    │  EventStore (SQLite) ◄───┘  EventBus ──► WS clients / notifications │
                    └────┼────────────────────────────────────────────────────────────────┘
                         ▼
                  pi --mode rpc --session <file>.jsonl   (1 процесс на 1 conversation)
```

### Сущности

| Сущность | Что это | Хранится |
|---|---|---|
| Workspace | Рабочая директория (cwd) проекта | SQLite |
| Conversation | Логическая сессия, ссылка на Pi `session.jsonl` | SQLite + Pi JSONL |
| Runtime | Живой процесс `pi --mode rpc`, может отсутствовать | в памяти + PID в SQLite |
| Client | Подключённая поверхность (web / cli / android / desktop) | в памяти |

Pi JSONL — истина для модели. SQLite — истина для менеджера. JSONL не используется как база данных менеджера.

---

## 2. Инварианты (проверяются тестами)

- [ ] **I1.** У одной Conversation не больше одного живого Runtime.
- [ ] **I2.** Любая запись в stdin Pi идёт только через очередь команд этой сессии. Два клиента физически не могут писать одновременно.
- [ ] **I3.** Событие сначала записывается в SQLite, потом рассылается клиентам.
- [ ] **I4.** `seq` внутри сессии строго монотонный и без пропусков.
- [ ] **I5.** Нет живого процесса без записи в БД и нет записи `LIVE` без живого процесса (reconciliation при старте и периодически).
- [ ] **I6.** `stop` и `hibernate` завершают всё дерево процессов (включая pytest/gradle, запущенные агентом).
- [ ] **I7.** Каждый `ui.request` разрешается ровно один раз.
- [ ] **I8.** Prompt с одним `idempotencyKey` выполняется не более одного раза.
- [ ] **I9.** JSONL одной Conversation пишет не больше одного процесса Pi (ownership).

## 3. State machine Runtime

| Из | Событие | В |
|---|---|---|
| — | start / resume | `STARTING` |
| `STARTING` | Pi готов | `IDLE` |
| `STARTING` | ошибка запуска / таймаут | `RESTORABLE` (с причиной) |
| `IDLE` | prompt | `WORKING` |
| `WORKING` | turn завершён (settled) | `IDLE` |
| `WORKING` | extension UI-запрос | `WAITING_USER` |
| `WAITING_USER` | ответ клиента | `WORKING` |
| `WORKING` / `WAITING_USER` | interrupt | `ABORTING` → `IDLE` |
| `IDLE` | idle-таймаут, сессия не закреплена | `HIBERNATING` → `HIBERNATED` |
| `HIBERNATED` / `RESTORABLE` | prompt или resume | `STARTING` |
| любое живое | неожиданный выход процесса | `RESTORABLE` |
| любое | stop | `STOPPING` → `STOPPED` |

Правила:
- Переход не из таблицы — ошибка в лог с `sessionId`, состояние не меняется.
- Ожидание слота модели — это не отдельное состояние, а `activity: waiting_model` внутри `WORKING`.
- Состояние `EXTERNAL` относится к Conversation (найдена снаружи, runtime не наш), а не к Runtime.

## 4. Этапы

### B0. Подготовка и страховка

Цель: зафиксировать текущее поведение до рефакторинга.

- [ ] Зафиксировать поддерживаемую версию Pi (сейчас 0.85.1), проверять `pi --version` при старте daemon'а, при несовпадении — предупреждение в `/v1/health` и в UI.
- [ ] Записать реальные RPC-транскрипты (stdin и stdout JSONL) как fixtures:
  - обычный turn с текстовым ответом;
  - turn с несколькими tool calls;
  - interrupt посреди tool call;
  - ошибка модели / недоступный провайдер;
  - extension UI-запрос (confirm/select) и ответ;
  - compact, смена модели;
  - длинный вывод инструмента.
- [ ] По fixtures составить документ «какие RPC-команды и события мы используем» — точные имена команд (prompt / steer / follow_up / abort и т.д.) сверять с реальными транскриптами, а не по памяти.
- [ ] Реализовать **fake-pi**: процесс, который воспроизводит fixtures и умеет по сценарию: падать, зависать, отвечать с задержкой, обрывать строку JSON, писать мусор в stdout.
- [ ] Характеризационные тесты текущего TaskBridge: браузер продолжает живую сессию, restore после рестарта, текущий `capacity=1`.

**Критерии готовности:** сценарий «prompt → tools → settled» проходит на fake-pi в CI за секунды; все существующие функции покрыты хотя бы smoke-тестом.

### B1. Ядро runtime

Цель: вынести `PiRpcSession` и `RuntimeSupervisor` в отдельный модуль с явными инвариантами.

- [ ] State machine из раздела 3, одна точка изменения состояния, каждое изменение — событие `session.state_changed`.
- [ ] Очередь команд на сессию (актор / mutex). Все операции (prompt, abort, ui-response, stop, hibernate) проходят через неё.
- [ ] Корреляция запрос → ответ по id, таймаут на каждый запрос, по таймауту — ошибка клиенту и лог, без вечного ожидания.
- [ ] Чтение stdout:
  - буферизация по строкам, корректная обработка строки, разорванной между чанками;
  - декодирование UTF-8 с учётом многобайтовых символов на границе чанков (кириллица!);
  - невалидная строка JSON → лог + событие `error`, сессия не падает.
- [ ] stderr Pi — в отдельный лог сессии, последние N строк прикладываются к причине падения.
- [ ] Windows: завершение дерева процессов.
  - Предпочтительно Job Object с kill-on-close (при падении daemon'а дочерние процессы не остаются сиротами — управлять ими без pipe всё равно нельзя).
  - Минимум: `taskkill /PID <pid> /T /F` после graceful-таймаута.
- [ ] Хранить PID и время старта процесса в SQLite; при старте daemon'а находить и завершать сирот (проверка по PID + времени старта, чтобы не убить чужой процесс с переиспользованным PID).
- [ ] Неожиданный выход процесса → `RESTORABLE` с причиной (код выхода, хвост stderr).

**Критерии готовности:** на fake-pi проходят тесты: kill во время tool call, отсутствие ответа на команду, оборванная строка JSON, кириллица на границе чанка, stop с «дочерним» процессом-долгожителем (после stop процессов не остаётся).

### B2. Модель данных и EventStore

- [ ] SQLite с миграциями с первого дня, WAL-режим, `busy_timeout`.
- [ ] Таблицы (минимум):
  - `workspaces(id, path, title, created_at)`
  - `conversations(id, workspace_id, provider, provider_session_file, title, pinned, ownership, created_at, updated_at, last_activity)`
  - `runtimes(conversation_id, pid, process_started_at, state, activity_json, started_at)`
  - `events(conversation_id, seq, ts, type, source_kind, client_id, payload_json)` — PK `(conversation_id, seq)`
  - `prompts(idempotency_key UNIQUE, conversation_id, status, created_at)`
  - `ui_requests(id, conversation_id, status, resolved_by, created_at)`
- [ ] Выдача `seq` и запись события — в одной транзакции (I3, I4).
- [ ] Стриминговые дельты ответа модели **не** пишутся в SQLite: они идут live-кадрами без `seq`. В базу пишется финальное сообщение. Текущий незавершённый текст хранится в памяти runtime и отдаётся в snapshot.
- [ ] Длинные выводы инструментов: в событии — усечённый вывод + размер; полный вывод по отдельному запросу.
- [ ] Политика хранения: старые tool outputs сжимаются/удаляются через N дней, сообщения остаются.

**Критерии готовности:** после рестарта daemon'а список сессий, их состояния (живые → `RESTORABLE`) и история событий совпадают с состоянием до рестарта.

### B3. API v1 — единый контракт

Все клиенты (браузер, CLI, KMP) используют только этот API. После завершения этапа контракт замораживается; изменения — только обратно совместимые или через `/v2`.

#### REST

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/health` | версия daemon'а, версия Pi, статус |
| GET | `/v1/workspaces` | список проектов |
| GET | `/v1/sessions?cwd=&state=` | список сессий |
| POST | `/v1/sessions` | новая сессия `{cwd, provider, title?, model?}` |
| GET | `/v1/sessions/{id}` | snapshot сессии |
| PATCH | `/v1/sessions/{id}` | `{title?, pinned?}` |
| GET | `/v1/sessions/{id}/events?fromSeq=&limit=` | история постранично |
| POST | `/v1/sessions/{id}/prompt` | `{text, mode: auto\|followUp\|steer, idempotencyKey}` |
| POST | `/v1/sessions/{id}/interrupt` | идемпотентно |
| POST | `/v1/sessions/{id}/ui-response` | `{requestId, value}` |
| POST | `/v1/sessions/{id}/command` | `{name, args}` — model, compact и др. |
| POST | `/v1/sessions/{id}/resume` | поднять runtime |
| POST | `/v1/sessions/{id}/stop` | завершить runtime |
| GET | `/v1/sessions/{id}/tool-output/{toolCallId}` | полный вывод инструмента |

Коды ошибок: `404` нет сессии, `409` недопустимо в текущем состоянии, `423` сессия внешняя/заблокирована, `429` превышен лимит runtime'ов. Тело ошибки: `{code, message, state?}`.

#### Envelope события

```json
{
  "v": 1,
  "sessionId": "c_7da2",
  "seq": 1284,
  "ts": "2026-09-24T21:14:03.120Z",
  "type": "tool.started",
  "source": { "kind": "pi", "clientId": null },
  "payload": { "toolCallId": "t_91", "name": "bash", "summary": "pytest tests/world_model" }
}
```

Типы: `session.state_changed`, `message.user`, `message.assistant`, `tool.started`, `tool.finished`, `ui.request`, `ui.resolved`, `prompt.queued`, `prompt.dispatched`, `runtime.started`, `runtime.exited`, `error`.

#### WebSocket `/v1/sessions/{id}/stream`

- Клиент → сервер: `hello {clientId, clientKind, fromSeq}`, `ping`.
- Сервер → клиент: `snapshot {session, lastSeq, partialAssistantText}`, `event {…}`, `live {delta}`, `presence {clients}`, `pong`, `error`.
- Алгоритм подключения без дыр:
  1. подписаться на EventBus и буферизовать события;
  2. прочитать из БД события с `seq > fromSeq`;
  3. отправить snapshot и историю;
  4. отправить из буфера только события с `seq` больше последнего отправленного;
  5. дальше — live.
- Отдельный WS `/v1/stream` для списка сессий (изменения состояний всех сессий) — для главного экрана клиентов.

#### Прочее

- [ ] **Idempotency key** на prompt: повтор с тем же ключом возвращает исходный результат, агент не получает задачу дважды.
- [ ] Авторизация: токен для LAN, выдача через QR-код pairing (URL + токен) для мобильных клиентов.
- [ ] CORS для браузерного клиента.
- [ ] Схема моделей описана один раз (JSON Schema / OpenAPI), из неё генерируются или сверяются модели клиентов.

**Критерии готовности:** контрактные тесты на все эндпоинты и WS-протокол; тест «переподключение с `fromSeq` во время активного turn» — ни одного пропуска и дубля.

### B4. Несколько клиентов на одной сессии

- [ ] Prompt во время `WORKING`:
  - `mode=auto` → в очередь как follow-up;
  - `mode=steer` → steer в текущий turn;
  - клиент получает `prompt.queued` и затем `prompt.dispatched`.
- [ ] Extension UI-запросы (в т.ч. от bench-harness):
  - рассылаются всем подключённым клиентам;
  - засчитывается первый ответ, остальным — `ui.resolved {resolvedBy}`;
  - повторный ответ → `409`;
  - если клиентов нет — уведомление (через KMP).
- [ ] Interrupt идемпотентный: второй interrupt во время `ABORTING` — no-op с `200`.
- [ ] Presence: какие клиенты подключены к сессии.
- [ ] Каждое пользовательское событие помечено источником (`web`, `cli`, `android`, `desktop`).

**Критерии готовности:** тест с тремя виртуальными клиентами, одновременно отправляющими prompt, interrupt и ответ на UI-запрос, даёт детерминированный результат и проходит 100 прогонов подряд.

- [ ] Детектор конфликтов cwd: предупреждение при второй живой сессии в той же директории; опционально — создание git worktree на сессию.

**Критерии готовности:** 4 параллельные сессии на fake-pi и 2 на реальной модели работают час без утечек процессов, без зависших `WORKING` и с корректными статусами ожидания модели.

### B6. Жизненный цикл

- [ ] Idle-таймаут (настраиваемый: 30 мин / 2 ч / навсегда), закрепление сессии (`pinned`) отключает hibernate.
- [ ] Hibernate: дождаться `IDLE` → graceful shutdown Pi → проверить, что процесса нет → `HIBERNATED`.
- [ ] Auto-resume: prompt в `HIBERNATED` / `RESTORABLE` ставится в очередь, runtime поднимается с `--session`, prompt отправляется после `IDLE`.
- [ ] Гонка «prompt пришёл во время засыпания» закрывается очередью команд из B1 (hibernate — тоже команда в очереди).
- [ ] Graceful shutdown daemon'а: запретить новые команды, дождаться/прервать turn'ы по политике, остановить все runtime'ы, записать состояния.
- [ ] Reconciliation при старте: живые в БД → `RESTORABLE`, сироты завершены.

**Критерии готовности:** chaos-тесты: kill daemon во время turn, перезагрузка ПК, prompt ровно в момент hibernate — после восстановления ни одной потерянной или задвоенной задачи.

### B8. CLI `taskbridge pi`

CLI — тонкий клиент API v1, **не** запускает Pi сам.

- [ ] Команды:
  - `taskbridge pi` — attach к сессии текущего cwd (одна → сразу, несколько → выбор, нет → предложить `new`);

  - `taskbridge pi new`;
  - `taskbridge pi detach`;

- [ ] Горячие клавиши: Ctrl+C во время работы → interrupt; в idle → detach. Stop — только явной командой.

**Критерии готовности:** сценарий «терминал → detach → телефон пишет → attach в терминале» показывает всю историю и продолжает тот же PID Pi.

## 5. Тестовая стратегия

- **Unit:** state machine (все переходы из таблицы и отказ на остальных), парсер stdout, выдача `seq`.
- **Интеграционные на fake-pi:** все сценарии из fixtures B0.
- **Контрактные:** API v1 и WS-протокол; эти же фикстуры отдаются KMP-команде.
- **Chaos-набор (перед каждым релизом):**
  - kill Pi посреди tool call;
  - kill daemon посреди turn;
  - обрыв WS и переподключение с `fromSeq`;
  - двойной prompt с одним idempotency key;
  - prompt во время hibernate;
  - три клиента одновременно.
- **Soak (ночь, реальная модель):** утром — ноль процессов-сирот, ноль вечных `WORKING`, рост БД в ожидаемых пределах.
- Каждый баг, найденный руками, сначала превращается в тест, потом чинится.
