Итоги по плечам

  • A (напоминания, Q3): модель собрала проект сама, но на 28-й минуте и после 4 попыток. Первые два напоминания «нет правок» ушли на шагах 24 и 26 — до скелета (13-я минута).
  • B (автосборка, Q3): механизм не сработал: детектор искал скелет только в корне, а проект оказался в подкаталоге TodoApp/. Исправлено и покрыто тестом; перепроверить на Q3 не успели.
  • anwap_bug (существующий проект): всё сработало мгновенно — автосборка на 17-й секунде, модель сама прогнала падающий тест (воспроизведение), исправила одну строку. Независимая проверка: git diff — верный фикс, ./gradlew :app:testDebugUnitTest → BUILD SUCCESSFUL, 25/25.
  • IQ4_XS (64k, новый проект): пишет быстрее Q3 (TG 39–47 против 27–39 ток/с), но долго раскачивается: первая правка на 32-й минуте, до этого 64 шага разведки. Окно 64k упирается в компакцию чаще: 3 компакции за час, контекст стоит у порога (53 093 из 65 536 = 81 %). Механизм сработал полностью: phase_change (шаг 65) → автосборка ×2 (шаги 71–72).

3. Главные выводы

  1. Разброс модели между прогонами огромен. Одна и та же модель на одном промпте: первая правка на 8-й минуте против 21-й; сборка на 28-й против 51-й. A/B при n=1 сравнивать по «когда» нельзя — сравнивать надо факт срабатывания механизма и его эффект. Для калибровки чисел нужно n≥3.
  2. Механизм работает там, где у него есть триггер. Существующий проект: автосборка на 17-й секунде, потому что сборка есть с первой минуты. Новый проект: триггер — появление скелета, а его может не быть за час (плечо B не создало его в корне вовсе).
  3. Автосборка без правильного классификатора бесполезна. Три случая: сборка через cmd //c "gradlew.bat …" не распознавалась; падающий тест считался «недописанным кодом» и замалчивался; плагинный резолв (Error resolving plugin … could not be satisfied) уходил в unknown → молчание. Каждый случай найден тестами и фикстурами, а не «на глаз».
  4. Напоминание-совет доходит до модели (в размышлениях она пересказывала текст надзирателя своими словами), но бюджет и пауза критичны: без кулдауна два напоминания ушли на шагах 24 и 26 — весь бюджет за 96 секунд.
  5. Фазы проекта — правильная модель. phase_change (recon → work) сработал в обоих прогонах с подкаталогом; без фаз бюджет тратится на разведку и заканчивается к началу работы.

6а. Что дальше (по важности)

  1. Второй триггер автосборки для проекта с нуля: «есть код, прошло N минут, сборки не было». Сегодня механизм ждёт именно скелет, а он появился только на 32-й минуте (IQ4_XS).
  2. Перепрогнать Q3-плечо B с исправленным детектором — чтобы получить чистый A/B по Q3.
  3. Каналы против долгой раскачки: сегодня есть только порог шагов. Нужен механизм «первая компакция без единого файла → заставить начать» (в IQ4_XS до первой правки прошло 64 шага и одна компакция).
  4. Тесты для нового кода: test-measure.mjs и test-project-detect.mjs уже покрывают детекторы и классификатор; при правках — прогонять перед каждым экспериментом.

7. Открытые вопросы

  1. Триггер автосборки для проекта «с нуля». Скелет может появиться поздно (IQ4_XS: 32-я минута) или не в корне. Нужен второй триггер: «прошло N минут, есть .kt-файлы, сборки не было» → собрать самим. Сейчас при скелете на 32-й минуте механизм уже не экономит много времени.
  2. Проект Q3-плеча B надо перепроверить после правки детектора подкаталогов: там механизм не сработал именно из-за дыры, и выигрыш на Q3 остаётся неизмеренным.
  3. requireRepro не проверен: в полигоне бага модель воспроизвела симптом сама за 17 секунд, и напоминание не понадобилось. Проверять надо на баге без готового теста.
  4. Калибровка чисел (пороги, кулдаун, workNudgeAfter) — нужны n≥3 на класс задачи; разброс модели между прогонами больше, чем эффект любой отдельной правки.
  5. IQ4_XS раскачивается долго (64 шага разведки, 32 минуты до первой правки). Для такого поведения в build-project нужен отдельный механизм: не только порог шагов, но и жёсткое требование «начни файл» после первой компакции.

8. Оговорки к замерам (чтобы не повторять ошибок)

  • TG за интервал считается по завершённым запросам: на одном длинном запросе покажет почти ноль. Для мгновенной скорости — две выборки счётчика с паузой.
  • Счётчики /metrics кумулятивные по загруженной модели: при двух прогонах подряд на одной модели интервал нужно считать внутри каталога конкретного прогона (так и сделано в status-run).
  • Разница в «первой правке» между плечами на разных моделях — это разброс модели, а не эффект обвязки. Сравнивать по ней при n=1 нельзя.
  • Перед каждым экспериментом гонять test-measure.mjs и test-project-detect.mjs: три недействительных замера были получены из-за непроверенных детекторов.
